## 三、两组「为什么同时存在」的依赖
### 3.1 `weixin-java-pay`（下单）+ `wechatpay-java`（退款）
不是重复引入，而是**分工**，代码里能逐条对上：
- **下单走 binarywang**：`PayService` 的 import 全是 `com.github.binarywang.wxpay.*`（`WxPayService`、`WxPayUnifiedOrderV3Request`、`WxPayOrderQueryV3Result`、`SignatureHeader`、`WxPayNotifyV3Result`），负责 `/api/orders/{id}/pay` 与支付回调 `/api/pay/notify`。
- **退款走官方 SDK**：`MerchantRefundService` 用 `com.wechat.pay.java.service.refund.RefundService`，`RefundWxPayConfiguration:49-50` 用 `RSAAutoCertificateConfig` 构建，`MerchantRefundNotifyController` 用 `NotificationParser` 解退款通知。
- **为什么这样切**：`PayService.java:155-157` 的注释写得很直接——「与商家拒单退款统一走 MerchantRefundService：同一套官方 APIv3 SDK（**不再用 binarywang 的 refundV3**），同一套状态落库逻辑」。`pom.xml:68`、`:74` 的注释也标了这是 task-12 / task-14 两次接入的结果。
- **代价与风险**：两套 SDK 各带一套 HTTP 客户端（httpclient4 vs okhttp）、各带一套证书处理（bouncycastle vs 官方 `RSAAutoCertificateConfig`），jar 体积与冲突面都翻倍；更要紧的是**配置必须同时正确**——`application.yml:72-73` 明确记录了历史故障：「历史上存在过 campus.wxpay 第二套前缀，两套 enabled 开关会拼出『能下单不能退款』的半配置状态，已合并」。改支付相关配置时必须同时验证下单与退款两条链路。
- **可替换性**：可以统一到官方 `wechatpay-java`（它同样有 JSAPI 下单与回调解析），但需要重写 `PayService` 的下单与回调验签，收益是砍掉 httpclient4 / xstream / guava / bouncycastle 一大串传递依赖。

### 3.2 `sensitive-word`（houbb）与 `toolgood-words`（ToolGood）
- **当前实际生效的是 ToolGood**。`AuditService` 注入的是 `SensitiveWordEngine`（`AuditService.java:47-48` 注释写明「敏感词引擎：ToolGood.Words」），而 `SensitiveWordEngine` 只 import `toolgood.words.IllegalWordsSearch` / `IllegalWordsSearchResult`（`SensitiveWordEngine.java:5-6`）。全仓库检索 `com.github.houbb`，**没有任何 import**；`houbb` 字样只出现在 `SensitiveWordEngine.java:24` 的一句注释里。
- **结论：`sensitive-word 0.2.0` 是未被使用的直接依赖**。`pom.xml:81` 说它「保留作为对照与回退方案」，但代码层面没有回退开关，删掉不影响功能，还能顺带去掉 4 个传递依赖（`heaven`、`opencc4j`、`nlp-common`、`apiguardian-api`）。若确实想留回退路径，应显式实现一个可切换的引擎接口，而不是留一个无人引用的 jar。
- **ToolGood 承担了什么**：DFA 多模式匹配 + 忽略大小写 + 全角半角归一（`UseIgnoreCase`、`UseDBCcaseConverter`）+ 跳字符（`UseSkipWordFilter` + `SetSkipWords`，见 `SensitiveWordEngine.java:63-73`），能拦住「刷 单」「刷-单」「Ｓ刷单」这类绕过写法；白名单仍由 `AuditService.isCoveredByAllowWord` 按出现位置判断，因为引擎自带的白名单只按整词相等剔除。

| 小程序 `node_modules` | 17.67 MB / 4557 个文件 | 其中 `tdesign-miniprogram` 是主要占用 |

**jar 多大？现在给不了实测值**。要拿到就执行 `mvn -o package -DskipTests`，然后看 `backend/target/campus-life-api-1.0.0.jar`。按 104 个依赖、其中含 Tomcat embed、Spring 全家桶、httpclient4 + okhttp + bouncycastle 的组合，量级在几十 MB（**这是估算，不是实测**）。想让 jar 更小，最直接的两刀就是：删掉未使用的 `sensitive-word`，以及把支付统一到官方 SDK（可去掉 httpclient4 / xstream / guava / bouncycastle 一条链）。

**启动影响**：`AuditService.initialize()` 是 `@PostConstruct`，启动时就会 `reloadWords()` 构建一次敏感词 DFA（`AuditService.java:55-58`）；词表为空时用内置兜底词（`FALLBACK_WORDS`），不会启动失败。`CircleWebSocketManager` 的 `@PostConstruct` 起一个守护心跳线程（30 秒一次）。除此之外没有重量级初始化。

## 八、升级建议
**不编 CVE 编号**——下面只指出「版本偏旧 / 已停更 / 需要主动关注」的事实，具体安全公告请以官方渠道为准。

| 依赖 | 当前 | 关注点 | 建议 |
| --- | --- | --- | --- |
| `spring-boot-starter-parent` | 3.2.5 | 3.2.x 已不在主流支持窗口 | 评估升 3.3.x / 3.4.x；升级会连带 Jackson、Tomcat、Hibernate Validator 一起动，需完整回归 |
| `httpclient` / `httpcore` | 4.5.13 / 4.4.16 | Apache HttpClient **4.x 已 EOL**，不再收安全修复 | 由 `weixin-java-pay` 引入；升 binarywang 到 4.7.x 或统一到官方 SDK 可摆脱 |
| `commons-io` | 2.7 | 明显偏旧（当前主线 2.1x） | 随 `weixin-java-pay` 升级自然更新 |
| `xstream` | 1.4.20 | 历史上反序列化风险高发 | 跟随 binarywang 升级；若改走官方 SDK 可直接移除 |
| `bouncycastle` `*-jdk15on` | 1.70 | `jdk15on` 分支已停更，主线转 `jdk18on` | 跟随 binarywang 升级 |
| `mysql-connector-j` | 8.3.0 | 8.3 非 LTS | 评估升 8.4 LTS 或 9.x（注意驱动类名与时区参数） |
| `jsqlparser` | 4.9 | 由 MyBatis-Plus 3.5.6 锁定 | 单独升级会破坏分页，必须与 MP 版本一起动 |
| `weixin-java-pay` | 4.6.0 | 明显落后于主线 4.7.x | 升级前先跑通下单 + 回调验签 + 退款三条链路 |
| `sensitive-word`（houbb） | 0.2.0 | **代码未使用** | 直接从 `pom.xml` 删除，减 4 个传递依赖 |
| 前端 `vite` / `tailwindcss` | 5.4.11 / 3.4.19 | 均为上一大版本 | Vite 6/7、Tailwind 4 都是破坏性升级，建议排在业务迭代之后单独做 |

想拿到准确的「有哪些新版本」，在有网环境执行（这些命令要联网拉元数据，本次离线环境未执行）：

```bash
mvn versions:display-dependency-updates     # 后端：列出可升级项
mvn versions:display-plugin-updates         # 插件同理
mvn dependency:tree -Dincludes=org.apache.httpcomponents   # 定位某个传递依赖是谁拉进来的
# 前端
pnpm outdated
pnpm audit
```

对于「某个依赖有没有已知漏洞」，用 `pnpm audit`（前端）和 OWASP Dependency-Check / `mvn org.owasp:dependency-check-maven:check`（后端）自行扫描，比任何手写清单都可靠。
