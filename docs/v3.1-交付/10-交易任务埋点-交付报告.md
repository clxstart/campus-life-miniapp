## 三、隐患

1. **外卖/兼职的「发分触发」链路（已补自动化）。** `MerchantPointsAwardIntegrationTest`（5 例）与 `JobSettleAwardIntegrationTest`（4 例）用真库临时 schema + 真实 `AfterCommitPointsAwarder` + `DataSourceTransactionManager`，把 `complete()`/`confirmHours()`/`arbitrate()` 跑在真实事务里，断言了「提交后才发 / 回滚不发 / 幂等」。**剩余边界**：测试直接 `new` Service，没有走 Spring MVC，接口层鉴权、参数绑定和真实支付回调仍不在覆盖内。
2. **发分失败只进日志，没有告警也没有补偿。** `AfterCommitPointsAwarder` 吞掉所有异常（设计稿要求「不阻塞交易主流程」），但副作用是：积分表锁等待/连接抖动的那个时间窗里，订单完成了、分没发，用户看到的 `pointsAwarded=0` 与「本该 +10」不一致。目前只能靠人工查 `[campus] 交易发分失败` 日志。缺一个「发分失败重试队列」或每日对账任务。
3. **日上限的提示只覆盖「确认人」。** `confirm` 返回的 `skipReason=daily_cap` 算的是卖家（确认人）自己的上限；买家当天已满 2 笔时，卖家仍看到「成交成功，+5 积分」，而买家实际没到账 —— 双方体感不一致，客诉会落在买家侧。修法：`confirm` 分别返回买卖双方各自的 awarded 状态（约 0.5 人日）。
4. **买家刷新后「等待卖家确认」状态会丢（已修）。** 新增 `GET /api/market/{goodsId}/trade`：只回当前登录买家自己在这件商品上的成交（没有返回 `{}`，不 404）；`pages/market-detail` 在 `onShow` 调一次，`pending` 且买家是我才恢复 `tradePending`，`cancelled`/`confirmed`/无记录回到正常售卖态。`MarketTradeQueryIntegrationTest`（4 例）锁住「自己 pending 可查 / 别的买家为空 / 卖家为空 / 取消后 `cancelled`」。受写作用域限制，本轮没有改 `utils/api/*`，页面直接复用已导出的 `api.request`；若允许动 api 层，可再抽成 `getMarketTrade(goodsId)`。
5. **退款不追回积分，提示条仍会显示「+10 已到账」。** 设计稿 §3 明确不追回；但完成后再退款时，订单页的 `pointsAwarded` 仍 > 0、绿条仍出现，用户会觉得「退款了怎么还有分」。这是产品口径问题，不是 bug；要么补一句文案，要么在退款成功后把提示条改成「该单已退款」。
6. **回滚/降级时 `goods.status=2` 是单向的。** 确认成交把商品置为已售（2），而市场列表/详情只认 `status=1`。回退代码不会把已售商品改回在售，需要人工 `UPDATE goods SET status=1`，否则卖家会看到「商品消失了但也没法重新上架」。
7. **取消/确认与商品置已售不是同一条 SQL。** `confirm` 的条件 UPDATE 成功后，`markGoodsSold` 是紧跟的第二条语句（同一 Spring 事务内，但非一条语句）。进程在两者之间崩溃会出现「成交 confirmed、商品仍在售」：列表里还能看到它，再发起会被「已有成交记录」挡住（不会产生第二笔），但列表数据脏，需要人工修正 status。
8. **`pointsAwarded` 三处查询都依赖 `point_log` 存在。** v3.1 全量部署没问题（`module-points-v31.sql` 是所有积分功能的前置）；但若只上交易埋点、没跑积分脚本，三处查询都会报 SQL 错误。代码里已各自 try/catch 归 0（订单详情 / 履约详情 / 我的兼职），降级表现是「提示条不出现 + 一条 warn 日志」，主流程不受影响 —— 但这条降级路径**没有测试覆盖**（测试库里 `point_log` 一定存在）。
9. **`mine` 的积分查询是 N+1。** `GET /api/jobs/mine` 对每条 `settled` 的我承接合约单独查一次 `point_log`（走 `uk_user_biz`，单次很快）；列表上限 200 行，极端用户会有 200 次小查询。当前规模可接受，量大后应改成一次 `IN` 批量查。
10. **「我的发布」列表上限 100 行且无分页。** `sellerTrades` 是 `LIMIT 100`，发布超过 100 件商品的卖家看不到更早的商品；虽然 `pending` 排最前降低了「待确认成交被挤出」的概率，但不是零。
11. **二手「成交」只是意向确认，没有任何资金/履约约束。** 没有担保、没有线上支付、没有评价（设计稿 §7 明确不做），所以两个人完全可以互相点「我已买到 → 确认成交」来刷分；三层防刷（单商品唯一 + 同对用户 7 天一次 + 日限 2 笔）只降低频率，不识别团伙/小号（无设备、IP、实名维度风控）。
12. **并发发起时落败方看到的文案不稳定。** 两个买家同时点「我已买到」：走「先查到 pending」路径的拿到 409「该商品已有待确认的成交」，走「INSERT 撞唯一键」路径的拿到 400「该商品已有成交记录」。语义都对，但同一场景两种提示，客诉排查时容易被当成两个不同问题。
13. **争议裁定账务不重算（已修）。** 争议冻结时 `writeLedger(..., "frozen")` 已按承接方申报量把 `earnings_ledger` 三行金额写死；`record()` 是 `INSERT IGNORE`，裁定 `settled` 时 `switchStatus` 只改状态 —— 管理员按不同计价数量裁定时，账单仍显示申报量。修复：`EarningsLedgerMapper.reprice(bizNo, amountCents, note)` + `JobService.writeLedger()` 在 `frozen→settled/refunded` 推进后，用传入 `hours` 重算 payable/fee/income（`refunded` 时 `hours=0` → 三行归零）。回归：`JobSettleAwardIntegrationTest.arbitrationSettledRepricesLedgerToConfirmedHours` —— 申报 5 冻结为 12500/500/12000，裁定 3 后为 7500/300/7200，并用 `isNotEqualTo` 明确排除旧值；退款合约三行重算为 0。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 发分可观测性 | 发分失败进重试队列/死信，配「今日应发 vs 实发」对账任务与告警 | 约 2 人日（重试表 + 定时对账 + 后台看板） |
| 触发链路自动化 | 用 `@SpringBootTest` + 测试容器跑通「下单→支付→完成→发分」与「履约→结算→发分」端到端 | ✅ 本轮已补服务层真库自动化（外卖 5 例 / 兼职 4 例，真实事务 + `afterCommit`）；MVC + 真实支付回调仍未覆盖，剩余约 1 人日（要先把支付/通知/派单外部依赖替换成测试替身） |
| 防刷风控 | 设备指纹、同 IP/同设备批量成交识别、账号可信度分级后再决定发分 | 约 3 人日 + 需要客户端埋点；纯服务端做只能到「频率+关系图谱」 |
| 成交流程完整性 | 资金担保（平台代收代付）、订单评价、纠纷仲裁、退款联动积分 | 担保交易涉及支付牌照（设计稿明确不做）；评价+仲裁约 5 人日，资金侧不具备条件 |
| 买家侧状态一致性 | 成交状态在商品详情就能读到（`myTradeStatus`），刷新后按钮仍是「等待卖家确认」 | ✅ 本轮已补：`GET /api/market/{goodsId}/trade` + 页面 `onShow` 恢复（4 例真库测试）；页面直连已导出的 `api.request`，抽独立 api 封装属可选优化 |
| 双方各自到账口径 | `confirm` 返回买卖双方各自的 `awarded`，页面分别提示 | 约 0.5 人日 |
| 退款联动积分 | 退款成功后按策略冲正/标注，页面同步改为「该单已退款」 | 约 1 人日（涉及「积分已花掉」的边界，设计稿选择不追回） |
| 日上限的可解释性 | 页面直接显示「今日成交积分 2/2 已满」，不用等点了才知道 | 约 0.3 人日（`GET /api/points/tasks` 已有 `doneToday`，缺的是页面展示） |

**一句话**：现在能保证「成交双方确认、一件商品只成交一次、同一对用户 7 天只计一次、日限 2 笔、并发只发一次」，但发分这条链路**只能靠日志和对账人肉兜底**，防刷也只到「频率+关系」这一层；这两点在真实用户量上来后必须先补。

```sql
UPDATE task_catalog SET enabled = 0 WHERE task_key IN ('food_order','job_settle','market_trade');
```

- 效果：三个场景不再发分；页面上的提示条因为 `pointsAwarded=0` **自动不再出现**（不需要发版）；二手成交、外卖完成、兼职结算主流程全部照常
- 生效时间：`task_catalog` 有 30 秒本地缓存（`PointsService` 的 `CATALOG_TTL_MS`），最迟 30 秒

**方案二：回退代码**

- 后端回退第五节列出的后端文件（`pointsAwarded`、`skipReason`、订单详情字段、买家成交通态查询、`reprice` 一并消失）
- 小程序回退 5 个页面（提示条/按钮/角标消失；`pages/profile` 的「我发布的物品」整块消失）
- 回退后端而未回退小程序时：页面拿到 `pointsAwarded` 为 `undefined`，三处提示条都判 `<=0` 不显示，不会报错 —— 前后端可独立回退

**数据回退（按风险从低到高）**

1. 什么都不做：已发积分留在 `user_points`/`user_growth`/`point_log`，成交记录留在 `market_trade`。这是最安全的选择 —— 回滚目的是止血，不是抹账
2. 若必须回收已发积分：按 `point_log.module IN ('commerce','jobs','market')` 与 `biz_key` 前缀（`food_order:`/`job_settle:`/`market_trade:`）人工做负数冲正，**不要批量执行**（用户可能已经花掉这些积分，冲正会把余额打成负数）
3. **已售商品必须人工处理**：确认成交把 `goods.status` 置为 2，市场列表/详情只认 `status=1`。回退代码后这些商品仍是「已售」且从列表消失。要重新上架需逐个确认后执行：
   ```sql
   UPDATE goods SET status = 1 WHERE id = <确认过没有真实成交的商品>;
   ```
   注意：**真的有成交的商品不要改回 1**，否则会被再次发起（虽然会被「已有成交记录」挡住，但列表数据会脏）
4. 彻底清理（会丢数据，非必要不做）：
   ```sql
   DROP TABLE IF EXISTS market_trade;
   ```
   已发的积分、已完成的外卖/兼职不受影响；二手成交历史全部丢失

**开关**：本功能没有独立的 feature flag 总开关。三种停用方式按力度排序：`task_catalog.enabled=0`（只停发分）→ 回退小程序（只停提示/按钮）→ 回退后端（接口不再返回 `pointsAwarded`/`skipReason`）。二手成交流程本身**没有**优雅停用开关，因为它是三个写接口：要停只能回退代码或在网关层屏蔽 `/api/market/**/trade`。

**风险点**：回滚后 `market_trade` 若保留，重新上线时不会重复发分（`point_log` 的 `uk_user_biz` 与 `task_log` 的 `uk_task_idem` 仍在库里）；但如果回滚期间有人手工改过 `market_trade.status`，再上线后 7 天互刷判定会按改后的 `confirmed_at` 算，需要人工核对。
