### 小程序端

- **`pages/circle-create`（新页，四件套）**
  - 三段结构：首屏骨架 → 无权限说明卡（段位不足 / 开关关闭）→ 表单
  - 表单：圈子名称（≤16，实时字数）、分类（`picker`，与后端 `USER_CATEGORIES` 一致的 5 项）、简介（≤64，实时字数）、封面（可选，`wx.chooseMedia` 单图，前端拦 2MB，提交时走 `api.uploadImages`）
  - 本地校验口径与后端一致（名称必填且 ≤16、分类必选、简介 ≤64），校验失败行内红字 + toast，不发请求
  - 提交走 `api.createCircle`（`POST /api/circles`，写接口不兜底）；提交中按钮置灰、`submitting` 守卫防连点；失败原样展示后端 message（如「最多创建 1 个圈子」「内容包含违规词：…」）
  - 成功 → toast「创建成功，待审核通过后展示」→ 0.9s 后返回圈子列表（有上一页则 `navigateBack`，否则 `redirectTo` 圈子页）
- **`pages/discover` 建圈入口**
  - 分类标签下方新增卡片「创建一个自己的圈子」，**入口不按段位隐藏**（设计稿 §2.5：隐藏会让用户永远不知道有这条路径）
  - 权限只认 `/api/points/me` 的 `privileges.circleCreate` 与 `effectiveTierCode`：段位不足 → 弹窗「创建圈子需要黄金段位（成长值 200）」+「去积分页」按钮；黄金但开关关闭 → toast「圈子创建暂未开放」
  - 名额：无查询接口，用本机标记 `circle_created_v1` 灰显「你已创建 1 个（上限 1）」/「名额已满」，点击只提示不跳转
  - `onShow` 重新拉特权与列表，建圈返回后入口状态立刻更新；不改动原有轮播 / 分类 / 卡片布局
- **`app.json`** 注册 `pages/circle-create/circle-create`
- **`utils/api/points.js`** 的 `createCircle` 之前已存在且已导出（本轮未改）

> 与设计稿的文案差异：提交成功提示用「创建成功，待审核通过后展示」（本轮任务书指定），设计稿 §2.5 原写「已提交，等待审核」，语义一致（都表示已提交、待审）。其余文案（段位不足、名额上限、开关关闭）与设计稿逐字一致。

## 三、隐患

1. **名额状态是「本机标记」，不是服务端事实。** 后端没有「我已创建的圈子」查询接口，前端只能用 `Storage` 标记 `circle_created_v1` 灰显入口。换设备、清缓存、卸载重装、或管理端删掉用户圈子后，灰显状态都会与真实名额不一致：可能「灰着但其实能建」，也可能「亮着但一点就 403」。服务端 403 文案仍是唯一权威，前端文案会先于它出现。补一个 `GET /api/circles/mine` 约 0.5 人日。
2. **「审核中」角标没有做。** 设计稿 §2.3 要求「我的圈子」里待审圈子显示灰色「审核中」角标，但 `GET /api/circles` 只返回 `status=1`，待审圈子不进列表，也没有任何接口返回我的待审圈子。所以用户提交成功之后、审核通过之前，**除了那一次 toast，界面上没有任何凭据**——杀进程重进就再也看不到自己的申请。这是本轮最明显的体验缺口，需要配合隐患 1 的接口一起补。
3. **驳回后无法「修改再提交」，等于一次判死。** 设计稿 §2.3 写「驳回 → 可修改后重新提交（仍占 1 个名额）」，管理端驳回弹窗也照这句写了说明；但名额按 `creator_id` 计数、`status=0` 也计入，又没有 `PUT /api/circles/{id}` 编辑接口，结果是：用户被驳回后名额仍被占满，既不能改也不能建新的。当前只能靠管理端放行或人工删行。**管理端界面上的承诺与实际能力不一致，运营会按界面文案回复用户。** 要么补编辑接口，要么让驳回不占名额（或给一次性重提额度），约 1 人日。
4. **封面上传只有前端校验。** 后端 `createForUser` 只对 `cover` 做 `trim`，不校验类型/大小/域名。绕过小程序直接调接口可以塞任意 URL 或超大图，列表页会加载它。需要在服务端加图片类型/大小/归属校验（约 0.5 人日）。
5. **敏感词命中会把命中词回显给用户。** `AuditService` 的拒绝文案形如「内容包含违规词：测试」，前端原样展示。用户可据此逐词试探审核规则，也容易看到不该展示的词。对外建议统一成「名称或简介包含不适合的内容，请修改后重试」，命中词只进 `audit_log`（合规风险，约 0.5 人日）。
6. **圈子页首屏请求数 +1。** 入口权限要读 `/api/points/me`，`pages/discover` 现在首屏固定发 4 个请求（分类、热门、列表、积分），且每次 `onShow` 重新拉列表与权限。校园内网可接受，但页面再叠加功能时该合并成一次聚合接口（约 1 人日）。
7. **段位/开关判定的时间差。** 前端凭 `privileges` 放行、后端提交时重判（这是正确设计）。若运营在用户点击入口与提交之间关掉开关，用户会在建圈页提交时被 403 拦下——属于预期，但文案上会像「突然失败」，运营关停前最好先在后台备注里提醒。
8. **建圈审核没有 SLA 与提醒。** 待审圈子只靠管理端人工巡视；积压时用户会长期停在「提交成功但列表没有」。没有超时提醒、没有审核队列排序（按创建时间）。量上来后需要审核提醒与批量通过。
9. **审核通过后「圈主」能力只到 owner 行。** `circle_member(role='owner')` 已写入，但小程序端没有圈主专属操作（改名、踢人、置顶、解散），圈主与普通成员在界面上无差异；设计稿只要求「可发圈内帖」，这条已满足，但作为「建圈」卖点偏薄。
10. **真机交互完全没验。** picker、textarea 计数、`wx.chooseMedia`、toast 时序、`navigateBack` 后列表刷新、iPhone 安全区，全部只有静态检查与手工清单兜底。首次真机走查建议按第二节 1–15 逐条过。

| 我的圈子 / 审核进度 | 独立「我创建的圈子」列表：状态（待审/通过/驳回）、驳回原因、可编辑重提 | 约 1.5 人日（`GET /api/circles/mine` + 页面 + 编辑接口） |
| 驳回后可重提 | 驳回不占名额或给重提额度，编辑后原地重新提交 | 约 1 人日（与上一行共用接口） |
| 封面上传治理 | 服务端校验类型/大小、压缩裁剪、防盗链、审核图片本身 | 约 1 人日（含图片审核接通） |
| 建圈风控 | 账号龄/段位真实性校验、同设备多账号建圈识别、名称与简介去重 | 约 2 人日 |
| 审核运营 | 待审队列排序、批量通过、超时提醒、审核原因模板库 | 约 1 人日 |
| 圈主工具 | 改名/换封面/公告/成员管理/解散、圈主交接 | 约 3 人日 |
| 群聊合规 | 圈聊内容审核（当前是盲区，见设计稿 §9） | 约 3 人日（依赖审核服务扩容） |
| 数据与埋点 | 建圈漏斗（入口曝光 → 点击 → 提交 → 通过）、按段位分组的转化率 | 约 1 人日 |

**一句话**：现在能保证「只有黄金能建、每人 1 个、建了必须审、审核可追溯」，但**建圈之后用户看不见自己的申请、被驳回也改不了**——这两点是上线后投诉的主要来源，必须优先于「第二名额」之类的扩展。

## 七、上线前置

**顺序不能换：**

1. `mysql campus_life < backend/src/main/resources/db/module-tier-v31.sql`
   （建 `tier_config` / `user_privilege`、补 `circle.creator_id` 与索引、写两个开关；整份脚本幂等，可重复执行）
2. **确认 `backend/src/main/resources/db/module-audit.sql` 已执行**
   `insertUserCircle` 会写 `circle.audit_status / audit_reason / audit_at`，缺这三列建圈直接 500（这是最容易漏的一步）
3. 确认 `circle` 表已有 `status / hot / sort`（来自 `module-circles.sql`）与 `member_count`
4. 校验段位种子：`SELECT tier_code, name, g_threshold, enabled FROM tier_config ORDER BY sort;`
   预期：bronze(0) / silver(60) / gold(200) 三行 `enabled=1`，其余 5 行 `enabled=0`
5. 校验开关：
   ```sql
   SELECT flag_key, enabled FROM feature_flag
   WHERE flag_key IN ('circle.create.enabled','post.fastlane.enabled');
   ```
   预期 2 行且 `enabled=1`（缺 key 时 `isEnabled()` 也按开启处理，但落库才能让运营一键关停）
6. 校验列：`SHOW COLUMNS FROM circle LIKE 'creator_id';` 应有 1 行
7. 重启后端（无新增环境变量）
8. **小程序发新版本**：`pages/circle-create` 是新增页面，必须随版本发布；只发后端的话旧版小程序没有入口
9. 首启抽查：黄金账号 `POST /api/circles` → 返回 `status:"pending"`；管理端 `/circles` 选「待审核」→ 通过 → 小程序圈子列表可见、创建者收到站内通知

**运营前置**：建圈上限为 1，且驳回也占名额（见隐患 3）；上线前要让审核同学知道「驳回 = 用户本期不能再建」，拿不准就先通过或直接删行。

## 八、回滚方案

**开关（最快止血，30 秒缓存后生效，不用发版）**

```sql
UPDATE feature_flag SET enabled = 0 WHERE flag_key = 'circle.create.enabled';
```

效果：`privileges.circleCreate=false` → 黄金用户点入口提示「圈子创建暂未开放」，建圈页直接给说明卡；**已创建的圈子、圈子列表、圈聊全部不受影响**。免审出问题同理关 `post.fastlane.enabled`。

**代码**

- 小程序：删 `pages/circle-create/` 四件套 + `app.json` 那一行 + `pages/discover` 的入口（三处 WXML/JS/WXSS 改动）。已发布版本需要发新版本才能消失，所以**已发版时优先用开关**。
- 后端：回退 `CircleController` 的 `POST /api/circles` 与 `CircleService.createForUser`；圈子的 list/hot/detail/join/leave 是独立端点，不受影响。

**数据**

- 默认**不回退数据**：`circle` 里的用户建圈记录保留（列 `creator_id` 为 NULL 时与管理端建的圈完全兼容，不阻塞任何读路径）。
- 只想隐藏用户建的圈：`UPDATE circle SET status = 0 WHERE creator_id IS NOT NULL;`（不删数据，可恢复）。
- 彻底清理（会丢圈内帖子与成员关系，非必要不做）：
  ```sql
  DELETE FROM circle_member WHERE circle_id IN (SELECT id FROM circle WHERE creator_id IS NOT NULL);
  DELETE FROM circle WHERE creator_id IS NOT NULL;
  ```
- `tier_config` / `user_privilege` / `feature_flag` 行与 `circle.creator_id` 列**不回退**：功能 4（段位）与功能 5（免审）仍在用，删了会连带关掉段位展示。

**风险点**

- 若只回退后端、不回退小程序：旧前端点入口会 404/405，用户看到「请求失败」；必须同时关开关或回退前端。
- 回滚后 `circle_created_v1` 本机标记仍在，用户入口会保持灰显；恢复上线前让用户清缓存或忽略（服务端 403 会兜底说明）。
