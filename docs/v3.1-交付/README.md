## 二、每份报告的固定结构（八节）

每份报告必须八节齐全，**顺序不能变**，缺一节算没写完：

1. **完成了什么** —— 分后端 / 小程序端 / Web 端三段，逐条对应设计稿的章节号。写"做了什么"，不写"计划做什么"。
2. **如何测试** —— 两段：能自动化的（给出 `mvn -Dtest=XxxTest test` 或 `curl` 命令，可直接抄）；只能手测的（给步骤、点击路径、预期结果，写成表格）。每条都要有预期值，不接受"应该正常"。
3. **隐患** —— 已知缺陷、性能风险、数据一致性风险、合规风险。**这一节不许写"暂无"**，写不出来说明没想透。
4. **与商业级产品的差距** —— 具体到"差什么能力、差多少工作量、什么条件下必须补"。不接受"后续优化"这种空话。
5. **改动清单** —— 文件级：改了哪些、新增哪些、删了哪些。让人能据此做 code review。
6. **未做与原因** —— 设计稿里有、这次没做的；以及为什么不做（砍掉 / 延期 / 被外部依赖卡住）。
7. **上线前置** —— 必须先执行的 SQL、必须先开的开关、必须先配的环境变量，以及执行顺序。
8. **回滚方案** —— 出问题时怎么退：代码怎么退、数据怎么退、开关怎么关。**没有回滚方案的功能不上线。**

## 四、写作纪律

- **不夸大**：没做的就写没做，测试没过就写没过。交付报告的价值在于可信，夸一次就全废了。
- **隐患不隐瞒**：越是"上线后可能出事"的东西越要写在第 3 节，别埋在第 6 节。
- **差距要具体**：写"没有分布式事务，扣分与发券在单库单事务内，多实例下靠条件更新兜底，若将来拆库需要引入补偿任务（约 2 人日）"，不写"架构上还有优化空间"。
- **测试要能抄**：命令复制粘贴就能跑，不写"参考某某文档"。
- **结果栏如实回填**：设计稿第六节的"结果"列，实施完成后回填通过/失败，失败的不擦掉，写清原因。
