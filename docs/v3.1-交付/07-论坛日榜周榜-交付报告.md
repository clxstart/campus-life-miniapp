## 三、隐患

1. **算分口径与「被赞」的时效。** 被赞按 `post_like.created_at` 落窗；取消点赞再点会重复计分（点赞明细目前是「删一行/加一行」，历史时点不做去重）。日榜金额小，但周榜前 20 会被反复点赞刷分，需要风控（见第四节）。
2. **快照表没有历史清理策略。** 每天日榜 + 每周周榜各写一批行，长期会累积；目前无归档/清理任务，一年约 10（日）×365 + 20×52 ≈ 4700 行，量不大，但缺少保留策略。
3. **重结算会覆盖分数但不回滚已发奖励。** 若某用户先上榜发奖、后被判定刷分下榜，分数会被删掉快照行，但已发的分/成长值不会自动回收，需要人工冲正。
4. **`awarded` 置位与发分不是同一事务。** `PointsService.award` 成功后、`markAwarded` 前崩溃，会留下「已发分但 awarded=0」；下次重结算走 `AwardResult.ALREADY` 分支补置位并补通知，不会重复发分，但依赖 `task_log` 幂等键仍在。
5. **日榜/周榜结算在 00:10 与宿舍周榜 00:20 之间没有依赖。** 两个任务独立；若 00:10 那次因重启错过，只能靠管理端手动补跑（已提供入口）。
6. **「今天还没有人上榜」与「今日未结算」是两种状态。** 页面已区分，但运营文案容易混；接口用 `settled` 字段区分，前端不应自己按 `rows` 是否为空推断。
7. **榜单是全校还是跨校？** 当前算分 SQL 不按 `school_id` 过滤，是**全平台榜**。设计稿未要求分校榜；若未来要分校，需要在快照表加 `school_id` 并重写唯一键（约 1 人日）。
8. **通知依赖 `notification` 表。** 通知写失败只记日志，不影响发分；但用户可能「有分没通知」。
9. **手动重结算权限较宽。** super/school 都能调；school 管理员目前也能重算全平台榜单（没有按校隔离），属于跨校越权风险，应改为仅 super 或按校过滤（见第四节）。
10. **时区固定 Asia/Shanghai。** 换服务器时区不影响；但若未来做多时区校园，周期键需要带时区。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 刷分风控 | 同用户对同一帖的赞只计一次（按点赞明细幂等）、异常频率识别、榜单异常告警 | 约 2 人日 |
| 榜单分校 | 快照带 `school_id`，分校榜 + 全校榜两套 | 约 1 人日 |
| 奖励回收 | 下榜/封禁后按流水冲正，写「榜单回收」流水 | 约 1 人日 |
| 快照生命周期 | 归档表 + 保留 N 个月 + 定时清理 | 约 0.5 人日 |
| 结算可观测 | 结算耗时、失败行数、补跑次数进监控与告警 | 约 1 人日 |
| 榜单反作弊申诉 | 用户申诉入口 + 人工复核工作流 | 约 1.5 人日 |

**一句话**：算分、快照、幂等、补跑都成立；差的是反刷分、奖励回收与分校能力。

## 八、回滚方案

**代码**：回退第五节 6 个后端文件与两个前端页面/路由。

**数据**：

- 停发：`UPDATE task_catalog SET enabled=0 WHERE task_key IN ('rank_daily','rank_weekly');` —— 结算仍写快照，但不发分
- 删表（会丢快照，已发积分留在账本）：`DROP TABLE IF EXISTS forum_rank;`（非必要不做）
- 已发出的积分/成长值不会自动回收；需要时按 `point_log.module='points'` 且 `biz_key LIKE 'rank_%'` 人工冲正

**开关**：无 feature flag；用任务目录 `enabled` 停发是最小回滚。回滚代码后定时任务随之消失，无需额外清理。

**风险点**：若只停任务不删表，重新开启后会按已结算快照继续补发 `awarded=0` 的行；若要彻底停止，必须同时停任务或删快照。
