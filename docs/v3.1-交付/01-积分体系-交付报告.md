**核心文件**

- `service/PointsService.java` —— 唯一发放口，三个入口：`award()`（固定奖励，P/G 取自目录）、`awardCustom()`（变额奖励，P/G 传参）、`spend()`（扣分，条件更新防扣负）
- `mapper/PointsMapper.java` —— 全仓库唯一能写 `user_points` / `user_growth` / `point_log` 的 Mapper
- `controller/PointsController.java`、`controller/AdminTaskCatalogController.java`
- `config/AuthInterceptor.java` —— `/api/points` 进私有读前缀，未登录直接 401（设计稿用例 10）

**与设计稿的差异（三处，都是实现时发现原签名不成立）**

1. **`award()` 不接收 P/G，改为从 `task_catalog` 取值。** 设计稿签名是 `award(userId, taskKey, bizKey, p, g, remark)`，但 §2.2 又要求「后台改 P/G，30 秒内生效」——如果 P/G 由调用方传进来，后台改了不生效。改法：`award()` 从目录取，变额场景（派遣奖励、宿舍周榜）走 `awardCustom()`。
2. **新增 `spend()`，不用负数 `award()`。** 设计稿说扣分「走同一张流水，p 传负数」，但扣分不是「任务达成」，写进 `task_log` 会污染日上限计数。现在扣分只写 `point_log`，幂等靠 `uk_user_biz`。
3. **日上限超限时 `task_log` 留痕不删除。** 设计稿说「回滚本次插入」，实际保留：一是插入本身是幂等键，二是超限的业务事件本身需要留痕。代价是同一个 `bizKey` 之后不会再试（符合预期）。

## 三、隐患

1. **`task_catalog` 缓存是进程内的 30 秒。** 多实例部署时各节点独立，后台改完最多 30 秒内不一致；`updateTask()` 只清本节点缓存。要跨实例即时生效必须上 Redis 或消息广播。
2. **日上限存在并发穿透的窗口。** 「先插 `task_log` 再数数量」能挡住同一 `bizKey` 的并发（唯一键），但**不同 `bizKey` 的并发**仍可能同时看到 `count = cap-1` 而各发一次，导致当天多发 1–2 次。上限是软约束，不是硬约束。
3. **`point_log.balance_after` 不是权威值。** 它在事务内 `UPDATE` 之后读取，同用户并发两笔时会读到对方的结果。对账应以 `user_points.balance` 为准。
4. **`/api/points/me` 组合了段位/签到/特权三个服务。** 任一服务抛异常会让整个 `/me` 失败；目前没有降级，首屏会整块不可用。段位服务读的是 `tier_config` 与 `user_growth`，行缺失时返回青铜，不会抛错，但 `tier_config` 不可用时会向上冒泡。
5. **没有任何对账任务。** 如果哪天有人绕开 `PointsService` 直接改库（或手工 SQL 修数据），`user_points.balance` 与 `SUM(point_log.amount)` 会永久对不上，且不会有人发现。目前只在代码层面用「唯一写入口」防守。
6. **`pet_dispatch` 是 `daily_cap=0`（不限次）。** 派遣奖励的金额由调用方给，如果哪天调用方算出负数或超大值，`awardCustom` 只挡了 `p==0 && g==0`，没有上限校验。支付侧没有这条路径，但它是唯一一个「金额来自代码而非配置」的入口。
7. **`spend()` 里 `ensurePointsRow` 与 `deductPoints` 不是原子的一对。** 先建行再扣，两步之间没有锁；并发下只是多建一行零余额，不会出错，但也不能当成"原子建号+扣款"用。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 账目对账 | 每天定时跑 `SUM(point_log.amount)` 与 `user_points.balance` 比对，差异告警 | 约 1 人日（含差异表与告警） |
| 积分有效期 | 按批次记 `expire_at`，过期自动扣减并写「过期」流水 | 约 2 人日，且要用户协议支持 |
| 风控 | 单用户日发放上限、异常模式（同一 IP 多账号、秒级连发）识别与冻结 | 约 3 人日 |
| 分布式一致 | `task_catalog` 走配置中心/Redis 广播；发分走消息队列削峰 | 约 2 人日 |
| 审计与追溯 | 每笔发分记录来源 IP、设备、触发场景，可反查 | 约 1.5 人日 |
| 上限硬保证 | 用「计数行 + 条件更新」把日上限做成数据库级硬约束，而不是先数后发 | 约 1 人日 |

**一句话**：现在是「单库单事务 + 唯一键」的正确性等级，能保证不重复发、不扣成负数，但**没有对账兜底、没有风控、没有有效期**。商业级产品在这三块上花的力气通常比发分逻辑本身还多。

## 七、上线前置

**顺序不能换：**

1. **执行 SQL**：`mysql campus_life < backend/src/main/resources/db/module-points-v31.sql`（幂等，可重复执行；已在本地 dev 库执行两次验证）
2. **确认种子**：`SELECT COUNT(*) FROM task_catalog;` 应为 17
3. **重启后端**（无新增环境变量、无新增开关）
4. 首启后抽查一条：任一用户在宠物签到一次，`point_log` 应出现 `biz_key='pet_checkin:<日期>'`、`module='pet'`

> **注意**：`point_log` 加了唯一索引 `uk_user_biz(user_id, biz_key)`。历史行的 `biz_key` 为 `NULL`，MySQL 唯一索引允许多个 `NULL`，不会与历史数据冲突——但**执行前仍需确认** `SELECT COUNT(*) FROM point_log WHERE biz_key IS NOT NULL` 为 0，否则说明库里有别的写法在写这一列。

## 八、回滚方案

**代码**：回退上表 10 个 Java 文件 + 删 1 个测试文件。

**数据**：本次是**只增不删**的结构变更——新增 3 张表、`point_log` 新增 4 列与 1 个索引，没有改任何既有列的类型或语义。回滚代码后：

- `user_points` / `point_log` 旧字段照常可用，宠物模块回到原来的直写方式
- 新增的 3 张表与 4 个列可以留着（不写就是死数据，不影响旧代码）
- 若要彻底清理：`DROP TABLE user_growth, task_catalog, task_log;`（会丢已发出的成长值，**非必要不要执行**）

**开关**：无。这个功能没有 feature flag——它是底座，关掉等于停用宠物积分。

**风险点**：回滚后新产生的 `point_log` 行 `biz_key` 为 `NULL`，唯一索引仍存在但不生效，无副作用。
