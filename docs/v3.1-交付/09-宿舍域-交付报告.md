## 三、隐患

1. **`all_done` 置位早于发分。** 全员达成时先把 `dorm_sign.all_done` 从 0 改成 1 再逐人发分；若进程在置位后、发分前崩溃，剩余成员当天不会补发（重跑也不会，因为 `all_done=1`）。这是有意选择「宁可少发、不可重发」的取舍，但对账时会出现「宿舍达成、个别成员没分」的投诉，需要人工补。
2. **当日中途加入者可白拿全员奖励。** 判定基数是首签时固化的成员数，但发分遍历的是**发分时刻**的成员列表。若某人当天在「差 1 人达成」时加入，可能没签到也拿到 +5P。单人单日上限 5P，收益很小，但规则上不干净。修法需要把「达成时刻的成员集合」也冻结下来（约 0.5 人日）。
3. **周榜分数口径包含一切任务积分。** `SUM(task_log.p)` 会把发帖、签到、外卖等全部算进宿舍分，等于「谁更活跃谁赢」，不是「宿舍更团结谁赢」。这是设计稿 §3 明确选的口径，但容易被理解成宿舍专属行为榜，运营文案要写清。
4. **`/api/dorm/me` 每次请求都全表聚合周榜。** `weekScores` 对全部正常宿舍做 `task_log` 聚合；宿舍数和流水增长后，这个接口会变成慢查询。当前无缓存，也没有按 `school_id` 限制。宿舍上千后需加「周榜快照表 + 定时写入」（约 1 人日）。
5. **解散后页面无法自行知道「已解散」。** 成员关系已按设计删除，`/me` 只能返回「未加入」；顶部「该宿舍已解散」提示目前靠站内通知，页面上的 `dissolved` 字段实际不会被置真。属于设计稿「解散后成员关系解除」与「页面提示已解散」两条同时成立时的数据模型冲突。
6. **没有舍长转让接口。** 舍长还有舍友时不能退出，只能找管理员解散；设计稿写了「需先转让或由管理员解散」，转让没做（见第六节）。
7. **解散通知写失败不影响解散。** 通知是 best-effort；如果 notification 表异常，成员只会看到「未加入」，不会收到解散说明。
8. **周榜结算只在本机单实例验证。** 依赖 `ClusterLock` 租约减少重复执行；多实例下若租约过期后两节点重叠，靠 `task_log` 唯一键兜底不重复发分，但「冠军是谁」可能被后一次结算覆盖为同一结果（分数已固定，风险低）。
9. **`dorm_all_sign` 的日上限是「每人每天 1 次」。** 如果同一宿舍当天达成后又有新成员加入并触发二次判定（理论上不会，因为 `all_done` 已置 1），第二波人拿不到分；这是有意的。
10. **管理端列表的子查询在宿舍量大时偏慢。** 成员数与本周分都是相关子查询，`LIMIT` 之后才计算，宿舍上万时列表会拖慢；当前规模（校内）可接受。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 舍友真实性 | 对接教务/宿管系统核验同宿舍关系，或要求上传合照+人工抽检 | 依赖外部系统；无接口则至少 2 人日做抽检工作流 |
| 舍长转让 / 宿舍继承 | 舍长可指定继承人，空宿舍自动回收 | 约 0.5 人日（接口 + 页面） |
| 周榜快照 | 每周结算写快照表，页面只读快照，不实时聚合全表 | 约 1 人日 |
| 达成成员冻结 | 记录「达成时刻的成员集合」，发分只发给集合内成员 | 约 0.5 人日 |
| 解散可恢复 | 管理端「恢复宿舍」入口 + 成员一键回迁 | 约 1 人日 |
| 作弊风控 | 同 IP/同设备批量建宿、邀请码互刷识别与冻结 | 约 2 人日 |
| 奶茶券供应链 | 商户后台库存管理、核销对账、未发券补偿 | 依赖商户合作，非纯开发 |

**一句话**：现在能保证「一人一宿舍、全员只发一次、周榜可复算」，但没有舍友真实性核验、没有舍长转让、周榜是全表实时聚合；这三点在宿舍规模上来后必须补。

## 七、上线前置

**顺序不能换：**

1. `mysql campus_life < backend/src/main/resources/db/module-points-v31.sql`（任务目录与积分账本；宿舍发分依赖它）
2. `mysql campus_life < backend/src/main/resources/db/module-sign-v31.sql`（签到事实表；全员判定依赖 `sign_roll`）
3. `mysql campus_life < backend/src/main/resources/db/module-dorm-v31.sql`（幂等，已在临时库连跑两次验证：3 张表 + 2 条任务 + 1 条 `milk_tea`，重复执行不重复插入）
4. 校验种子：`SELECT COUNT(*) FROM task_catalog WHERE task_key IN ('dorm_all_sign','dorm_week_first');` 应为 2
5. 校验商品：`SELECT item_key, stock FROM reward_item WHERE item_key='milk_tea';` 应为 1 行、`stock=0`（要发奶茶再由运营加库存）
6. 重启后端（无新增环境变量、无新增开关）
7. 首启抽查：任一已认证用户建宿舍 → 另一账号用邀请码加入 → 两人签到 → `GET /api/dorm/me` 应显示 `allDone:true`，两人各 +5P/+8G

> **注意**：执行第 3 步前确认 `dorm` 三张表不存在（本脚本只 `CREATE TABLE IF NOT EXISTS`，不会覆盖已有数据）。`milk_tea` 的插入带 `ON DUPLICATE KEY UPDATE item_key=item_key`，不会覆盖运营已设置的库存。

## 八、回滚方案

**代码**：回退本报告第五节列出的 6 个后端文件与前端宿舍页；`AuthInterceptor` 去掉 `/api/dorm` 前缀。签到主流程不依赖宿舍（回调是接口扩展点），回退后签到照常工作。

**数据**（按风险从低到高）：

1. 只停功能：把 `task_catalog` 里 `dorm_all_sign`、`dorm_week_first` 的 `enabled` 置 0 —— 签到照常，但不再发宿舍分；页面仍可看已有宿舍。
2. 删商品行：`DELETE FROM reward_item WHERE item_key='milk_tea';`（只影响周榜奶茶券，不影响成长值）。
3. 彻底清理（会丢数据，非必要不做）：
   ```sql
   DROP TABLE IF EXISTS dorm_sign, dorm_member, dorm;
   ```
   已发出的积分/成长值留在 `user_points` / `user_growth` / `point_log`，**不会自动回退**；要回收需人工按 `point_log.module='dorm'` 做负数冲正（不建议批量做）。

**开关**：无 feature flag。宿舍是独立域，关掉的方式是把两个任务行 `enabled=0`（发分停止）或直接回退代码；页面入口在 `app.json` 与 `profile`，回退代码即消失。
