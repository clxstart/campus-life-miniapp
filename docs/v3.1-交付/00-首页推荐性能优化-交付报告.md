## 一、完成了什么

**后端**

| 改动点 | 之前 | 之后 |
|---|---|---|
| `RecommendMapper.hotGoods` 的收藏标记 | `(SELECT COUNT(*) ... WHERE f.goods_id=g.id AND f.user_id=?)>0` 挂在 SELECT 里，每行一次相关子查询，且让整份结果无法按批次缓存 | 移除。改为独立方法 `favoriteGoodsIds(userId, goodsIds)`，一次 `IN` 查完 |
| `RecommendService` | 每次请求 4 条 SQL：2 条 `COUNT(*)` 全表 + 2 条按计算式 `ORDER BY heat` 全表扫 + filesort | 加 60 秒进程内缓存，覆盖两条 COUNT 与两条排序结果；收藏标记**不进缓存**，每次按用户现算 |
| 降级 | 收藏子查询失败会让整个首页 500 | `favoredIds()` 吞掉异常返回空集，星标降级为 false，首页照常返回 |

**小程序端**：无改动（接口路径、字段名、返回结构全部不变）。

**Web 端**：无改动。

## 三、隐患

**这个缓存是"够用"级别，不是"正确"级别，四条要记住：**

1. **进程内缓存，多实例不同步。** 单机没问题；开两个实例后各存各的，同一时刻两个用户可能看到不同推荐。将来要做"运营改完立即生效"必须换 Redis 或加主动失效——现在没有，改数据要等 60 秒。
2. **无主动失效。** `toggleGoodsFavorite`、`viewGoods`、`orderPlaced` 这些写操作都**不清理缓存**。热度排名最多滞后 60 秒。对"今日推荐"可接受，但如果哪天有人拿它当实时榜看，就会觉得"数据不对"。
3. **`CACHE_MAX` 满了是整体 clear()。** 不做 LRU，粗暴但正确——只是会让下一次请求全部回源。256 个条目按 `size+offset` 组合，正常数据量到不了。
4. **没有命中率监控。** 缓存到底有没有生效，现在只能看日志或加断点，没有指标。

**另有一条不是这次引入的**：`hotGoods` / `hotShops` 的 `ORDER BY heat` 依然是计算式排序，缓存只是把它的执行频率从"每人每次"降到"每分钟一次"。数据量涨到十万级商品时，即使每分钟一次也会变慢——那时要物化 `heat` 列，不是加缓存能救的。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 缓存位置 | Redis，多实例共享 + 主动失效（收藏/下单/改价时删 key） | 约 1 人日（含降级到本地缓存） |
| 热度计算 | `heat` 物化成真实列，由定时任务每 10 分钟重算并建索引，排序走索引 | 约 2 人日 |
| 首页数据聚合 | 一次请求返回推荐 + banner + 今日课程，而不是前端打多个接口 | 约 1.5 人日 |
| 缓存可观测 | 命中率、回源次数、慢查询告警 | 约 0.5 人日 |
| 推荐逻辑 | 现在只有"热度排序 + 轮换"，没有个性化、没有冷启动、没有去重曝光 | 这是产品能力差距，不是工程差距 |

**一句话**：这次改动解决的是"同一份数据被反复全表扫"，属于止血。商业级产品会在数据层就把热度沉淀好，接口层只做查询——这是两套思路，不是加个缓存的问题。

## 六、未做与原因

| 未做 | 原因 |
|---|---|
| Redis 缓存 | 当前单机部署，进程内缓存已够；引入 Redis 依赖要先确认 `CAMPUS_HA_REDIS_URL` 是否真的可连 |
| `heat` 物化列 | 需要新增定时重算任务 + 索引，属结构改动，等商品数据量过万再做更划算 |
| 去掉两条 `COUNT(*)` | 它们是 `hasMore` 与 offset 取模的依据，换成"多取一条判断"会改变 `hasMore` 的语义，收益不抵风险 |
| 压测 | 无可用数据库实例 |
| 真实 MySQL 的 EXPLAIN 对比 | 同上 |
