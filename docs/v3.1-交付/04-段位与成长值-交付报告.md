**核心文件**

- `service/TierService.java` —— 推导（`forGrowth` / `forUser` / `tierCodeForGrowth`）、比较（`rankOf`）、**特权唯一入口** `effectiveTierCode()` / `privileges()`、体验段位 `grantTrial()`、管理端只读 `configForAdmin()`
- `mapper/TierMapper.java` —— 配置（`ORDER BY g_threshold, sort`）、成长值、未过期特权（SQL 里 `expires_at IS NULL OR expires_at > NOW()`）、体验特权 upsert
- `controller/AdminTierController.java` —— 只读段位配置
- `resources/db/module-tier-v31.sql` —— `tier_config` 8 行 + `user_privilege` + `circle.creator_id` + 两个特权开关（`post.fastlane.enabled`、`circle.create.enabled`）

**与设计稿的差异（三处）**

1. **设计稿 §5 的 JSON 示例 `"percent": 71` 与 §6 用例 6 的 58 自相矛盾。** 按公式 `(142-60)/(200-60)×100 = 58.57 → 58`，实现取 **58**（§6 用例 6 与代码一致，§5 示例的 71 是笔误）。已回填 §6 时保留原表，未改设计稿正文。
2. **新增 `effectiveTierCode()` 作为特权判定的唯一入口。** 设计稿 §9 风险表只写了「特权判定统一走 `TierService.effectiveTier(userId)`」，实现落地为 `effectiveTierCode()` + `rankOf()`，语义是「G 推导段位 与 未过期体验段位（`user_privilege.priv_key=tier_trial_*`）取较高者」。展示口径仍按 G（`forGrowth`），**体验段位不改变铭牌**。
3. **`privileges()` 三项特权都带开关语义。** `priorityReply`（白银）无开关常开；`postFastlane`（黄金）与 `circleCreate`（黄金）各受一个 `feature_flag` 控制，关闭时对应特权一律 false，入口保留由前端提示。

## 三、隐患

1. **Web 段位表的字段名与后端不一致，两列永远为空。（真实缺陷，本轮已修）** 原 `web/src/views/PointsTasks.vue` 读 `tier.tierCode`、`tier.honorLabel`，而 `TierService.configForAdmin()` 返回的是 `code`，且没有 `honorLabel`。已改为：`:key` 与名称读 `code`，特权摘要优先读后端 `privilegeSummary`；同时删掉设计稿未要求的「荣誉标识」列，表格改为 4 列。设计稿 §2.4 要求的三列（段位/G/是否开放/特权摘要）现已全部有值。
2. **晋升 toast 未实现，升级没有即时反馈。（本轮已修）** `pages/points/points.js` 新增 `LAST_TIER_KEY` 与 `maybeNotifyTierUp()`：首次进入只记录，之后段位序号上升时 toast `晋升白银·圈内熟人`；体验段位到期回落不弹。
3. **个人页不显示段位，段位曝光只有一个入口。（本轮已修）** `pages/profile` 的 `loadPoints()` 读取 `/api/points/me` 的 `tier.name`，未认证时昵称旁显示两字段位 chip（如「白银」）；已认证时仍只显示认证标签，符合设计稿「只显示认证标签」的硬约束。
4. **`awardCustom()` 不校验 P/G 非负，「成长值只涨不降」可被调用方破坏。** `PointsService.doAward()` 只挡了 `p==0 && g==0`，`overrideG` 传负数会直接执行 `g_total = g_total + delta`，`overrideP` 传负数会走 `balance = balance + delta`，**绕开 `spend()` 的「余额不足不扣」条件更新**。目前两个调用方（`ForumRankService` 提前返回 0 奖励、`PetCompanionService` 用 `rewardMin/rewardMax`）都不会主动传负数，但 `pet_dispatch` 的金额来自数据库配置，配错一个负值就能扣成负数、把 G 拉低，且没有对账发现。单点校验（`if (p < 0 || g < 0) throw`）约 0.1 人日。
5. **门槛是可被 SQL 直接改写的数据，而代码只做读取。** 「只允许上调、必须公告」目前是**流程约束不是代码约束**：任何人 `UPDATE tier_config SET g_threshold=...` 立即造成掉段/升段，没有校验（如新门槛必须 ≥ 旧门槛）、没有历史版本表、没有变更审计。设计稿 §2.4 说「不提供后台编辑」，但库权限仍在。
6. **`tier_config` 的门槛顺序没有约束。** 推导依赖「按 `g_threshold` 升序扫」这一顺序前提。如果有人插了一行门槛写反（如黄金 30 < 白银 60）或两段同门槛，推导会静默错段（不会报错），而且没有启动自检。建议加一条启动校验：门槛严格递增、`bronze` 门槛为 0。
7. **30 秒缓存多实例不一致。** 每个节点各自缓存，`evict()` 只清本节点。设计稿只读、改门槛靠发版，所以可接受；但若运维直接用 SQL 改门槛，最多 30 秒内各节点判定不同，且**没有任何一处能强制刷新全集群**。
8. **`maxOpen` 后进度条不再有信息量。** G=200 与 G=9999 都是 `percent=100` +「已完成当前开放段位」，卡片上唯一还能看出差距的是 `gTotal` 数字本身。对高活跃用户来说，「成长值还在涨但段位不动」需要一个「更高段位敬请期待」之外的承接（例如距铂金 600 还有多远），否则 G 的数值增长失去语境。
9. **`g_total` 没有对账与回填。** 若有人绕开 `PointsService` 直接改 `user_growth`（或手工修数据），段位会随数字漂移，且和 `SUM(point_log.g_amount)` 的差异永远没人发现。迁移期历史 `point_log.g_amount` 全为 0、`user_growth` 为空，两者一致**无需回填**；但将来若决定按历史行为补发成长值，缺一份一次性脚本。
10. **`rankOf()` 依赖配置行完整。** 它按 `config().tiers()` 的行序返回 1..8，`user_privilege` 里的 `tier_trial_*` 若指向一个配置里不存在的段位（例如删过行），`rankOf` 返回 0，体验特权静默失效，也不会报错。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 晋升通知 | 站内信 + 订阅消息 + 页面弹层，三端一致；带「解锁了什么特权」 | 约 1 人日（站内信已有基建） |
| 门槛版本化 | `tier_config_history` 表 + 变更审计 + 只允许上调的 DB 约束 | 约 1 人日 |
| 当季活跃值 S | `s_threshold` 真正参与判定，季度重置，防躺平 | 约 3 人日（大表 V3.3） |
| 段位衰减 | 赛季衰减/保级（大表明确说不做，属商业级反向能力） | 约 2 人日，且需公告与申诉 |
| 铭牌与徽章 | 图标/特效素材、主页皮肤、徽章 18 枚 | 约 5 人日 + 设计素材（V3.2/V3.3） |
| 段位排行榜 | 按 G 的校内榜/全校榜 | 约 2 人日（可复用论坛榜的快照+结算管线） |
| 成长值对账 | 每日比对 `user_growth.g_total` 与 `SUM(point_log.g_amount)`，差异告警 | 约 0.5 人日 |
| 前端展示一致性 | 段位卡与说明弹层的视觉状态（圆点/竖条/灰显）与后端字段名对齐 | 约 0.5 人日（含隐患 1、3，本轮已修） |

**一句话**：推导、边界、只涨不降、并发、配置缓存都是成立且被用例钉住的；差的是**晋升的站内信/订阅消息、门槛治理（版本/校验/审计）与两端字段对齐**——隐患 1–3 的三个用户可见缺陷本轮已修，门槛治理仍是商业级差距。

## 八、回滚方案

**代码**：回退第五节中 `TierService` / `TierMapper` / `AdminTierController` 三个后端文件 + `PointsController` 的 `tier`/`privileges` 两个字段 + `PointsMapper` 的成长值方法 + 前端段位卡与 Web 段位表。

**数据**：

- `tier_config` / `user_privilege` 可保留（旧代码不读，就是死数据）；删表：`DROP TABLE IF EXISTS user_privilege, tier_config;`（**丢配置**，重上线需重跑种子脚本；不会丢成长值）
- `user_growth` **不要删**：它是功能 1 的资产底座，`PointsService` 仍在写；删了会丢所有用户的成长值且无法恢复
- 停特权（不发版的最小降级）：`UPDATE feature_flag SET enabled=0 WHERE flag_key IN ('post.fastlane.enabled','circle.create.enabled');` —— 黄金的两项特权立即关闭；**`priorityReply`（白银）没有开关**，只能回滚代码或改判定逻辑

**开关**：无段位 feature flag。可用的是两个特权开关（见上），粒度到「免审 / 建圈」，不到「段位展示」。

**风险点**：

1. 只关特权开关、不回滚代码时，`privileges()` 仍会返回 `effectiveTierCode` 与 `priorityReply=true`，前端若按它渲染，会出现「白银仍显示优先应答」——白银特权没有开关是设计缺口。
2. 回滚后 `point_log.g_amount` 继续累积（`PointsService` 未变），只是不再展示；将来重新上线时 `g_total` 历史完整，不需要补数据。
3. `tier_config` 若被回滚前改过门槛，重新上线会按新门槛直接生效，用户可能已「被升段/降段」，回滚不负责还原门槛历史（无版本表，见隐患 5）。
