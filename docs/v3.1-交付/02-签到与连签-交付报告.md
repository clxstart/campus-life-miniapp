**核心文件**

- `service/SignService.java` —— 签到 / 只读状态 / 下一档里程碑；六档 `MILESTONES = {3,5,7,15,20,30}`
- `mapper/SignMapper.java` —— `insert` / `streakOn` / `streakOnShared` / `updateStreak`
- `controller/SignController.java` —— 只一个 `POST /sign`，与积分查询分开（签到有自己的事务语义）
- `service/SignCompletedListener.java` —— 签到后置钩子，宿舍域实现（不引入循环依赖）
- `resources/db/module-sign-v31.sql` —— 建表 + 任务种子，整份可重复执行

**与设计稿的差异（两处）**

1. **并发双击的失败方要用加锁读回状态。** 设计稿写「冲突 → 已签到，直接返回现状」，但如果直接调只读 `status()`，失败方的事务在早期读 `task_catalog` 时已建立一致性读快照，随后普通 `SELECT` 读不到对方刚提交的那一行，会返回 `signedToday=false, streakDays=0` ——前端按钮重新亮起，用户以为没签上。实现改为 `SELECT ... LOCK IN SHARE MODE` 回读当天行，并显式置 `signedToday=true`。用例 `concurrentDoubleClickOnlyAwardsOnce` 就是钉这一条。
2. **「签到暂未开放」放在 `data.message`，不在顶层 `msg`。** 设计稿错误表写 `msg="签到暂未开放"`，而全站返回体统一是 `{code, data, msg}`，实现放在 `data.message` 里（成功时为空串）。

### 小程序端

- `pages/points` 顶部签到卡：`今日签到` + `已连续签到 N 天`；主按钮两态（`签到 +1 积分` / 置灰 `今天已签到`）；三个圆点（最近一档已达成 + 接下来两档）；`下一档：连签 N 天，额外 +X 积分`；六档全达成时兜底文案「连签里程碑已全部达成」
- 防连点：本地 `signBusy` + `cp-btn-primary--disabled` + `hover-class="tap-btn"`，进函数先判 `signedToday`
- 成功后**局部刷新**（余额、连签、圆点、下一档、任务列表、明细），不整页重载；里程碑单独第二条 toast（`连续签到 N 天，额外 +X 积分`），不与主 toast 合并
- 失败 → toast 错误文案 + 按钮恢复可点
- 入口：`我的` → `我的积分`（`utils/api/points.js` 的 `signPoints()`）

### Web 端

**按设计稿无页面。** 排查某个用户为什么没签到，走「用户管理 → 该用户 → 积分明细」，看 `task_key=daily_sign` 的记录。

**用例 6 / 7 的做法说明**

- **用例 6（本轮升级为真时钟）**：`SignService` 原来「今天」直接取 `LocalDate.now(SHANGHAI)`，没有注入点。本轮把时间源收敛成构造器参数 `@Nullable Clock`（容器里没有 Clock bean 时回落 `Clock.system(SHANGHAI)`，**生产行为不变**），于是可以用固定时钟真的把时间拨到「3-1 23:59:59」与「3-2 00:00:01」各签一次，断言两个不同 `biz_date`、连签 1→2（`signsOnEitherSideOfShanghaiMidnightLandOnDifferentDays`）。原「造昨天行」的 `crossDaySignAdvancesStreakAndWritesTwoBizDates` 保留作回归。
- **用例 7**：临时 `TimeZone.setDefault()` 换成一个「当前日期与上海不是同一天」的时区（上海时 19 点后必用 UTC+14 的 Kiritimati，其余用 UTC-11 的 Midway，二者必有一个与上海异日），再签到，断言 `sign_roll.biz_date` 等于上海今天、`status()` 判为已签。若代码写成不带时区的 `LocalDate.now()`，这条会立刻失败。测试结尾恢复原时区（`finally`），不影响同 JVM 的其他用例。

**另有 4 条补充用例**（设计稿未列，但都是真实边界）

| 用例 | 钉住什么 |

## 三、隐患

1. **开关关闭时前端会误报「签到成功」。（真实缺陷，本轮已修，且产品态已补齐）** 后端在 `daily_sign.enabled=0` 时返回 `code=0`、`signedToday=false`、`awarded=[]`、`message="签到暂未开放"`；原 `pages/points/points.js` 的 `sign()` 拿到返回值后无条件 `setData({signedToday:true})` 并 toast `签到成功 +1 积分`。第一轮已改为：`awarded` 为空时按 `message` 弹 info toast、不置灰按钮、立即 `loadMe()` 回读真实状态。本轮再补齐产品态：新增 `signDisabled`（由 `/points/tasks` 是否下发 `daily_sign` 推断，拉取失败时保留上次判断），按钮灰显不可点，下方小字「签到暂未开放」，与设计稿 §2.1 对齐；运行中后端回「暂未开放/已关闭/维护」也会切到该态。
2. **跨天边界曾经没有真时钟验证。（本轮已补）** 原来用例 6 是「造昨天那行」的近似；本轮给 `SignService` 加了可注入 `@Nullable Clock`（无 bean 时回落上海系统时钟，生产行为不变），用固定时钟在 3-1 23:59:59 与 3-2 00:00:01 各签一次，断言两个 `biz_date`、连签 1→2（`signsOnEitherSideOfShanghaiMidnightLandOnDifferentDays`）。仍存在的局限：这只是「边界两侧各一次」，不是真实时钟自然流逝。
3. **连签是单点脆弱数据。** 连签只靠 `sign_roll` 昨天那一行，没有冗余累计。任何一次写入丢失（回滚、误删、迁移漏行）都会让用户从 30 天掉回 1 天，而我们**没有任何修复工具**——没有补签、没有后台改连签、没有对账。设计稿明确不做补签（属 V3.2 徽章体系），所以这是被接受的风险，但它会直接产生客诉。
4. **开关关闭期间连签必然断。** 关闭 `daily_sign` 期间没人能签，重新打开后所有人的连签从 1 重新开始。设计稿没提供「关闭期间连签冻结/补偿」的方案。运营若因为一次故障关 3 天开关，损失的是全站用户的连签，且无公告模板。
5. **无任何风控。** `daily_sign` 是唯一「不产出内容就能拿分」的任务：注册机每天每号白拿 1P/1G，30 天还能拿满 6 档里程碑共 106P/106G。当前没有设备/IP/频次维度限制，也没有异常账号识别。金额极小，但按号计的成本是线性的。
6. **签到与宠物签到并存，同一天最多 6P。** 设计稿刻意保留（宠物 5 + 全局 1）。若将来要收敛，改 `task_catalog.pet_checkin.p_reward=0` 一行即可，不动代码；但**存量用户已经拿过的 5P 不会回收**。
7. **`sign_roll` 没有生命周期管理。** 一活跃用户一天一行，一年 = 365 × DAU 行，没有归档/清理策略。当前量级无所谓，但 `idx_sign_streak` 会随表增长，且历史行对业务只用于「昨天有没有签」。
8. **连签天数无上限。** 超过 30 天后 `streak_days` 继续累加，页面只剩「连签里程碑已全部达成」，没有任何新的激励点；`nextMilestone=null` 时前端只显示兜底文案。这是设计缺口（不是 bug），但会让第 31 天起的老用户失去钩子。
9. **里程碑金额是「读时取目录」。** `nextMilestone` 的 p/g 与真正发放取同一张 `task_catalog`，运营中途调金额会让「页面上写的 10」和「实际发 15」在极端时序下不一致（缓存 30 秒窗口）。金额一般不动，属低风险。
10. **时区口径依赖两处约定。** 业务日期用 `ZoneId.of("Asia/Shanghai")`（显式，好）；但 JDBC 连接串也写了 `serverTimezone=Asia/Shanghai`（`MysqlIntegrationSupport` 与生产配置同款）。将来若有人用字符串/`java.sql.Date` 写 `biz_date`，两处约定不一致会出现「差一天」；目前所有写入都走 MyBatis 的 `LocalDate`，暂时安全。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 签到日历 / 补签 | 月历视图 + 补签卡（用积分买「时间」），断签可救 | 约 3 人日（含表、页面、后台发放补签卡） |
| 签到提醒 | 订阅消息模板 + 定时触发（晚 20:00 未签提醒） | 约 2 人日，前置是模板申请与审核 |
| 连签补偿 | 开关关闭/故障期间冻结连签，或按漏签天数批量补 | 约 1 人日（需一张连签修正流水，才能审计） |
| 反作弊 | 设备/IP/行为频次风控，异常账号冻结发放 | 约 3 人日（与积分体系同一套风控） |
| 时区可测 | 注入 `Clock`，跨天/时区用例变成真时钟测试 | 约 0.5 人日 |
| 签到数据可运营 | 签到率、连签分布、次留看板 | 约 1 人日 |
| 关闭开关的产品态 | 按钮灰显 + 小字说明 + 埋点（当前会误报成功） | 约 0.5 人日 |

**一句话**：签到发分、连签推算、幂等、并发、时区口径都是成立且被用例钉住的；差的是**玩法（日历/补签/提醒）与风控**，以及**开关关闭时的产品态处理**——后者是本轮真实缺陷，不是「后续优化」。

## 七、上线前置

**顺序不能换：**

1. **执行任务目录底座**（若尚未执行）：`mysql campus_life < backend/src/main/resources/db/module-points-v31.sql`
2. **执行本功能 SQL**：`mysql campus_life < backend/src/main/resources/db/module-sign-v31.sql`（幂等，可重复执行）
3. **校验种子**：`SELECT COUNT(*) FROM task_catalog WHERE task_key='daily_sign' OR task_key LIKE 'sign_streak_%';` 应为 **7**
4. **校验金额**：`SELECT task_key,p_reward,g_reward,daily_cap FROM task_catalog WHERE task_key LIKE 'sign%' ORDER BY sort;` 应为 1/1、5/5、10/10、15/15、20/20、30/30、50/50，`daily_cap` 全为 1
5. **确认时区口径**：JDBC 连接串带 `serverTimezone=Asia/Shanghai`；业务日期由代码 `ZoneId.of("Asia/Shanghai")` 计算，不用数据库时区
6. **重启后端**（无新增环境变量、无 feature flag）
7. **首启冒烟**：任一账号 `POST /api/points/sign` → `streakDays=1`、余额 +1；`GET /api/points/me` 的 `signedToday=true`；`SELECT COUNT(*) FROM sign_roll WHERE user_id=<该账号>` 为 1
8. **回归**：`bash ../tools/mvn-lock.sh -o test -Dtest=SignServiceIntegrationTest` 应 13 条全绿

> 开关：本功能唯一的「开关」是任务目录 `task_catalog.daily_sign.enabled`。注意它是**服务端开关**，关闭后前端会误报成功（隐患 1），上线后若要临时关闭，请同时知会前端改文案，或先只关 `sign_streak_*`（不停 `daily_sign`）。

## 八、回滚方案

**代码**：回退第五节中 `Sign*` 三个后端文件 + `SignCompletedListener` + `PointsController` 的三个字段 + `AuthInterceptor` 的 `/api/points` 前缀（后两处会连带影响功能 1 的 401 行为，见风险点），前端回退 `pages/points` 的签到卡与 `utils/api/points.js` 的 `signPoints`。

**数据**（只增不删，回滚代码后不阻塞）：

- 停发（最小回滚，不用发版）：`UPDATE task_catalog SET enabled=0 WHERE task_key='daily_sign' OR task_key LIKE 'sign_streak_%';`
- `sign_roll` 可保留（旧代码不读，就是死数据）；若要彻底清理：`DROP TABLE IF EXISTS sign_roll;`（**丢连签事实**，重新上线后所有用户从 1 天开始，非必要不要执行）
- 已发出的积分/成长值留在 `point_log` / `user_growth`，不会回收；需要时按 `point_log.type IN ('daily_sign','sign_streak_3'…)` 人工冲正

**开关**：没有 feature flag，只有任务目录 `enabled`。`enabled=0` 时服务端不写签到、不发分，但**前端仍会提示「签到成功」**（隐患 1）——这是回滚路径上最容易踩的坑：必须同时降级前端，或接受当天用户被告知成功。

**风险点**：

1. 回滚 `AuthInterceptor` 会让 `/api/points` 变回「不校验 token」，未登录会拿到空账而不是 401（功能 1 的已知要求），建议只回滚签到相关文件，保留私有前缀。
2. 回滚后 `sign_roll` 若被新版本写过，`biz_date` 与 `streak_days` 仍在，重新上线可直接接续连签（不需要重算）。
3. `task_catalog` 停发不影响 `point_log` 唯一键，重新启用后同一用户同一天不会重复领（`biz_key=日期` 已存在）。
