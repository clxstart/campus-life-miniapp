## 一、完成了什么

### 后端

| 设计稿章节 | 落地情况 |
|---|---|
| §6 新人礼包发放 | `AuthService.issueFor()` 在首次建号成功时调 `grantNewbieGift()`：`points.award(userId, 'newbie_gift', 'onboard', '新人礼包')`（30P 由 `task_catalog.newbie_gift` 的 `p_reward=30` 决定，`daily_cap=1`）+ `tierService.grantTrial(userId, SILVER, 7)`；`biz_key='newbie_gift:onboard'` 保证一辈子只发一次；发分/发体验各自 try/catch，失败只记日志不阻断登录 |
| §6 建号幂等 | 建号只发生在 `created=true` 分支；重复登录复用同一账号，不再发放；DB 侧靠 `point_log` 唯一键 + `user_privilege` 幂等 |
| §4 商品池 | `db/module-reward-v31.sql`：`reward_item`（价格/库存/限购/券标题/面额/门槛/有效天数/启停/排序）+ `redeem_record`（限购计数依据），种子 4 档外卖券 |
| §4 券表改造 | `coupon` 扩 `value_cents / threshold_cents / scope / expire_on / locked_at / used_at / order_id / source` + `idx_coupon_user_state`；状态机 `1 可用 / 2 锁定 / 3 已核销 / 0 作废` |
| §6 `GET /api/points/rewards` | 登录本人：商品池（下架不返回）+ 我的已兑次数 + `soldOut/limitReached/valueYuan` + 余额 |
| §6 `POST /api/points/redeem` | 事务内：库存条件更新 → 发券（`value_cents = price_p`，1P=1 分）→ 写 `redeem_record` → `PointsService.spend` 条件扣分；任一步失败整体回滚 |
| §6 券列表 | `GET /api/users/{id}/coupons` 只返回 status=1 且未过期，按新到旧；个人页「N 张可用」与列表同口径 |
| §6 管理端 | `GET /api/admin/reward-item`、`PUT /api/admin/reward-item/{itemKey}`（价格/库存/限购/券标题/面额/启停） |
| §5 券结算 | `BizService.createOrder()` 在服务端用 `couponService.usable()` 校验并锁券，`total = subtotal - shop_discount - coupon_discount + 费用`，前端不能传抵扣额；`pay_amount_cents` 走同一金额链 |
| §5 三条账 | `PaymentLedgerService.applyCoupon()`：核销券 + 记 `delivery:{orderId}:subsidy`（`platform_subsidy`，平台出账）；商家 `income` 不含券额 |
| §5 退款 | `MerchantRefundStatusService`：退实付额、`income` 冲销、`platform_subsidy` 置 `void`、券作废不退（防「下单→用券→退款→再用券」套利） |
| §5 关单释放 | `PayService` 对账/超时关单时 `couponService.releaseByOrder()`，锁定的券回到可用 |
| §5 缺陷修复 | `UserService.coupons()` 过滤已用/作废/过期；`coupon.expire_on DATE` 新增且旧 `expire_at` 保留兼容；店铺满减与券抵扣分列 `discount_amount / coupon_discount` |

- **`pages/points`**：余额卡下方「去兑换」按钮跳 `points-redeem`。
- **`pages/profile`**：「优惠与权益」读取券列表，按可用券展示（标题/面额/有效期）。
- **本次新增：新人礼包一次性提示。** 后端登录返回 `newUser=true` 时，`app.js` 把标记写入 `globalData.newUser`；首页 `pages/index` 在登录完成（`onLoginReady`）或 `onShow` 时判断，满足「登录已完成 + 首次建号 + 本地未弹过」才用 `utils/ui-popup-helper` 的 `popup.modal` 弹出：
  - 标题「新人礼包已到账」，正文两行「30 积分」「白银体验 7 天（快速应答）」，按钮「去看看」（跳 `/pages/points/points`）与「知道了」；
  - 先写 `storage` 键 `newbieGiftShown=1` 再弹，避免弹窗期间页面重入弹两次；
  - 不用 `wx.showModal`，不叠加学生认证引导（设计稿要求礼包优先）；
  - 未挂载 `ui-popup` 组件时由 helper 自身兜底为 toast，不抛异常。
- **2026-11-11 收尾轮新增：外卖下单页选券（`pages/food-order`）。** 这是本轮补的最大产品缺口——后端早就支持券结算，但下单页不传 `couponId`，用户兑了券也用不出去：
  - 结算页加载后拉 `GET /api/users/{id}/coupons`（只返回可用券），本地按 `thresholdCents ≤ 商品合计` 过滤，**默认自动选「抵扣最多」的一张**；用户手动选过（含选「不使用」）就不再自动改；
  - 订单卡新增「优惠券」行：选中显示 `券名 −¥1.00 ›`，没有可用券显示 `暂无可用` 并在下一行给门槛原因（如 `满 20.00 元可用`）；
  - 点该行打开 `popup.sheet`：可选券在前（当前项 `✓`、带抵扣额与有效期）、不可选券带原因（点了只 toast 原因、不选中）、最后一项「不使用优惠券」；
  - 合计区新增 `券抵扣 −¥1.00` 分隔行，合计与底部实付同步为券后金额，底部说明补「已扣满减与优惠券」；
  - 提交时 payload 带 `couponId`，**幂等键签名加入券 id**（换券 = 换一次结算，必须换新 key，否则复用旧订单会导致券对不上）；
  - 下单成功后用订单返回的 `total / couponDiscount` **校准**展示金额（客户端只是预估）；
  - 券相关服务端错误（被别的订单锁走 / 过期 / 门槛不足）原样 toast 中文原因，并刷新券列表重选；券列表拉取失败不阻塞下单。

### 只能手测

**接口层（启动服务）**

```bash
BASE=http://localhost:8080
TOKEN=...   # 小程序登录后的 JWT
curl -s $BASE/api/points/rewards -H "Authorization: Bearer $TOKEN"          # 商品池 + 余额
curl -s -X POST $BASE/api/points/redeem -H "Authorization: Bearer $TOKEN" \
     -H 'Content-Type: application/json' -d '{"itemKey":"takeout_0_1"}'    # 10P 商品
curl -s $BASE/api/users/1/coupons -H "Authorization: Bearer $TOKEN"        # 券列表
# 管理端：下架 / 改价（super）
curl -s -X PUT $BASE/api/admin/reward-item/takeout_0_1 \
     -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
     -d '{"priceP":10,"stock":0,"perUserLimit":10,"couponTitle":"外卖立减券","couponAmount":"0.10 元","couponExpire":"30天","enabled":1}'
```

| 步骤 | 预期 |
|---|---|
| `GET /api/points/rewards` | 只返回 `enabled=1` 的商品；售罄 `soldOut=true`、达限 `limitReached=true`；余额与 `/points/me` 一致 |
| 余额够，`POST /api/points/redeem {"itemKey":"takeout_0_1"}` | `code:0`；返回 `coupon{valueCents:10, thresholdCents:1000, status:1}`；余额 -10；库存 -1 |
| 余额不足再兑 | 400「积分不足，还差 N 分」；余额、库存、券、流水都不变 |
| `stock=0` 再兑 | 400「该商品已兑完」 |
| 同一商品超限购 | 400「每人限兑 N 件」 |
| `enabled=0` 再兑 | 400「该商品已下架」 |
| 兑换后 `GET /api/users/1/coupons` | 新券在首位，`valueCents` 与商品 `priceP` 相等，`expireOn` 为 30 天后 |
| 管理端 `PUT` 改库存/限购/启停 | 返回成功；用户侧商品池立即按新值展示（无缓存） |

## 三、隐患

1. **「商家不少收」只有计价口径，没有结算账目。（本轮新发现，未修）** 设计稿 §5.2 要求记三条账：商家 `delivery:{orderId}:income`（不减券）、平台服务费、平台补贴。实际落地只有第三条——`earnings_ledger` 里 `delivery:{orderId}:income` 是 `DispatchService.recordDeliveryIncome()` 写的**骑手配送报酬**（"配送报酬（履约账单，非余额）"），全仓库没有任何商家结算/收入账目（`merchant_*` 表只有入驻申请与退款单）。也就是说「用户少付、商家按原价结算、平台补差价」目前只体现在**计价**上（`subtotal` / `discount_amount` 不被券改写，`coupon_discount` 单列），没有任何一条流水能证明商家最终按原价收到钱。一旦将来做商家结算，若按 `order.total` 对账，商家就会少收券额。建议结算口径明确写死 `subtotal − shop_discount + packing + delivery`（即 `total + coupon_discount`），并补一条商家收入账（约 1 人日）。
2. **换券会换幂等键，可能同时锁住多张券。** 幂等签名含券 id 是正确的（否则复用旧订单会导致券对不上），但代价是：用户在同一结算里先选 A 券下单未支付、再改选 B 券提交，会生成第二笔 `created` 订单。A 券要等第一笔订单超时关单被 `releaseByOrder` 释放，这段时间 A 券处于锁定态（别的订单用不了）。若关单任务没跑或延迟，用户会看到「券没了」。属可接受的设计代价，但运营侧要知道「锁定 ≠ 使用」。
3. **选券弹层没有真正的「置灰」。** `ui-popup` 的 sheet 只渲染 `item.label`，没有 `disabled`/副标题，不可选券只能写成「标题 · 不可选（满 20.00 元可用）」，用户仍可点击，靠 toast 拦住。真正的灰显需要改共享组件（`components/ui-popup`），不在本功能范围。
4. **下单页看不到「已用/已过期」的券。** 券列表接口只返回 `status=1` 且未过期的券，等到下单页时用户根本不知道某张券为什么不在了（个人页同口径）。券中心分组属设计稿之外的增强。
5. **客户端金额是预估，只有下单后才被校准。** 页面用 `min(券额, 商品合计 − 店铺满减)` 与服务端同口径算展示值；若服务端规则变化（新增品类限制、叠加规则、金额上限），页面会短暂显示与服务端不同的数字，只能靠下单返回的 `total/couponDiscount` 纠正，且页面没有「重新计算」入口。
6. **自动选券只看面额，不看有效期。** 「抵扣最多」用 `valueCents` 降序，快过期的券不会被优先推荐；用户可能让即将过期的券闲置到作废。商业级做法是「先按可用、再按面额，最后把 3 天内到期的置顶提示」。
7. **券列表文案与券的实际用途矛盾。** `pages/profile` 的 `openCoupons()` 在用户点券时 toast「已领取『…』，到店出示即可使用」；但本期券只支持平台内外卖订单抵扣，不支持到店出示。用户会拿着手机去店里出示，商家无法核销。需改为「下单时选择本券抵扣」或直接跳外卖下单。
3. **并发售罄测试自身 flaky。（已修复）** `RewardServiceIntegrationTest.concurrentSoldOutOnlyOneWinner` 原先断言「没抢到的人余额必须是 100」，隐含 `ME` 必赢；真实并发下赢家不确定，单独重跑 3 次失败 2 次。已改为「两人余额合计 190、较小者 90、较大者 100」且不假设赢家，修后连跑 3 次 12/12 全绿。功能侧（库存条件更新）本来就是对的。
4. **新人礼包发放可能只发一半。** `grantNewbieGift()` 里发分与发 7 天白银体验是两次独立调用、各自 try/catch。若 `TierService.grantTrial` 失败，用户拿到 30P 却没有白银体验，且没有任何补偿任务或告警；用户也不会知道「礼包少了一半」。
5. **礼包发放还依赖任务目录开关，停了不会报错。** 30P 不是硬编码，来自 `task_catalog.newbie_gift`（`p_reward=30`）；如果有人把该行 `enabled=0`，`PointsService.award()` 返回 `DISABLED` 而不抛异常，登录照常成功、礼包静默不发。上线前必须把这一行列入检查项（见第七节）。
6. **礼包提示是设备级一次性，不是账号级。** `newbieGiftShown` 存在本地 storage：换手机、清缓存、重装小程序后会再弹一次。发奖靠 `biz_key` 幂等不会重复发，所以最坏情况是「弹了但没新奖励」，属于提示重复而非资损；但文案「已到账」会让人以为又发了一次。
7. **`coupon_amount`（展示）与 `value_cents`（结算）是双源。** 管理端可以单独改商品池的券面额文案，而兑换时 `value_cents` 被强制等于 `priceP`。运营把 `coupon_amount` 改成「2.00 元」而价格仍是 10P，用户看到 2 元券、实际只能抵 0.1 元——直接投诉与合规风险。管理端校验没有「面额必须等于价格/100」这条规则。
8. **管理端改不了门槛与有效期天数。** `PointsRewards.vue` 只提交 `priceP/stock/perUserLimit/couponTitle/couponAmount/couponExpire/enabled`，`thresholdCents` 与 `expireDays` 只能改 SQL。设计稿 §2.4 的编辑项包含「有效期」，现在只能改展示文案、改不了真实 `expire_on`。
9. **平台补贴没有预算护栏。** 设计稿 §十 要求按「月活 × 0.3–0.8 元」设月度预算告警、超支先关高档券；当前没有补贴金额统计页、没有预算阈值、没有告警，只有账本明细。券是平台真金白银支出，一旦被刷分兑券，事后才能从 `earnings_ledger` 发现。
10. **券列表只返回「可用」，用户看不到已用/过期券。** 接口按设计只返回可用券，这会让用户觉得「券怎么没了」；商业级产品通常分「可用 / 已使用 / 已过期」三组。本期未做分组。
11. **`openCoupons` 的券 sheet 无可操作项。** 每张券点下去只是再弹一个 toast，没有「去使用」「查看详情」，属于展示型占位，等选券入口补齐后才闭环。

| 差距 | 商业级做法 | 补齐成本 |

## 八、回滚方案

**开关/运营层（最快）**

```sql
-- 立即停止兑换：下架全部商品（用户侧立刻看不到，已兑换的券不受影响）
UPDATE reward_item SET enabled = 0;
```

- `POST /api/points/redeem` 对所有 itemKey 返回「该商品已下架」，不再产生新券与新支出。
- 已发出去的券仍可在订单里抵扣（若选券入口已上线）；如需完全止血，把 `coupon` 里 status=1 的券批量置 0（作废，需用户沟通）。

**新人礼包提示（前端）**

- 回退 `app.js` 的 `globalData.newUser` 写入与 `pages/index/index.js` 的 `maybeShowNewbieGift`，或临时把判断改成 `if (false)`；`newbieGiftShown` 键留在本地不影响功能。
- 若只想停弹窗、保留发放：前端摘掉弹窗即可，后端发奖保持（发奖本身是权益，没有风险）。

**代码**

- 回退 `RewardService`、`RewardController`、`AdminRewardController`、`RewardMapper`、`CouponService`、`BizService`/`PaymentLedgerService`/`MerchantRefundStatusService`/`PayService` 的券改动、`pages/points-redeem`、`pages/points` 入口、`PointsRewards.vue` 与路由。
- 回退券结算时必须同时确认：`createOrder` 不再引用 `coupon` 列、`UserOrder.coupon_discount` 不再被读取，否则旧库字段缺失会 500。

**下单页选券（前端，可独立回退）**

- 回退 `pages/food-order` 的三件套即可：payload 去掉 `couponId`、幂等签名去掉券 id、`order-card` 去掉「优惠券/券抵扣」两行。后端 `POST /api/orders` 对不传 `couponId` 的请求完全兼容（金额链不变），所以只回退前端不会 500，只是用户又用不了券。
- 注意：**幂等签名与 payload 必须同时回退**。只回退其一会出现「签名按券变、payload 不带券」或反之，导致换券复用旧订单、券与订单对不上。
- 已锁定未支付的券：回退前端后这些订单不会再被支付，等超时关单任务 `releaseByOrder` 释放；若要立刻止血，按 `UPDATE coupon SET status=1, order_id=NULL, locked_at=NULL WHERE status=2 AND order_id IN (SELECT id FROM user_order WHERE status='created')` 手工释放（需与关单任务确认不冲突）。

**数据（谨慎）**

- `reward_item` / `redeem_record` 可保留；旧代码不读它们不会报错。
- 券扩列是 `NOT NULL DEFAULT`，旧代码忽略新列，**不需要回滚 DDL**。
- 已发积分与已发券是真实用户资产，**不要回滚删除**；若因刷分需要回收，按 `point_log.module='redeem'` + `source='redeem'` 人工冲正并留痕。
- 平台补贴账已写入 `earnings_ledger` 的 `platform_subsidy` 条目，回滚代码不会删账；退款冲销逻辑若一起回退，已退款订单的补贴条目需要人工置 `void`。

**风险点**

- 只关商品池不回代码：兑换入口还在，用户点进去全是「已兑完/已下架」，体验差但无资损。
- 回滚「券结算」而不回滚「兑换发券」：用户会拿到无法使用的券，必须同步下架商品池。
- 新人礼包发放没有 feature flag，无法单独关闭；只能回退代码或临时注释 `grantNewbieGift()` 调用（回退后已建号用户不受影响）。
