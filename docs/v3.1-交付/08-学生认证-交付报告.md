## 一、完成了什么

### 后端

| 设计稿章节 | 落地情况 |
|---|---|
| §4 数据表 | `db/module-verification-v31.sql`：`user_verification` 扩 `school_id/college/real_name/student_no/phone/submitted_at/source/submit_date/submit_count`，幂等脚本可重复执行（INFORMATION_SCHEMA 预查 + PREPARE/EXECUTE）；`user_id` 早有唯一键，一人一行 |

| §6 `POST /api/verification/apply` | `VerificationService.apply()`：开关 → 学校存在 → 必填/格式校验（含 `phone`）→ 审核中/已认证拦截 → 每日限频 → 写入 pending 并计数。校验顺序保证「填错不消耗次数」 |
| §6 `GET /api/verification/config` | 公开读：`enabled / require{4} / studentNoPattern / reviewMode / dailyLimit`，小程序按 `require` 渲染表单 |
| §6 `GET /api/verification/me` | 补返回 `schoolId/college/realName/studentNo/phone(脱敏)/submittedAt/source/rejectReason/verifiedAt/label/canTakePaidJob/selfApplyOpen` |

| §6 管理端审核 | `POST /api/admin/verifications/{userId}/review`：状态白名单校验、校管跨校 403、驳回原因截断 200 字、写审计日志 |
| §4 手机号链路（收尾补齐） | 配置键 `verification.require.phone` 真正生效：`user_verification.phone` 落原文；必填时空 →「请填写手机号」；填了但非 11 位 →「手机号格式不正确」；选填空放行；`/me`、管理端列表、审核返回统一 `maskPhone()` 脱敏（`138****1234`） |
| §4 权限洞修复 | `AppConfigController` 的 `list/save` 补 `super` 角色校验（`AdminInterceptor` 只保证 super/school，平台配置不能给校管） |
| 三条铁律 | ① `effectiveReviewMode()`：`auto` 必须正则非空且可编译，否则回落 `manual` 并记一次 warn；② `status()` 只读状态列不读配置（改严不追溯）；③ `dailyLimit()` 1–10 截断、缺失/非数字回落 3 |
| §5 状态机 | 复用 `none/pending/verified/rejected`；`verified` 要求实名与学生双通过；auto 命中记 `provider=auto_rule`，与人工 `manual_admin` 可区分 |
| §6 接单联动 | `status()` 返回 `paidJobsOpen` 与 `canTakePaidJob = verified && paidJobsOpen`；`requireVerifiedForPaidJob()` 仍 fail-closed |

## 三、隐患

1. ~~**`verification.require.phone` 是断的配置项。**~~ **已修（2026-11-11，保留记录）。** 原实现里配置键、`/config`、小程序表单都有，但 `apply` 不读 `phone`、表里也没有列，用户填的手机号被静默丢弃。修法：`module-verification-v31.sql` 幂等加 `phone VARCHAR(20)`；`UserVerification` 加字段、`adminList` SQL 带出；`apply()` 增加第 6 个参数并按「必填空 → 请填写手机号；填了非 11 位 → 手机号格式不正确；选填空 → 放行」校验后落库；`status()`、`listForAdmin()` 统一走 `maskPhone()` 脱敏；Controller 解析 body 的 `phone`；小程序提交带 `phone` 且不回填脱敏值；Web 审核弹窗展示脱敏号。回归：`phone*` 7 例单测 + `SqlMigrationIdempotencyTest` + 契约脚本请求体断言。
2. **注销账号不清理认证材料。** `UserService.deleteAccount()` 只清用户表的昵称/头像/openid/学校，`user_verification` 里的真实姓名、学号、学院、手机号原样保留，与设计稿第十节「用户可申请删除（注销时随账号删除）」不符。涉及个人信息合规，上线前必须补删除/匿名化（约 0.5 人日）。
3. **个人页文案与接单开关矛盾。** `pages/profile/profile.wxml` 的校园卡在 `verified=true` 时显示「已完成学生与实名认证，可接取有偿校内任务」，但 `job.paid.enabled=0` 时 `canTakePaidJob=false`。这正是设计稿反复强调会引起投诉的表述（`pages/profile` 不在本任务写作用域，未改）。
4. **`/api/verification/me` 未登录返回 403 而非 401。（本轮已修）** 设计稿第七节与页面边界都写「未登录 401 → 跳登录」，原实现只有写接口是 401，`/me` 走 Controller 的 `ForbiddenException` → 403，前端按「拿不到就显示未认证」兜住会掩盖登录失效。已按建议在 `AuthInterceptor` 的私有读前缀里精确加入 `/api/verification/me`（`/config` 仍公开，避免把认证页的表单结构也挡在登录后面），Controller 的兜底校验保留作纵深防御。回归用例：`V31AuthGateTest#v31PrivateReadsRequireToken` + `#v31PublicReadsStayOpen`。
5. **限频计数不是原子更新。** `submit_count` 是「读旧值 → 写新值」，同一用户两个并发提交都读到 `2` 时可能都写 `3`，实际放过第 4 次；同一用户并发首次提交还会撞 `uk_verification_user`，第二个请求以 500 返回（未在 `GlobalExceptionHandler` 单独映射）。影响面小（需刻意并发），但「每天最多 3 次」不是强约束。
6. **auto 模式有「学号格式对就能过」的天然缺口。** 正则只防乱填，防不了冒用；`provider=auto_rule` 虽然留痕，但后台没有按来源筛选、也没有随机抽查工具（设计稿要求「随机抽 10% 私聊核实」）。第二所学校接入时学号规则必然冲突，必须切回 manual（提醒写在 remark 里，但代码没有「多校即禁用 auto」的保护）。
7. **认证材料仅手机号脱敏，姓名/学号仍是明文。** 手机号已统一 `maskPhone`（`138****1234`），但 Web 审核页与接口返回的学号/姓名仍是明文；管理员操作会写审计（`adminAuth.log`），Web 端却没有审计查询入口；也没有「谁能看材料」的二次授权，任何 school 角色都能看本校全部申请材料。
8. **页面与凭证依赖真实微信链路。** 本地开发登录不建号，`newUser` 永远为 false，新账号授权、驳回后重提、开关关闭三态在本地不易复现，只能靠真机。

## 四、与商业级产品的差距

| 差距 | 商业级做法 | 补齐成本 |
|---|---|---|
| 材料真实性 | 接学信网/高校统一身份认证，OAuth 回跳拿学籍；或至少「学号 + 姓名」双向比对校方名单 | 外部资质 + 2–3 人日对接；无接口时只能人工抽查 |
| 抽查工具 | 按学院/学号段聚合、随机抽样队列、批量审核、审核 SLA 与超时提醒 | 约 2 人日 |
| 审核可观测 | 待审积压量、平均审核时长、驳回率按学院分布、异常学号段告警 | 约 1.5 人日 |
| 风控与申诉 | 同一学号被多次提交/跨账号复用检测、用户申诉与复核工作流、封禁联动 | 约 2 人日 |
| 数据合规 | 学号/姓名加密存储或字段脱敏、访问审计、注销即删除、导出留痕 | 约 1.5 人日 |
| 多校规则 | `school.verify_config` 每校一套（正则/必填/审核方式），`auto` 按校开关 | 约 2 人日 |
| 状态透传 | 帖子/评论/二手列表作者带「已认证」标（注意 N+1） | 约 1 人日 |

**一句话**：提交、限频、人工审核、配置化与三条铁律都已成立；差的是「材料真实性来源」「审核运营工具」「个人信息合规」三块，这三块决定它能不能在真实校园规模下跑。

## 八、回滚方案

**开关（最快，1 分钟内生效）**

```sql
UPDATE feature_flag SET enabled=0 WHERE flag_key='verification.student.enabled';
```

- 效果：`/apply` 一律 403「认证申请暂未开放」；`/me`、`/config` 仍可读，已认证用户状态不受影响。
- 这是首选止血手段：不重启、不丢数据、不影响已认证记录。

**代码**

- 回退 `VerificationService`、`VerificationController`、`AdminVerificationController`、`AppConfigController`、`AppConfigService`、`UserVerificationMapper`、`UserVerification`、`pages/verify`、`pages/profile` 的认证改动、`app.json` 注册、`web/src/views/Verification.vue`。
- 回退后 `/api/verification/*` 回到「只有 `/me`」的旧形态，页面入口会 404/无响应，因此代码回滚必须与开关关闭同时做。

**数据（谨慎，按需）**

- 只停功能不删数据即可；`user_verification` 的扩列是 `NULL/默认空`，旧代码忽略新列，**不需要回滚 DDL**。
- 若要彻底回退：`DELETE FROM app_config WHERE config_key LIKE 'verification.%';`（会丢运营改过的规则，做之前先导出）。
- 已审核通过的记录是真实业务结论，**不建议删除**；如需重置某用户，用管理端审核接口改回 `none` 并留痕。

**风险点**

- 只关开关不回代码：旧入口仍会返回 403，用户看到「暂未开放」属预期。
- 只回代码不关开关：若回退不彻底（例如 `AppConfigController` 的 super 校验被一起回退），校管可再次改平台配置——回滚时必须确认这个校验仍在，或同时关闭认证入口。
- 已提交待审的材料不会因为回滚消失，恢复后可直接继续审核。
