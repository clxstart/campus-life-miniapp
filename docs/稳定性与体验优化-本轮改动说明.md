## 二、可观测性：怎么用

### 2.1 日志

新增 `backend/src/main/resources/logback-spring.xml`：

| 文件 | 内容 | 保留 |
|---|---|---|
| `logs/app.log` | 全部日志，按天 + 100MB 轮转 | 30 天，超出 gz 压缩 |
| `logs/error.log` | 只收 WARN 及以上 | 30 天 |

每行格式带 traceId：

```
2026-10-27 19:11:23.451 [a1b2c3d4e5f6] INFO  [http-nio-8080-exec-3] c.c.c.RequestTraceFilter - GET /api/posts?page=1 -> 200 12ms
```

### 2.2 traceId 怎么串起来

- `RequestTraceFilter` 给每个请求生成 12 位 id，放进 MDC，同时通过响应头 `X-Request-Id` 返回
- 用户报障时报这个 id，服务端 `Select-String -Path logs/app.log -Pattern <id>` 就能拿到这一次请求的全部日志
- 上游（Nginx）如果已经给了 `X-Request-Id`，会沿用，便于跨层串联

**验证过的效果**：

```
X-Request-Id = ad88d09f3e55
日志命中: 2026-10-27 16:06:35.931 [ad88d09f3e55] INFO ... GET /api/schools -> 200 3ms
```

### 2.3 健康检查

- `/actuator/health` 只返回 `{"status":"UP|DOWN"}`，**不暴露内部细节**
- 完整明细走 `/api/admin/system/overview`（管理员鉴权）
- 自定义检查项：数据库真跑 `SELECT 1`、上传目录可写、磁盘剩余 > 5%、连接池是否有人排队

### 2.4 管理端「系统状态」页（左侧菜单 → 系统状态）

展示：
- 服务健康状态 + 问题清单（有问题直接列出来）
- JVM 堆使用率、线程数、运行时长
- 数据库连接池 活跃/上限（带进度条，超 80% 变红）
- 磁盘 总容量/剩余（超 95% 变红）
- 业务计数（用户/帖子/二手/兼职/活动/评论/订单/待处理举报）
- 最近慢请求列表

**这一页在系统出问题时最能派上用场**，所以每项都做了独立容错：取不到就显示 unknown，不会整页 500。

> 实测时它立刻抓到一个真实问题：**本机磁盘已用 97%，只剩 1.2GB**，状态直接报 DOWN。这是预期的正确行为。

## 三、可控制：功能开关

### 3.1 有哪些开关

| 开关 | 关闭后行为 |
|---|---|
| `ai_chat.enabled` | AI 页提示「维护中」 |
| `upload.enabled` | 上传提示「暂不支持上传」 |
| `pay.enabled` | 支付提示「通道维护中」（订单仍可下单） |
| `enroll.material.enabled` | 材料报名**降级为一键报名**（不阻断报名） |
| `circle_chat.enabled` | 群聊提示「维护中」 |
| `post.publish.enabled` | 发帖/评论提示「维护中」（读帖点赞不受影响） |

### 3.2 怎么用

管理端 → **系统状态** → 底部「功能开关」→ 点「关闭/开启」→ 二次确认。

- 改动写入 `feature_flag` 表，记录最后修改人
- 服务端缓存 30 秒，**约 30 秒内全站生效**
- 读不到开关数据时**默认全部开启**（宁可功能可用，也不要因一次查询失败把全站功能关掉）

## 四、可控制：全局限流

| 场景 | 规则 | 超限返回 |
|---|---|---|
| 登录 / 开发登录 | 同 IP 10 次/分钟 | 429 +「登录过于频繁，请 N 秒后再试」 |
| 发帖 / 评论 / 群聊 | 同用户 10 次/分钟 | 429 + 中文提示 |
| AI 对话 | 同用户 60 次/小时 | 429 |
| 上传 | 同来源 20 次/分钟 | 429 |

实现：单机内存固定窗口计数（`RateLimiter`）。上多实例时换 Redis 即可，调用方不用改。

## 五、可降级

| 依赖 | 失败时 | 用户感受 |
|---|---|---|
| 微信文本/图片审核 | 放行 + 记 WARN | 无感（但日志会留痕） |
| 微信订阅消息 | 静默跳过 | 无感 |

| 后端整体不可达 | 跳「服务维护页」 | 看到说明，而不是无限转圈 |

报名、支付、发布、注销这类操作，宁可报错也不能假装成功。

## 六、合规三件

### 6.1 隐私政策 / 用户协议

- 路径：`pages/agreement/agreement?type=privacy|terms`
- 入口：个人中心 →「设置」→ 隐私政策 / 用户协议
- 正文放在小程序内，**离线可读**（后端挂了用户也能看自己同意了什么）
- 两篇互相可达

### 6.2 账号注销

- 路径：个人中心 → 设置 → 注销账号 → 二次确认
- 后端 `DELETE /api/users/{id}/account`
- 做法：**软删除 + 匿名化**
  - 昵称→「已注销用户」、头像/学校/openid 清空、`status=0`
  - 订单、支付、审计记录保留（法规要求，且对账需要）
  - openid 清空后，同一微信再登录会被当成新用户建号
- **旧 token 立即失效**：`AuthInterceptor` 会查用户状态（本地缓存 60 秒，注销时主动失效）
- 前置校验：有未完成订单时拒绝注销

### 6.4 用户拉黑（双向不可见）

举报是"事后"，拉黑是"事前"——被骚扰的用户需要能立刻自保，而不是等处理。

| 项 | 说明 |
|---|---|
| 入口 | 帖子详情右上角「更多」→ 屏蔽作者；设置 → 黑名单（可解除） |
| 语义 | **双向不可见**：A 拉黑 B 后，双方都看不到对方的帖子/评论，且无法互发私信 |
| 为什么双向 | 单向屏蔽会让被拉黑方继续单向骚扰（能看、能发消息），起不到保护作用 |
| 生效范围 | 帖子流过滤作者；私聊发送拦截（409 +「对方与你之间存在拉黑关系」） |
| 性能 | 拉黑列表本地缓存 30 秒；拉黑/解除时双向失效，做到操作立即生效 |

**实测**：拉黑后用户 1 和用户 2 的流里互相都看不到对方；双向私聊均被拒；解除后恢复（11/11 通过，加上私聊专项 2 项）。

> 顺带修掉一个真实 bug：`profile.js` 里 `openSettings` 被定义了两次，后者覆盖前者，
> 导致先写的协议/注销入口成了**死代码**——用户点设置只能看到空壳菜单。
> 这和之前 `activities.js` 的 `onShow` 是同一类问题（同名键静默覆盖）。现已合并为一份。
### 6.3 内容举报

- 小程序：帖子详情右上角「举报」→ 选原因（广告/辱骂/色情/诈骗/侵权/其他）
- 后端：`POST /api/reports`（需登录）、`GET /api/admin/reports`、`POST /api/admin/reports/{id}/handle`
- 管理端：左侧菜单 →「内容举报」，待处理队列、可标记已处理/判定不成立
- **不自动下架**：举报进队列由人判断，避免被恶意举报利用
- 防刷：同一个人对同一条内容只能举报一次（数据库唯一键兜底）

## 七、流畅度改动

### 7.1 索引

`module-perf-index-2.sql`：

| 表 | 索引 | 解决 |
|---|---|---|
| `comment` | `(post_id, id)` | 评论列表从「全索引扫描」变「ref 定位」（EXPLAIN 已确认） |
| `favorite` | `(user_id, id)` | 我的收藏按用户查 |
| `user_order` | `(pay_status, paid_at)` | 支付统计按时间范围聚合 |

**改前 vs 改后（EXPLAIN）**：

```
改前: type=index  key=PRIMARY        rows=22   ← 扫全表
改后: type=ref    key=idx_comment_post rows=2  ← 直接定位
```

### 7.2 支付统计去掉 N+1

`AdminPaymentService.stats()` 原来：把所有订单读进内存循环 + 未核验/退款各一轮「逐条 selectById」。现在改成 3 条聚合 SQL，耗时与数据量基本无关。

压测对比：管理端订单接口 p95 **47.8ms → 20.8ms**。

### 7.3 列表硬上限

活动、兼职、店铺列表原来没有 `LIMIT`，数据涨起来会把整表塞进响应体。现在统一 `LIMIT 200` 兜底。

### 7.4 图片懒加载

社区、二手、外卖、活动、发现、学习、搜索 7 个列表页共 **19 张图**加了 `lazy-load`。详情页首图不加（要立刻看到）。

### 7.5 列表真分页 + 触底加载（第 2 批完成）

之前列表一次加载全部（靠 LIMIT 200 兜底），用户滑到底就没了。现在：

**后端**：`/api/goods`、`/api/jobs`、`/api/activities` 支持 `page`/`size`

- **传 page** → 返回 `{list,total,page,size}`
- **不传 page** → 返回原来的扁平数组（**老调用方完全不受影响**，分页是加法不是替换）
- `size` 服务端上限 50

**小程序**：新增 `getGoodsPage` / `getJobsPage` / `getActivitiesPage`，二手 / 兼职 / 活动三个页面加了 `onReachBottom` 触底加载：

| 行为 | 说明 |
|---|---|
| 翻页追加 | 按 id 去重，翻页期间有人发布也不会出现重复卡片 |
| 到底提示 | 底部显示「没有更多了」 |
| 切换筛选 | 自动回到第 1 页并清空列表 |
| 加载中 | 底部显示「加载中…」，不会重复触发 |

**实测**：第 1 页 ids `54,53,52`，第 2 页 `51,50,49`，两页无重叠。

### 7.6 前端错误上报（第 3 批完成）

**解决什么**：用户真机上白屏、点击无反应，服务端日志里**一条记录都没有**，只能等投诉且往往复现不了。

| 端 | 钩子 | 位置 |
|---|---|---|
| 小程序 | `App.onError` + `App.onUnhandledRejection` | `app.js` |
| 管理端 | `window.onerror` + `unhandledrejection` + Vue `errorHandler` | `web/src/utils/error-report.js`、`main.js` |

设计要点：

- **匿名可上报**：小程序未登录时也可能崩溃，要求 token 会让最该看到的问题收不上来 → 用**限流**（同 IP 30 条/分钟）代替鉴权
- **同错 10 秒去重**：连环报错不会把后端刷满
- **字段严格截断**：page≤128、message≤500、stack≤2000，避免被当网盘用
- **上报失败静默**：上报本身绝不抛错，否则会连环报错
- 只记错误与页面路径，**不采集用户输入内容**
- 管理端在「系统状态 → 前端错误」查看，可按端筛选、可「查看更多」
- 提供 `POST /api/admin/client-errors/purge?days=30` 清理旧记录

**验证**：匿名上报成功、超长字段被截断、按端筛选正确、今日计数可见、超 30 条被 429（11/11 通过）。
