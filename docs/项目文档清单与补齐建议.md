## 三、答辩前最低限度要补的 5 份

按「补了收益最大、不补最容易被问倒」排序。

| 优先级 | 文档 | 为什么是它 | 建议投入 |
| --- | --- | --- | --- |
| 1 | **测试报告（含结果与缺陷统计）** | 现有 `全模块测试手册` 只能证明「知道该测什么」，不能证明「测过且结果如何」。评委看项目第一眼就是「有没有验证」。而且它成本最低——手册已写好，照着跑一遍填数字即可 | 2–3 天 |
| 2 | **数据库设计说明书（ER + 数据字典）** | 52 张表是本项目最容易被追问、也最答不上来的地方。评委随手指一张表问「这字段干什么的」就会暴露。有了它，整个项目的「工程感」立刻不同 | 4–6 天（可分工） |
| 3 | **系统架构设计说明书** | 三端 + 多校隔离 + 218 接口，没有一张架构图很难讲清。现有 `项目总览` 是介绍性材料，缺设计决策与理由（为什么这么隔离、为什么这样分层） | 3–4 天 |
| 4 | **部署手册（服务器版）** | 决定「能不能真的跑起来给人看」。现有文档只解决本机调试；若答辩要现场演示线上环境，这份是硬前提 | 3–5 天 |
| 5 | **需求规格说明书（SRS，精简版）** | 回答「需求从哪来」。可精简到 10 页左右：角色、核心用例、功能清单、非功能需求。配合已有的 `扩展功能规划`，能讲出「已做—待做」的完整故事 | 3–4 天 |

### 为什么不选其他几份

| 文档 | 暂缓理由 |
| --- | --- |
| 用户手册 / 管理员手册 | 重要但**不救命**：评委更关心「你做成了什么、怎么验证的」，操作说明可现场演示替代；且截图已齐，随时能补 |
| 性能测试报告 | 加分项，但需先有稳定部署环境；优先级低于部署手册 |
| 正式测试用例集 | 与测试报告重叠度高，先把报告做出来，用例可作为附录 |
| 开题/中期材料 | 通常已在流程中单独提交，不属于「项目文档」范畴 |

## 四、补齐建议的推进方式

| 阶段 | 做什么 | 说明 |
| --- | --- | --- |
| 第 1 步 | 统一口径（1.4 节的三个数字） | 半天，先做。否则后面每份文档都会重复这个错 |
| 第 2 步 | 测试报告 → 需求规格 | 前者靠跑，后者靠回忆+git 记录，可并行 |
| 第 3 步 | 数据库设计 → 架构设计 | 数据库是架构的子集，先表后图更顺 |
| 第 4 步 | 部署手册 | 需要一台服务器或云主机，**外部依赖，提前准备** |
| 第 5 步 | 用户/管理员手册、性能与安全报告 | 有余力再补，属加分 |

## 五、写作口径建议

| 建议 | 原因 |
| --- | --- |
| 每份文档开头写「来源 / 时间 / 状态」 | 现有几份文档已有此习惯（如「来源：从 controller 逐文件提取」），保持一致即可，且能自证不是编的 |
| 数字标注口径 | 「19 个后台页面」要说明是路由数还是 `.vue` 文件数；「211 接口」说明是方法级映射数 |
| 已知缺口如实写 | 本项目确实有未完成项（订阅消息 0 处、举报拉黑无、认证闭环未做）。写进文档并给出规划，比被问出来强得多，`扩展功能规划.md` 可直接引用 |
| 不写「未确认」之外的模糊表述 | 不确定的地方标注「未确认」，比含糊其辞更专业 |

## 七、一句话总结

这个项目的文档现状是**「实现讲得很清楚，来路和去处讲得不够」**：接口、测试手册、单功能设计说明都扎实且有来源标注，但缺需求依据、缺数据库与架构的设计论证、缺测试结果数据。答辩前按第三节的 5 份补，投入约 2 周，性价比最高。
