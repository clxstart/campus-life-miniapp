# 扩展功能规划

> 本文所有结论均来自对当前仓库代码的实读，不引用未经验证的设想。
> 盘点时间：2026-10-27。统计口径与读码发现的口径偏差见「一、现状速览」。

### 1.3 本次读码发现的口径偏差（需先对齐）

以下 4 点与「已知缺口」的表述有出入，规划时按代码实际情况处理：

| 原表述 | 代码实际 | 影响 |
| --- | --- | --- |
| 没有接入 `msgSecCheck` / `imgSecCheck` | **已接入**（`AuditService:189` / `:323`），但 `appid`/`secret` 为空、或 openid 缺失/以 `dev-` 开头时**静默跳过**，只走本地词库 | 开发环境表现为「只有敏感词库」，生产配好参数才生效 |
| 审核只覆盖部分场景 | 文本已覆盖：帖子、评论、二手、兼职、私聊、后台建圈子；**未覆盖**：圈子群聊（WebSocket）、昵称/头像修改、AI 聊天输入、活动报名 | 真正的缺口是**覆盖面**，不是「没接」 |
| 图片审核全覆盖 | 仅 `post.image` 与 `goods` 图片；**头像、活动报名材料、群聊图片无图片审核** | 歌手大赛等材料上传是审核盲区 |
| 管理端无移动端适配 | `AdminLayout`/`MerchantLayout` 已有 `md:` 断点、侧栏折叠与移动横向导航；26 个视图中仅 6 个做了 `overflow-x-auto` | 外壳部分适配，**表格与表单页**未适配 |

## 二、P0：不做会卡住上线/审核

| 编号 | 功能名 | 为什么值得做（解决什么具体问题） | 工作量 | 涉及端 | 技术要点 / 风险 |
| --- | --- | --- | --- | --- | --- |
| P0-1 | 微信订阅消息 | 小程序 `requestSubscribeMessage` 出现次数为 **0**。订单状态变化、帖子被回复、活动审核结果目前只写 `notification` 表，用户不打开小程序就永远不知道 | 4–6 人日 | 小程序 + 后端 | 需先建模板 ID 并申请类目；一次性订阅每条消息都要用户点击授权，**不能批量静默下发**；必须在关键动作前（下单、报名、发帖）挂授权，不能进页面就弹 |

| P0-3 | 举报与拉黑 | 全仓库 `举报`/`拉黑` 命中 **0 处**。用户遇到骚扰、诈骗、违规内容只能忍着；平台没有被动发现通道，微信审核也会关注这一点 | 6–8 人日 | 小程序 + 管理端 + 后端 | 新建 `report`（对象类型/ID/原因/状态）与 `user_block`；拉黑要作用于私聊、评论、群聊三处过滤，**群聊是 WebSocket 推送，需在推送前过滤**；举报处理要进现有审核工作台，避免再造一套后台 |

## 五、建议的实施顺序

排序原则：先解决「不通过审核就无法上线」，再解决「上线后用户不知道发生了什么」，最后做增长。**订阅消息（P0-1）必须晚于事件源梳理（P1-7 的前半），否则会重复改两遍。**

| 阶段 | 内容 | 前置依赖 | 为什么排在这里 |
| --- | --- | --- | --- |
| 第 1 批 | P0-6 隐私协议 → P0-5 真实支付切换 | 无（支付需商户号资质，需提前申请） | 都是**外部依赖 + 审核硬门槛**，资质申请周期最长，必须最先启动 |
| 第 2 批 | P0-4 审核覆盖补齐 → P0-7 待审队列 | P0-4 依赖 `AuditService` 现有能力（已具备） | 审核是 UGC 平台的上线前提；先补覆盖面，再补运营处理台，顺序不能反 |
| 第 3 批 | P0-2 认证闭环 → P0-3 举报 + P1-8 处理台 | P0-2 复用私有上传与审核队列 | 认证与举报都要走同一条审核链路，P0-2 先做可把审核队列打磨好，P0-3 直接复用 |
| 第 4 批 | P1-7 消息中心 → P0-1 订阅消息 | P1-7 先统一事件源，P0-1 再挂通道 | **顺序关键**：先有稳定的事件表，订阅消息只做「读事件→发模板」，避免事件源反复改 |
| 第 5 批 | P1-1 搜索历史 → P1-2 埋点 → P1-3 批量 → P1-4 导出 | P1-2 独立；P1-3/P1-4 依赖管理端分页与权限现状 | 运营刚需，彼此独立可并行；埋点越早做数据越早积累 |
| 第 6 批 | P1-5 移动适配、P1-6 音频材料 | 无 | 可随时插入，适合作为迭代间隙的填充任务 |
| 第 7 批 | P2 全部 | P2-5 依赖 P1-2；P2-1 依赖 P0-4 | 增长与体验增强，上线稳定后再做 |

## 六、P0 条目的落地拆解

只拆最卡上线的 3 条，其余按同样方式展开即可。每条按「表 → 后端 → 前端 → 联调」四步走。

### P0-2 校园身份认证闭环

| 步骤 | 具体动作 | 产出 |

| 1. 建表 | `user_verification(id, user_id, school_id, real_name, student_no, college, material_url, status, reject_reason, submitted_at, audited_at, auditor_id)`，`status` 取 0 待审 / 1 通过 / 2 驳回 | SQL 文件放 `db/module-*.sql`，与现有风格一致 |

### P0-3 举报与拉黑

| 步骤 | 具体动作 | 产出 |
| --- | --- | --- |
| 1. 建表 | `report(id, target_type, target_id, reporter_id, reason_code, reason_text, status, handled_by, handled_at)`；`user_block(id, user_id, blocked_user_id, created_at)` | 唯一键防重复举报 |
| 2. 后端-举报 | 提交举报（限频，防刷）、管理端列表与处理（下架/驳回） | 处理动作要联动内容状态并写 `audit_log` |

### P0-1 订阅消息

| 步骤 | 具体动作 | 产出 |
| --- | --- | --- |
| 1. 前置 | 小程序后台申请订阅消息模板（订单状态、互动提醒、审核结果），拿到模板 ID | **外部依赖，需提前 1–2 周启动** |
| 2. 事件源 | 先统一 `notification` 写入的事件集合（谁触发、给谁、什么类型） | 与 P1-7 共用，避免两套事件 |
| 3. 后端 | 事件落库后异步调 `subscribeMessage.send`，记录发送结果（成功/用户未授权/额度用尽） | 发送失败不能影响主事务，必须异步 |
| 4. 前端 | 在下单、报名、发帖等**动作发生时**调 `requestSubscribeMessage` 请求授权 | 不能进页面就弹，会被判骚扰且用户易拒 |
| 5. 兜底 | 用户拒绝授权时，站内通知仍是主通道，消息页要能补看 | 产品流程必须接受部分用户收不到 |

## 七、明确不做（避免范围蔓延）

| 不做的事 | 原因 |
| --- | --- |
| 自建内容安全模型 | 微信 `msg_sec_check`/`img_sec_check` 已接入，先补覆盖面即可，自建模型成本远超收益 |
| 二手资金托管 | 涉及支付牌照与资金合规，学生项目不具备条件；先做信用与评价展示 |
| 教务系统爬取 | 各校无公开接口且不稳定，维持 CSV 导入（`CampusController:110` 注释已说明原因） |
| 骑手端页面立刻重建 | 后端接口尚在，但属 P2；先把 P0 合规项做完 |
| 全量埋点 | 先定义 6–8 个关键事件，全量埋点会拖慢主链路且数据难用 |

## 八、统一风险提示

| 风险 | 说明 |
| --- | --- |
| 多校越权 | 新增的批量接口、导出接口、举报处理都必须带 `school_id` 校验；现有 `AdminOrderService` 已有 `schoolId + role` 模式，照抄即可 |
| 审核静默失效 | `AuditService` 在缺 `appid`/`secret` 或 openid 为 `dev-` 时**静默放行**。上线前必须验证配置生效，否则以为在审其实没审 |
| 订阅消息不可静默 | 一次性订阅需用户每次点击授权，产品流程必须接受「部分用户收不到」，不能设计成唯一触达手段 |
| 工作量估算前提 | 以上人日为「熟悉本仓库的 1 名开发者」口径，不含联调等待与资质审批时间；跨端任务（如 P0-2、P0-3）需前后端同时投入 |
| 未确认项 | 微信支付商户号资质状态、小程序类目与订阅消息模板是否已申请，代码中无法体现，需向项目负责人确认 |
