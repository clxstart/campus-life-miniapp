> 来源：`backend/src/main/java/com/campuslife/service/PetService.java`、`PetCompanionService.java`、`backend/src/main/resources/db/module-pet.sql`（现状）；本文档为其扩展设计。

## 一、这个功能解决什么问题

**现状（读码核实）**

| 事实 | 位置 |
|---|---|
| 积分只有两张表：`user_points(user_id, balance, total_earned, updated_at)`、`point_log(id, user_id, amount, type, ref_id, remark, created_at)` | `db/module-pet.sql` |
| 写入分散在 **2 个 Mapper、4 处调用**：宠物签到 `+5P`、喂食扣分、衣柜兑换扣分、派遣奖励 | `PetMapper.java:29/36`、`PetCompanionMapper.java:63/118`、`PetService:82-88`、`PetCompanionService:155/299` |
| 没有任何日上限、没有幂等键、没有成长值、没有任务目录 | 全仓库无匹配 |

**不做会怎样**

- 用户在论坛发帖、浏览、签到拿不到任何回报，V3 大表里 30 多个任务一个都挂不上。
- 想加第二个发分场景时，只能再写一套「查余额 → 加 → 写日志」，迟早对不上账。
- 没有日上限，一次 bug 或一次刷分就能把积分池打穿。

**做完得到什么**：一个**唯一发放口** `PointsService.award()`，所有任务、榜单、交易埋点、新人礼包都从这里出分；一次调用完成「幂等 + 日上限 + 余额 + 成长值 + 流水」五件事。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范（主题变量、`cp-*` 类、`ui-popup`、`hover-class` 三档、状态四件套）见 `docs/v3.1/前端设计-双端总览.md`。本节只写本功能独有部分。

### 2.1 小程序端 · `pages/points/points`（新页）

**入口两处**

1. `pages/profile/profile` 菜单第 4 行插入「我的积分」，右侧 `value` 显示 `{{balance}} 分`，点击 `navigateTo`。
2. 不做常驻首屏入口（避免首屏过挤）；只在积分到账 toast 后，用一次性的「查看我的积分」引导。

**页面结构（自上而下）**

| 区域 | 内容 | 数据来源 | 交互 |
|---|---|---|---|
| 余额卡 `.cp-card` | 大号余额 `63`、`≈¥0.63`、标题「我的积分」 | `GET /api/points/me` | 无 |
| 签到区（见第 2 份文档） | 签到按钮 + 连签进度 | 同上 | 点击签到 |
| 段位区（见第 4 份文档） | 段位铭牌 + 成长值进度条 | 同上 | 点击看八段位说明 |
| 今日任务 `.cp-card` 列表 | 每行：任务名、进度（`18/20 分钟`）、奖励 `+2` | `GET /api/points/tasks` | 已完成的打勾置灰 |
| 明细分页 | 时间、说明、`+5` / `-10`、余额后值 | `GET /api/points/logs` | 上拉加载更多 |
| 底部合规文案 `.cp-hint` | 「100 积分 = 1 元，仅作价值参考，不可提现」 | 常量 | 无 |

**操作步骤**

1. 从「我的」进入 → 并行请求 `/me` 与 `/tasks`（任一失败不阻塞另一个）。
2. 下拉刷新 → 重拉 `/me`、`/tasks`，并把 `/logs` 重置回第 1 页。
3. 上拉到底 → `page+1` 拉明细；没有更多时底部显示「没有更多了」。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 未登录 | 401 → 跳登录，不显示空页 |
| 首屏加载 | 余额卡骨架 + 任务列表 3 行骨架（`skeleton-list`） |
| 断网 | `offline-banner` + 显示上次缓存的余额，角标「离线数据」 |
| 任务为空 | `empty-state`：「今天没有可做的任务」 |
| 明细为空 | `empty-state`：「还没有积分记录，先去签到吧」 |
| 接口失败 | 对应卡片内错误块 + 「重试」，不影响其他卡片 |

### 2.2 Web 端 · `web/src/views/PointsTasks.vue`（新页）

**页面结构**

- 标题区：`积分任务配置` + 说明「改动 30 秒内生效，不需要发版」。
- 筛选区：模块下拉（全部/基础/论坛/交易/宿舍/宠物）、启用状态下拉、刷新按钮。
- 表格列：任务键、名称、模块、P、G、日上限、启用开关、操作。
- 编辑弹窗 `NoModal`：P、G、日上限、启用。

**操作步骤**

1. 进入 → `GET /api/admin/task-catalog` 拉列表（前端分页，数据量小）。
2. 点「编辑」→ 弹窗带出当前值 → 修改 → 「保存」→ `PUT /api/admin/task-catalog/{taskKey}`。
3. 保存成功：弹窗关闭，行内数值更新，顶部绿条「已保存，30 秒内生效」。
4. 点开关直接提交，先二次确认：「关闭后用户不再获得该任务积分，已发的不回收」。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 加载 | 表格「正在加载…」 |
| 空 | 「没有符合条件的任务」 |
| 保存失败 | 顶部红条 + 开关回滚到原值（不允许界面与库不一致） |
| 无权限 | 非管理员直链进入 → 401/403 跳登录 |

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 账本表 | 复用 `user_points` + 扩展 `point_log` | 新建 `points_account` / `points_ledger`（大表 V3 技术字段里写的是这套） | 宠物模块已经在写这两张表，新建等于双钱包，历史余额还要迁移；扩展列的成本远低于迁移 |
| 流水表数量 | `task_log`（任务事实）+ `point_log`（余额变动）两张 | 只留一张流水 | 日上限靠「今天这个任务发了几次」计数，这是任务事实；余额变动要能审计。两者语义不同，混表会让"发 0 分的任务"无处记录 |
| 发放时机 | 同步、同事务 | 异步队列 | 任务发分量小（每人每天 <20 次），同步能保证「发帖成功 ⇄ 加分」强一致；异步会引入"帖子在、分没到"的客服问题 |
| 幂等键 | `task_log` 唯一键 `(user_id, task_key, biz_key)` | 只靠业务代码判断"发过没有" | 并发下业务判断必然穿透；唯一键是数据库级兜底 |
| 日上限口径 | `daily_cap` = 当日最多发放**次数** | 当日最多发放**积分数** | 次数口径能同时表达"签到 1 次""外卖 2 单"，不需要再加一列 |

## 四、数据表与字段

### 4.1 现有表（不改结构，只改语义）

| 表 | 字段 | 说明 |
|---|---|---|
| `user_points` | `user_id` PK / `balance` / `total_earned` / `updated_at` | 全站唯一余额；`total_earned` 只累加正数 |
| `point_log` | `id` / `user_id` / `amount` / `type` / `ref_id` / `remark` / `created_at` | 余额流水 |

### 4.2 `point_log` 扩列

```sql
ALTER TABLE point_log ADD COLUMN module       VARCHAR(16)  NOT NULL DEFAULT 'pet';
ALTER TABLE point_log ADD COLUMN biz_key      VARCHAR(64)  NULL;
ALTER TABLE point_log ADD COLUMN g_amount     INT          NOT NULL DEFAULT 0;
ALTER TABLE point_log ADD COLUMN balance_after INT         NULL;
ALTER TABLE point_log ADD UNIQUE KEY uk_user_biz (user_id, biz_key);
```

- `biz_key` 由服务端拼成 `taskKey:bizKey`，例如 `post_create:draft-88`，保证同一个任务同一笔业务只发一次。
- 唯一键含 `user_id`，可空列（MySQL 允许多个 NULL），宠物历史行不受影响。

### 4.3 新表

```sql
CREATE TABLE user_growth (
  user_id    BIGINT PRIMARY KEY,
  g_total    INT      NOT NULL DEFAULT 0,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) COMMENT='成长值，只涨不降';

CREATE TABLE task_catalog (
  task_key   VARCHAR(32) PRIMARY KEY,
  module     VARCHAR(16) NOT NULL,
  name       VARCHAR(32) NOT NULL,
  p_reward   INT         NOT NULL DEFAULT 0,
  g_reward   INT         NOT NULL DEFAULT 0,
  daily_cap  INT         NOT NULL DEFAULT 1 COMMENT '当日最多发放次数，0=不限',
  enabled    TINYINT     NOT NULL DEFAULT 1,
  sort       INT         NOT NULL DEFAULT 0
) COMMENT='任务目录，管理端可改，30 秒缓存生效';

CREATE TABLE task_log (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT      NOT NULL,
  task_key   VARCHAR(32) NOT NULL,
  biz_date   DATE        NOT NULL COMMENT '服务端按 Asia/Shanghai 计算',
  biz_key    VARCHAR(64) NOT NULL,
  p          INT         NOT NULL DEFAULT 0,
  g          INT         NOT NULL DEFAULT 0,
  created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_task_idem (user_id, task_key, biz_key),
  KEY idx_task_day (user_id, task_key, biz_date)
) COMMENT='任务完成事实，幂等与日上限的唯一依据';
```

## 五、接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/points/me` | 登录用户本人 | 余额、累计、成长值、段位、今日任务进度、`valueYuan` |
| GET | `/api/points/tasks` | 登录用户本人 | 任务目录 + 今日完成次数 + 是否可领 |
| GET | `/api/points/logs?page=1&size=20` | 登录用户本人 | 明细，倒序，返回 `balanceAfter` |
| POST | `/api/points/sign` | 登录用户本人 | 每日签到（见第 2 份文档） |
| GET | `/api/admin/task-catalog` | 管理员 | 任务目录列表 |
| PUT | `/api/admin/task-catalog/{taskKey}` | 管理员 | 改 P/G/日上限/开关 |

**统一响应**：`{ "code": 0, "msg": "ok", "data": ... }`；未登录 401，非本人 403（沿用 `AuthInterceptor` 与 `CurrentUser`）。

### 5.1 `PointsService.award()` 契约

```
award(userId, taskKey, bizKey, p, g, remark)
```

单事务内按顺序：

1. 读 `task_catalog`，不存在或 `enabled=0` → 直接返回 `notAwarded`（不改任何数据）。
2. `INSERT task_log`；捕获唯一键冲突 → 返回 `alreadyAwarded`（幂等，不改余额）。
3. 若 `daily_cap > 0`：`SELECT COUNT(*) FROM task_log WHERE user_id=? AND task_key=? AND biz_date=?`，超限 → 回滚本次插入并返回 `capped`。
4. `UPDATE user_points SET balance = balance + ?, total_earned = total_earned + GREATEST(?,0) WHERE user_id = ?`；影响行数 0 则先 `INSERT ... ON DUPLICATE KEY UPDATE` 兜底建行。
5. `UPDATE user_growth SET g_total = g_total + ?`，同样兜底建行（G 永不为负）。
6. `INSERT point_log(module, biz_key=taskKey+':'+bizKey, amount=p, g_amount=g, balance_after, remark)`。

**扣分场景**（兑换）走同一张流水，`p` 传负数，`UPDATE` 必须带 `AND balance + ? >= 0`，防止扣成负数。

## 七、已知限制与本期不做

- **不做月末清零**：大表第五节有清零规则，但需协议 + 弹窗 + 常驻入口三处明示，本期不启用，避免用户争议。
- **不做混合兑**：`积分 + 现金` 依赖真实支付与商户结算，`campus.pay.simulate` 仍是模拟（见 `docs/真实支付接入指南-五条件.md`）。
- **不做全量埋点**：只接大表 A 里 V3.1 列出的任务，其余任务留 `task_catalog` 空位，后续加行即可。
- **宠物 4 处写入调用要改造**：`PetService`（喂食扣分、签到加分）与 `PetCompanionService`（衣柜兑换、派遣奖励）各自直调 `mapper.addPoints / deductPoints / logPoints`，必须全部改为走 `PointsService`，否则余额会出现两条并行写法。这是本期最容易出错的一步，改造后必须跑第 8 条回归。

## 九、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 余额与流水对不上 | 改造宠物写入口时漏改一处，或某处直接 `UPDATE user_points` | 改造后全仓库只允许 `PointsService` 写 `user_points`；加静态检查：`grep -rn "UPDATE user_points" backend/src` 只应命中 `PointsMapper` 一处 |
| `total_earned` 语义漂移 | 扣分时若把负数累进 `total_earned`，净值会小于历史 | 只累加 `GREATEST(p,0)` |
| 唯一键误伤 | `biz_key` 拼接不含用户维度时，两个用户同一业务会互斥 | 唯一键含 `user_id`，且 `biz_key` 由服务端生成，不接受客户端传入 |

**砍掉代价**：其余 9 项功能全部失去落点——每项都要自己写加减分，最后一定对不上账。这是唯一不建议砍的一项。
