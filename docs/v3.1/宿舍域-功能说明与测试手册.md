# 宿舍域 — 功能说明与测试手册

> 来源：全仓库检索 `dorm` / `宿舍` 确认**无任何宿舍表、无宿舍页面**（`宿舍` 仅出现在 `AuditService` 的敏感词白名单、`module-school-location.sql` 的地点类型、以及种子数据的收货地址文本里）。`user` 表已有 `school_id`（`module-multischool-admin.sql:59`），`coupon` 表可用于发券。
> 编写时间：2026-11-08
> 状态：**已交付**（全部 15 条均有真库自动化用例）
> 对应大表：**A-34 宿舍全员当日签到**（+5/人 P、+8/人 G）、**A-35 宿舍周榜第一**（每人奶茶 1 杯 + 30 G）

---

## 一、这个功能解决什么问题

**现状（读码核实）**

- 没有任何宿舍概念：没有宿舍表、没有舍友关系、没有宿舍签到、没有宿舍榜。
- 你能看到的最接近的东西是：`user_address` 里手填的「学生公寓 6 号楼 312」文本，以及 `school_location` 里一个叫「宿舍」的地点类型。

**为什么大表把它单独列两行**

因为它是**唯一能一次拉动 4–8 个人**的钩子：一个人签到不算什么，但"全宿舍都签了我才拿得到分"会让人去催舍友——这是社交绑定，不是单人任务能替代的。「宿舍周榜第一每人一杯奶茶」在大表里被标成"平台 0 成本（奶茶店冠名）"，是留存的最强杠杆。

**但这也是本期最重的一块**：全新域 + 舍友关系真实性 + 奶茶券外部依赖。所以取舍表里我标注为"不建议本期做"。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范见 `docs/v3.1/前端设计-双端总览.md`。小程序端一个页面两套结构（未加入 / 已加入）；Web 端一个宿舍管理页。

### 2.1 小程序端 · `pages/dorm`（新页）

**入口**：`pages/profile/profile` 菜单插入「我的宿舍」，右侧 value 显示宿舍名或 `未加入`。

---

**态 A：未加入**

| 区域 | 内容 |
|---|---|
| 说明卡 | `和舍友一起签到，全员到齐每人 +5 积分` |
| 主按钮 | `创建宿舍`（需已认证） |
| 次按钮 | `用邀请码加入` |

- 未认证点「创建宿舍」→ toast `创建宿舍需要先完成学生认证` + 一个「去认证」按钮跳 `pages/verify`。
- 点「创建宿舍」→ `popup.modal` 带三个输入：宿舍名（如 `6号楼312`）、楼栋、房间号 → 提交 → 生成邀请码，直接进入态 B。
- 点「用邀请码加入」→ `popup.modal` 单个输入框（6 位），提交后进入态 B。

---

**态 B：已加入**

| 区域 | 内容 |
|---|---|
| 宿舍卡 `.cp-card` | 宿舍名 + 楼栋房间 + 成员数 `6 / 8` + `邀请码 ABCD12` + 「复制」按钮 |
| 今日签到区 | 成员头像格子（每人一格）：已签打勾实心、未签灰色描边；标题 `今日 4 / 6 已签到` |
| 差人提示 | `还差 2 人签到，全员到齐每人 +5 积分` |
| 全员达成 | 绿色条：`312 全员到齐，每人 +5 积分` |
| 本周榜 | `本周第 3 名 · 142 分` + `距第一还差 40 分`；第 1 名显示「本周宿舍冠军」 |
| 底部 | 小字按钮「退出宿舍」（二次确认，提示「退出后今天的全员奖励不会重发」） |

**操作步骤**

1. 进页面 → `GET /api/dorm/me`，按有没有宿舍渲染 A 或 B。
2. 态 A 创建/加入成功 → 就地切到态 B，并 `popup.modal` 展示邀请码 + 「复制到剪贴板」。
3. 态 B 点「复制」→ `wx.setClipboardData` → toast `邀请码已复制`。
4. 今日签到不单独做按钮：用户去积分页签到，签完后回本页刷新即见打勾（`onShow` 重拉）。
5. 全员达成时 → toast `312 全员到齐，每人 +5 积分`。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 未认证 | 可加入、不可创建 |
| 宿舍满 8 人 | 「用邀请码加入」提交 → toast `该宿舍已满 8 人` |
| 邀请码错误 | 行内红字 `邀请码无效，请确认后重试` |
| 已在其他宿舍 | 加入 → `请先退出当前宿舍` |
| 宿舍被解散 | 页面降级为态 A，顶部提示 `该宿舍已解散` |
| 断网 | `offline-banner` + 显示缓存的上次状态，按钮不可点 |

### 2.2 Web 端 · `web/src/views/Dorms.vue`（新页）

**页面结构**

- 标题区：`宿舍管理` + 说明「解散后成员关系解除，历史签到记录保留」。
- 筛选：学校、状态（正常/已解散）、关键字（宿舍名）。
- 表格列：宿舍名、学校、楼栋房间、成员数、本周分、状态、创建时间、操作。
- 操作：查看成员（展开行）、解散。

**操作步骤**

1. 进入 → `GET /api/admin/dorm?page=1`。
2. 点「查看成员」→ 行内展开成员列表（昵称、加入时间、今日是否签到）。
3. 点「解散」→ `NoModal` 填原因（必填）→ `POST /api/admin/dorm/{id}/dismiss`。

**状态与边界**：已解散宿舍灰显、不可再解散；列表空显示「还没有宿舍」。

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 舍友关系怎么来 | **用户自建宿舍 + 邀请码加入**，上限 8 人 | 绑定学校教务的宿舍分配数据 | 各校教务无接口；自建虽不严谨，但可运营，且"一起住的人自然会加同一个" |
| 是否要认证 | 建宿舍需已认证，加入不强制 | 都可加入 | 建的人是组织者，风险最高，卡认证；加入者是响应者，门槛低才拉得动人 |
| 一人几个宿舍 | 1 个 | 多个 | 多人多宿舍会出现"跨宿舍刷全员签到"；一人一宿舍才能算"全员" |
| 全员签到判定 | 当日签到人数 == 成员数 | 舍长代签 | 代签等于作弊；必须本人签到 |
| 周榜口径 | 宿舍成员本周在任务系统获得的总积分 | 宿舍帖数/群聊活跃 | 积分总和覆盖所有行为，口径统一且已有数据 |
| 奶茶怎么给 | 有商户券库存则发券，否则发 30G + 集体铭牌 | 平台自掏现金买奶茶 | 大表写"商户冠名、平台 0 成本"；没谈成商户就不该承诺实物 |
| 解散 | 仅管理员可解散；舍友可退出 | 舍长解散 | 舍长解散会让其他成员数据出错；退出更安全 |
| 签到入口 | 复用全局签到，不新增宿舍签到按钮 | 宿舍单独签到 | 一次签到同时完成个人与宿舍两件事，用户不用记两个按钮 |

## 四、数据表与字段

```sql
CREATE TABLE dorm (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  school_id    BIGINT       NULL,
  name         VARCHAR(32)  NOT NULL COMMENT '如 6号楼312',
  building     VARCHAR(32)  NOT NULL DEFAULT '',
  room         VARCHAR(16)  NOT NULL DEFAULT '',
  leader_id    BIGINT       NOT NULL,
  invite_code  CHAR(6)      NOT NULL,
  member_limit TINYINT      NOT NULL DEFAULT 8,
  status       TINYINT      NOT NULL DEFAULT 1 COMMENT '1=正常 0=已解散',
  created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_dorm_code (invite_code),
  KEY idx_dorm_school (school_id, status)
) COMMENT='宿舍；一人最多属于一个';

CREATE TABLE dorm_member (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  dorm_id   BIGINT   NOT NULL,
  user_id   BIGINT   NOT NULL,
  role      VARCHAR(16) NOT NULL DEFAULT 'member' COMMENT 'leader|member',
  joined_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_dorm_user (user_id) COMMENT '一人一宿舍',
  KEY idx_member_dorm (dorm_id)
) COMMENT='宿舍成员；uk_dorm_user 是"一人一宿舍"的数据库级保证';

CREATE TABLE dorm_sign (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  dorm_id      BIGINT NOT NULL,
  biz_date     DATE   NOT NULL,
  signed_count INT    NOT NULL DEFAULT 0,
  all_done     TINYINT NOT NULL DEFAULT 0,
  UNIQUE KEY uk_dorm_sign (dorm_id, biz_date)
) COMMENT='宿舍当日签到汇总；全员达成时 all_done=1';
```

**任务行**：`dorm_all_sign`（5P/8G，`daily_cap=1`，`biz_key=dorm:{dormId}:{date}`）、`dorm_week_first`（0P/30G，`daily_cap=1`，`biz_key=week:{periodKey}`）。

## 五、接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/dorm/me` | 登录 | 我的宿舍、成员、今日签到状态、本周排名 |
| POST | `/api/dorm` | 登录 + 已认证 | 创建：`{name, building, room}`；返回邀请码 |
| POST | `/api/dorm/join` | 登录 | 加入：`{inviteCode}` |
| DELETE | `/api/dorm/leave` | 登录 | 退出（舍长退出需先转让或由管理员解散） |
| GET | `/api/admin/dorm?page=` | 管理员 | 宿舍列表、成员数、状态 |
| POST | `/api/admin/dorm/{id}/dismiss` | 管理员 | 解散 |

**全员签到判定（挂在 `SignService` 成功之后）**

```
1. 取该用户 dorm_id；无宿舍 → 结束
2. UPSERT dorm_sign(dorm_id, biz_date) SET signed_count = signed_count + 1
3. memberCount = SELECT COUNT(*) FROM dorm_member WHERE dorm_id=?
4. 若 signed_count >= memberCount 且 all_done=0：
     ALL_DONE = 1
     对每个成员 PointsService.award('dorm_all_sign', 'dorm:{id}:{date}')
5. 同一事务；重复签到不会重复 +1（sign_roll 主键已挡）
```

**周榜结算（周一 00:20，排在论坛周榜之后）**

```
对每个 status=1 的宿舍：
  score = SUM(该宿舍成员本周所有 task_log 的 p)   -- 任务积分总和
按 score DESC 取第 1 名（并列取 dorm_id 小者）
对第 1 名每个成员 award('dorm_week_first', 'week:{periodKey}', 0P, 30G)
若 reward_item 中 milk_tea 有库存 → 额外发券（每人 1 张），库存不足则跳过并记日志
```

## 七、已知限制与本期不做

- **舍友关系靠自己认领**：不校验"你们真的住一起"。这是自建模式的固有弱点，只能靠邀请码 + 上限 8 人约束。
- **奶茶券依赖商户**：没有商户库存时只发成长值与铭牌，**不承诺实物**。
- **不做宿舍群聊**：圈子群聊已有 WebSocket，但宿舍群聊要额外做审核覆盖（群聊审核目前是盲区，见 `docs/扩展功能规划.md` P0-4），本期不开。
- **不做宿舍积分加成**：大表提到"下周宿舍积分 +10%"，需要乘算逻辑与防叠加，本期不做。
- **不做跨校宿舍**：宿舍绑定 `school_id`，跨校不互通。
- **不做宿舍照片/装扮**：无素材。
- **中途退出当日不补发**：规则写死"当日判定完成后不再变动"，避免有人卡在最后一刻退出/加入刷分。

## 九、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 宿舍造假 | 4 个人互相加，凑不满 8 人也能设 8 人上限，实际 4 人天天全员签到 | 全员判定按**实际成员数**而不是上限；造假者只能拿到 4 人份的 +5P，收益有限 |
| 刷周榜 | 一个宿舍集中做任务拉高总分 | 分数来自真实任务流水（有日上限），总量有天花板 |
| 位置隐私 | 楼栋房间号是敏感信息 | 仅成员可见；解散后成员关系解除；注销账号时级联删除 |
| 解散丢数据 | 管理员误解散 | 解散只改 `status=0`，不物理删除，可恢复 |
| 与全局签到的时序 | 签到在 `SignService`，宿舍判定在其后；若宿舍判定失败，不能让签到失败 | 宿舍判定放在签到事务提交后执行，失败只记日志不回滚签到 |

**砍掉代价**：大表 A-34/A-35 两行空着；「一次拉动 4–8 人」的社交绑定没有替代品；宿舍周榜这个你认可的钩子拿不到。
