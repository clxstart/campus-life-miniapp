# 签到与连签 — 功能说明与测试手册

> 来源：`backend/src/main/java/com/campuslife/service/PetService.java:74`（现有宠物签到）、`backend/src/main/resources/db/module-pet.sql`；本文档为全站签到的扩展设计。
> 编写时间：2026-11-08
> 状态：**已交付**（未自动化项见第六节）
> 对应大表：**A-2 每日签到**（1P/1G，日上限 1 次）、**A-3 连续签到里程碑**（+5/10/15/20/30/50 P 与 G）

---

## 一、这个功能解决什么问题

**现状（读码核实）**

- 全站只有一个"签到"：宠物签到。`PetService` 里 `checkin` 分支给 `exp+20`、`points+5`、日上限 1 次，签到状态挂在宠物身上。
- 用户不养宠物就没有签到入口；`pages/` 下没有任何全局签到页面。

**为什么必须有**

积分体系最怕冷启动：新人第一天没有任何积分，兑换池最便宜的商品也拿不到。签到是**唯一不需要用户产出内容就能拿到第一笔积分**的任务，也是「每天回来一次」的最低成本钩子。大表把连签做成 3/5/7/15/20/30 天六档里程碑，就是为了把「回来一次」拉成「连续回来一个月」。

## 二、前端页面与操作（小程序端 + Web 端）

> 本节只写本功能独有部分，通用规范见 `docs/v3.1/前端设计-双端总览.md`。**Web 端无页面**——签到是纯用户行为，运营不需要后台操作，只在小程序端出现。

### 2.1 小程序端 · 复用 `pages/points/points` 顶部卡片

签到不单独开页，嵌在积分页第一张卡片里（用户一天只来一次，多开一页反而多一次跳转）。

**卡片结构**

| 区域 | 内容 |
|---|---|
| 左侧 | `今日签到` 标题 + `已连续签到 4 天` |
| 右侧 | 主按钮 `.cp-btn-primary`：`签到 +1 积分`；已签到变 `.cp-btn-primary--disabled`，文案 `今天已签到` |
| 下方 | 连签进度：`下一档：连签 5 天，额外 +10 积分` + 3 个圆点示意（已达成实心 / 未达成描边） |
| 再下方 | 八档里程碑横向提示，只展示「已过 / 下一个」，不铺满 6 个 |

**操作步骤**

1. 进页面 → 读 `/api/points/me` 的 `signedToday` 与 `streakDays`，决定按钮态。
2. 点按钮 → 立即 `disabled` + `hover-class="tap-btn"`（防连点）→ `POST /api/points/sign`。
3. 成功 → `popup.toast(this, '签到成功 +1 积分', { tone: 'success' })`；若返回含里程碑，再追加一条 `连续签到 5 天，额外 +10 积分`。
4. 成功后局部刷新余额、连签天数、任务列表第一行，**不整页重载**。
5. 失败 → `popup.toast(this, '签到失败，请稍后重试', { tone: 'error' })`，按钮恢复可点。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 今天已签 | 按钮置灰不可点，文案 `今天已签到`，不报错 |
| 连签中断回来 | 显示 `已连续签到 1 天`，不显示「断了」这类负面措辞 |
| 未登录 | 401 → 跳登录 |
| 开关关闭 | 按钮灰显，下方小字「签到暂未开放」 |
| 接口超时 | 按钮恢复，toast 提示可重试 |

### 2.2 Web 端

**无页面。** 如需排查某个用户为什么没签到，走「用户管理 → 该用户 → 积分明细」，看 `task_key=daily_sign` 的记录即可，不单独做签到后台。

### 2.3 文案清单

| 场景 | 文案 |
|---|---|
| 可签到 | `签到 +1 积分` |
| 已签到 | `今天已签到` |
| 连签进度 | `已连续签到 4 天` |
| 下一档 | `下一档：连签 5 天，额外 +10 积分` |
| 成功 | `签到成功 +1 积分` |
| 里程碑 | `连续签到 5 天，额外 +10 积分` |
| 开关关闭 | `签到暂未开放` |
| 刻意不出现的词 | 「断签」「连续中断」「补签」 |

**刻意不做**：不做签到日历弹窗、不做补签卡、不做签到分享图。补签属于「用积分买时间」，会削弱连签的意义，且大表把它放在徽章体系（V3.2）里。

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 签到记录表 | 独立 `sign_roll(user_id, biz_date, streak_days)` | 复用 `task_log` 推算连签 | 连签要回答「昨天签没签」，`task_log` 里混着几十种任务，每次扫表推算既慢又容易错；一张一天一行的表最直接 |
| 连签计算 | 查昨天那一行是否存在 | 客户端传 `streakDays` | 客户端可伪造，服务端一行 `SELECT` 就能算 |
| 里程碑幂等键 | `sign_streak_N` + 当天日期 | 整个账号只发一次 | 断签后重新连到 7 天，应该**再给一次**奖励，否则用户没有重新开始的理由 |
| 宠物签到 | 保留原样（+5P，`task_key=pet_checkin`） | 合并成一个签到 | 合并要改宠物页面文案与既有测试，收益只是"少一个按钮"；保留后两笔都在同一账本，可审计、可随时收敛 |
| 断签处理 | 直接重置为 1 | 宽限期（如 36 小时） | 宽限期会让「连续」失去确定边界，也带来跨天争议；不做 |

## 四、数据表与字段

```sql
CREATE TABLE sign_roll (
  user_id     BIGINT   NOT NULL,
  biz_date    DATE     NOT NULL,
  streak_days INT      NOT NULL DEFAULT 1,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, biz_date)
) COMMENT='每日签到；一天一行，连签靠昨天那行推算';
```

- `biz_date` 由服务端按 `Asia/Shanghai` 计算，不用数据库时区。
- 主键 `(user_id, biz_date)` 即幂等键：双击签到只会插成功一次。
- 任务行：`daily_sign`（1P/1G，日限 1）、`sign_streak_3`（5P/5G）… `sign_streak_30`（50P/50G），全部 `daily_cap=1`。

## 五、接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/points/sign` | 登录用户本人 | 签到；返回连签天数与本次奖励 |
| GET | `/api/points/me` | 登录用户本人 | 内含 `signedToday`、`streakDays`、`nextMilestone` |

**`POST /api/points/sign` 返回体**

```json
{
  "code": 0,
  "data": {
    "signedToday": true,
    "streakDays": 5,
    "awarded": [{ "taskKey": "daily_sign", "p": 1, "g": 1 },
                 { "taskKey": "sign_streak_5", "p": 10, "g": 10 }],
    "balance": 63
  }
}
```

**错误与边界**

| 情况 | 返回 |
|---|---|
| 今天已签 | `code=0`，`signedToday=true`，`awarded=[]`（幂等，不报错） |
| 未登录 | 401 |
| 任务被停用（`daily_sign.enabled=0`） | `code=0`，`awarded=[]`，`msg="签到暂未开放"` |

**服务端流程**

1. `biz_date = LocalDate.now(ZoneId.of("Asia/Shanghai"))`。
2. `INSERT sign_roll`，冲突 → 已签到，直接返回现状。
3. `SELECT streak_days FROM sign_roll WHERE user_id=? AND biz_date=? - 1天`：有则 `+1`，无则 `1`。
4. 回写 `streak_days`；调 `PointsService.award(daily_sign)`。
5. 若 `streak_days ∈ {3,5,7,15,20,30}`，再调 `award('sign_streak_N', biz_date)`。
6. 全部在同一事务内；任一步失败整体回滚，不会出现「连签加了、积分没发」。

## 六、测试计划与人日工作量

**工作量：2 人日**

| # | 测什么 | 怎么测 | 预期 | 结果 |
|---|---|---|---|---|
| 1 | 首次签到 | 新账号签到 | 连签 1 天，+1P/+1G | ✅ `firstSignGivesOneDayAndOnePoint` |

| 5 | 里程碑二次达成 | 断签后重新连到 3 天 | 再发一次 +5P/+5G | ✅ `milestoneCanBeEarnedAgainAfterReset` |

| 7 | 时区 | 服务器 UTC 时跑第 6 条 | 仍按北京时间分日 | ✅ `signUsesShanghaiDateEvenWhenJvmDefaultZoneIsFarAway`（`TimeZone.setDefault` 换成与上海异日的时区，落库日期仍为上海今天） |
| 8 | 与宠物签到共存 | 同一天宠物签到 + 全局签到 | 两笔都成功，`point_log` 两条不同 `module` | ✅ `petCheckinAndDailySignWriteSeparateLedgerModules` |
| 9 | 并发双击 | 同一秒并发 2 次请求 | 只发一次，主键冲突被吞 | ✅ `concurrentDoubleClickOnlyAwardsOnce`（10 并发只发 1 次，失败方也回 `signedToday=true`） |

## 七、已知限制与本期不做

- **不做补签/补签卡**：属于徽章体系（V3.2），本期不加。
- **不做签到日历**：只有「连续 N 天 + 下一档」。
- **不做签到提醒推送**：订阅消息模板尚未申请（见 `docs/扩展功能规划.md` P0-1），本期只能靠页面入口。
- **宠物签到与全局签到并存**：同一天可以有 6P（宠物 5 + 全局 1）。这是刻意保留的既有行为，若要收敛，改 `task_catalog.pet_checkin.p_reward=0` 一行即可，不动代码。
- **清零**：签到奖励计入积分，本期积分不清零（见第 1 份文档）。

## 九、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 时区错位 | 服务器 UTC，若用 `LocalDate.now()` 不分时区，会把北京时间早上 8 点前算成前一天 | 统一 `ZoneId.of("Asia/Shanghai")`，与 `CircleStreakService.BEIJING` 保持同一写法 |
| 连签被"跨零点"操作重置 | 用户在 23:59 签、00:01 又被提示"今天还没签"，实际是两天 | 页面显示"今天已签/明天再来"按服务端 `signedToday` 判定，不做本地时间推算 |
| 两个签到入口混淆 | 用户以为宠物签到就是全站签到 | 宠物签到文案改为「宠物互动」，不再出现「签到」字样（只改文案，不改逻辑） |

**砍掉代价**：日活底盘缺失，任务体系冷启动困难；新人第一天拿不到任何积分，「7 日首兑率 ≥60%」这个目标直接不成立。
