> 来源：全仓库检索确认无段位/成长值实现（无 `g_total`、无 `tier`）；本文档为新建。段位门槛引自《全功能积分任务与段位特权大总表_V3.md》大表 B。
> 编写时间：2026-11-08
> 状态：**已交付**（未自动化项见第六节）
> 对应大表：**B 段位·荣誉·徽章·特权 六合一总表**（段位由成长值 G 推导）

## 一、这个功能解决什么问题

**现状（读码核实）**

- 没有任何 `g_total` / 段位 / 等级概念。宠物有 `level`，但那是宠物的，与用户身份无关。
- 用户做完所有任务后，除了积分余额没有任何"身份变化"。

**为什么需要**

积分是**消耗品**（换券就没了），成长值是**资产**（只涨不降）。只有积分没有成长值，用户会产生"我攒了又花掉，等于白干"的感觉；而段位是把"白干"变成"我在升级"的唯一叙事。大表把段位放在 B 表正中央，理由是它同时承载三层作用：身份（铭牌）、特权（见第 5 份文档）、留存（怕掉段就得持续做任务）。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范见 `docs/v3.1/前端设计-双端总览.md`。段位不做独立页面：小程序端两个展示位 + 一个说明弹层；Web 端只做只读查看。

### 2.1 小程序端 · 展示位 1：积分页段位卡

位于余额卡下方，与余额卡同一张 `.cp-card` 或紧邻的独立卡片。

| 元素 | 内容 |
|---|---|
| 铭牌 | `白银 · 圈内熟人`（纯文本标签，无图片无特效） |
| 进度 | 进度条 + `142 / 200 成长值`，右侧小字 `距黄金还差 58` |
| 右侧箭头 | `›`，点击打开段位说明弹层 |

### 2.2 小程序端 · 展示位 2：个人页昵称旁

- 昵称后面跟一个 `.campus-chip`，内容为两字段位（`白银`）。
- 与认证标签同时存在时，**只显示认证标签**，段位放进个人页的段位卡（避免昵称行挤三个标签）。

### 2.3 小程序端 · 说明弹层（`popup.sheet`）

八行列表，每行：段位名、`G ≥ 门槛`、一句特权摘要。

| 状态 | 样式 |
|---|---|
| 已达成 | 实心圆点 + 主色文字 |
| 当前段位 | 加粗 + 左侧竖色条 |
| 未开放（enabled=0） | 灰显 + 右侧「未开放」小字 |

**操作步骤**

1. 进积分页 → 用 `/api/points/me` 返回的 `tier` 一次性渲染，不再单独请求。
2. 点段位卡 → 打开 sheet，展示八段位。
3. 点「未开放」的段位 → 不跳转，只显示一行小字「该段位暂未开放，开放后会第一时间通知」。

**状态与边界**

| 情况 | 表现 |
|---|---|
| `G=0` | 青铜，进度 `0/60` |
| 已达最高开放段位（黄金） | 进度条满，文案 `已完成当前开放段位`，不显示「还差多少」 |
| 未登录 | 不渲染段位区（整页 401 已跳登录） |
| 晋升瞬间 | 首次进入积分页时对比本地 `lastTier`，变了就 `popup.toast('晋升白银·圈内熟人', { tone: 'success' })`，并更新本地值 |

### 2.4 Web 端 · 并入 `PointsTasks.vue` 下半部分（只读）

| 列 | 内容 |
|---|---|
| 段位 | 青铜 / 白银 / 黄金 / 铂金… |
| G 门槛 | 0 / 60 / 200 / 600… |
| 是否开放 | 已开放 / 未开放（灰标） |
| 特权摘要 | 「快速应答」「免审 + 建圈」等一句话 |

**不可编辑**：门槛一旦放开修改，已达成用户会被"改高后掉段"，争议成本高；要调门槛走代码发布。

### 2.5 文案清单

| 场景 | 文案 |
|---|---|
| 进度 | `142 / 200 成长值` |
| 差额 | `距黄金还差 58` |
| 已满级 | `已完成当前开放段位` |
| 晋升 | `晋升白银·圈内熟人` |
| 未开放 | `未开放` / `该段位暂未开放，开放后会第一时间通知` |

**第一版只有文本标签**：不做铭牌图片、不做昵称特效、不做主页皮肤（无设计素材，且大表把它们排在 V3.3）。

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 段位是否落库 | **读时由 `g_total` 推导**，只存成长值 | 存 `user.tier` 字段 | 存字段就要维护"什么时候升级、什么时候刷新"，一旦漏写就会出现"成长值到了但段位没升"；推导永远一致 |
| 降不降级 | 永不降级 | 按赛季衰减 | 大表明确「成长值永久只涨不降」；衰减会让老用户有被剥夺感 |
| 段位开放范围 | 只开放青铜/白银/黄金 | 八段全开 | 铂金以上的特权（置顶、抢单提前、1对1急送）依赖大表 C 的规则与更多用户量，提前开放等于空头支票 |
| 超出黄金怎么显示 | 仍显示「黄金」，并提示「更高段位敬请期待」 | 显示「铂金（未开放）」当作已达成 | 不能让用户以为自己拿到了不存在的东西 |
| 特权判定依据 | 成长值 G | 当季活跃值 S | S 是大表 V3.3 的内容，第一版不做（见第 5 份文档「已知限制」） |

## 四、数据表与字段

```sql
CREATE TABLE user_growth (
  user_id    BIGINT PRIMARY KEY,
  g_total    INT      NOT NULL DEFAULT 0,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) COMMENT='成长值，只涨不降，写入只走 PointsService';

CREATE TABLE tier_config (
  tier_code   VARCHAR(16) PRIMARY KEY,
  name        VARCHAR(32) NOT NULL,
  g_threshold INT         NOT NULL,
  s_threshold INT         NOT NULL DEFAULT 0 COMMENT '当季活跃值门槛，V3.1 不启用',
  honor_label VARCHAR(32) NOT NULL DEFAULT '',
  enabled     TINYINT     NOT NULL DEFAULT 1,
  sort        INT         NOT NULL DEFAULT 0
) COMMENT='段位配置；V3.1 仅前三段 enabled=1';
```

**种子（与大表 B 一致）**

| tier_code | name | g_threshold | enabled |
|---|---|---|---|
| bronze | 青铜·萌新 | 0 | 1 |
| silver | 白银·圈内熟人 | 60 | 1 |
| gold | 黄金·活跃分子 | 200 | 1 |
| platinum | 铂金·风云人物 | 600 | 0 |
| diamond | 钻石·一校红人 | 1500 | 0 |
| star | 星耀·校园顶流 | 3500 | 0 |
| king | 王者·城市之星 | 8000 | 0 |
| legend | 传奇·校宝名人堂 | 18000 | 0 |

> `enabled=0` 的段位只作为「未开放」展示，不产生任何特权。

## 五、接口清单

段位不单独开接口，挂在积分接口里返回，避免小程序首屏多一次请求。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/points/me` | 返回 `tier` 对象（见下） |
| GET | `/api/admin/tier-config` | 管理端只读查看段位门槛与开关 |

**`tier` 返回结构**

```json
{
  "tier": {
    "code": "silver",
    "name": "白银·圈内熟人",
    "gTotal": 142,
    "gThreshold": 60,
    "nextCode": "gold",
    "nextName": "黄金·活跃分子",
    "nextThreshold": 200,
    "percent": 71,
    "maxOpen": false
  }
}
```

- `percent` = `(gTotal - 当前段位门槛) / (下一段位门槛 - 当前段位门槛) × 100`，向下取整，封顶 100。
- 已达最高开放段位（黄金）时：`nextCode=null`，`maxOpen=true`，前端显示「更高段位敬请期待」。

**推导规则（`TierService.current(G)`）**

1. 取 `enabled=1` 且 `g_threshold <= G` 的段位，按 `g_threshold` 降序取第一条 → 当前段位。
2. 下一段位 = `enabled=1` 且 `g_threshold > G` 的最小一条；没有则为 `null`。
3. 若 `G` 已超过最后一个开放段位门槛，当前段位固定为最后开放段位，`maxOpen=true`。

## 六、测试计划与人日工作量

**工作量：2 人日**

| # | 测什么 | 怎么测 | 预期 | 结果 |
|---|---|---|---|---|
| 1 | 初始段位 | 新用户 `g_total=0` | 青铜，进度 0/60 | ✅ `newUserWithoutGrowthRowIsBronzeWithZeroProgress`（集成，库里无 `user_growth` 行）、`newUserIsBronzeWithZeroProgress`（单元） |
| 2 | 边界 59→60 | 手工把 G 改为 59、60 | 59 是青铜，60 升白银 | ✅ `boundaryFiftyNineStaysBronzeAndSixtyBecomesSilver`、`derivesTiersAndProgressFromRealConfig` |
| 3 | 边界 199→200 | 199 白银，200 升黄金 | 一致 | ✅ 同用例 2（单元 + 真库两侧都钉） |
| 4 | 超出开放段 | G=9999 | 仍显示黄金，`maxOpen=true`，不显示铂金 | ✅ `beyondLastOpenTierStaysGoldAndMarksMaxOpen` |
| 5 | 只涨不降 | 连续做任务再查 | `g_total` 单调递增，无任何接口能减 G | ✅ `growthOnlyIncreases`（连发 +2、同 bizKey 幂等不加、扣积分不减 G） |
| 6 | 进度计算 | G=142，白银 60，黄金 200 | `percent=(142-60)/(200-60)=58` | ✅ `progressIsFloorAndMatchesDesignExample`、`progressIsFlooredAndClampedWithinEachBand`（另钉 61→0、150→64、199→99、60→0） |
| 7 | 并发成长 | 同时 10 个任务发分 | `g_total` 精确等于 10 次之和，无丢更新 | ✅ `concurrentAwardsDoNotLoseGrowth` |
| 8 | 配置改动 | 后台把黄金门槛改为 150 | 30 秒后查询，段位按新门槛推导 | ✅ `TierServiceTest#configCacheExpiresAfterThirtySecondsOnInjectedClock`（注入可推进的 `Clock`：29 秒内不再查库、31 秒后回源）+ `thresholdChangeTakesEffectAfterCacheEvict`（真库改门槛，`evict()` 后按 150 推导、改回复原） |

**补充自动化用例**（原表未列）：`configIsCachedUntilEvicted`（连读 3 次只查库 1 次，`evict()` 后回源）、`trialTierIsValidOnDayOneAndFallsBackOnDayEight`（固定时钟：体验段位第 1 天生效、第 7 天末仍生效、到期后回落青铜）、`expiredTrialDoesNotRaiseTier`（真实 SQL 的过期过滤：过期即失效、有效期内只抬特权不改铭牌）、`featureFlagOffRemovesPrivileges`（关开关后免审/建圈立刻 false）。

**未自动化**：① ~~30 秒 TTL 的真等待~~ **已自动化**（`configCacheExpiresAfterThirtySecondsOnInjectedClock`，用假时钟快进，不再真等 30 秒）；② ~~未登录 401~~ **已自动化**（`V31AuthGateTest`），`school` 角色 403 仍属接口层、需 curl 手工验证；③ Web `/points-tasks` 段位表与小程序段位卡的页面交互（无浏览器/真机自动化）。原先此处记的「Web 表两列恒为 `—`」是交付时的真实缺陷，**本轮已修**：前端改读 `code` + `privilegeSummary` 并删掉「荣誉标识」列，详见 `docs/v3.1-交付/04-段位与成长值-交付报告.md` 隐患 1。

> 注：本文档 §5 的 `tier` 示例里 `"percent": 71` 与本表用例 6 的 58 矛盾。按公式应为 58.57 → 58，实现与用例 6 一致；示例的 71 是笔误（交付时未改正文，此处记录）。

## 九、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 段位与特权不同步 | 段位读 `user_growth`，特权读 `user_privilege`（含体验段位），两处不一致会出现「显示白银但享受不到白银特权」 | 特权判定统一走 `TierService.effectiveTier(userId)`，该方法是唯一入口，先取 G 推导、再取体验段位取较高者 |
| 门槛调整引发争议 | 用户已按旧门槛达成，改高后"掉段" | 只允许上调新段位门槛，且必须公告；第一版先不做后台改门槛，只读 |
| 用户量少时段位无意义 | 前 10 个用户可能全是青铜 | 这与事实相符，不做假数据填充 |

**砍掉代价**：特权、荣誉、徽章全部失去载体；用户做完任务只看到积分数字涨，没有"我在变强"的叙事，长期留存少一根支柱。
