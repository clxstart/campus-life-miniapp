## 一、这个功能解决什么问题

**现状（读码核实）**

- 用户有一个 `coupon` 表（券），但**没有任何地方能产生券**：全仓库只有种子数据里插了 3 张，兑换入口只有宠物衣柜（扣积分换宠物道具）。
- 积分只有"进"没有"出"（第 1 份文档落地后），用户攒到 30 分也不知道能干嘛。

**不做会怎样**

大表 V3 的核心改动就是「首次兑换从 20–30 天压缩到 2–3 天」，靠的是两条：注册即送 30P + 10–40P 的低门槛商品池。没有这一节，积分体系只有"打卡"没有"兑现"，7 日留存的目标无从实现。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范见 `docs/v3.1/前端设计-双端总览.md`。小程序端一个兑换页 + 一处一次性提示；Web 端一个商品池管理页。

### 2.1 小程序端 · 新人礼包提示（一次性）

**触发**：首次登录建号成功、进入首页后。

**形式**：`popup.modal`（不是 toast，因为要给用户时间读完），标题 `新人礼包已到账`，正文两行：

- `30 积分`
- `白银体验 7 天（快速应答）`

底部按钮：`去看看`（跳积分页）/ `知道了`。**只弹一次**，本地 `storage` 记 `newbieGiftShown`；重复登录不再弹。

### 2.2 小程序端 · `pages/points-redeem`（新页）

**入口**：积分页余额卡下方按钮「去兑换」，以及余额不足时明细页底部的引导。

**页面结构**

| 区域 | 内容 |
|---|---|
| 顶部 | 当前余额 `63 积分` + `≈¥0.63` |
| 商品网格 `.cp-grid-2` | 每格：名称、`10 积分`、`≈¥0.10`、`库存 还剩 198`、`每人限 5 件` |
| 商品状态 | 售罄盖灰标「已兑完」；达限购标「已达上限」；下架不显示 |
| 底部 | 合规说明「100 积分 = 1 元，仅作价值参考，不可提现」 |

**操作步骤**

1. 点商品 → `popup.modal`：标题 `确认兑换`，正文 `将扣除 10 积分，兑换后不可退`，按钮 `兑换` / `取消`。
2. 点「兑换」→ 按钮 `disabled` + 提交中 → `POST /api/points/redeem`。
3. 成功 → `popup.toast('兑换成功，已放入「我的优惠券」', { tone: 'success' })`，局部刷新余额与商品库存。
4. toast 后 2 秒内页面顶部出现一条可点的引导条「查看我的优惠券 ›」，点击跳 `pages/profile` 的券区。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 积分不足 | 按钮可点，点击后 toast `积分不足，还差 10 分`，并给「去赚积分」按钮跳积分页 |
| 售罄 | 按钮置灰，文案「已兑完」 |
| 达限购 | 按钮置灰，文案「已达上限」 |
| 并发售罄 | 后端 400 → toast `手慢了，刚刚被兑完`，刷新库存 |
| 未登录 | 401 → 跳登录 |

### 2.3 小程序端 · 券列表（`pages/profile` 优惠与权益）

**不改造逻辑**，只确认新券能落在列表首位，展示 `title` / `amount` / `expire_at`。兑换成功后从积分页跳过来，能看到刚兑的券。

### 2.6 小程序端 · 外卖下单页选券（**本轮补的交互，设计稿原文未写**）

> 本文成文时只规划了「券只在平台内订单抵扣」，没写用户在哪里选券，导致后端锁券/抵扣链路对用户不可达。本节记录本轮补上的实现细节，页面为 `pages/food-order`。

**页面结构**

| 区域 | 内容 |
|---|---|
| 订单卡「优惠券」行 | 默认自动选中「当前订单可用且抵扣最多」的一张，显示 `外卖立减 1 元 −¥1.00 ›`；没有可用券时显示 `暂无可用`，下一行小字给出门槛原因（如 `满 20.00 元可用`） |
| 合计区 | 选中券时多一行 `券抵扣 −¥1.00`；合计与底部实付同步为券后金额，底部说明补「已扣满减与优惠券」 |
| 选券弹层（`popup.sheet`） | 可选券在前（券名 · 抵扣额 · 有效期，当前项前缀 `✓`）；不可选券带原因（`不可选（满 20.00 元可用）`，点了只提示原因、不选中）；最后一项 `不使用优惠券` |

**操作步骤**

1. 进结算页 → 读 `GET /api/users/{id}/coupons`（接口只返回 status=1 且未过期的券）→ 本地按 `thresholdCents ≤ 商品合计` 过滤出可用券 → 自动选抵扣最多的一张。
2. 点「优惠券」行 → 弹层选券或选「不使用」→ 合计与实付即时重算（**只是展示预估**）。
3. 提交 → `POST /api/orders` body 带 `couponId`；幂等键签名含「店铺 + 商品 + 地址 + 券」，换券等于换一次结算，必须换新键，否则会复用旧订单导致券对不上。
4. 下单成功 → 用订单返回的 `total` / `couponDiscount` 校准展示金额（服务端金额才是准的）。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 券被别的订单锁走 / 已过期 / 门槛不足 | 服务端返回中文原因，原样 toast，并刷新券列表让用户重选 |
| 券列表拉取失败 | 不阻塞下单，按「暂无可用」展示；提交时服务端仍会校验 |
| 订单返回金额与本地预估不同 | 以订单返回金额覆盖展示 |
| 未登录 | 401 → 跳登录 |

> **视觉限制**：`ui-popup` 的 sheet 只渲染文字项，没有禁用态与副标题，所以「不可选置灰」降级为 `标题 · 不可选（满 20.00 元可用）` 的文字标注；真正的灰显需要共享组件支持 `disabled`（本期不改组件）。

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 券的载体 | 复用现有 `coupon` 表 | 新建 `reward_grant` 表 | 用户已经在"优惠与权益"页看券，复用后兑换结果立即可见；再建一套会出现两个券列表 |
| 券的使用范围 | **仅平台内订单抵扣**（外卖下单减钱） | 到店出示 / 实物自提 | 你已确认「在系统里面使用，不在外面用」。到店凭证要靠店员肉眼确认、实物要靠提货码，两者都是线下履约，本期不碰 |
| 券的成本承担 | **平台补贴**：用户少付，商家按原价结算，平台补差价 | 商家承担 | 你已确认。商家侧账目不变，对账不打架；代价是平台要建一笔真实支出账（见第五节） |
| 兑换记录 | 新增 `redeem_record` | 只靠 `point_log` | 券可能过期、可能核销，需要独立的生命周期；流水只记"扣了多少分" |
| 商品层级 | 只上 70% 低门槛层（10–40P 虚拟品） | 7:2:1 全部上 | 20% 混合兑依赖真实支付、10% 限量依赖商户赞助，两者都是外部依赖，先不做 |
| 并发扣分 | `UPDATE ... WHERE balance >= ?` 条件更新 | 先查再扣 | 先查后扣在并发下必然超扣（两个请求同时看到 10 分，各扣 10） |
| 新人礼包发放时机 | 首次微信登录建号成功时 | 每次登录检查 | 每次登录检查会多一次查询；建号只发生一次，天然幂等 |
| 白银体验 7 天 | `user_privilege.expires_at = now + 7d` | 直接改 `g_total` | 改 G 会让"体验"变成永久资产，到期收不回 |
| 兑换是否可退 | 不可退 | 可退积分 | 券一旦发出就可能被核销，退款逻辑会牵扯商户；文案明确"不可退" |

## 四、数据表与字段

```sql
CREATE TABLE reward_item (
  item_key      VARCHAR(32) PRIMARY KEY,
  name          VARCHAR(32)  NOT NULL,
  zone          VARCHAR(16)  NOT NULL DEFAULT 'virtual' COMMENT 'virtual|mixed|limited',
  price_p       INT          NOT NULL,
  cash_cents    INT          NOT NULL DEFAULT 0 COMMENT '混合兑现金部分，V3.1 恒为 0',
  stock         INT          NOT NULL DEFAULT 0 COMMENT '0=售罄（不用负数表示无限）',
  per_user_limit INT         NOT NULL DEFAULT 1,
  coupon_title  VARCHAR(64)  NOT NULL,
  coupon_amount VARCHAR(16)  NOT NULL DEFAULT '',
  coupon_expire VARCHAR(16)  NOT NULL DEFAULT '',
  enabled       TINYINT      NOT NULL DEFAULT 1,
  sort          INT          NOT NULL DEFAULT 0
) COMMENT='兑换商品池';

CREATE TABLE redeem_record (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT      NOT NULL,
  item_key   VARCHAR(32) NOT NULL,
  price_p    INT         NOT NULL,
  coupon_id  BIGINT      NOT NULL COMMENT '生成的 coupon.id',
  created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_redeem_user (user_id, created_at),
  KEY idx_redeem_item (item_key, user_id)
) COMMENT='兑换记录；同一用户对同一商品的次数用 idx_redeem_item 统计';
```

**商品池：四档外卖券（已定，严格 1:1）**

你已确认「券只在系统内用」+「平台承担成本」，两条约束一碰，面额就只能等于积分价值：`100P = 1 元` 是公示口径，券面额超过它就是在亏钱。所以四档面额由积分价格反推，没有别的地儿可调。

| item_key | 名称 | price_p | 券面额 | 使用门槛 | stock | 每人限 |
|---|---|---|---|---|---|---|
| `takeout_1` | 外卖立减 1 元 | 100 | `1.00 元`（100 分） | 满 20 元 | 200 | 3 |
| `takeout_0_5` | 外卖立减 0.5 元 | 50 | `0.50 元`（50 分） | 满 15 元 | 300 | 6 |
| `takeout_0_25` | 外卖立减 0.25 元 | 25 | `0.25 元`（25 分） | 满 15 元 | 400 | 8 |
| `takeout_0_1` | 外卖立减 0.1 元 | 10 | `0.10 元`（10 分） | 满 10 元 | 500 | 10 |

**三条落地注意**

1. **低档是真的弱**。`10P` 抵 `0.1 元`，在外卖单里几乎没有感知。它存在的唯一理由是「新人 30P 当天就能兑一次」，完成"我兑过东西"的心理教育，不是靠金额吸引人。
2. **商品卡排序把大额放前面**（`sort` 让 `takeout_1` 排第一）。用户的参照点会变成"攒到 100P 减 1 元"，这是免费且有效的定价心理学——档位从低往高排，用户会觉得整池都鸡肋。
3. **必须有使用门槛**（`threshold_cents`）。没有门槛，`0.1 元`的券会被用在 1 元的订单上，等于 10% 折扣，羊毛党会专门刷。

**为什么不做"免打包费 / 免配送费"**：这两项面额由平台自定（打包费 2 元），抵 2 元的券按 1:1 要 `200P`，新人兑不到；若按 `30P` 卖就是每张亏 1.7 元，比外卖券亏得更多。它们适合放到"限量稀缺池"（第二版，靠商户赞助）。

**券表改造**（与第五节配套，必须一起上）

```sql
ALTER TABLE coupon
  ADD COLUMN value_cents     INT         NOT NULL DEFAULT 0 COMMENT '抵扣额（分）；amount 只是展示文案，算钱只认这个',
  ADD COLUMN threshold_cents INT         NOT NULL DEFAULT 0 COMMENT '使用门槛（分），0=无门槛',
  ADD COLUMN scope           VARCHAR(16) NOT NULL DEFAULT 'takeout' COMMENT '适用品类，本期只有 takeout',
  ADD COLUMN expire_on       DATE        NULL COMMENT '过期日；旧 expire_at 保留一版兼容',
  ADD COLUMN locked_at       DATETIME    NULL COMMENT '下单锁定时间',
  ADD COLUMN used_at         DATETIME    NULL COMMENT '核销时间',
  ADD COLUMN order_id        BIGINT      NULL COMMENT '核销订单',
  ADD COLUMN source          VARCHAR(16) NOT NULL DEFAULT 'seed' COMMENT 'seed|newbie|redeem|admin',
  ADD KEY idx_coupon_user_state (user_id, status, expire_on);
```

`status` 复用为一套状态机：**1=可用 / 2=锁定 / 3=已核销 / 0=作废**。老数据全是 1，语义不变，不用迁移。

## 五、券的结算与成本（平台补贴）

**你已确认：券只在系统内用（外卖下单抵扣），成本由平台承担，商家按原价结算。**

### 5.1 金额链

`BizService.createOrder()` 现在已经在算 `subtotal / packingFee / deliveryFee / discountAmount / total / payAmountCents`，加券只是多减一项，**不需要重构结算**。

| 字段 | 公式 | 谁承担 |
|---|---|---|
| `subtotal` | Σ(单价 × 数量) | — |
| `shop_discount` | 店铺满减（原 `discountAmount`） | 商家 |
| `coupon_discount` | 券面额（**新增字段**） | **平台** |
| `packing_fee` / `delivery_fee` | 不变 | 用户 |
| `total` | `subtotal − shop_discount − coupon_discount + packing_fee + delivery_fee` | — |
| `pay_amount_cents` | `total × 100` | 微信实收 |

> **唯一入口原则**：`coupon_discount` 只能在 `createOrder()` 里算，接口不接受前端传金额。否则改一下请求体就能自选抵扣额。

### 5.2 三条账

| `biz_no` | `entry_type` | 金额 | 谁受益 |
|---|---|---|---|
| `delivery:{orderId}:income` | `delivery_income`（现有） | `subtotal − shop_discount + packing_fee + delivery_fee` | 商家，**不减券** |
| `delivery:{orderId}:fee` | `platform_fee`（现有） | 现有费率 | 平台 |
| `delivery:{orderId}:subsidy` | `platform_subsidy`（**新增**） | `coupon_discount` | 平台出账 |

`earnings_ledger.entry_type` 是 `VARCHAR(24)`，加枚举值不用改表；但 Java 侧的枚举与校验白名单要同步，否则新值写不进去。

### 5.3 退款（必须一起改，否则账不平）

1. 退给用户的金额 = `pay_amount_cents`（已含券抵扣，即只退实付）。`UserRefundService:96` 现有口径就是这样，**不用改**。
2. 商家 `income` 反向冲销（现有退款流程已覆盖）。
3. **平台补贴条目同步置 `void`**——不冲销的话，账本上会留下「平台为一张已退款订单补贴了 1 元」。
4. **券不退，退款后作废。** 理由：平台补贴是真实支出，退券会造成「下单 → 用券 → 退款 → 再用券」的循环套利。

### 5.4 核销三态（缺一必出事故）

| 时机 | 券状态 | 谁触发 |
|---|---|---|
| 下单成功 | `locked`（锁定，别人用不了） | `createOrder()` |
| 支付成功 | `used`（写 `used_at` + `order_id`） | `PaymentLedgerService.applyVerifiedPayment()` |
| 订单取消 / 超时关闭 | 回到 `available` | 关单任务 |

只在「下单时校验、支付时扣」会漏两个 case：下单不付款导致券被永久占用；两个订单同时锁同一张券。

### 5.5 必改的现有缺陷

| 缺陷 | 现状 | 改法 |
|---|---|---|
| `coupon.expire_at` 是字符串 | `VARCHAR(16)`，靠字典序比日期 | 改 `DATE`（或新增 `expire_on DATE`，旧列留一版兼容） |
| 过期券仍显示「可用」 | `UserService.coupons()` 无 `status`/过期过滤 | 加 `WHERE status=1 AND (expire_on IS NULL OR expire_on >= CURDATE())` |
| 个人页「N 张可用」偏大 | `profile.js:79` 直接 `coupons.length` | 同上口径，过期的不计入 |
| `discount_amount` 混用 | 店铺满减也写这里 | 拆 `shop_discount` + `coupon_discount`，否则退款页与对账分不清 |
| 券无法核销 | 无 `used_at` / `order_id` | 加 `locked_at` / `used_at` / `order_id` |
| 兑换防重模型不能照抄 | 宠物靠 `pet_item_owned` 唯一键做「一人一件」 | 券是「每人限 N 张」，必须走 `redeem_record` 计数 + 库存条件更新两条独立约束 |

| GET | `/api/points/rewards` | 登录 | 商品池 + 我的已兑次数 + 是否售罄 |
| POST | `/api/points/redeem` | 登录 | body `{itemKey}`；返回生成的券 |
| GET | `/api/users/{id}/coupons` | 本人（现有） | 券列表（只返回可用券） |
| POST | `/api/orders` | 登录本人 | 下单；body **可选 `couponId`**，抵扣额由服务端按券面额与门槛计算，客户端不能传金额 |
| GET | `/api/admin/reward-item` | 管理员 | 商品池列表 |
| PUT | `/api/admin/reward-item/{itemKey}` | 管理员 | 改价格/库存/限购/上下架 |

**`POST /api/orders` 的券字段（V3.1 结算）**

```json
{
  "shopId": 1,
  "items": [{ "goodsId": 11, "count": 2 }],
  "address": "学生公寓 6 号楼312 · 林同学",
  "contactName": "林同学",
  "contactPhone": "13800000000",
  "idempotencyKey": "co-mf3k2x9a7b1c",
  "couponId": 99101
}
```

- `couponId` 可省略；传了就必须是「本人 + status=1 + 未过期 + scope=takeout + 达到门槛」的券，否则 400 中文原因（`优惠券已使用或已失效` / `优惠券已过期` / `满 20.00 元可用` / `该券不适用于外卖订单`）。
- 返回体在原有 `orderId / total / payAmountCents / outTradeNo / payStatus` 之外带 `couponDiscount`（元）；**前端用它校准展示金额**，不允许自己算最终价。

**`POST /api/points/redeem` 事务流程**

1. 查 `reward_item`：`enabled=0` 或 `stock<=0` → 400「该商品已下架/已兑完」。
2. 查 `redeem_record` 计数 ≥ `per_user_limit` → 400「每人限兑 N 件」。
3. `UPDATE user_points SET balance = balance - ? WHERE user_id = ? AND balance >= ?`，影响行数 0 → 400「积分不足」。
4. `UPDATE reward_item SET stock = stock - 1 WHERE item_key = ? AND stock > 0`，影响行数 0 → 抛异常回滚（并发售罄）。
5. `INSERT coupon(user_id, title, amount, expire_at, status=1)` 拿到 `coupon_id`。
6. `INSERT redeem_record`。
7. `PointsService` 记一笔 `point_log(amount=-price_p, module='redeem', biz_key='redeem:'+recordId)`。

**新人礼包**（`AuthService` 建号成功后）

```
PointsService.award(userId, 'newbie_gift', 'onboard', 30, 0, '新人礼包')
INSERT user_privilege(user_id, 'tier_trial_silver', expires_at = now + 7 天)
```

`biz_key='onboard'` 保证同一个人一辈子只发一次（即使重复登录也不会重复发）。

## 八、已知限制与本期不做

- **不做积分 + 现金混合兑**：需要真实支付与商户结算，当前 `campus.pay.simulate=true`（见 `docs/真实支付接入指南-五条件.md`）。
- **不做限量稀缺池**（10% 层）：需商户赞助与预约制，无供给就不上架，避免出现"有商品但兑不到"。
- **券只在平台内订单抵扣**：外卖下单减钱；线下到店券与实物自提本期不做（见第五节）。
- **不做扫码核销**：支付成功即自动核销，不出现「出示二维码给店员扫」这一步。
- **不做退回**：兑换即消耗，文案明确不可退。
- **不做月末清仓节**：积分不清零（第 1 份文档），清仓节失去前提。
- **不进微信卡包**：券只在平台内流转，不接入微信卡券，避免卡券审核与资质问题。
- **下单页选券是本轮补的实现细节**：设计稿只规划「券在系统内抵扣」，没写用户在哪里选券；`pages/food-order` 的选券行、自动选最优、不可选原因、幂等键含券、提交后金额校准都是本轮补的（见 §2.6）。
- **选券弹层没有真正的「置灰」**：`ui-popup` 的 sheet 只渲染文字项，不支持禁用态，不可选券只能标「不可选（原因）」；要做灰显需改共享组件（本期不改）。
- **下单页只看得到可用券**：券列表接口只返回 `status=1` 且未过期的券，「已用/已过期」的券在下单选券时不可见（与个人页券区同口径）。

## 十、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 平台补贴超预算 | 券是平台真金白银出钱，被刷分兑券就是直接亏现金 | 面额严格 1:1（`value_cents = price_p`）+ 使用门槛 + 库存上限 + 每人限购；再按大表口径「月活 × 0.3–0.8 元」设月度预算告警，超支先关 `takeout_1` 高档 |
| 积分通胀 | 每天发 10P 以上，商品池消耗不掉 | 库存上限 + 每人限购 + 后续按大表公式 `月活 × 0.3–0.8 元` 设预算告警 |
| 并发超扣 | 两个请求同时扣 | 条件 `UPDATE ... WHERE balance >= ?` + 库存条件更新，两条都在事务内 |
| 与宠物衣柜双重扣分口径 | 宠物道具不属于 `reward_item` | 宠物兑换保留原路径但改调 `PointsService`，`module='pet'` 区分 |

**砍掉代价**：积分只有入口没有出口，"攒分"不成立；新人第一天拿不到任何东西，7 日首兑率目标（≥60%）直接落空。
