> 来源：`service/OrderStatus.java`（`created→paid→accepted→delivering→picked→completed`）、`service/MerchantService.java:278`（商家标记完成）、`service/JobService.java`（合约状态含 `settled` 终态）、`db/module-market-jobs-activities.sql`（`goods` 表，二手只有私聊 `contactGoods`，**无成交确认流程**）、`config` 中 `campus.pay.simulate`（模拟支付开关）。
> 编写时间：2026-11-08
> 状态：**已交付**（第六节 14 条均有自动化覆盖：13 条直接用例 + 用例 3 间接覆盖；仍存在的真实边界见交付报告第六节）
> 对应大表：**A-19 外卖点单**（10P/20G）、**A-23 二手成交**（5P/12G）、**A-24 兼职接单成功**（5P/15G）

## 一、这个功能解决什么问题

**现状（读码核实）**

| 交易类型 | 事件源 | 缺什么 |
|---|---|---|
| 外卖 | `OrderStatus.COMPLETED`，`MerchantService.complete()` 与骑手链路都会走到 | 完成后没有积分反馈 |
| 兼职 | 合约 `settled`（`JobService` 结算分支，双方确认工时后写入账单） | 结算后没有积分反馈 |
| 二手 | **只有私聊**，`contactGoods` 只记 `contact_count` | 没有"成交"这个事件，连数据都没有 |

**为什么重要**

大表第八节的闭环逻辑是：**高频任务拉留存 → 交易任务做变现 → 两者都给分互相导流**。现在交易侧完全没有积分回路，等于"逛的人"和"买的人"是两拨互不相干的人。补上之后，一个点过外卖的用户会在积分明细里看到"外卖完成 +10 积分"，从而更愿意回到首页继续逛。

> 浏览时长（原第 3 项）已删除，"拉时长"这一半的闭环改由签到连签 + 发帖评论承担；交易侧这半不受影响，独立成立。

**但二手成交是全新流程**（现在连"已成交"按钮都没有），所以这一项风险最高。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范见 `docs/v3.1/前端设计-双端总览.md`。本功能**不新增任何页面**，只在三个已有页面各加一处提示或按钮；**Web 端无改动**（后台订单页/合约页本就能看到状态）。

### 2.1 外卖订单详情 · `pages/food-order-detail`（改造）

**结构**：订单状态为 `completed` 时，页面顶部插入一条成功色提示条（`.cp-card` 变体，绿色调）：

```
订单完成，+10 积分已到账
```

- 4 秒后自动收起，或点「×」关闭；**不遮挡**下面的订单明细。
- 触发条件是接口返回 `pointsAwarded > 0`；模拟支付 / 退款订单后端返回 0，前端**不显示**这条（避免"我看到+10但明细里没有"）。

**操作步骤**：用户无需操作，订单被商家/骑手置为完成 → 用户下次进入详情页即见提示条。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 当日已满 2 单 | 不显示提示条（后端未发分） |
| 模拟支付 | 不显示 |
| 退款后 | 提示条不再出现，但已发的积分不回收（见第七节） |

### 2.2 兼职合约 · `pages/job-mine` / `pages/job-detail`（改造）

**结构**：合约 `settled` 后，合约卡片顶部一行：

```
结算完成，+5 积分已到账
```

争议中（`disputed`）不显示；转 `settled` 后再出现。

### 2.3 二手成交 · `pages/market-detail` + 我的发布（新增两步确认）

这是本期唯一需要新交互的地方。

**买家侧：`pages/market-detail` 底部按钮区**

| 按钮 | 样式 | 说明 |
|---|---|---|
| `私聊卖家` | 主按钮（现有） | 不变 |
| `我已买到` | 次按钮（新增） | 仅商品在售、且我不是卖家时显示 |

点击 → `popup.modal`：

- 标题 `确认已买到？`
- 正文 `确认后会通知卖家，需要卖家确认才算成交；成交后双方各得 5 积分`
- 按钮 `确认` / `取消`

确认成功 → 按钮变灰 `等待卖家确认`，不可重复点。

**卖家侧：`pages/profile` → 我的发布**

- 有待确认成交的商品卡右上角显示角标 `待确认成交`。
- 卡片底部出现 `确认成交` / `没有成交` 两个按钮。
- 点「确认成交」→ `popup.modal`：`确认与 XX 成交？确认后双方各得 5 积分` → `POST /api/market/trade/{id}/confirm`。
- 成功 → 商品状态变「已售出」，toast `成交成功，+5 积分`。
- 点「没有成交」→ `popup.modal` 确认 → 状态变 `cancelled`，买家侧看到「卖家未确认」。

**操作步骤（完整链路）**

1. 买家在商品详情点「我已买到」→ 发起成交（`pending`）。
2. 卖家在「我的发布」看到「待确认成交」→ 点「确认成交」。
3. 双方各 +5 积分，商品变「已售出」。
4. 若同一对用户 7 天内已成交过 → 仍可确认成交，但**不发分**，页面提示 `本次成交已完成（同一对用户 7 天内只计一次积分）`。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 商品已售/已下架 | 不显示「我已买到」 |
| 自己是卖家 | 不显示「我已买到」 |
| 已有成交记录 | 点击返回 `该商品已有成交记录` |
| 买家发起后被拒 | 商品卡角标消失，可再次发起（商品仍在售） |
| 日限 2 笔已满 | 确认成交成功但提示 `今日成交积分已满 2 笔` |

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 外卖发分时机 | 订单 `completed` 且 `pay_status=paid` | 下单即发 / 支付即发 | 下单可取消、支付可退款，只有"送达完成"是确定成交 |
| 模拟支付是否发分 | **不发**（开关 `points.award.simulated.pay=0`） | 发 | 内测期 `campus.pay.simulate=true`，谁都能点一下完成，发分等于开无限刷分口 |
| 退款是否追回 | **不追回** | 退款回滚积分 | 单笔 10P≈0.1 元，追回要处理"部分退款、积分已花掉、券已核销"等边界，复杂度远高于收益；异常情况人工扣分 |
| 兼职发分时机 | 合约 `settled` | 接单即发 / 开工即发 | 接单可能违约，开工可能争议；结算才是真实完成 |
| 有偿接单 | **本期不开放**（`job.paid.enabled=0`） | 打开 | 需资质与核验流程确认，属外部依赖；本期只有无偿岗位能结算发分 |
| 二手成交 | 新增两步确认（买家发起 → 卖家确认） | 只让卖家点"已卖出" | 单方确认可刷；双方确认才有真实成交的置信度 |
| 二手防互刷 | 同一对用户 7 天内只计 1 笔 | 不限 | 两个人互相"成交"同一件商品是最容易的刷分路径 |
| 二手是否涉及资金 | **不涉及**，纯确认 | 担保交易 | 资金托管涉及支付牌照，`docs/扩展功能规划.md` 已明确不做 |

## 四、数据表与字段

```sql
CREATE TABLE market_trade (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  goods_id   BIGINT      NOT NULL,
  buyer_id   BIGINT      NOT NULL,
  seller_id  BIGINT      NOT NULL,
  status     VARCHAR(16) NOT NULL DEFAULT 'pending' COMMENT 'pending|confirmed|cancelled',
  created_at DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  confirmed_at DATETIME  NULL,
  UNIQUE KEY uk_trade_goods (goods_id) COMMENT '一件商品只能有一笔成交',
  KEY idx_trade_pair (buyer_id, seller_id, confirmed_at)
) COMMENT='二手成交确认；不涉及资金流';

CREATE TABLE market_trade_cancel (
  id        BIGINT PRIMARY KEY AUTO_INCREMENT,
  trade_id  BIGINT NOT NULL,
  user_id   BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_cancel_trade (trade_id)
) COMMENT='撤销/拒绝记录（可选，用于审计）';
```

**任务行**：`food_order`（10P/20G，日限 2）、`job_settle`（5P/15G，日限 2）、`market_trade`（5P/12G，日限 2，双方各算一次）。

## 五、接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/market/{goodsId}/trade` | 登录（买家） | 发起成交；商品须在售、买家≠卖家 |
| POST | `/api/market/trade/{id}/confirm` | 登录（卖家） | 确认成交，双方发分 |
| POST | `/api/market/trade/{id}/cancel` | 买卖任一方 | 取消待确认的成交 |
| GET | `/api/market/{goodsId}/trade` | 登录（买家本人） | 买家刷新/重进商品页时恢复「等待卖家确认」；只回当前买家自己的成交，没有则 `data={}`（不 404） |

**埋点位置**

| 位置 | 改动 | 幂等键 |
|---|---|---|
| `MerchantService.complete()` 及骑手送达完成分支 | 事务提交后调 `PointsService.award(buyerId,'food_order','order:{orderId}',10,20)` | `order:{orderId}` |
| `JobService` 结算成功分支 | `award(workerId,'job_settle','contract:{contractId}',5,15)` | `contract:{contractId}` |
| `MarketTradeService.confirm()` | 双方各 `award(userId,'market_trade','trade:{tradeId}:{userId}',5,12)` | `trade:{id}:{uid}` |

**外卖发分的前置判断**

```
if (order.status == completed
    && "paid".equals(order.payStatus)
    && !(pay.simulated && !flags.enabledStrict("points.award.simulated.pay")))
    award(...)
```

**二手成交流程**

1. 买家 `POST /api/market/{goodsId}/trade`
   - 商品 `status=1`（在售）、`seller_id != buyerId`、无既有 `market_trade` 记录。
   - 插入 `market_trade(status='pending')`。
2. 卖家 `POST /api/market/trade/{id}/confirm`
   - 校验 `seller_id=我`、`status='pending'`。
   - 查该对用户最近 7 天内是否有 `confirmed` 记录：有 → 仍确认成交，但**不发分**（记日志）。
   - 改 `status='confirmed'`、`confirmed_at=now`；双方各发 5P/12G。
   - 商品 `status` 改为已售（复用现有商品状态字段，若没有则新增 `sold` 值）。
3. 取消：`status='cancelled'`，不发分。

## 七、已知限制与本期不做

- **有偿接单不开放**：`job.paid.enabled=0`，所以兼职任务只会对**无偿岗位**产生结算。这是刻意保持的合规状态，不是遗漏。
- **退款不追回积分**：见第三节；异常通过人工扣分处理。
- **二手不涉及资金**：没有担保、没有线上支付、没有评价；只有"成交确认"这一个动作。
- **不做二手评价**：双向评价属 V3.2（`docs/扩展功能规划.md` P2-2）。
- **不做跑腿/外卖 CPS 抽成**：变现侧不在本期。
- **不做"挂单→议价→成交"完整流程**：本期只有两步确认，聊价格仍在私聊里完成。

## 九、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 模拟支付刷分 | 内测期可无限刷 | 开关 `points.award.simulated.pay=0`，模拟支付一律不发 |
| 二手互刷 | 两人互相成交刷分 | 双方确认 + 同一对用户 7 天 1 笔 + 商品唯一成交 + 日限 2 笔 |
| 发分失败阻塞交易 | 积分服务异常导致订单完成失败 | 发分放在事务提交**之后**，失败只记日志，不影响交易主流程 |
| 兼职争议期发分 | 争议中结算 | 只在 `settled` 发分，`disputed` 不发，转 `settled` 后再发 |
| 商品无"已售"状态 | 现有 `goods` 表状态字段可能不含 `sold` | 实施时先确认字段取值；若无则补一个值并同步前端筛选 |

**砍掉代价**：交易与积分两套体系互不相干，"逛→买"的交叉导流不成立；外卖/兼职用户不会沉淀到内容侧，反之亦然。
