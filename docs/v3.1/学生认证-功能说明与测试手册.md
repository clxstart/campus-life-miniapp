## 一、这个功能解决什么问题

**现状（读码核实）**

| 事实 | 位置 |
|---|---|
| 有 `user_verification` 表，字段只有 `real_name_status` / `student_status` / `provider` / `reject_reason` / `reviewer_id` / `verified_at` | `db/module-verification.sql` |
| 用户端只有一个读接口：`GET /api/verification/me` | `VerificationController` |
| 管理端能改状态：`GET /api/admin/verifications`、`POST /api/admin/verifications/{userId}/review` | `AdminVerificationController` |
| 自助申请开关默认关闭（`verification.student.enabled=0`，备注「未接入可信核验源」） | `db/module-safety-gates.sql:12` |
| 小程序认证项显示「未开通」，点了没有页面 | `pages/profile/profile.js:23` |

**这意味着**：现在管理员可以给任意用户 id 手动点"已认证"，但**用户没有任何提交入口**——管理员怎么知道该给谁认证？只能靠线下沟通。整条链路是断的。

**不做会怎样**：没有可信身份，就谈不上"认证后能接单""认证后能建宿舍"；拉新时也没有"我是真实在校生"这个信任钩子。

## 二、前端页面与操作（小程序端 + Web 端）

> 通用规范见 `docs/v3.1/前端设计-双端总览.md`。小程序端一个入口 + 一个新页（四态）；Web 端在现有 `Verification.vue` 上改造。

### 2.1 什么时候出现（触发时机）

**结论：主动认证为主，不做「打开小程序就弹」的强制引导。**

| 触发点 | 形式 | 频率 | 说明 |
|---|---|---|---|
| 个人页菜单项 | 常驻入口 | 始终可见 | 唯一稳定入口，右侧显示真实状态 |
| 建宿舍被拦 | 点击时 `popup.modal` | 每次点 | `创建宿舍需要先完成学生认证` + 一个「去认证」按钮 |
| 接有偿岗位被拦（开关打开后） | 拦截提示 | 每次 | 复用现有闸门文案，补「去认证」按钮 |
| 首次发帖成功后 | 个人页顶部引导条 | **仅 1 次**，可关闭 | 不弹窗，不打断 |
| 新人礼包弹窗 | **不叠加** | — | 两个弹窗会互相遮挡，礼包优先，认证引导顺延 |
| 启动 / 首次进入 | **不做** | — | 见下方理由 |

**为什么不做开屏弹窗**

1. 认证不是全站硬门槛（只有建宿舍、有偿接单需要），一进来就弹，等于拿一个还没发生的需求去骚扰用户。
2. 微信审核对「强制认证 / 强制授权」敏感，开屏拦截是常见驳回点。
3. 从转化看，用户「正要建宿舍被拦住」时的认证意愿，远高于刚打开小程序时。

**用户最可能认证的三个时刻**

| 时刻 | 动机强度 | 我们给什么 |
|---|---|---|
| 建宿舍被拦 | 强 | 弹窗 + 一键去认证，认证完自动回到建宿舍 |
| 看到同学的帖子挂「已认证」标签 | 中 | 个人页菜单项常驻 + 状态真实 |
| 接有偿单被拦（`job.paid.enabled` 打开后） | 强 | 拦截提示 + 一键去认证 |

**明确不做**：开屏全屏引导页、登录后立即拦截、连续多次弹窗、「跳过认证继续」的假按钮。

### 2.2 小程序端 · `pages/profile/profile` 菜单项（改造）

| 状态 | 右侧 value | 点击 |
|---|---|---|
| `none` | `未认证` | 进 `pages/verify` 填表 |
| `pending` | `审核中` | 进 `pages/verify` 看进度（表单只读） |
| `verified` | `已认证` | 进 `pages/verify` 看已通过信息 |
| `rejected` | `认证未通过` | 进 `pages/verify` 看原因并可重提 |

当前 `pages/profile/profile.js:23` 写死的「未开通」要删掉，改成读 `/api/verification/me` 的 `label`（该接口与字段已存在）。

### 2.3 小程序端 · `pages/verify`（新页，四态同一页面）

**态 1：未提交（表单）**

| 字段 | 控件 | 校验 | 错误提示 |
|---|---|---|---|
| 学校 | `picker`，数据取 `GET /api/schools` | 必选 | `请选择学校` |
| 学院 | 输入框 | 默认选填；填了要 2–32 字 | `请填写学院` |
| 真实姓名 | 输入框 | 2–20 字，中文/字母/· | `请填写真实姓名` |
| 学号 | 输入框 | 4–20 位数字/字母 | `学号格式不正确` |
| 手机号 | 输入框 | 默认选填；打开 `require.phone` 后必填；11 位、1 开头 | `请填写手机号` / `手机号格式不正确` |
| 底部 | 主按钮「提交认证」 | 必填项齐全才可点 | — |

> 上表是「五项全开」时的样子。实际渲染按 `GET /api/verification/config` 的 `require` 来，被关掉的项不显示也不要求必填；默认只有姓名和学号必填，**学院、手机号选填**。

表单下方一张 `.cp-card` 说明：「我们只保存姓名、学号、学院、手机号，用于人工核对，**不采集证件照片**」。

**态 2：审核中**

状态卡（黄色调）：`认证审核中` + `提交时间 11-08 21:30` + 只读回显已填字段（手机号展示为 `138****1234`）+ 说明「1–2 个工作日内人工核对，结果会通过站内消息通知你」。

**态 3：已认证**

状态卡（绿色调）：`已认证` + `通过时间` + 回显已填字段（手机号脱敏）。底部一行 `.cp-hint`：「认证用于身份标识；有偿接单开放时间另行通知」（因为 `job.paid.enabled=0`，必须提前说清）。

**态 4：已驳回**

状态卡（红色调）：`认证未通过` + 驳回原因（`rejectReason`）+ 按钮「修改并重新提交」，点后回到态 1 并带出上次填写值（手机号需重新输入明文——`/me` 只下发脱敏值，回填脱敏值再提交会被判格式错误）。

**操作步骤**

1. 从个人页点认证项 → 进页面 → 先拉 `/me` 决定渲染哪一态（不做「先显示表单再切换」的闪烁）。
2. 态 1 填写 → 提交按钮 `disabled` + 「提交中…」→ `POST /api/verification/apply`。
3. 成功 → 就地切到态 2，`popup.toast('已提交，等待审核', { tone: 'success' })`。
4. 失败（400）→ 在对应字段下方显示行内错误，不弹窗。

**状态与边界**

| 情况 | 表现 |
|---|---|
| 开关关闭 | 整页替换为说明卡「认证申请暂未开放」 |
| 当日超 3 次 | toast `今天提交次数过多，请明天再试` |
| 重复提交（审核中） | 按钮不可点 |
| 未登录 | 401 → 跳登录 |

### 2.4 Web 端 · `views/Verification.vue`（改造）

**新增列**：学校、学院、姓名、学号、提交时间。

**新增筛选**：状态下拉（现有）+ 学校下拉 + 关键字搜索（姓名/学号）。

## 三、设计取舍

| 决策 | 选了 | 没选 | 为什么 |
|---|---|---|---|
| 认证来源 | 人工审核（`provider='manual_admin'`） | 接学信网/学校接口 | 各校无公开接口，且需要资质；人工抽查是当下唯一可信且可落地的来源 |
| 材料形式 | 纯文本（学校/学院/姓名/学号） | 上传学生证照片 | 你已确认不传照片；少一类敏感数据，隐私声明与存储风险都大幅降低 |
| 照片缺失的可信度 | 靠"抽查"：随机抽一部分联系本人/学院核实 | 靠学号规则校验 | 学号规则各校不同，本地校验只能防乱填，防不了冒用 |
| 状态机 | 复用现有四态 `none/pending/verified/rejected`，实名与学生两个维度各一套 | 新建一套状态 | 现有表和后台页已经在用，扩展字段比新建表便宜 |
| 实名维度 | 与学号一并提交，一起审核 | 先做学生、后做实名 | 只有学生认证没实名认证时，`verified` 恒为 false（现有实现要求两者都 verified），拆开反而绕 |
| 开关 | 打开 `verification.student.enabled=1` | 保持关闭 | 这正是本期要的；但保留开关，出现冒用泛滥可一键关停 |
| 限频 | 每人每天最多提交 3 次 | 不限 | 防止用不同学号暴力试探 |
| 配置化粒度 | 平台一套，存 `app_config`，后台可改必填项与审核方式 | 每校一套 JSON / 后台动态加字段 | 现在只有一所学校，一套规则就够；`app_config` 已有 30 秒缓存与写后失效，改完立即生效；多校时只换数据源，接口结构不变。动态字段会把小程序表单、Web 审核页、存储、查询四处都变成通用渲染器，成本远超收益 |

## 四、可配置项（平台统一配置）

**结论：认证「要填什么、怎么审」由后台配置，平台一套，不做每校一套。**

**为什么放 `app_config` 而不是 `school.verify_config`**

1. 现在只有一所学校，就是一套规则，没必要为一所学校的差异先建数据模型。
2. `AppConfigService` 已有 30 秒本地缓存 + 写后主动失效，改完立即生效，不用重启服务。
3. 将来多校时迁移便宜：键名不变，只把数据源从「全局一行」换成 `school.verify_config`，`GET /api/verification/config` 的返回结构一个字都不用改。

**配置项分工**

| 配置项 | 存放 | 谁能改 | 决定什么 |
|---|---|---|---|
| 平台总闸 | `feature_flag`：`verification.student.enabled`（已存在，默认 0） | 超管 | 整个申请入口开不开放 |
| 认证细则 | `app_config`，`verification.*` 前缀 | 超管 | 下表 7 个键 |

| `config_key` | 默认值 | 含义 | 合法值 |
|---|---|---|---|
| `verification.require.real_name` | `1` | 真实姓名必填 | `0` / `1` |
| `verification.require.student_no` | `1` | 学号必填 | `0` / `1` |
| `verification.require.college` | `0` | 学院必填 | `0` / `1` |
| `verification.require.phone` | `0` | 手机号必填（**已生效**：开启后提交必填；填写即校验 11 位、1 开头；接口只下发脱敏值） | `0` / `1` |
| `verification.student_no_pattern` | `^(20[0-9]{2})[0-9]{6,10}$` | 学号正则（`auto` 判定 + 前端格式提示） | 空 或 可编译的正则 |
| `verification.review_mode` | `manual` | `manual`=全部人工审；`auto`=正则命中直接通过 | `manual` / `auto` |
| `verification.daily_limit` | `3` | 每人每天提交上限 | `1`–`10`（越界截断） |

> 学院默认**选填**：你定的材料是「学校 + 学号 + 姓名」三项。学院打开必填后，抽查才有「学号与学院是否匹配」这条判断依据，建议上线一周后视驳回率再决定要不要打开。
>
> 手机号默认**选填**，且已全链路生效（V3.1 收尾补齐）：新增 `user_verification.phone` 列（`module-verification-v31.sql` 用 INFORMATION_SCHEMA 预查 + PREPARE，幂等可重复执行），存原文供审核联系；开启必填后空值拒绝（「请填写手机号」）、填写则校验 11 位且 1 开头（「手机号格式不正确」）；`GET /me` 与后台列表统一脱敏为 `138****1234`。开启必填前先确认审核员确实需要电话联系，否则多收一项个人信息。
>
> `verification.student.enabled`（开不开）与 `verification.review_mode`（开了怎么审）是两个层级，不要混用。

**三条铁律**（都是「配置组合出来的漏洞」，不写清楚上线必踩）

1. **空正则 + `auto` = 谁都能过。** 判定规则：`review_mode=auto` 必须同时满足「正则非空」且「能编译通过」，否则强制回落 `manual`，并记一条 `warn` 日志。系统不允许被配置成「任何学号都通过」。
2. **配置改严不追溯。** 已 `verified` 的记录**永不在读时按新配置重新校验**——`status()` 只读状态列，不读配置。改配置只影响新提交。否则把「学院」从选填改成必填，全体老用户会突然显示「认证未通过」。
3. **平台一套 ≠ 永远一套。** `auto` 模式只适合当前单校阶段；第二所学校进来时学号规则必然冲突，届时要么迁到 `school.verify_config`，要么关掉 `auto` 全走人工。这句话要写进 `verification.review_mode` 的 `remark`，别让后人靠翻代码猜。

**种子 SQL**（新建 `backend/src/main/resources/db/module-app-config-verification.sql`，幂等）

```sql
INSERT INTO app_config (config_key, config_value, remark) VALUES
  ('verification.require.real_name',  '1', '真实姓名是否必填：1=必填 0=选填'),
  ('verification.require.student_no', '1', '学号是否必填：1=必填 0=选填'),
  ('verification.require.college',    '0', '学院是否必填：1=必填 0=选填'),
  ('verification.require.phone',      '0', '手机号是否必填：1=必填 0=选填'),
  ('verification.student_no_pattern', '^(20[0-9]{2})[0-9]{6,10}$', '学号正则；为空时禁止 auto 模式'),
  ('verification.review_mode',        'manual', 'manual=全部人工审核；auto=正则命中直接通过（仅单校阶段可用）'),
  ('verification.daily_limit',        '3', '每人每天最多提交次数（1-10）')
ON DUPLICATE KEY UPDATE config_key = config_key;
```

**必须同时补的一个权限洞**

`AppConfigController` 现在**没有任何角色校验**：`AdminInterceptor` 只要求 `super` 或 `school` 身份，所以**校管也能写全局 `app_config`**。以前这里只有二维码和文案，校管误改后果有限；一旦装上「学号正则」和「审核方式」，任何一个校管都能改掉全平台的认证规则。

修法：在 `AppConfigController.save()` 与 `list()` 上加 `super` 角色校验（照抄 `AdminFeatureFlagController:45` 的写法）。平台级配置不该给校管改——注意 Web 路由上的 `meta.superOnly` 只是前端隐藏，后端必须自己拦。

**加新配置项的真实成本**：`AppConfigService.WRITABLE_KEYS` 是 Java 硬编码白名单，加键要同时改 SQL、Java 白名单、前端配置卡片三处。别指望运营在后台自助加字段。

**读取接口**

`GET /api/verification/config`（公开，不登录也能读，用于渲染表单）

```json
{
  "enabled": true,
  "require": { "realName": true, "studentNo": true, "college": false, "phone": false },
  "studentNoPattern": "^(20[0-9]{2})[0-9]{6,10}$",
  "reviewMode": "manual",
  "dailyLimit": 3
}
```

小程序 `pages/verify` 按 `require` 决定渲染哪几个输入框，**不写死四个**；`studentNoPattern` 前端只做即时格式提示，最终判定仍以后端为准（前端正则是体验，不是校验）。

**配置界面**：`views/Verification.vue` 顶部加一张「认证规则」卡片（4 个开关 + 正则输入 + 审核方式下拉 + 每日次数），保存走 `PUT /api/admin/app-config`，仅 `super` 可见。

## 五、数据表与字段

```sql
ALTER TABLE user_verification ADD COLUMN school_id    BIGINT       NULL;
ALTER TABLE user_verification ADD COLUMN college      VARCHAR(64)  NOT NULL DEFAULT '';
ALTER TABLE user_verification ADD COLUMN real_name    VARCHAR(32)  NOT NULL DEFAULT '';
ALTER TABLE user_verification ADD COLUMN student_no   VARCHAR(32)  NOT NULL DEFAULT '';
ALTER TABLE user_verification ADD COLUMN phone        VARCHAR(20)  NOT NULL DEFAULT '' COMMENT '核对用手机号（接口下发时脱敏）';
ALTER TABLE user_verification ADD COLUMN submitted_at DATETIME     NULL;
ALTER TABLE user_verification ADD COLUMN source       VARCHAR(16)  NOT NULL DEFAULT 'self' COMMENT 'self=用户提交，admin=管理员直接核验';

```

> 原表注释「不保存证件号、证件影像等原始材料」仍然成立：**学号不是证件号**，姓名、学院与手机号是审核必需的核对信息；证件影像依然不存。手机号原文只落库供审核联系，所有接口只下发脱敏值（`138****1234`）。

**状态约定（沿用现有）**

| 状态 | 含义 | 用户可见文案 |
|---|---|---|
| `none` | 未提交 | 未认证 |
| `pending` | 已提交待审 | 审核中 |
| `verified` | 通过 | 已认证 |
| `rejected` | 驳回 | 认证未通过（附原因） |

`verified` 的判定沿用 `VerificationService.status()`：**实名与学生都为 verified** 才算已认证。

## 六、接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/verification/apply` | 登录本人 | 提交认证：`{schoolId, college, realName, studentNo, phone}` |
| GET | `/api/verification/me` | 登录本人 | 现有，补返回 `schoolId/college/realName/studentNo/phone(脱敏)/submittedAt/source` |
| GET | `/api/verification/config` | 公开 | 认证配置，供表单动态渲染（见第四节） |
| GET | `/api/admin/verifications?status=` | 管理员 | 现有，补返回学校名、学院、姓名、学号、手机号（脱敏） |
| POST | `/api/admin/verifications/{userId}/review` | 管理员 | 现有，通过/驳回 |
| PUT | `/api/admin/app-config` | **超管** | 现有接口，扩展 `verification.*` 白名单；**需补 `super` 角色校验** |

**`POST /api/verification/apply` 校验**

| 字段 | 规则 | 失败提示 |
|---|---|---|
| `schoolId` | 必须存在于 `school` 表 | 请选择学校 |
| `college` | 2–32 字 | 请填写学院 |
| `realName` | 2–20 字，只含中文/字母/· | 请填写真实姓名 |
| `studentNo` | 4–20 位，数字/字母 | 学号格式不正确 |
| `phone` | 默认选填；开启 `require.phone` 后必填；11 位、1 开头 | 请填写手机号 / 手机号格式不正确 |
| 频率 | 当日提交 ≤3 次（`user_verification.updated_at` 或独立计数） | 今天提交次数过多，请明天再试 |
| 当前状态 | `pending` 不允许重复提交 | 正在审核中，请耐心等待 |
| 开关 | `verification.student.enabled=1` | 认证申请暂未开放 |

> 上表是五项全开时的校验口径。`verification.require.*` 关掉的字段**不要求非空**；但用户填了仍会校验格式（填了就要能存），与学院语义一致。手机号落库为原文，任何接口下发前统一脱敏（`138****1234`）。

**提交后**：写 `real_name_status='pending'`、`student_status='pending'`、`provider='manual_admin'`、`source='self'`、`submitted_at=now`；清空旧 `reject_reason`。

**管理端抽查建议**（写进 `Verification.vue` 说明文案）

1. 学号与学院是否明显不匹配（如文学院学号前缀是 01 而填了 03）。
2. 同一学院/学号段短时间内大量提交 → 重点核。
3. 随机抽 10% 通过「用户主页 → 私聊」联系本人确认。

## 八、已知限制与本期不做

- **不接学信网/学校接口**：无公开接口与资质，人工抽查是唯一来源。
- **不存证件影像**：连此项能力都不开放，隐私面最小。
- **不发学生证照片上传入口**：未来若要做，需要先补隐私声明、私有存储与过期清理。
- **认证不等于能接有偿单**：`job.paid.enabled` 仍为 0，认证只是"人可信"，平台侧"有偿接单"仍关闭。**这一点必须对用户如实说明**，否则会出现"我认证了怎么还是不能接单"的投诉。
- **不做认证透传到列表**：帖子/评论/二手列表的作者认证标签属第二版（要给各列表 DTO 加字段，注意 N+1）。
- **不做拉新奖励**：你已确认第一版不做邀请码，认证本期只提升可信度与解锁后续能力。
- **不做"校园卡拍卡认证"**：同上，涉及证件影像。

## 十、风险与被砍代价

| 风险 | 说明 | 处理 |
|---|---|---|
| 冒用他人学号 | 无照片核验时，填别人的学号也能过（如果管理员不抽查） | 限频 + 抽查 + 学号与学院一致性检查；出现集中冒用可一键关开关 |
| 管理员工作量大 | 每份申请都要人看 | 只做"抽查"不做"全量核对"，后台支持按学院/学号段排序批量看 |
| 认证 ≠ 可用 | 用户以为认证就能接单，实际 `job.paid.enabled=0` | 认证页与通过后的提示都写明「认证用于身份标识；有偿接单开放时间另行通知」 |
| 校管越权 | 跨校审核 | 现有 `VerificationService.review()` 已带 `scopeSchoolId` 校验，沿用 |
| 隐私争议 | 收姓名/学号是否过度 | 字段最小化、不存影像、隐私声明明示；用户可申请删除（注销时随账号删除） |
| 配置误改放大风险 | 平台一套配置，改错影响所有学校的申请；正则为空 + auto 更是「谁都能过」 | 三条铁律落到代码（空正则禁 auto / 改严不追溯 / 越界截断），写操作限 `super`，改动记操作日志 |

**砍掉代价**：没有可信身份，宿舍域（第 9 份文档）无法开工；拉新缺少信任钩子；管理端继续只能靠线下沟通给用户点认证。
