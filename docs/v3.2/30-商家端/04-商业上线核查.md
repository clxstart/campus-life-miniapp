## 二、资金与对账

**结论：不通过（原因：平台代收货款但没有向商家结算的任何能力，也没有对账）。**

| 项 | 现状 | 证据 |
|---|---|---|
| 学生付款流向 | 全部进平台商户号（单一商户号代收） | `backend/src/main/java/com/campuslife/service/MerchantRefundService.java:49-62`（退款用同一商户号原路退回，说明收款也是同一个） |
| 分账 | **无**。没有分账接收方、没有分账指令 | 全库无 `profit_sharing`/`receiver` 相关代码 |
| 商家结算单 | **无**。商家后台 4 个页签里没有"收入" | `web/src/layouts/MerchantLayout.vue:36` |
| 商家对账单 | **无** | 同上 |
| 提现/打款 | **无**。`wallet.enabled=0` | `backend/src/main/resources/db/module-safety-gates.sql:7` |
| 佣金计提 | **无**。商家域没有费率字段 | `module-merchant.sql:44-64`；对照兼职域 `module-jobs-marketplace.sql:66-77` |
| 平台收入可见性 | **无**。管理端没有"平台佣金收入"页 | 管理端路由清单（`web/src/router/index.js:22-60`）无对应项 |
| 拒单退款 | ✅ 有（先建本地退款单再异步提交渠道） | `MerchantService.java:236-252`、`MerchantRefundService.java:24-76` |
| 退款失败处理 | 🟠 标 `failed` 后无重试、无告警 | `MerchantRefundService.java:30-33`（见 30-09） |

**结论展开**：本域是目前全仓库里"钱最多、账最少"的一段。学生下单付的是真钱（微信支付），商家拿到的却是"营业额数字"。在没有分账能力的前提下，唯一可行的补救是"周期结算单 + 线下打款登记"，而这条路径需要：①按订单明细汇总应结金额；②扣除平台佣金（当前连佣金率都没有）；③登记打款凭证；④商家可查看与申诉。这是一条完整的功能，不是补一个字段。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：先备份；`shop` 是核心大表，加列需评估锁表）。**

### 4.1 脚本内容与顺序

| 顺序 | 脚本 | 内容 | 依赖 |
|---|---|---|---|
| 1 | `backend/src/main/resources/db/module-food.sql` | `shop_goods` / `user_order` 建表（商家端全靠它们） | 无 |
| 2 | `backend/src/main/resources/db/module-merchant.sql` | `admin_user` 加 `shop_id`；`shop` 加 8 列；建 `merchant_apply`、`refund_record` | 第 1 步 |
| 3 | `backend/src/main/resources/db/module-safety-gates.sql` | `wallet.enabled=0`（结算前置条件） | `feature_flag` 表 |
| 4 | 支付配置（非 SQL） | `campus.pay.*`、退款回调 URL、证书 | 商户号 |

> 顺序依据：`module-merchant.sql:10-42` 对 `shop` 加列、`:66-77` 建 `refund_record`，而 `refund_record` 依赖 `user_order`（第 1 步）。本顺序**未实际执行验证**（推测）。

### 4.2 幂等性

- 加列前全部查 `information_schema`（`module-merchant.sql:4-42`）。
- 建表 `CREATE TABLE IF NOT EXISTS`（`:44`、`:66`）。
- 可重复执行，不会覆盖已有数据（无 `UPDATE` 回填，这一点比兼职域简单也更安全）。

### 4.3 回滚

**⚠️ 没有回滚脚本。** 手写如下（仅试运行环境）：

```sql
-- 回滚（先 dump；生产禁止删表，只能停用）
DROP TABLE IF EXISTS refund_record;
DROP TABLE IF EXISTS merchant_apply;
ALTER TABLE shop
  DROP COLUMN contact_phone, DROP COLUMN address, DROP COLUMN owner_name, DROP COLUMN intro,
  DROP COLUMN open_time, DROP COLUMN close_time, DROP COLUMN is_open;
ALTER TABLE admin_user DROP COLUMN shop_id;
-- 商家账号：停用而非删除
UPDATE admin_user SET status=0, token_version=token_version+1 WHERE role='merchant';
```

**风险**：`admin_user.shop_id` 一旦回滚，商家账号全部变成"未绑定店铺"，登录即被拦截器拒绝（`AdminInterceptor.java:80-83`）——这反而是安全的降级。`shop` 撤列会丢营业时间与打烊状态（学生侧"是否可下单"立刻失真）。因此生产回滚只做"停商家账号 + 关店铺 status"。

## 九、结论

**不可上线。** 阻断项：**30-01**（商家零结算能力，平台代收货款但商家拿不到钱）、**30-02**（餐饮资质与入驻协议字段缺失，合规无法自证）。

补充判断：30-02 是"审核不通过"级别的合规缺口——在校园场景里食品安全是监管重点，只有营业执照不足以支撑"平台代商家收款卖饭"这件事。30-01 是商业闭环问题——商家入驻后第一个问题就是"钱怎么给我"，当前没有答案。

若平台愿意以"纯 SaaS 工具（只做撮合与订单，不做代收）"上线，则 30-01 可降级；但那等于要改造支付链路（学生直接付商家），工作量远大于补一个结算页。
