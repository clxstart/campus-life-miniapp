## 一、设计优点（为什么这么设计，好在哪）

### 1.1 身份与店铺的绑定放在 token 里，且每请求复核

商家所有接口都不接受 `shopId` 参数，一律取拦截器从 JWT 解析后写入的属性（`backend/src/main/java/com/campuslife/controller/MerchantController.java:103-105`）。更关键的是每个请求都回查库，比对 `role/schoolId/shopId/tokenVersion`（`backend/src/main/java/com/campuslife/config/AdminTokenGuard.java:49-56`）——**平台把商家换绑到别的店、把账号停用，旧 token 下一条请求就废**。这直接封死了"越权看别家订单"最常见的那条路（改 token 里的 shopId、或留着旧 token 继续用）。实测读码结论：商家 A 拿 B 的订单 id 调 `accept`，`order(id, shopId)` 命中 0 行 → 「订单不存在」（`MerchantService.java:306-310`、`MerchantMapper.java:156-157`）。

### 1.2 审核通过是"一个事务里做完五件事"

锁申请行（`SELECT … FOR UPDATE`）、校验仍是 pending、建店、建账号、回写状态带 `status='pending'` 条件（`MerchantService.java:87-111`）。任何一步失败整体回滚，**不会出现"店建好了但申请还是待审核"或"账号建了但没店"的孤儿数据**。回写那一步的条件 UPDATE 是点睛之笔：它同时兼作并发保护。

### 1.3 一次性密码 + 强制改密

商家初始密码随机生成、只返回一次、库里 `must_change_password=1`，且服务端在拦截器里强制"未改密不能访问任何业务接口"（`MerchantService.java:104-106`、`AdminInterceptor.java:68-72`）。这比"手机号后六位当默认密码"安全一个数量级，也解释了为什么用户名用 `m`+后 8 位而不是手机号本身（`MerchantService.java:100-103`）。

### 1.4 私有证件图的处理是完整的

营业执照走 `/private/` 私有路径 + 审核时按需读取 + 路径正则白名单 + `Cache-Control: no-store` + 走存储适配层（本机目录/对象存储都能跑）（`MerchantAuditController.java:27`、`:49`、`:50-57`）。这套做法可以直接复用给其他证件场景（例如学生认证、骑手证件）。

### 1.5 退款"不配置就不假装成功"

`properties.isEnabled()` 为假时明确标 `failed` 并写「微信退款未配置，需平台人工处理」（`backend/src/main/java/com/campuslife/service/MerchantRefundService.java:30-33`）。渠道调用异常时不直接判失败，而是先查单，查不到才保持 `pending`（`:66-75`）。`success` 是终态不可覆盖（`MerchantMapper.java:178-180`）。**"不确定就保持 pending"** 是资金类集成里最该有的态度。

### 1.6 退款单号确定性 + 唯一键

`out_refund_no = "MR" + orderId`，配合 `uk_refund_order(order_id)` 唯一键（`MerchantService.java:237`、`module-merchant.sql:75`）——商家手抖连点三次拒单，也只会有一条退款记录。

### 1.7 商家不能替骑手完成订单

`complete` 检查 `rider_id` 非空就拒绝（`MerchantService.java:274-280`），并给出准确文案。这条约束防止了骑手侧在途列表与订单状态不一致——这是派单/配送域最容易被破坏的不变量。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 商家收不到钱

这是本域最根本的缺陷。平台用单一商户号代收学生付款，商家侧**没有分账、没有结算单、没有对账单、没有提现**。四个页签里没有"收入"（`web/src/layouts/MerchantLayout.vue:36`），首页只有一个"今日营业额"（`MerchantMapper.java:132-133`），连"这个月平台该给我多少钱"都查不到。商家入驻后第一次提问必然是"钱什么时候到"。

### 2.2 资质字段撑不起一家餐饮店

`merchant_apply` 只有 `license_no` + `license_image`（`module-merchant.sql:52-53`）。缺的：食品经营许可证、证照有效期、法人身份证、门店租赁合同、入驻协议签署、佣金费率确认。食品安全是校园场景的高压线，只有营业执照是不足以开店的。

### 2.3 入驻入口零防护

`/api/merchant/apply` 免鉴权（`AdminInterceptor.java:28`）、无验证码、无限流、无去重，表上也没有唯一键（`module-merchant.sql:44-64`）。任何人可以脚本灌 10 万条申请把审核台刷爆；同一主体重复通过还会建出多个店铺和多套账号（`MerchantService.java:100-111`）。

### 2.4 商家能单方面决定骑手的收入

配送费由商家在店铺设置里自己填（`MerchantService.java:149`），没有上下限审核（`amount()` 只挡负数与 999999.99，`:337-341`），而骑手配送报酬直接取 `delivery_fee`（`backend/src/main/java/com/campuslife/mapper/DispatchMapper.java:46`）。商家把配送费设成 0.01 元，骑手这一单就白跑；设成 99 元，学生被狠宰。平台两头都没有护栏。

### 2.5 接单之后就没有退路了

`cancelOrder` 的条件只有 `status='paid'`（`MerchantMapper.java:162-163`），所以拒单只能在接单前。接了单之后发现食材没了、灶坏了、排队 40 分钟，商家没有任何操作能做——只能硬做，或者线下联系学生让他自己申请退款。这是缺能力，不是刻意约束（代码里没有任何注释解释为什么）。

### 2.6 商家账号是"一次性的"

账号建好之后：不能停用（违规商家封不掉）、不能重置密码（忘了只能改库）、不能换绑店铺（换法人/换店无路径）。对照骑手域有完整的 4 个接口（`RiderAdminController.java:25-83`），商家域一个都没有。

### 2.7 审核动作没有进统一审计

兼职域的审核/改费率/裁定都写 `admin_auth` 审计（`backend/src/main/java/com/campuslife/service/JobService.java:1063-1067`），商家审核只写了 `merchant_apply.audit_by/audit_at`（`module-merchant.sql:58-59`）。"谁批准了这家店、当时看的是什么材料"查不到完整链路，而开店+建账号是本系统里权限最大的一次性动作。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 好处 | 代价 | 本仓库是否选了 |
|---|---|---|---|
| A. 商家独立账号表 | 语义干净 | 要重写鉴权/令牌/改密全链路 | **没选**，复用 `admin_user` + `AdminInterceptor` + `AdminTokenGuard` |
| B. 商家注册后自动通过 | 转化率高 | 无法核验证照，校园餐饮风险大 | **没选**，必须人工审核（`MerchantService.approve`） |
| C. 商家自填手机号当账号 | 好记 | 手机号可被猜、形成事实默认密码 | **没选**，`m`+后 8 位 + 随机密码（`:100-106`） |
| D. 营业执照走公开 `/uploads/` | 简单 | 证件图可被任意人扫到 | **没选**，强制 `/private/` + 鉴权读取（`:45-46`、`MerchantAuditController.java:45-59`） |
| E. 平台代收 + 微信分账 | 商家能自动到账 | 需商户号与分账能力书面确认（方案 §6.4） | **未落地**：当前只有代收，没有分账 |
| F. 商家自定配送费（现状） | 灵活、可按距离定价 | 无护栏，能挤压骑手收入或转嫁学生 | **选了 F**，护栏缺失 |
| G. 拒单直接调渠道、失败就报错 | 实现简单 | 渠道抖动会把"商家拒单"变成"拒单失败" | **没选**，先建本地退款单再异步提交（`:236-252`） |

## 五、如果重做会怎么改

1. **先回答"钱怎么给商家"，再写商家端。** 现在的商家端是一个"能改菜、能接单，但收不到钱"的后台。若确定走分账，就把分账接进 `approve`（建店时同时建分账接收方）；若只能线下结算，就必须有"周期结算单"这个页面，否则商家端没有存在意义。
2. **入驻表单按"证照清单"设计，而不是按"字段数量"设计。** 用一张 `merchant_license` 子表（类型/编号/图片/有效期/审核状态），营业执照只是其中一种。这样加"食品经营许可证""酒类许可"都不用改表。
3. **审核动作接进统一审计。** 开店+建号是权限最大的一次性动作，必须和兼职域的删单/裁定一样进 `admin_auth`。
4. **商家能改的东西要有护栏。** 配送费、起送价、满减都直接影响学生实付与骑手收入，应该走"平台给区间、商家在区间内选"，而不是"商家想填多少填多少"。
5. **补一条"接单后取消"的合法路径。** 现实里商家一定会在接单后才发现做不了。现在的设计让商家只能硬做或私聊学生，这是把系统问题推给人。
6. **账号生命周期补齐。** 建号只是开始，停用/改密/换绑/注销四件事都要有，且都要 `token_version+1`。
