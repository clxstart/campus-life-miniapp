## 一、这个功能解决什么问题

让校内的餐饮商家能**自己管店**：提交入驻申请 → 平台审核建店建号 → 商家登录后改店铺信息、上架菜品、接单/拒单/完成、看今日经营数据。

它由三段组成，三段的入口完全不同：

| 段 | 谁用 | 入口 | 鉴权 |
|---|---|---|---|
| 入驻申请 | 未登录的商家（公开页） | Web `#/merchant/apply` | **免鉴权**（白名单放行） |
| 入驻审核 | 校管 / 超管 | Web `#/merchant-audit` | 管理端 JWT（`super|school`） |
| 商家经营 | 商家账号（`admin_user.role='merchant'`） | Web `#/merchant/**`（4 页） | 管理端 JWT（`role=merchant` + `shopId`） |

**商家账号不是小程序用户**。它和骑手一样，是 `admin_user` 表里的一行：`role='merchant'`、`shop_id` 指向自己的店（`backend/src/main/resources/db/module-merchant.sql:4-7`、`backend/src/main/java/com/campuslife/mapper/MerchantMapper.java:78`）。所以商家登录用的是管理端登录接口，只是角色不同。

`app.json` 内**没有**任何商家页面——小程序端完全没有商家端，商家必须用 Web。

## 二、用户看到的样子（小程序端）

### 2.1 学生侧：只看到"店"，看不到"商家后台"

学生看到的是外卖域的东西：店铺列表、菜单、下单、订单详情（`backend/src/main/java/com/campuslife/controller/BizController.java:33-42`）。商家端的任何能力都不在小程序暴露。

有一处能间接感受到商家：订单详情的 `shopName`、商家联系方式（`PayService.detail` 里 `shopName`，`backend/src/main/java/com/campuslife/service/PayService.java:247-248`）。但这属于外卖域，不属于商家端。

### 2.2 商家侧：小程序零入口

`app.json` 注册的 47 个页面中没有商家相关页面（`grep -n "merchant" app.json` 无命中）。商家**无法在小程序上接单**——高峰期的出餐窗口工作人员只能用电脑或手机浏览器开 Web。

### 2.3 入驻申请页（Web 上的公开页）

路径 `#/merchant/apply`，路由 `meta.public: true`（`web/src/router/index.js:7`）。这是全站唯一不需要登录的业务页。

表单 9 个字段（`web/src/views/MerchantApply.vue:108`）：店铺名称、经营分类、所属学校、联系人、联系电话（11 位手机号）、店铺地址、营业执照号、营业执照照片、店面照片，另有选填简介（≤300 字）。

两张图的存储路径不同、校验也不同：

- **营业执照**走私有上传 `POST /api/admin/upload/private`，返回 `/private/<32位hex>.<ext>`（`web/src/views/MerchantApply.vue:134`、`backend/src/main/java/com/campuslife/service/MerchantService.java:45-46`）；
- **店面照片**走公开上传 `POST /upload`（`MerchantApply.vue:134`、`MerchantService.java:47-50`）。

提交成功后展示"申请已提交"，不返回任何账号信息（账号要等审核通过才创建）。

## 三、运营看到的样子（Web 端）

### 3.1 入驻审核（`#/merchant-audit`）

`web/src/views/MerchantAudit.vue`（133 行）+ `MerchantAuditController`（5 个接口）。

- 三个页签：待审核 / 已通过 / 已拒绝，带计数（`MerchantAudit.vue:71`）。
- 列表可按状态筛选、看学校、看联系人（`MerchantAudit.vue:27`）。
- 点"查看"开详情：分类、学校、联系人、电话、地址、营业执照号、简介（`MerchantAudit.vue:39`）。

- "拒绝"→ 必填原因（≤200 字）（`MerchantService.java:115-122`）。

### 3.2 商家后台（`#/merchant/**`，4 页）

四个页签由 `MerchantLayout.vue` 定义（`web/src/layouts/MerchantLayout.vue:36`）：首页 / 店铺设置 / 菜品管理 / 订单管理。

| 页面 | 内容 | 证据 |
|---|---|---|
| 首页 | 今日订单数、今日营业额、待接单数、店铺卡片 | `web/src/views/merchant/Home.vue`、`MerchantService.dashboard:124-130` |

### 3.3 店铺管理（管理后台 `#/shops`）

## 五、数据表与字段

### 5.1 `merchant_apply`（入驻申请）

`backend/src/main/resources/db/module-merchant.sql:44-64`：

| 字段 | 说明 |
|---|---|
| `shop_name` / `category` / `contact_name` / `contact_phone` / `address` | 店铺与联系人基本信息 |
| `school_id` | 所属学校（审核后建店的落点） |
| `license_no` / `license_image` | 营业执照号与私有图路径 |
| `shop_image` | 店面照片（公开路径） |
| `intro` | 简介 ≤300 |
| `status` | `pending|approved|rejected`（`:56`） |
| `reject_reason` / `audit_by` / `audit_at` / `created_shop_id` | 审核留痕 + 建成后的店铺 id |

**约束缺口**：只有 `idx_merchant_apply_status`、`idx_merchant_apply_school` 两个普通索引（`:62-63`），**没有** `contact_phone` 或 `(school_id, shop_name)` 唯一键 → 同一主体可无限重复申请（见 30-03）。

### 5.2 `admin_user.role='merchant'` + `shop_id`（商家账号）

`module-merchant.sql:4-7` 给 `admin_user` 加 `shop_id`。账号由审核通过时创建（`MerchantMapper.java:78-80`）：

- `role='merchant'`、`shop_id`=新店 id、`must_change_password=1`、`credential_rotated_at=NOW()`；
- 用户名规则 `m` + 手机号后 8 位，重名加数字后缀（`MerchantService.java:100-103`）；
- 初始密码随机生成、只显示一次（`MerchantService.java:104-106`）。

### 5.3 `shop`（店铺，既有表 + 扩列）

`module-merchant.sql:9-42` 给既有 `shop` 表加 8 列：`contact_phone`、`address`、`owner_name`、`intro`、`open_time`、`close_time`、`is_open`，另有既有 `min_price`/`delivery_fee`/`delivery_time`/`discount`/`discount_threshold`/`discount_amount`（`MerchantMapper.java:119-127` 的 UPDATE 列清单就是全字段清单）。

### 5.4 `shop_goods`（菜品）

`backend/src/main/resources/db/module-food.sql:12-16`：`shop_id / category / name / price / monthly_sales / image / sort_num / status`。**没有规格、加料、库存、限量字段**——奶茶只能整杯下单，不能选甜度冰度（甜度只能写备注，见种子数据的 `notice`）。

### 5.5 `refund_record`（拒单退款账本）

`module-merchant.sql:66-77`：`order_id` 唯一键（`:75`）→ 同一单只能有一条退款记录；`status` 由 `MerchantRefundStatusService` 驱动（`pending/success/failed`）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 入驻申请的校验链（`MerchantService.submit:33-60`）

顺序固定，任一不过即 400：

| # | 规则 | 行号 |
|---|---|---|
| 1 | 店铺名 2-64 字 | `:35` |
| 2 | 分类必须命中 3 组别名之一（快餐/快餐便当、奶茶/奶茶饮品、水果/水果轻食、超市、零食、其他） | `:21`、`:36-37` |
| 3 | 联系人 2-32 字、电话必须是 `^1\d{10}$` | `:38-40` |
| 4 | 地址 1-128 字 | `:41` |
| 5 | 学校必须存在且启用 | `:42-43` |
| 6 | 营业执照号 1-64 字 | `:44` |
| 7 | 营业执照图**必须**是 `/private/` 私有路径 | `:45-46` |
| 8 | 店面图必须是 `/uploads/` 或 http(s) | `:47-50` |
| 9 | 简介 ≤300 字 | `:51-52` |

**没有的校验**：手机号是否已被注册过、营业执照号是否与已通过的商家重复、同一学校同店名是否重复、验证码/频率限制（见 30-03）。

### 7.2 审核通过（`MerchantService.approve:85-113`）

一个事务里做五件事：

1. `SELECT … FOR UPDATE` 锁住申请行（`:87`）——防两个管理员同时点"通过"。
2. 校验状态仍是 `pending`，否则「该申请已审核」（`:90`）。
3. 建店 `insertMerchantShop`（`:97`），店铺字段直接取自申请（`:94-96`）。
4. 建账号：用户名 `m` + 手机号后 8 位，重名循环加后缀（`:100-103`），密码随机（`:106`）。
5. 回写申请 `status='approved', created_shop_id`，条件 `status='pending'`（`:111`）。回写失败则整个事务回滚——**不会留下没有申请归属的店和号**。

返回 `{shopId, username, initialPassword}`，前端弹窗展示一次（`MerchantAudit.vue:59`）。

### 7.3 商家侧权限边界

| 规则 | 实现 | 行号 |
|---|---|---|
| 请求里不带 shopId 也没用 | 一律取 token 属性 | `MerchantController.java:103-105` |
| token 里没有 shopId 直接 403「商家账号未绑定店铺」 | 拦截器强制 | `AdminInterceptor.java:80-83` |
| 只能操作自己的菜品 | 每条 SQL 都带 `shop_id=#{shopId}` | `MerchantMapper.java:92-93`、`:102-106`、`:108-109`、`:111-117` |
| 只能操作自己的订单 | `requireOwnedOrder` → `order(id, shopId)` | `MerchantService.java:306-310`、`MerchantMapper.java:156-157` |
| 不能改学校、不能改上架状态 | 请求体带这两个键直接 403 | `MerchantService.java:136-137` |
| 店铺与账号被平台调整后旧 token 立即失效 | 每请求比对 `role/schoolId/shopId` + `tokenVersion` | `backend/src/main/java/com/campuslife/config/AdminTokenGuard.java:49-56` |

### 7.4 订单四态与商家能做什么

| 订单状态 | 商家能做 | 证据 |
|---|---|---|
| `paid`（已付款待接单） | 接单 → `accepted`；拒单 → `cancelled` + 建退款单 | `MerchantService.java:203-224`、`:226-258` |
| `accepted`（已接单） | 若**无骑手**：标记完成 → `completed`；若已派骑手：只能等 | `MerchantService.java:270-288` |
| `delivering/picked`（骑手配送中） | **什么都不能做**（无取消、无拦截） | 无对应接口（见 30-05） |
| `completed` | 只读 | — |

**为什么商家不能替骑手完成**：订单已被骑手接单（`rider_id` 非空）时 `complete` 直接拒绝「该订单已由骑手接单，请等待骑手送达后再标记完成」（`MerchantService.java:274-280`）。否则骑手侧的在途列表会和订单状态不一致。

### 7.5 拒单的补偿动作

`MerchantService.rejectOrder:226-258`，一次事务里：

1. 条件 UPDATE 把订单置 `cancelled`，**只允许 `status='paid'`**（`MerchantMapper.java:162-163`）；
2. 释放该单锁定的优惠券（`MerchantService.java:232`）；
3. 原状态是 `paid` 时建退款单：退款号 `MR{orderId}`、金额 = `pay_amount_cents` 全额、原因「商家拒单：xxx」（`:236-241`）；
4. 事务提交后调 `MerchantRefundService.submitAfterCommit` 真正提交微信退款（`:243-252`）；
5. 给学生发站内通知「订单已取消」（`:256`）。

**拒单只能发生在 `paid`**：一旦商家点了接单，`cancelOrder` 的 `status='paid'` 条件命中 0 行 → 抛「订单状态不允许拒单」（`MerchantService.java:230-231`）。这是刻意的，代价是商家接单后没有任何撤回手段（见 30-05）。

### 7.6 退款的三种结果

`MerchantRefundService.submitAfterCommit:24-76`：

| 情形 | 结果 | 行号 |
|---|---|---|
| 未配置微信支付（`properties.isEnabled()==false`）或退款服务未装配 | 标 `failed`，备注「微信退款未配置，需平台人工处理」 | `:30-33` |
| 金额/原支付状态无效（`payStatus` 不是 `paid/refunding`，或金额 <1） | 标 `failed`，需人工 | `:35-42` |
| 缺原支付单号（`transaction_id` 与 `out_trade_no` 都空） | 标 `failed`，需人工 | `:43-47` |
| 渠道调用异常 | 先查单（`queryByOutRefundNo`），查不到则保持 `pending` + 备注「结果暂时无法确认」 | `:64-75` |

### 7.7 什么情况会拒绝（对商家可见的错误）
