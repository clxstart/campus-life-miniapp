## 一、设计优点（为什么这么设计，好在哪）

### 1.1 单一责任人的做法最省事也最不易错

「同一订单只有一个有效责任配送人」没有用额外的分配表或状态标志位，而是**只保留 `user_order.rider_id` 一列**：改派就是覆盖这一列，旧骑手的所有 SQL 因为带 `rider_id=#{riderId}` 条件而自然命中 0 行（`backend/src/main/java/com/campuslife/service/DispatchService.java:26-27`、`backend/src/main/java/com/campuslife/mapper/RiderMapper.java:69-73`）。这比"再开一张 rider_order 关系表 + 有效标志"少一半的坑。

### 1.2 自动派单失败不拖垮主流程

十步判定，任何一步不过就 `queue`（进异常队列）而不是抛异常；并且派单发生在商家接单事务的 `afterCommit`（`DispatchService.java:111-116`、`backend/src/main/java/com/campuslife/service/MerchantService.java:214-223`）。派单系统坏了，用户可以正常下单、商家可以正常接单，只是订单堆在异常队列里等人处理。这个失败边界划得很对。

### 1.3 派单的所有写操作都是条件 UPDATE

`assignAuto` 的 WHERE 里带 `rider_id IS NULL AND status='accepted'`（`DispatchMapper.java:42-51`），`reassign` 带 `status IN ('accepted','delivering','picked')`（`:73`），`pick/deliver` 带 `rider_id` + 当前状态（`RiderMapper.java:69-73`）。并发派单、并发改派、旧骑手手快，全部靠影响行数兜住，没有一处"先查后写"。

### 1.4 手机号的最小必要暴露做对了

订单池只给遮掩号（`RiderService.java:34-36`、`:137-141`），完整号码必须按单调用 `contact-phone`，并且只对"本人承运 + 配送中/已取货"生效（`RiderMapper.java:62-63`）。列表接口的字段用白名单投影，未列入白名单的列不会泄露到响应里（`RiderService.java:25-32`、`:52-60`）。这是本仓库里数据最小化做得最规矩的一处。

### 1.5 记账失败会整体回滚

`deliver` 里送达与记报酬同一事务，记账写不进去就回滚，不允许出现"订单完成了但收入没记"的假成功（`RiderService.java:102-103`）。更细的是 `ensureLedgerWritten` 把 `INSERT IGNORE` 返回 0 行区分为"已存在（合法幂等）"和"真失败（抛异常）"（`DispatchService.java:202-211`）——这个处理兼职域就没做（对比问题 09-02）。

### 1.6 改派留痕完整

`order_dispatch_log` 记录动作、原责任人、新责任人、操作者类型与 id、原因、时间，六个字段全齐（`backend/src/main/resources/db/module-rider-dispatch.sql:35-46`、`DispatchService.java:155-156`），并且校管只能看本校订单的调度记录（`DispatchService.java:216-224`）。事故复盘时这份日志就是唯一依据。

### 1.7 骑手账号体系复用了管理端的令牌治理

骑手不是另起一套用户表，而是 `admin_user` 里 `role='rider'`；直接继承了 `AdminTokenGuard` 的每请求校验（启用状态、`token_version`、角色/学校/店铺一致性）（`backend/src/main/java/com/campuslife/config/AdminTokenGuard.java:44-57`）。停用一个骑手，他手里的 token 下一毫秒就废。这比"再写一套骑手鉴权"省了几百行，也避免了漏校验。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 骑手拿不到钱，且没有任何结算出口

`earnings_ledger` 明确写着"不是钱包余额、不是已付款、不可提现"（`backend/src/main/resources/db/module-earnings-ledger.sql:1-8`），`wallet.enabled=0`。所以骑手跑完单，系统里只有一行数字，**没有任何提现、结算单、批量打款能力**。骑手端页面还把 `delivery_fee` 直接当"共赚 ¥X"展示（`web/src/views/rider/History.vue:20`）——用户会真的以为那是钱。

### 2.2 送达没有任何凭证

`deliver` 的判定就是"你是这单的骑手 + 状态是 picked"（`RiderMapper.java:72-73`），没有任何额外的证明：没有送达照片、没有定位、没有收件人确认、没有送达码。学生也没有"确认收货"的入口。骑手点一下，钱就记上了（`DispatchService.java:194-199`）。一旦接入真实结算，这就是可刷单套现的路径。

### 2.3 "接管"这个功能是假的

方案要求"负责人可接管订单并作为实际配送人"（`docs/校园帮功能方案-兼职钱包配送与圈子.md:155`）。代码里 `assign` 要求被指派账号 `role='rider'`（`DispatchService.java:131`），而校管账号是 `school/super`，不是骑手。Web 弹窗给了"负责人接管"这个选项（`web/src/views/Dispatch.vue:105`），但仍然强制选一个骑手（`Dispatch.vue:227`）。结果：**"接管"只是给改派换了个标签**，谁来送这件事没变。

### 2.4 改派不管已经发生的工作量

改派只覆盖 `rider_id/actual_rider_id` 与 `delivery_pay_counted`（`DispatchMapper.java:66-77`）。原骑手可能已经到店、已经取餐、甚至已经在路上，这些事没有任何字段记录，配送费 100% 归最终送达人（`DispatchService.java:145-157`）。方案 §7.2 说"默认整笔归实际完成配送的人"，逻辑上没错，但实际运营里"骑手跑了三公里被改派，一分没有"会在第二天变成投诉。

### 2.5 骑手没有异常处理路径

`RiderController` 8 个接口：stats/pool/grab/mine/contact-phone/pick/deliver/history（`backend/src/main/java/com/campuslife/controller/RiderController.java:19-65`）。没有"订单异常上报""退回队列""联系不上用户""商家出餐慢"任何一个。骑手取餐后发现地址错了、电话打不通、宿舍楼下不去，只能在微信里找负责人，而负责人的处理手段只有改派（改派又要求选另一个骑手）。**结果骑手面前只有两条路：硬点送达，或者弃单不管**——前者叠加 2.2 就变成虚假送达。见 10-15。

### 2.6 骑手端只有 Web

`app.json` 里没有骑手页（`app.json` 全文无 `rider`）。骑手要接单必须打开电脑浏览器登录 `/rider`。校园兼职骑手是移动场景，这个形态在真实运营里基本走不通——课间十分钟要接一单，不可能回宿舍开电脑。

### 2.7 统计口径与账本口径两条线

骑手看到的"本月共赚"来自 `SUM(delivery_fee)`（元，`RiderMapper.java:105-111`），账本里是 `delivery_pay_cents`（分）。两者还不一致：前者不排除"接管不计酬"的单（`delivery_pay_counted=0`）。同一件事有两个数字，迟早对不上。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 好处 | 代价 | 本仓库是否选了 |
|---|---|---|---|
| A. 全校自由抢单 | 运力利用率高、骑手体验好 | 无人对结果负责；跨校/跨楼混乱；方案明确否掉 | **没选**，接口保留但默认关闭（`RiderService.java:64-68`） |
| B. 楼栋责任区自动派单 | 责任清晰、可追责、运营可控 | 依赖楼栋字典与默认骑手配置，配错就整栋楼瘫痪 | **选了 B** |
| C. 骑手账号独立建表 | 语义干净，不影响 `admin_user` | 要重写一套鉴权/令牌/停用体系 | **没选**，复用 `admin_user` + `AdminTokenGuard`（`config/RiderInterceptor.java:29-31`） |
| D. 抢单用 Redis 原子操作 | 天然原子 | 多一层依赖与一致性处理 | 没选，用多表条件 UPDATE（`RiderMapper.java:48-56`） |
| E. 配送费进钱包 | 骑手可提现、体验完整 | 受支付合规限制（方案 §6.4） | 没选，只记账（`module-earnings-ledger.sql:1-8`） |
| F. 改派时按"已跑里程/已接单时长"拆分报酬 | 公平 | 需要轨迹或时长数据，当前没有任何采集 | 没选，整笔归最终送达人 |
| G. 送达要收件人确认码 | 杜绝虚假送达 | 需要短信/通知能力与用户配合，弱网下易卡死 | 没选 |

## 五、如果重做会怎么改

1. **先把"送达"这件事的证据链定下来。** 现在的 `deliver` 只有"骑手自己说他送到了"。至少要三选一：送达照片、取件码/收件码、GPS 围栏。没有证据的"完成"不能产生可结算报酬——报酬状态应停在 `recorded`，等证据齐全或用户确认再进 `settled`。
2. **结算模型必须先于运力模型。** 现在的顺序反了：先把派单、改派、留痕做得很完整，再发现钱根本出不去。正确顺序是：结算能力 → 记账口径 → 派单。
3. **给骑手一个移动端。** 校园骑手不可能回宿舍开电脑。最小可用形态是"接单/取货/送达"三个按钮的小程序页，或一个 PWA。
4. **把"异常"当成一等公民。** 现在只有"正常推进"这一条路；真实配送的 30% 时间在处理异常（找不到楼、电话打不通、商家慢、雨天超时）。应加异常上报 + 超时自动升级。
5. **统一骑手收入口径到账本。** 页面上的钱只能来自 `earnings_ledger`，不能直接 `SUM(delivery_fee)`。`delivery_fee` 是"顾客付了多少配送费"，不是"骑手赚了多少"。
6. **接管要能真的接管。** 给校管一个"我自己送"的账号形态（`admin_user.can_deliver=1`），或允许 `takeover` 指定管理员本人。

## 六、本维度未覆盖的部分（说明原因）

- **真实运力压测**：无压测环境，派单吞吐与并发改派的表现未测（`docs/v3.2/04-证据与复核台账.md:77`）。
- **地址匹配准确率**：`matchBuilding` 的匹配逻辑读过（`DispatchService.java:231-249`），但真实地址样本匹配率未统计——需要一份真实订单地址清单。
- **小程序真机**：骑手端在小程序里不存在，无页面可走；学生侧订单详情只做了读码。
- **资金侧**：本域不持有资金，账户与退款风险归 `docs/v3.2/07-支付与退款/`。
- **骑手劳动合同/劳务协议**：`admin_user` 里没有任何签约字段，本域也没有协议留存能力——这一条与兼职域同性质（对照 09-05），未单列问题因为当前连"骑手是雇员还是合作方"都没定义。
