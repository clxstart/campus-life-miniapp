## 一、这个功能解决什么问题

外卖下单后「谁去送、怎么证明送到了、送完给多少钱」这三件事。

派单模型在方案里定得很死（`docs/校园帮功能方案-兼职钱包配送与圈子.md:150-156`）：**不开放全校自由抢单**，而是「楼栋责任区」——每栋宿舍楼配一个默认责任骑手，订单地址匹配到楼栋后自动派给该栋楼的默认骑手；缺配楼栋、骑手请假/忙碌、地址匹配不上，就进「异常待处理队列」由负责人改派或接管。

代码完整实现了这个模型，并且把不变量写进了类注释（`backend/src/main/java/com/campuslife/service/DispatchService.java:18-28`）：

1. 每栋楼配默认责任骑手，自动派给"当前可用"的那一个；
2. 缺配/不可用/匹配不上 → 异常队列，负责人改派；
3. 自由抢单接口保留但默认关闭；
4. 改派/接管必须留痕（谁、原责任人、新责任人、原因、时间）；
5. **同一订单只有一个有效责任配送人**——靠 `user_order.rider_id` 单列自然成立，旧骑手的 `pick/deliver` SQL 带 `rider_id` 条件，改派后立即命中 0 行。

三个概念必须先分清，否则会看错代码：

| 概念 | 是什么 | 在哪 |
|---|---|---|
| 骑手账号 | `admin_user` 表里 `role='rider'` 的行，**不是**小程序用户 | `backend/src/main/resources/db/module-rider.sql:25-30`、`backend/src/main/java/com/campuslife/mapper/RiderMapper.java:51` |
| 骑手端 | Web 独立路由 `/rider/**`（4 页），用管理端 JWT 但由 `RiderInterceptor` 只放行 `role=rider` | `backend/src/main/java/com/campuslife/config/WebConfig.java:45`、`web/src/router/index.js:65-76` |
| 楼栋责任区 | `building` 表，一行一栋楼，`default_rider_id` 指向骑手 | `backend/src/main/resources/db/module-rider-dispatch.sql:6-16` |

> ⚠️ **`pages/dispatch` 不是骑手派单**。那是**宠物派遣**页（`pet_dispatch` 表、`pet-api`、`pet-stage` 组件），与本功能无关——证据：`pages/dispatch/dispatch.js:1-9` 的头部注释与 `pages/dispatch/dispatch.json` 引用的 `pet-stage`/`task-card` 组件。骑手侧**没有**任何小程序页面（`app.json` 内无 rider 相关页面）。

## 二、用户看到的样子（小程序端）

### 2.1 学生侧：只有"我的订单里能看到骑手"

小程序端**没有骑手功能**，学生只能在下单后的订单详情看到配送进度与骑手信息：

- 订单详情页读取订单后展示「配送骑手」一行：姓名取 `order.riderName`、电话取 `order.riderPhone`（`pages/food-order-detail/food-order-detail.wxml:19`）。
- 数据来自外卖订单详情接口的返回体，`PayService.detail` 放了 `riderId / riderName / acceptedAt / pickedAt / deliveredAt`（`backend/src/main/java/com/campuslife/service/PayService.java:249-252`）——**但没有 `riderPhone`**，所以页面上那一行电话恒为空（见问题 10-10）。
- 另有一个 `RiderService.studentOrder`（`backend/src/main/java/com/campuslife/service/RiderService.java:123-129`）本来是为学生侧准备的（会遮掩骑手电话），但**没有任何 Controller 调用它**——死代码（见问题 10-13）。
- 学生侧**没有**"确认收货"动作。订单由骑手点送达即置 `completed`（`RiderMapper.java:72-73`），学生只在事后看到"已完成"。

### 2.2 骑手侧：小程序无入口

`app.json` 注册的 47 个页面里没有骑手页（`app.json` 全文无 `rider`）。骑手只能用 Web。

### 2.3 学生能看到的订单状态

`created → paid → accepted → delivering → picked → completed`，另有 `cancelled / closed / refunding / refunded`（`backend/src/main/java/com/campuslife/service/OrderStatus.java:18-20`）。其中：

- `delivering` = 骑手已接单、正在取餐；
- `picked` = 骑手已取到餐、正在配送；
- 两者都算"配送中"，骑手端 `activeCount` 用的就是这两个值（`backend/src/main/java/com/campuslife/mapper/RiderMapper.java:28`）。

另有一个只在超管可见的**批量补派**按钮（`POST /api/admin/dispatch/redispatch`），把历史上"已接单但无骑手"的单再派一次（`Dispatch.vue:196-207`、`backend/src/main/java/com/campuslife/controller/DispatchAdminController.java:63-71`）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 自动派单的判定链（`DispatchService.autoDispatch`）

顺序固定，任一步失败就进队列而不是抛错（`DispatchService.java:56-91`）：

| 步骤 | 判定 | 失败后果 | 行号 |
|---|---|---|---|
| 1 | 订单存在 | `skipped` | `:58-59` |
| 2 | 已有责任骑手 | `skipped`（幂等） | `:60-61` |
| 3 | 状态必须是 `accepted` | `skipped` | `:62` |
| 4 | 地址匹配到楼栋（去空白、取最长匹配） | `queued`「地址未匹配到楼栋」 | `:65-66`、`:231-249` |
| 5 | 楼栋配了默认骑手 | `queued`「未配置默认骑手」 | `:67` |
| 6 | 骑手账号存在且 `role='rider'` | `queued` | `:70-72` |
| 7 | 账号启用（`status≠0`） | `queued`「已停用」 | `:73` |
| 8 | 骑手学校 = 订单学校（fail-closed，无学校也算不匹配） | `queued` | `:74-76` |
| 9 | 骑手状态 `idle/available/online` 或为空 | `queued`「当前不可用」 | `:77-78`、`:271-275` |
| 10 | 条件 UPDATE 派单（`rider_id IS NULL AND status='accepted'`）影响 1 行 | `skipped`「已被其他流程处理」 | `:81-85`、`DispatchMapper.java:42-51` |

**幂等与并发**：第 10 步是唯一判定，两个流程同时派同一单只会成一个（`DispatchMapper.java:38-40` 注释）。

**注意**：派单在**商家接单事务提交之后**执行（`MerchantService.accept` 的 `afterCommit`，`backend/src/main/java/com/campuslife/service/MerchantService.java:214-223`），失败只记录不影响接单成功。这是对的——派单不该让接单失败。

### 7.2 抢单（默认关闭）

`flags.enabledStrict("rider.grab.enabled")` 为假时直接 403「当前采用楼栋责任区派单，暂不开放自由抢单」（`RiderService.java:66-68`）。开关默认 0（`module-safety-gates.sql:11`）。

开抢后：条件 UPDATE 同时校验订单状态、骑手角色、骑手启用、**骑手与商家同校**（`RiderMapper.java:48-56`）。多表 UPDATE 的影响行数会被 MySQL 计成两行，所以判定写的是 `== 0` 而不是 `== 1`（`RiderService.java:69-72` 注释）。

### 7.3 取货与送达

| 动作 | 状态机 | SQL 条件 | 附加动作 |
|---|---|---|---|
| `pick` | `delivering → picked` | `rider_id` 匹配 AND `status='delivering'`（`RiderMapper.java:69-70`） | 无 |
| `deliver` | `picked → completed` | `rider_id` 匹配 AND `status='picked'`（`RiderMapper.java:72-73`） | 重算骑手忙碌状态 + 记配送报酬（`RiderService.java:101-103`） |

双重校验：先 `dispatchOf` 查单确认归属（`RiderMapper.java:66-67`），再走 `OrderStatus.requireTransition` 白名单（`RiderService.java:83`、`:97`），最后才 UPDATE。

### 7.4 改派 / 接管

`DispatchService.assign`（`:123-168`）：

1. 被指派账号必须存在、`role='rider'`、启用（`:129-132`）；
2. 校管只能调度本校订单（`:136-139`）；
3. 骑手学校必须 = 订单学校（fail-closed，`:140-144`）；
4. 条件 UPDATE：只允许 `status IN ('accepted','delivering','picked')`，`accepted` 会顺带推进到 `delivering`（`DispatchMapper.java:66-77`）；
5. 通知原来的骑手与新骑手重算 `rider_status`（`DispatchService.java:153-154`）；
6. 写 `order_dispatch_log`（`:155-156`）。

**改派后旧骑手立即失去权限**：`pick/deliver` 的 SQL 都带 `rider_id=#{riderId}`，旧骑手调用命中 0 行 → 报「订单状态已变化」。

### 7.5 配送报酬（记账，不是钱）

```
送达 → markDeliveryPayRecorded(0→1) 成功
     → countPay=false → 写 delivery:{id}:review 金额 0 状态 void
     → countPay=true  → 写 delivery:{id}:income 金额 delivery_pay_cents 状态 recorded
```

- **只记一次**：`delivery_pay_recorded` 条件更新 + `biz_no` 唯一键双保险（`DispatchService.java:171-179`）。
- **写不进去就整体回滚**：`ensureLedgerWritten` 在 0 行时区分"已存在（合法幂等）"与"真失败（抛异常，送达回滚）"（`DispatchService.java:202-211`）。这一点比兼职域做得对（对照问题 09-02）。
- **金额来源**：`delivery_pay_cents` 快照，不是当前店铺配送费（`DispatchMapper.java:132-133`）。
