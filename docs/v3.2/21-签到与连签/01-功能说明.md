## 一、这个功能解决什么问题

签到是"每天来一次"的最低成本动作，也是积分体系里唯一**不依赖用户创作**的发分口。它要解决三件事：

1. **一天只能签一次，且不能靠客户端状态判断**。幂等键是 `sign_roll` 的主键 `(user_id, biz_date)`，服务端并不知道也不信任前端"今天签过没" —— 证据 `backend/src/main/resources/db/module-sign-v31.sql:10-17`、`SignMapper.java:20-27`。
2. **连签要能算出来，且断签能重来**。连签不存"累计值"，靠"昨天那行是否存在"推算；六档里程碑（3/5/7/15/20/30 天）用 `sign_streak_N` + 当天日期做幂等键，所以断签后重新连到 7 天会**再发一次** —— 证据 `backend/src/main/java/com/campuslife/service/SignService.java:24-28`（注释）、`SignService.java:80-91`。
3. **宿舍联动不能反过来打死签到**。宿舍"全员到齐"要回到签到链路触发，但宿舍域失败绝不能回滚签到，所以用接口 + 提交后回调解耦 —— 证据 `backend/src/main/java/com/campuslife/service/SignCompletedListener.java:5-13`、`SignService.java:150-168`。

设计稿的口径与本实现一致：`docs/v3.1/签到与连签-功能说明与测试手册.md:141-146` 列的 6 步流程，代码逐步都有对应。

## 二、用户看到的样子（小程序端）

### 2.1 设计上的样子

签到不单独开页，复用积分页顶部卡片：标题「今日签到」、副标题「已连续签到 N 天」、按钮「签到 +1 积分」；未签时按钮可点，已签时变灰显示「今天已签到」；下方圆点展示"已达成 / 下一个 / 再下一个"三档 + 一行「下一档：连签 5 天，额外 +10 积分」—— 证据 `pages/points/points.wxml:28-52`、`pages/points/points.js:14-15`（`MILESTONE_DAYS`）、`pages/points/points.js:35-41`（圆点算法）。

### 2.2 实际：**用户看不到**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 签到 UI 在哪个页面 | 只在 `pages/points/points` | 全仓库 `grep -rln "签到" pages/` 只命中 `pages/points/*` 与 `pages/points-redeem/points-redeem.js` |
| 该页面是否注册 | **未注册** | `app.json:2-45` 无 `pages/points/points` |
| 是否有其他入口 | **没有**（无独立签到页、无首页签到浮层） | 全仓库 `grep -rn "signPoints"` 只命中 `pages/points/points.js:195`（调用）与 `utils/api/points.js:123`（定义） |

**后果**：小程序端签到功能**完全不可用**。用户没有任何路径能点到"签到"，`POST /api/points/sign` 只能靠 curl/Postman 触发。这与 20 的结论同源——四个 V3.1 新页面都没注册（见 `docs/v3.2/README.md:48`）。

### 2.3 交互设计上的一个亮点

签到按钮做了"本地置灰防连点"（`this.data.signBusy || this.data.signedToday` 直接 return），成功后**只局部刷新**（不整页重载），里程碑用**第二条 toast 单独说**，不把"+1"和"+10"糊成一句 —— 证据 `pages/points/points.js:187-222`。这个交互取舍是对的（用户能分清哪笔是哪笔）。

代价是：它把"是否成功"完全托付给了 HTTP 200，而不看返回体（问题 21-01）。

## 三、运营看到的样子（Web 端）

**无页面，且这是设计稿明确的选择**：`docs/v3.1/签到与连签-功能说明与测试手册.md:58-60` 写「**无页面。** 如需排查某个用户为什么没签到，走「用户管理 → 该用户 → 积分明细」」。

问题在于后半句的路径**不存在**：

| 设计稿指向的能力 | 代码实际 | 证据 |
|---|---|---|
| 用户管理 → 该用户 → 积分明细 | `web/src/` 全目录无 `points/logs` 调用；后端 `/api/points/logs` 恒为本人 | `PointsController.java:60-65`；本轮 `grep -rn "积分明细" web/src` 无命中 |
| 查 `task_key=daily_sign` 的记录 | 无管理端接口能按 userId 查 `task_log`/`point_log` | `PointsMapper.java:115-124`（`logs` 只被本人视角调用） |

所以运营现在的真实手段只有**直接连数据库**。对签到这种每天都在跑的功能，这是可观测性缺口（见 `20-积分体系/03-优缺点与问题.md` 问题 20-05）。

签到的**唯一**可观测信号是应用日志：`SignService` 没有专门的业务日志（成功不打印），宿舍联动失败打 `log.warn`（`DormService.java:285`）。

## 四、接口清单

本次实测本功能仅 2 条方法级接口（`SignController` 2 处映射含 1 处类级）：

| 方法 | 路径 | 权限 | 作用 | 证据 |
|---|---|---|---|---|
| POST | `/api/points/sign` | 登录用户本人 | 签到；返回连签天数、本次奖励、余额 | `backend/src/main/java/com/campuslife/controller/SignController.java:26-31` |
| GET | `/api/points/me` | 登录用户本人 | 内含 `signedToday`/`streakDays`/`nextMilestone` | `PointsController.java:39-53` |

返回体（与设计稿 `docs/v3.1/签到与连签-功能说明与测试手册.md:118-129` 一致）：

```json
{ "code": 0, "data": {
    "signedToday": true, "streakDays": 5,
    "awarded": [{ "taskKey": "daily_sign", "p": 1, "g": 1 },
                { "taskKey": "sign_streak_5", "p": 10, "g": 10 }],
    "balance": 63, "nextMilestone": {...}, "message": "" } }
```

字段来源核对：`SignService.java:93-96`（组装返回）、`SignService.java:139-148`（`addAwarded` 只把 `AWARDED` 的写进数组）。

## 五、数据表与字段

| 表 | 关键字段 | 用途 | 谁写 | 证据 |
|---|---|---|---|---|
| `sign_roll` | `user_id`+`biz_date` 主键、`streak_days` | 一天一行；既是签到事实，也是连签推算依据 | `SignMapper.insert/updateStreak` | `module-sign-v31.sql:10-17`、`SignMapper.java:20-31` |

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 会拒绝 / 不发放的情况

| 情况 | 行为 | 证据 |
|---|---|---|
| 未登录 | 403（`ForbiddenException("请先登录")`） | `SignController.java:28-30` |
| `daily_sign` 任务被停用 | **不写签到事实**，返回现状 + `message="签到暂未开放"` | `SignService.java:55-61` |
| 今天已签 | 返回 `signedToday=true`、`awarded=[]`、`message=""`，不报错（幂等） | `SignService.java:73-78` |
| 并发双击 | 唯一键冲突被捕获，按"今天已签"返回 | `SignService.java:64-71` |
| 里程碑任务被停用 | 连签照常推进，只是该档不发分 | `SignService.java:87-91` + `PointsService.java:102-103` |

### 7.2 跨天与时区边界

- "今天"固定 `LocalDate.now(Asia/Shanghai)`，与服务器时区无关 —— `SignService.java:35`、`:53`。
- 北京时间 23:59 签一次、00:01 再签 → 两个 `biz_date`，连签 +1（设计稿 `:161` 期望一致）。
- `streak_days` 先 `INSERT ... VALUES(1)` 再 `UPDATE` 成真实值（`SignMapper.java:20-21`、`SignService.java:80-82`），两步在同一事务内。

### 7.3 会补偿 / 不会补偿的情况

- **不会补偿**：`dorm_all_sign`（宿舍全员签到）没有任何补跑入口。对比 `dorm_week_first`（宿舍周榜第一）管理端有 `POST /api/admin/dorm/settle-week` 可补跑 —— 证据 `backend/src/main/java/com/campuslife/controller/AdminDormController.java:61-72`。这个不对称是问题 21-03 的一半。
- **不会回滚签到**：宿舍判定放在提交后回调，异常被 `catch (RuntimeException)` 吞掉 —— `DormService.java:280-287`。设计稿要求的"宿舍失败不回滚签到"**成立**。
- **不做的**：补签卡、签到日历、签到提醒推送（设计稿 `:170-174` 明确本期不做；`grep -rn "补签" backend/src` 无实现）。
