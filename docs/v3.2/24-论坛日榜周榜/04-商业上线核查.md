## 二、资金与对账

**结论：不通过（原因：24-02 会出现「已通知到账但账上无分」，且无对账口径）**

本功能不涉及真实货币收付，但**发的是积分与成长值**——`PointsService.java:43-44` 明确「100 积分 = 1 元，仅作展示换算」，即积分是有兑换价值的准货币。因此按「涉及资金」对待。

| 检查点 | 结论 | 依据 |
|---|---|---|
| 发分是否只有单一出口 | 通过：全部走 `PointsService.awardCustom`，本模块不碰 `user_points`/`point_log` | `ForumRankService.java:252-254`、`ForumRankMapper.java:17-18` |
| 重跑是否重复发分 | 顺序执行下通过（`task_log.uk_task_idem`）；并发下也通过（唯一键先插） | `db/module-points-v31.sql:77`、`PointsService.java:114-119` |
| 命中日上限后能否补发 | **不通过**：`CAPPED` 时 `task_log` 已提交，重跑走 `ALREADY`，分永远补不上，却仍发「已到账」通知（24-02） | `PointsService.java:116`/`:122-125` 对照 `ForumRankService.java:262-273` |
| 奖励金额是否可复核 | **不通过**：不发奖励快照，展示取当前目录值，历史值随后台改价而变（24-10） | `ForumRankService.java:299-316` |
| 对账口径 | **不通过**：没有任何日结/月结对账任务；「榜单发出多少分」只能靠 `point_log` 按 `type=rank_daily` 反推，而 `point_log.type` 存的是 `taskKey`，无 `period_key` 维度 | `PointsService.java:132-133`（`type=taskKey`、`biz_key=taskKey:periodKey`） |
| 是否存在发放上限 | 有：日榜 10 人 ×10P = 100P/天、周榜 20 人 ×15P = 300P/周（按目录默认值） | `ForumRankService.java:51-53`、`db/module-forum-rank-v31.sql:37-40` |

对账建议（可直接落成 SQL）：

```sql
-- 某周期实发积分（权威）
SELECT SUM(p) FROM point_log WHERE biz_key LIKE 'rank_daily:2026-11-08%';
-- 某周期快照声称已发（展示口径）
SELECT COUNT(*) * 10 FROM forum_rank WHERE board='daily' AND period_key='2026-11-08' AND awarded=1;
```

两条口径不一致时（24-02 就会不一致），必须能人工定位到具体用户。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：按顺序执行 + 执行前备份 `task_catalog`）**

### 4.1 前置 SQL 与执行顺序

```text
1) backend/src/main/resources/db/module-points-v31.sql     -- 必须先跑：task_catalog / task_log / point_log 是前置
2) backend/src/main/resources/db/module-forum-rank-v31.sql -- 建 forum_rank + 插两条任务种子
```

顺序理由：`module-forum-rank-v31.sql:37-40` 向 `task_catalog` 插种子，若 `module-points-v31.sql` 未跑，该 INSERT 会因表不存在而失败（脚本无容错）。

### 4.2 幂等性

| 脚本 | 是否可重复执行 | 依据 |
|---|---|---|
| `module-forum-rank-v31.sql` | 是 | `CREATE TABLE IF NOT EXISTS`（`:19`）+ `INSERT ... ON DUPLICATE KEY UPDATE task_key = task_key`（`:40`，不覆盖后台改过的值） |
| 依赖的 `module-points-v31.sql` | 是（同样写法） | `db/module-points-v31.sql:83` 起同款 `ON DUPLICATE KEY UPDATE` |

### 4.3 回滚

```sql
-- 回滚：先停发分（保留表与历史，最小破坏）
UPDATE task_catalog SET enabled = 0 WHERE task_key IN ('rank_daily','rank_weekly');

-- 彻底回滚（会丢历史快照，仅在确认无需复核时执行）
DROP TABLE IF EXISTS forum_rank;
DELETE FROM task_catalog WHERE task_key IN ('rank_daily','rank_weekly');
```

**注意**：`DROP TABLE forum_rank` 会让所有历史榜单不可查，「用户申诉时无法自证」——按 `04-证据与复核台账.md` 第八节精神，生产环境应优先用 `enabled=0` 软停，不做 DROP。

### 4.4 迁移就绪度缺口

- **没有迁移版本表**：`db/` 下 51 个 SQL 脚本没有执行顺序记录，靠人工记。本功能依赖前置脚本，属于「跑错顺序就失败」的类型。
- **未验证**：本轮没有连库确认 `forum_rank` 与两条 `task_catalog` 种子是否已在目标库中存在（见 `04-证据与复核台账.md` 第 3.2 节）。

```sql
  SELECT user_id AS uid, 3 AS pts FROM post WHERE status=1 AND created_at>='2026-11-08 00:00:00' AND created_at<'2026-11-09 00:00:00'
```

上线必须具备的最小回滚剧本：

```text
1. 事故发现（重复发分/分数异常）
```

## 九、结论

# 不可上线（阻断项：24-01、24-02、24-03、24-04、24-05）

逐项说明为什么这 5 条各自独立构成阻断：

1. **24-01 页面不可达（且当前整包编译失败）**——三类问题叠在一起：`app.json:45` 注册了不存在的 `pages/dorm/dorm` 让整包编译失败；`pages/verify` 缺 2 个文件；榜单页注册了但没有入口。第一条不属于本功能，但它让「本功能能不能用」这个问题失去意义——**修它优先于本功能的所有事**。
2. **24-02 奖励永久丢失 + 谎报到账**——直接影响准货币资产，且用户手里有「已到账」的站内信作为凭证，客服无法解释。属资损 + 信任双杀。
3. **24-03 可刷量**——榜一被机器占据后，这个功能从激励变成劝退；且刷量成本极低（限频只有 10 次/分钟）。
4. **24-04 漏跑无补无告警**——榜单是**周期性**功能，漏一个周期就是永久数据缺口，且无人知晓。
5. **24-05 展示假数据**——社会比较类内容的假数据会直接被截图传播。

完整列表与本目录 `03-优缺点与问题.md` 第四节一致（P0 1 条、P1 7 条、P2 3 条）。

放行路径（最小可行）：修完 24-01 ~ 24-05 后，**可降级为「有条件上线」**（条件：24-06、24-07 在灰度期修完；24-09 把 `resettle` 收窄为 super）。P2 三条可上线后迭代。
