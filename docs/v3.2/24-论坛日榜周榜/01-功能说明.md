## 一、这个功能解决什么问题

论坛需要一个「持续发言有回报」的正反馈循环：发帖、评论、被人点赞都产生分数，每天/每周结算一次，前若干名拿积分与成长值。

要解决三个具体问题：

1. **谁在活跃**——排行榜把活跃度显性化，让内容生产者被看见（设计意图，见 `ForumRankService.java:22-28` 类注释）。
2. **分不能抖**——实时排名会随互动抖动，用户看到「第 3 名」转眼变「第 4 名」会投诉；所以采用**先落快照、再按快照发奖**。
3. **分不能重发**——重跑结算必须幂等，否则一次误操作就是重复发钱。

明确**不做**的事（读码可见）：

- 不做实时排名，只展示已结算快照（`ForumRankService.java:76-106`）。
- 不发「名次之外的实物奖」，奖励只有 P（积分）/G（成长值）两项，从 `task_catalog` 读（`ForumRankService.java:413-426`）。
- 不按学校分榜：算分 SQL 里没有任何 `school_id` 条件（`ForumRankMapper.java:35-48`）。

权限：`/api/admin/**` 由 `AdminInterceptor` 统一校验 token；本控制器再限制 `super|school`（`AdminForumRankController.java:52-55`），但**没有学校范围**——校管与超管对同一张全平台榜有同等操作权，见 `03` 第 24-06 条。

## 五、数据表与字段

### 5.1 `forum_rank`（榜单快照，本功能独占写）

建表：`db/module-forum-rank-v31.sql:19-31`。

| 字段 | 类型 | 用途 |
|---|---|---|
| `board` | VARCHAR(8) | `daily` / `weekly` |
| `period_key` | VARCHAR(16) | `2026-11-08` / `2026-W45` |
| `user_id` | BIGINT | 上榜用户 |
| `score` | INT | 算分结果（发帖 3 / 评论 2 / 被赞 1） |
| `rank_no` | INT | 名次，并列按 `user_id` 升序 |
| `awarded` | TINYINT | 1=奖励已发放；重结算只补 0 的行 |

约束：`uk_rank (board, period_key, user_id)` 挡重复插入（同文件 `:29`）；`idx_rank_period (board, period_key, rank_no)` 供榜单读取。

写入方：只有 `ForumRankMapper`。类注释明确「forum_rank 只允许本 Mapper 写；发分的唯一出口仍然是 PointsService」(`ForumRankMapper.java:17-18`)。

### 5.2 `task_catalog`（只读，奖励来源）

本功能向其中插两条任务（`db/module-forum-rank-v31.sql:37-40`）：

| task_key | 名称 | P | G | daily_cap |
|---|---|---|---|---|
| `rank_daily` | 论坛日榜上榜 | 10 | 15 | 1 |
| `rank_weekly` | 论坛周榜上榜 | 15 | 25 | 1 |

读取时若读不到目录，回落硬编码默认值 10/15 与 15/25（`ForumRankService.java:60-61`、`:413-426`）。

### 5.3 被算分的四张业务表（只读）

`post`（`status=1`）、`comment`（`CHAR_LENGTH(TRIM(content))>=5`）、`post_like`、`comment_like`——全部按 `created_at` 落在周期窗口内计数（`ForumRankMapper.java:36-48`）。

### 5.4 `notification` / `task_log`（本功能写入）

- 上榜通知写 `notification`，`source_key = forum_rank:{board}:{periodKey}:{userId}`，靠唯一键幂等（`ForumRankMapper.java:115-124`）。
- 发分事实写 `task_log`，`biz_key = periodKey`，靠 `uk_task_idem (user_id, task_key, biz_key)` 幂等（`db/module-points-v31.sql:68-79`）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 会拒绝的情况

| 情况 | 行为 | 证据 |
|---|---|---|
| `type` 不是 daily/weekly | 400「榜单类型只能是 daily 或 weekly」 | `ForumRankService.java:406-410` |
| `periodKey` 为空 | 400「请指定要重算的周期」 | `ForumRankService.java:147` |
| `periodKey` 格式错（日榜非 `yyyy-MM-dd`、周榜非 `yyyy-Www`、周号越界、年份 <2020） | 400 | `ForumRankService.java:368-383` |
| 结算一个**还在进行中**的周期 | 400「该周期还未结束，不能结算」 | `ForumRankService.java:150`、`:386-390` |
| 管理端身份不是 super/school | 403「仅校级管理员可操作论坛榜单」 | `AdminForumRankController.java:52-55` |

### 7.2 算分规则

- 发帖 +3（仅 `post.status=1`，即审核通过/可见）；
- 评论 +2（`TRIM` 后 ≥5 字符，防「顶」「1」刷分）；
- 帖子被赞 +1、评论被赞 +1（被赞权重压到 1，降低互赞群影响）；
- 并列按 `user_id` 升序，保证同一份数据每次算出的名次完全一致。

口径写在 `ForumRankMapper.java:20-24` 与 SQL `:36-48`；`ForumRankServiceTest.java:146-171` 有对应断言（未执行，见 `02` 第六节）。

### 7.3 周期边界

- 时区统一 `Asia/Shanghai`（`ForumRankService.java:46`），窗口在 Java 里算好后传参，不用 MySQL `CURDATE()`（`ForumRankMapper.java:32-34`）。
- 日榜窗口 `[yyyy-MM-dd 00:00, +1 天 00:00)`；周榜 `[周一 00:00, +7 天 00:00)`（`ForumRankService.java:354-357`）。
- 周键用 ISO 周（`WeekFields.ISO`），跨年按 week-based-year：2026-01-01 属 2025-W53（`ForumRankService.java:344-351`、`:360-366`）。
- 结算时刻 00:10 而非 23:59，给最后一分钟的写入与事务提交留时间（`ForumRankService.java:160-166`）。

### 7.4 补偿规则

- **单行发奖失败**不影响其他行，该行留 `awarded=0`，下次重结算补（`ForumRankService.java:227-234`）。
- **发奖前进程被杀**（分已发、快照没置位）：下次结算走 `ALREADY` 分支，只补状态与通知，不再发分（`ForumRankService.java:262-267`）。
- **通知写入失败**不回滚发分（`ForumRankService.java:288-293`）。
- **奖励被后台改成 0**：不算失败，直接置 `awarded=1` 收掉状态（`ForumRankService.java:247-251`）。
- **重结算算出更少的人**（帖子被删/下架）：先删本周期 `awarded=0` 的旧快照再写新的；`awarded=1` 的永不删（`ForumRankMapper.java:54-61`）。

### 7.5 三层幂等（代码注释 `ForumRankService.java:34-38` 自述）

| 层 | 机制 | 证据 |
|---|---|---|
| 1 | `forum_rank.uk_rank` 不插第二行 | `db/module-forum-rank-v31.sql:29` |
| 2 | `task_log.uk_task_idem` 不重复发分 | `db/module-points-v31.sql:77` |
| 3 | `notification` 唯一键不重复通知 | `ForumRankMapper.java:119-124` |

这三层在**顺序执行**下成立。并发与「命中日上限」两种边界下不成立，见 `03` 第 24-02、24-03 条。
