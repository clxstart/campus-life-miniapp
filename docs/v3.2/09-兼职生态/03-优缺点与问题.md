## 一、设计优点（为什么这么设计，好在哪）

### 1.1 并发控制选对了工具

校内先到先接没有用「先查 `taken_by` 再写」，而是把「无人接 + 仍 open + 是校内 + 已过审 + 未过期」全部压进一条 UPDATE 的 WHERE，用**影响行数**当唯一判定（`backend/src/main/java/com/campuslife/mapper/JobMapper.java:30-39`）。稀有正确之处在于它连注释都写了为什么不能反过来写：「两步之间就是别人插进来的窗口」（`JobMapper.java:27-28`）。校外名额同理由 `accepted_count < headcount` 写进 WHERE 保证（`JobMapper.java:47-55`），所以**不存在超发**。

### 1.2 金额一律用分，且只有一处换算

库里 `pay_cents / fee_value / amount_cents` 全是 `INT` 分（`backend/src/main/resources/db/module-jobs-marketplace.sql:49`、`:75`、`backend/src/main/resources/db/module-earnings-ledger.sql:17`）。前端把分→元收敛到 `formatCents` 一个函数，并在文件头写明"页面里禁止再出现 `/100`"（`utils/job-format.js:5-7`、`:74-78`）。这是本仓库里对"0.01 误差累积"防得最认真的一处。

### 1.3 费率快照 + 服务费不可篡改

发布接口**故意忽略**请求里的 `feeMode/feeValue`，强制写 `none/0`，费率只能由管理端逐岗位配置（`backend/src/main/java/com/campuslife/service/JobService.java:307-309`、`backend/src/main/java/com/campuslife/controller/AdminJobController.java:58-76`）。接单/录用那一刻把报酬与服务费双双快照进履约单（`JobService.java:367-371`、`:493-497`）。代价是管理端改价不影响旧单——这正是想要的。预估与实结共用同一套 `feeCents`（`JobService.java:957-969` vs `:979`），不会出现"页面算的和账单不一样"。

### 1.4 "账单不是钱"这件事写进了 UI

不是靠口头约定。数据库脚本第一行、Service 类注释、小程序两个页面的固定文案、管理端页面顶部与裁定弹窗，五处都明写"不是钱包余额、不是已付款、不可提现"（`module-earnings-ledger.sql:1`、`JobService.java:39-40`、`pages/job-mine/job-mine.wxml:68`、`pages/job-detail/job-detail.wxml:48`、`web/src/views/Jobs.vue:7`、`:312`）。在没拿到支付机构书面能力确认的前提下（方案 §6.4），这是最不容易踩线的处理方式。

### 1.5 状态机有白名单，且展示态与权限态分离

`JOB_FLOW` 九态白名单（`JobService.java:76-85`）；权限判定只看 `job_contract` 的条件 UPDATE，`job.workflow_status` 只是聚合出来的展示列（`JobService.java:821-828`、`JobMapper.java:71-77`）。多名额岗位因此不会出现"第一张结算后第二张推不动"的死锁（`JobService.java:836-872`）。

### 1.6 下架不砸在途履约

管理端下架时，只要有履约过的痕迹就只改 `audit_status`、保留 `workflow_status`，让已经开工的单还能提交工时、结算、发起争议（`JobService.java:787-799`、`JobMapper.java:108-113`）。同时 `reject` 对已结算/已退回的岗位加了状态守卫，避免账单上下文被抹掉（`JobMapper.java:96-101`）。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 交易闭环缺最后一步，商业收入为零

账单生成后，**没有任何"雇主已付/兼职者已收"的确认动作**，也没有付款凭证、催收、平台服务费的实收动作。`earnings_ledger` 的 `settled` 只是"账单状态"，平台上没有任何一笔真实资金流动（见 09-01）。结果是：平台服务费永远收不到，兼职者也永远拿不到钱，而系统无法区分"雇主赖账"和"已经线下付了"。

### 2.2 争议裁定的金额没有落到账单上

这是本域最贵的一个缺陷。冻结时按承接方申报金额写账单（`JobService.java:911`），裁定按管理员填的数量算应付（`JobService.java:758-760`），但写账单走的是 `INSERT IGNORE`——行已存在就什么都不更新（`backend/src/main/java/com/campuslife/mapper/EarningsLedgerMapper.java:19-22`）。于是**裁定数量与账单金额永久不一致**（见 09-02）。

### 2.3 没有合同，只有字段

`job_contract` 有费率快照、有双方申报、有四个时间戳，但**没有协议正文、没有协议版本、没有双方签署记录**（`module-jobs-marketplace.sql:148-171`）。一旦兼职者投诉"当时说的是 80 一小时"，平台只能拿快照数字说话，拿不出双方认可过的条款（见 09-05）。

### 2.4 关键节点零通知

录用、开工提醒、工时待确认、结算完成、争议被提起、裁定结果——全部不通知。`JobService.java` 里 `notification` 出现次数为 0，而商家拒单是会通知学生的（`backend/src/main/java/com/campuslife/service/MerchantService.java:256`）。兼职是"低频 + 双方异步"的场景，不通知等于把流程交给用户自己想起来（见 09-06）。

### 2.5 三闸门默认全关，功能开箱即死

`job.offsite.enabled=0`、`job.paid.enabled=0`、`job.category.takeover_class.enabled=0`（`backend/src/main/resources/db/module-safety-gates.sql:8-10`），加上小程序发布表单强制日薪 > 0（`pages/publish/publish.js:134-137`），默认配置下**发布必 403、校外与有偿全不可用**，实际能跑的只有"无偿校内互助"，而这条路小程序又发不出去（见 09-07）。

### 2.6 维护成本：1190 行单类

`JobService.java` 一个类 1190 行，同时承担用户端、管理端、状态机、结算、账单、校验、小工具七件事。同类问题在 `DispatchService`(290) 与 `MerchantService`(357) 上尚可，兼职域已经明显超载。

| C. 平台担保交易（下单即冻结，确认后放款） | 体验最好 | 同样受钱包合规限制，且需要退款通道能力 | 未采用 |
| A'. 先到先接用数据库行锁 / Redis 分布式锁 | 实现直观 | 多实例下 Redis 锁要处理续期与脑裂；行锁要额外连接管理 | **没选**，选条件 UPDATE —— 这是更简单也更正确的做法（`JobMapper.java:16-18` 注释） |

| E. 争议裁定自动取承接方申报 | 省一次管理员输入 | 等于自动偏向一方（方案 §5.3.4） | **没选**，强制管理员填数量（`JobService.java:739-741`） |

## 五、如果重做会怎么改

1. **先把交易的"最后一公里"定下来，再写履约代码。** 现在 1190 行 Service 全都在为一张不可支付的账单服务。正确顺序是：确认支付能力（分账 or 只记账）→ 定"付款确认"模型 → 再写状态机。若只能记账，就必须有 `employer_paid_at / worker_received_at / payment_proof` 三个字段，否则 `settled` 是个假状态。
2. **账单写入统一走"upsert + 系数校验"。** 三条 `biz_no` 的金额只在"第一次写入"时正确，这是 `INSERT IGNORE` 的结构性问题。应改为 `ON DUPLICATE KEY UPDATE amount_cents = VALUES(amount_cents)`，并在写入后回读校验 `payable - fee = income`。
3. **调度与通知做成统一出口。** 现在每个域各写各的（商家域有通知、兼职域和配送域没有）。应在 `JobService` 抽 `notifyParties(contract, event)`，把 6 个状态推进点都接上。
4. **拆类。** `JobService` 按"用户端 / 管理端 / 结算账单"拆三个服务，结算单独一个 `JobSettlementService`——它是最需要单测的部分，而现在一条单测都没有。
5. **补三类测试。** 并发抢占（5 请求只 1 成功）、争议金额一致性（裁定后账单金额 = 裁定数量 × 快照单价）、取消幂等（重复取消不重复记账）。这三条正好覆盖两个 P0 和一个 P1。

## 六、本维度未覆盖的部分（说明原因）
