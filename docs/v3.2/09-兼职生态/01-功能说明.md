## 一、这个功能解决什么问题

校园里的**非正式用工撮合**：一个学生要找人代取快递、代跑腿、家教、促销、临时帮工，另一个学生想赚点钱。平台做三件事——

1. **撮合**：发布岗位 → 接单/报名 → 录用（`JobService`，`backend/src/main/java/com/campuslife/service/JobService.java:31-45`）。
2. **履约**：开工 → 双方各自提交计价数量（工时）→ 一致则结算，不一致自动转争议（`JobService.java:517-572`）。
3. **记账**：结算后生成三条履约账单——雇主应付、平台服务费、兼职者净收入（`JobService.java:917-944`）。

它**刻意不是钱包**。类注释写得很直白：「钱只进 earnings_ledger（履约账单）。这里没有钱包、没有余额、没有提现；金额一律人民币分，费率取合约快照」（`JobService.java:39-40`）。建表脚本第一行同样声明：「履约账单（**不是钱包余额、不是已付款、不可提现**）」（`backend/src/main/resources/db/module-earnings-ledger.sql:1`）。

设计上有两条分区（`docs/校园帮功能方案-兼职钱包配送与圈子.md:77-84`）：

| 分区 | 发布方 | 接单方式 | 默认开关 |
|---|---|---|---|
| `campus` 校内互助 | 同校学生 | 先到先接（一条条件 UPDATE 抢占） | 开 |
| `offsite` 校外兼职 | 合作方/机构 | 报名 + 发布者筛选 | **关**（`job.offsite.enabled=0`） |

另有两道独立闸门：替课类目 `job.category.takeover_class.enabled=0`、有偿接单 `job.paid.enabled=0`（`backend/src/main/resources/db/module-safety-gates.sql:8-10`）。三闸门全部默认关闭，因此**当前代码状态下的可运行形态是「无偿校内互助」**。

## 二、用户看到的样子（小程序端）

三个页面，均已在 `app.json` 注册（`app.json:31-33`）。

### 2.1 岗位列表 `pages/jobs/jobs`

`onShow` 并发拉三个接口：认证状态（`GET /verification/me`）、岗位开关（`GET /jobs/gates`）、岗位列表（`GET /jobs`）（`pages/jobs/jobs.js:47-51`）。

- 顶部分区切换：校内互助 / 校外兼职（`pages/jobs/jobs.js:9-12`）。
- 结算方式筛选：全部 / 日结 / 周结。
- 列表默认 `schoolScope=local`，即只看本校岗位（`pages/jobs/jobs.js:22`）。
- **开关不猜**：`gates.loaded=false` 时不显示"未开放"，等接口回来再显示（`pages/jobs/jobs.js:24-35` 的数据结构 + 注释）。
- 触底加载下一页（`pages/jobs/jobs.js:59-62`）。

> **发布入口不在 jobs 页**：兼职与二手/动态/活动共用同一个「发布」合页 `pages/publish`，选到"兼职"类型后提交 `api.publishJob`（`pages/publish/publish.js:164-172`）。表单只覆盖标题、日薪、结算方式、地点、时间说明、正文六个字段，后端支持的 `scope/takeMode/categoryKey/headcount/deadlineAt` 在小程序侧没有对应控件。另有一条前端硬规则：兼职必须日薪 > 0（`pages/publish/publish.js:134-137`）——这条与后端的有偿闸门冲突，后果见 02 第三节与问题 09-07。

### 2.2 岗位详情 `pages/job-detail/job-detail`

用户路径：列表点卡片 → 详情页 → 按分区出现不同按钮。

- 校内先到先接：`抢单` → `POST /jobs/{id}/take`（`pages/job-detail/job-detail.js:221`）。成功后提示「岗位已经归你。进入履约单后可以开工、提交计价数量…」（`pages/job-detail/job-detail.js:226`）。
- 校外报名：填写 200 字以内留言 → `POST /jobs/{id}/apply`（`pages/job-detail/job-detail.js:256`）。
- 发布者视角：详情页额外出现报名列表，可逐条 `录用/拒绝`（`pages/job-detail/job-detail.js:131`、`:305`）。
- 页脚固定两行合规文案：「服务费按接单那一刻的费率快照计算…」（`pages/job-detail/job-detail.wxml:47`）、「履约账单不是钱包余额，也不是已付款项，不能提现。」（`pages/job-detail/job-detail.wxml:48`）。

### 2.3 我的兼职 `pages/job-mine/job-mine`

`GET /jobs/mine` 一次返回三组：我发布的、我承接的、我作为发布方的履约单（`JobService.java:195-203`）。第三组是必需的，否则发布方录用完就找不到单子去确认工时（`backend/src/main/java/com/campuslife/mapper/JobMapper.java:218-240` 注释）。

按角色出现的动作按钮：

| 动作 | 接口 | 证据 |
|---|---|---|
| 开工 | `POST /jobs/contracts/{id}/start` | `pages/job-mine/job-mine.js:193` |
| 提交/确认计价数量 | `submit-hours` / `confirm-hours` | `pages/job-mine/job-mine.js:239-240` |
| 取消 | `POST /jobs/contracts/{id}/cancel` | `pages/job-mine/job-mine.js:287` |
| 发起争议 | `POST /jobs/contracts/{id}/dispute` | `pages/job-mine/job-mine.js:321` |

页面上有三块金额分别展示：雇主支付额、平台服务费、兼职者净收入，全部来自后端 `settlement`，前端只做分→元格式化，不重算公式（`utils/job-format.js:187-201`、`utils/job-format.js:9-10` 注释）。账单区固定标注「履约账单不是钱包余额，不是已付款项，不可提现。本页没有任何充值、提现或余额支付入口。」（`pages/job-mine/job-mine.wxml:68`）。

### 2.4 前端的展示口径

状态文案集中在 `utils/job-format.js`，与后端状态机一一对应：

- 岗位状态 9 项：`open/recruiting/taken/working/pending_confirm/settled/disputed/refunded/cancelled`（`utils/job-format.js:23-33`），只有 `open|recruiting` 可接可报（`utils/job-format.js:34-35`）。
- 履约单状态 7 项：`created/working/pending_confirm/settled/disputed/refunded/cancelled`（`utils/job-format.js:38-46`）。
- 账单条目 3 项：`job_payable / platform_fee / job_income`（`utils/job-format.js:66-70`），状态 `frozen/settled/refunded`（`utils/job-format.js:71`）。
- 金额换算只允许在 `formatCents` 一处做（`utils/job-format.js:74-78`），页面禁止出现 `/100`（`utils/job-format.js:5-7` 注释）。

## 三、运营看到的样子（Web 端）

入口：管理后台 `#/jobs`（`web/src/router/index.js:47`），页面 `web/src/views/Jobs.vue`（658 行），API 封装 `jobAdminApi`（`web/src/api/index.js:140-148`）。

两个页签：

1. **岗位审核**（`web/src/views/Jobs.vue:21`）：列表支持关键词、只看待审核、分页（`web/src/views/Jobs.vue:450-468`）。每行四个动作——通过 / 驳回 / 下架 / 费率 / 履约单（`web/src/views/Jobs.vue:87-91`）。
2. **履约与争议**（`web/src/views/Jobs.vue:22`）：按状态筛选履约单（`web/src/views/Jobs.vue:109`），每行可"详情"或"裁定"（`web/src/views/Jobs.vue:175-176`）。裁定弹窗要求：选择裁定方式、`settled` 必须填确认数量、必须填理由、必须勾选"已核对双方申报"（`web/src/views/Jobs.vue:616-657`）。

三个业务动作：

- **审核/下架** `POST /admin/jobs/{id}/review`（`web/src/views/Jobs.vue:510`）。下架必须填原因。
- **逐岗位费率** `POST /admin/jobs/{id}/fee`（`web/src/views/Jobs.vue:547`）。费率模式 `none|amount|rate`，`rate` 是万分比（500 = 5%），前端校验非负整数且 ≤10000（`web/src/views/Jobs.vue:547-576`）。
- **争议裁定** `POST /admin/jobs/contracts/{id}/arbitrate`（`web/src/views/Jobs.vue:616`）。页面明写「金额只改履约账单状态，不产生任何可提现余额」（`web/src/views/Jobs.vue:312`）。

页面顶部也有一句总声明：「这里的『履约账单』只是应付 / 应收记录，**不是钱包余额，也不是已付款，更不能提现**」（`web/src/views/Jobs.vue:7`）。

**权限**：`AdminJobController` 只允许 `super` 与 `school` 两种角色（`backend/src/main/java/com/campuslife/controller/AdminJobController.java:117-120`）；校管只能看本校，学校从登录态取，不接受前端传参（`AdminJobController.java:123-141`）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 三条闸门（服务端判定，前端藏按钮只是体验）

`JobService.assertGate`（`JobService.java:996-1008`）与 `publish` 的校验链（`JobService.java:270-280`）顺序固定：

1. `scope=offsite` → 必须 `job.offsite.enabled`，否则 403「校外岗位资质未核验，暂未开放」。
2. `category_key=takeover_class` → 必须 `job.category.takeover_class.enabled`，否则 403。
3. `pay_cents>0` → 必须 `job.paid.enabled` **且** 当前用户通过有偿岗位核验（`verification.requireVerifiedForPaidJob`）。

三开关默认 `0`（`module-safety-gates.sql:8-10`），且 `enabledStrict` 在查库失败/键不存在时**当作关闭**（`backend/src/main/java/com/campuslife/service/FeatureFlags.java:44-58`）——fail-closed。

### 7.2 谁能接、谁能报

| 规则 | 判定 | 证据 |
|---|---|---|
| 未过审不能接 | `audit_status != passed` → 拒绝 | `JobService.java:1010-1013` |
| 校内岗位必须同校 | fail-closed：岗位或用户任一方无学校都拒绝 | `JobService.java:1023-1032` |
| 过期不能接/报/录用 | `deadline_at < now()` → 拒绝，不是只做展示 | `JobService.java:1035-1039` |
| 不能接自己的岗位 | `userId.equals(job.getUserId())` → 拒绝 | `JobService.java:355`、`:397` |
| 校外岗位不能直接接 | 必须走 `apply` | `JobService.java:353` |
| 校内先到先接不能报名 | 直接接即可 | `JobService.java:398-400` |

### 7.3 并发与超发控制

- **校内抢占**：一条条件 UPDATE，`WHERE taken_by IS NULL AND workflow_status='open' AND scope='campus' AND audit_status='passed' AND (deadline 未过)`，影响 1 行才算接单成功（`backend/src/main/java/com/campuslife/mapper/JobMapper.java:30-39`）。
- **校外名额**：`UPDATE job SET accepted_count = accepted_count + 1 WHERE audit_status='passed' AND accepted_count < headcount AND workflow_status IN ('open','recruiting')`——名额上限写进 WHERE，不是先查再算（`JobMapper.java:47-55`）。
- **重复录用**：报名状态推进带 `status='pending'` 条件，第二次命中 0 行 → 抛异常 → 整个事务回滚 → 名额自动释放（`JobService.java:480-486`）。
- **名额归还**：开工前取消时校外岗位 `releaseSeat`（`JobMapper.java:61-65`、`JobService.java:588`）。

### 7.4 结算规则

- 双方各自写自己那一列（`worker_hours` / `employer_hours`），写入带状态条件 `status IN ('working','pending_confirm')`（`backend/src/main/java/com/campuslife/mapper/JobContractMapper.java:30-45`）。
- 两个值都到齐且相等 → `settle`（条件 `status='pending_confirm'`）→ 写三条账单（`JobService.java:545-572`、`:881-893`）。
- 两个值不等 → 自动转争议，账单按 `frozen` 写入（`JobService.java:568-569`、`:895-914`）。
- 结算金额：`payable = round(pay_cents_snapshot × hours)`；`fee = min(feeCents, payable)`；`income = max(0, payable − fee)`（`JobService.java:926-944`）。费率三模式：`amount`=分/单位×数量、`rate`=报酬×数量×万分比/10000、`none`=0（`JobService.java:957-969`）。
- 金额越界直接拒绝：单笔超 `Integer.MAX_VALUE` 分或负数抛「金额超出可记账范围」（`JobService.java:1096-1102`）。

### 7.5 取消与争议的边界

| 场景 | 结果 | 证据 |
|---|---|---|
| 开工前取消 | 履约单 `cancelled`；校外岗位归还名额；三条账单写 `refunded`，金额 0 | `JobService.java:585-591`、`JobContractMapper.java:66-70` |
| 开工后取消 | 只按 `min(worker, employer)` 结算，其余视为退回；双方都没确认则整单退回 | `JobService.java:593-602`、`:1089-1094` |
| 任一方发起争议 | 履约单 `disputed`，账单 `frozen`，不可结算 | `JobService.java:610-617`、`JobContractMapper.java:59-63` |
| 管理端裁定 `settled` | 必须显式传数量，不允许自动取承接方申报 | `JobService.java:739-743`、`AdminJobController.java:107-113` |
| 管理端裁定 `refunded` | 整单退回，账单 `refunded` | `JobService.java:761-764` |
| 同一裁定重复提交 | 数量相同 → 幂等返回；数量不同 → 拒绝「不能改为」 | `JobService.java:745-756` |

### 7.6 岗位状态机的白名单

`JOB_FLOW`（`JobService.java:76-85`）：

```text
open       -> taken | recruiting | cancelled
recruiting -> working | cancelled
taken      -> working | cancelled | disputed
working    -> pending_confirm | cancelled | disputed
pending_confirm -> settled | disputed | cancelled
disputed   -> settled | refunded | cancelled
settled / refunded / cancelled 是终态
```

但**展示状态不是靠单条边推进的**：多名额岗位由该岗位下所有履约单聚合计算（`JobService.java:836-872`），否则"第一张结算后岗位进 settled，第二张就再也推不动"（`:821-828` 注释）。真正决定权限的是 `job_contract` 的条件 UPDATE，不是 `job.workflow_status` 这一列。
