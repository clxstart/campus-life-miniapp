## 二、资金与对账（不涉及资金？——不，涉及但未实现）

**结论：不通过（原因：账单金额可能与裁定不一致；平台服务费无实收；无对账）。**

- **本域按设计不持有资金**：`earnings_ledger` 明确声明"不是钱包余额、不是已付款、不可提现"，脚本刻意不建 wallet/balance 表（`backend/src/main/resources/db/module-earnings-ledger.sql:1-8`、`module-jobs-marketplace.sql:7`）。`wallet.enabled=0`（`module-safety-gates.sql:7`）。
- **但这不等于"不涉及资金"**：账单是"谁该给谁多少钱"的唯一记录。它的正确性就是资金正确性。
- **P0 缺陷 1**：裁定后 `amount_cents` 不更新（`EarningsLedgerMapper.java:19-22` + `JobService.java:911`、`:758-760`）→ 账单金额与裁定数量不一致。
- **P0 缺陷 2**：平台服务费只在账单里"算了出来"（`JobService.java:929`、`:935`），没有任何收取动作，也没有"雇主已支付服务费"的确认 → 平台商业收入恒为 0。
- **无对账**：没有日对账任务、没有差异清单、没有"账单总额 vs 应结总额"的核对。定时任务全库只有 3 个（`docs/v3.2/04-证据与复核台账.md:44`），均不涉及兼职对账。
- **三处金额口径必须一致**，当前是分裂的：`pay_cents`（分）、`fee_value`（amount 模式=分/单位、rate 模式=万分比）、页面展示（元/两位小数）。口径本身写得清楚（`module-jobs-marketplace.sql:75`、`utils/job-format.js:74-78`），但 `amount` 与 `rate` 混用同一列存两种单位，是下一轮最容易出错的点。
- **回滚要求**：任何已写入 `earnings_ledger` 的行不允许物理删除，只能 `status='void'`（`EarningsLedgerMapper.java:34-35` 已具备该能力，但兼职域从未调用）。这条能力现在闲置，接入账单修正时必须用起来。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：先备份、按序执行、有回滚脚本）。**

### 4.1 前置 SQL 与执行顺序

| 顺序 | 脚本 | 内容 | 依赖 |

### 4.2 幂等性（可重复执行）

- 全部加列/索引都先查 `information_schema` 再 `ALTER`（`module-jobs-marketplace.sql:13-129`）。
- 建表一律 `CREATE TABLE IF NOT EXISTS`（`:132`、`:148`、`:174`；`module-earnings-ledger.sql:10`）。
- 开关一律 `INSERT IGNORE`，**不会覆盖运营已改过的值**（`module-safety-gates.sql:3`）。
- 数据回填只在"列刚添加"时执行一次（`module-jobs-marketplace.sql:52-56`、`:98-102`），重跑不覆盖人工修改。

### 4.3 回滚

**⚠️ 当前没有回滚脚本**。`module-jobs-marketplace.sql` 只做加列与建表，回滚需要手写：

```sql
-- 回滚（仅在确认无在途履约时执行；先 dump 备份）
-- 1) 删表（顺序：子表在前）
DROP TABLE IF EXISTS job_dispute;
DROP TABLE IF EXISTS job_contract;
DROP TABLE IF EXISTS job_application;
DROP TABLE IF EXISTS earnings_ledger;
-- 2) 撤列（13 列）
ALTER TABLE job
  DROP COLUMN `scope`, DROP COLUMN employer_kind, DROP COLUMN partner_id,
  DROP COLUMN take_mode, DROP COLUMN category_key, DROP COLUMN pay_cents,
  DROP COLUMN pay_unit, DROP COLUMN fee_mode, DROP COLUMN fee_value,
  DROP COLUMN headcount, DROP COLUMN deadline_at, DROP COLUMN workflow_status,
  DROP COLUMN taken_by, DROP COLUMN accepted_count;
ALTER TABLE job DROP INDEX idx_job_scope_workflow, DROP INDEX idx_job_taken_by;
-- 3) 开关（注意：会连带关掉其他功能读同一张表的开关，按 key 精确删）
DELETE FROM feature_flag WHERE flag_key IN
  ('job.offsite.enabled','job.paid.enabled','job.category.takeover_class.enabled');
```

**风险**：撤列会丢 `pay_cents` 回填过的价值；删表会丢全部履约与账单历史。所以回滚**只能在试运行环境做**，生产只允许"关闸门"（`feature_flag` 置 0），不允许删表。这条约束必须写进上线手册。

## 九、结论

**不可上线。** 阻断项：**09-01**（交易闭环缺最后一步，商业收入为零、兼职者拿不到钱、无法追责）、**09-02**（争议裁定后账单金额不更新，账实不符）。

两个 P0 都不大（合计约 6 人日），但性质严重：09-02 会直接产生错误的对账数字；09-01 会让"兼职生态"变成一个只发记录、不解决钱的产品。修完这两条 + 09-03/09-04/09-06/09-07 四条 P1，可转为"有条件上线"。
