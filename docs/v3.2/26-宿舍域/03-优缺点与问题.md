## 一、设计优点（为什么这么设计，好在哪）

### 1.1 三条硬规矩全部压在数据库上，不压在 Java 里

`DormService.java:28-33` 的类注释逐条对应：

| 规矩 | 数据库级实现 | 为什么这比 Java 判断强 |
|---|---|---|
| 一人一宿舍 | `dorm_member.UNIQUE KEY uk_dorm_user (user_id)`（`db/module-dorm-v31.sql:49`） | 并发、多实例、绕过接口直接插库，全都挡得住 |
| 全员判定基数当日冻结 | `ensureSignRow` 用 `ON DUPLICATE KEY UPDATE dorm_id = dorm_id`（`DormMapper.java:131-137`） | 第一行写入后再怎么调用都改不了 `member_count` |
| 奖励只发一次 | 条件更新 `... AND all_done = 0 AND signed_count >= member_count`（`DormMapper.java:159-164`） | 并发下 InnoDB 当前读 + 行锁，只有一个请求返回 1 |

`DormMapper.java:19-25` 甚至把这条纪律写成三条「纪律」：发分 SQL 一行都不写在这里；一人一宿舍靠唯一键；时间参数由 Java 传入不用 `CURDATE()`。

**这是全仓库把「正确性交给数据库」做得最彻底的一个模块。**

### 1.2 「最后一刻退出把 7/8 变成 7/7」这个坑被提前想到并堵住

`db/module-dorm-v31.sql:12-14` 的注释：

> 成员数固化（对应测试手册第 11 条「中途有人退出，当日不再补发」）：`member_count` 在当日第一行创建时写入，之后不再变。判定基数一旦跟着成员数变，「最后一刻退出」就能把 7/8 变成 7/7 白拿一次奖励 —— 判定基数必须冻结。

这条是本模块最有价值的设计判断。绝大多数同类实现都会用「当前成员数」做分母，然后被用户用「退出」绕过。

### 1.3 已签人数不盲加，按成员集合重算

`DormMapper.java:139-145` 的 `countSignedMembers` 是 `COUNT(*) ... JOIN sign_roll`，而不是 `signed_count = signed_count + 1`。

好处：**回调重复触发天然幂等**。签到回调可能因为重试、重复提交被调多次，盲加会算错，重算不会。注释也点明了这一点（`DormService.java:303-304`）。

### 1.4 事务边界的取舍：宿舍失败绝不回滚签到

`SignService.java:150-163` 用 `TransactionSynchronization.afterCommit` 注册回调；`DormService.java:280-287` 再套一层 try-catch。

两层保险的意图很清楚（`SignCompletedListener.java:8-11`）：「宿舍域依赖签到，签到不该依赖宿舍」「宿舍判定失败不能回滚签到」。方向完全正确：签到是主业务，宿舍是附加。

### 1.5 外部依赖全部容错，而且容错有层次

奶茶券链路涉及 `reward_item`（功能 6 的表，可能不存在）与 `coupon`：

- `rewardItem` 查询异常 → 吞掉，记日志，只发成长值（`DormService.java:402-408`）；
- 商品不存在/库存 0 → 不发券，只记 `log.info`（`:409-412`）；
- 扣库存失败 → `break`，保留已发的（`:421-424`）；
- 发券异常 → 吞掉，不影响成长值（`:427-430`）；
- 库存用条件更新 `WHERE item_key=? AND stock>0`，不会扣成负数（`DormMapper.java:239-241`）。

**「券可以没有，成长值必须有」** 这个优先级排得很清楚。

### 1.6 加入时先锁宿舍行

`DormService.java:238-239` 注释：「先锁宿舍行再数人数：否则 8 人宿舍能被第 9、第 10 个人同时挤进来」，落地就是 `SELECT id FROM dorm WHERE id = ? FOR UPDATE`（`DormMapper.java:59-60`）。

超员是这个功能最容易被忽略的错误类型：8 人上限在并发下变成 10 人，且很难复现。

### 1.7 时区与周期处理一致

`BEIJING` 常量与签到/积分/论坛榜同源（`DormService.java:45-46`）；`mondayOf` 用 `previousOrSame(MONDAY)`；周键走 ISO（`:512-521`）；Mapper 里不用 `CURDATE()`（`DormMapper.java:24-25`）。

### 1.8 管理端权限分得清

- 列表：校管强制本校，传别校 403（`AdminDormController.java:92-101`）；
- 详情/解散：`DormService` 再校验一次 `school_id`（`:460-463`、`:483-488`）；
- 补跑：仅 super，理由是影响全平台（`AdminDormController.java:61-66`）。

三层都拦，不是只靠前端隐藏。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 代价一：后端可以上线，但用户看不见它

宿舍域有 8 个接口、3 张表、536 行 service、一套完整的状态机——然后小程序里**没有页面**。

`pages/` 46 个目录里没有宿舍页；`getDormMe/createDorm/joinDorm/leaveDorm` 四个方法定义在 `utils/api/points.js:172-200`，**零调用**。

这不是「没写完」，是「写完了没接」。而它依赖的学生认证页也只有 `.js`（25-02）——两条链路一起断，建宿舍这件事在真机上走完不了一步。

### 2.2 代价二：「本期不做跨校互通」只写在注释里

`db/module-dorm-v31.sql:26` 注释：「`school_id` 所属学校；NULL=用户未绑定学校。**本期不做跨校互通**」。

但 `join` 完全不看学校（`DormService.java:226-250`）。任何学校的用户拿到 6 位码就能加入任何宿舍。而邀请码的设计初衷就是「口头传播」（`DormService.java:54-55` 注释：去掉易混字符「避免口头传播时抄错」）——口头传播天然跨群、跨校。

注释里的产品意图与代码行为不一致，且**没有任何一处拒绝逻辑**。

### 2.3 代价三：单人宿舍是合法的，于是全员签到奖励可以单人领

- `create` 只要已认证就能建，没有「至少 2 人」的要求（`DormService.java:179-223`）；
- `member_limit = 8` 是上限，没有下限（`:203`）；
- 全员判定是 `signed_count >= member_count`（`DormMapper.java:162`）。

于是：1 个人建宿舍 → 自己签到 → 1/1 达标 → 每天 +5P/+8G。

按 `task_catalog` 的 `daily_cap=1`，一个账号一天 5P/8G；10 个账号（或 10 个已认证的人各建一个单人宿舍）就是 50P/80G/天。认证门槛存在（要人工审核），但 auto 模式下一旦放开，成本极低。

**这不是漏洞，是设计里没设下限。**「宿舍」这个词隐含了多人，代码没把它变成约束。

### 2.4 代价四：`all_done` 置位与发分不在同一事务，中断即永久丢失

`DormService.java:307-321` 的顺序：

```
1. claimAllDone(dormId, bizDate)   → all_done: 0 → 1
2. for each member: points.award(...)
```

第 2 步任一成员失败只 `log.warn`，且注释明说「当日 all_done 已置位，不重复补发（避免重复发）」（`:318`）。

所以：如果进程在 1 与 2 之间挂了，或第 2、3 个成员发分时数据库抖动，**其余成员永远拿不到**，且没有任何补跑入口（论坛榜有 `resettle`，宿舍没有）。

「避免重复发」与「避免漏发」在这里被前者压倒了。技术上可以两者兼得：`task_log` 的 `biz_key = dorm:{id}:{date}` 已经是按用户维度的唯一键（`PointsService` 幂等），重复调用 `award` 只会返回 `ALREADY`，并不会重复发。所以这个「不重复补发」的理由**不成立**——补发是安全的。

### 2.5 代价五：周榜的分数口径与「宿舍」关系不大

`DormMapper.java:180-189`：

```sql
LEFT JOIN task_log t ON t.user_id = m.user_id AND t.biz_date BETWEEN #{from} AND #{to}
```

不区分 `task_key`。所以：

- 宿舍成员在论坛榜拿的分、外卖点单拿的分、兼职结算拿的分，**全算宿舍分**；
- 而 `task_log.p` 在 `PointsService` 判日上限**之前**就写入并提交（`PointsService.java:116` 对照 `:122-125`），所以**命中上限没实发的记录也被计入**。

两个后果：①分数虚高，且虚高部分与实发不对应；②一个高分用户加入哪个宿舍，那个宿舍就变强——这是 26-06 的基础。

### 2.6 代价六：没有冷却期，结算前跳槽可以偷冠军

周榜在周一 00:20 结算。在此之前的任何时刻，一个高分用户可以：

1. 退出当前宿舍（`leave` 无冷却、无惩罚，`DormService.java:257-272`）；
2. 新建一个只有自己的宿舍（`create` 无冷却，`:179-223`）；
3. 自己本周的 `task_log.p` 就是新宿舍的全部分数；
4. 若自己分数最高，新宿舍即冠军，自己拿 +30G（`DormService.java:368-382`）。

如果他原本就在强宿舍，这一步甚至可能让原宿舍失去冠军——**退出行为影响的不只是自己**。

修法很便宜：`leave` 后 N 天内不允许建/加入（冷却），或周榜分数只按「结算时仍在宿舍的成员在本周期间的在舍时间加权」。

### 2.7 代价七：舍长是「下不来的位置」

- 舍长有成员时不能退出（`DormService.java:264-266`），提示「需先把宿舍交给其他成员，或联系管理员解散」；
- 但**没有转让接口**（`DormController` 只有 me/create/join/leave 四个方法）；
- 也**没有舍长自行解散接口**（解散只有管理端）。

所以舍长唯一出路是找管理员。对一个「学生自发组织」的功能来说，这是死路：一个 8 人宿舍的舍长毕业了，只能让运营手动解散。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 优点 | 代价 | 为什么没选（依据代码注释） |
|---|---|---|---|
| **`member_count` 实时跟随实际成员数** | 逻辑直觉 | 「最后一刻退出」可把 7/8 变 7/7 白拿奖励 | 明确否决，`db/module-dorm-v31.sql:12-14`。这是本模块正确性最高的一处判断 |
| **`signed_count` 盲加 +1** | 一次 UPDATE，简单 | 重复回调会多算 | 改为按成员集合重算，`DormMapper.java:139-145` |
| **一人多宿舍** | 用户可以既属班级宿舍又属社团宿舍 | 跨宿舍刷全员签到 | 明确否决，`uk_dorm_user` 数据库级唯一（`db/module-dorm-v31.sql:6-8`） |
| **宿舍独立签到按钮** | 体验更聚焦 | 与全局签到重复、两套积分入口 | 明确否决，复用全局签到 + 回调（`SignCompletedListener.java:8-11`） |
| **宿舍判定放进签到事务** | 一次事务搞定 | 宿舍失败会回滚签到 | 明确否决，`afterCommit` 隔离（`SignService.java:150-163`） |
| **奶茶券发不出就报错** | 用户知道没拿到 | 券依赖外部表，会把成长值一起拖垮 | 明确否决，只记日志（`DormService.java:401-412`） |
| **周榜按学校分组** | 每校都有冠军，公平 | 单校阶段过度设计 | 未做。**多校后成为缺陷**（26-05） |
| **`leave` 冷却期** | 挡跳槽偷冠军 | 影响正常换宿舍体验 | 未做（26-06） |
| **`all_done` 与发分同事务** | 不漏发 | 一次发分失败会整体回滚，可能导致「一直发不出去」 | 选了「先置位再发」，代价是漏发无补（26-04）。**两种都能接受，但必须配补跑**——补跑没做，所以这个取舍失衡了 |

## 五、如果重做会怎么改

1. **把「宿舍」变成真多人**：`create` 后进入 N 天「待成团」状态，未达 2 人不成团、不发全员奖励、不参与周榜。这一个改动同时消掉 26-03 与 26-06 的一半。
2. **`all_done` 与发分改成「可重入」**：既然 `task_log` 的 `biz_key` 已经是用户维度唯一键，补发天然安全。把「置位后不再重试」改成「置位后允许补偿扫描」，26-04 消失。
3. **周榜分数改口径**：从 `SUM(task_log.p)` 改成「宿舍相关任务白名单」或直接用 `point_log` 实发金额。现在这个口径既虚高又与宿舍行为无关，是最该改的一处。
4. **加冷却期与转让**：`leave` 后 7 天冷却（挡 26-06）、`transfer` 接口（挡 26-07）。两条都是小工作量、高收益。
5. **补页面**（最大缺口）：后端写得很完整，缺的只是一个 `pages/dorm/dorm`。这是本模块性价比最高的一件事——3 人日换一个完整功能上线。
6. **补 4 条并发测试**（现在 0 条）：并发加入不超员、并发签到只发一次、中途退出不补发、一人一宿舍。这四条正好覆盖本模块所有「压在数据库上」的正确性声明——没有测试，这些声明就只是注释。
