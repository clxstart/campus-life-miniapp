## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：按顺序执行 + 补 `dorm_member` 与 `dorm_sign` 的外键/清理策略）**

### 4.1 前置 SQL 与执行顺序

```text
1) backend/src/main/resources/db/module-points-v31.sql   -- task_catalog / task_log / point_log 前置
2) backend/src/main/resources/db/module-sign-v31.sql     -- sign_roll：宿舍判定靠它
```

### 4.3 需要补的约束


### 4.4 回滚

```sql
-- 停发分（保留数据）
UPDATE task_catalog SET enabled = 0 WHERE task_key IN ('dorm_all_sign','dorm_week_first');

-- 停结算（代码层面）：把 DormService.scheduledSettle 的 @Scheduled 注释后重启

-- 彻底回滚（会丢历史签到汇总，仅在无需复核时）
DROP TABLE IF EXISTS dorm_sign;
DROP TABLE IF EXISTS dorm_member;
DROP TABLE IF EXISTS dorm;
DELETE FROM task_catalog WHERE task_key IN ('dorm_all_sign','dorm_week_first');
```

**注意**：`dorm_invite_code` 一旦作废，已经在群里传播的码全部失效，用户会集中投诉「码无效」。软停（`enabled=0`）优先。

已解散宿舍的恢复：

```sql
-- 当前无接口，只能改库（26-08）
UPDATE dorm SET status = 1, dismissed_at = NULL, dismiss_reason = '' WHERE id = ?;
-- 成员关系已被删除，需要重新加入（无法从 dorm_sign 反推完整成员，只能按最近签到记录尽力恢复）
```

第二句是重点：`dismiss` 会 `removeAllMembers`（`DormService.java:493`），**解散是不可逆的**——成员关系一旦删除，只能从 `dorm_sign`/`task_log` 反推，且不完整。所以注释里「误操作可由运维恢复」（`AdminDormController.java:18`）**不成立**。

```text
1. 发现异常（刷分 / 漏发 / 误解散）
```

## 九、结论

# 不可上线（阻断项：26-01、26-02、26-03、26-04、26-05、26-06）

逐项说明：

1. **26-01 小程序零页面**——功能在用户侧不存在。这是最硬的一条，也是唯一「只要不在小程序上线就完全没有用户可感知风险」的一条。如果本期只上 Web 管理端（纯运营观察），26-01 可以不阻断；但那样也没有用户侧的宿舍，功能等于没上。
2. **26-02 跨校加入无校验**——外校人可进本校宿舍名单。多校隔离是功能 02 的核心承诺，这里直接破口。
3. **26-03 单人宿舍刷分**——已认证用户建单人宿舍即可日领 5P/8G，批量可放大。
4. **26-04 漏发不可补**——`all_done` 置位与发分不在同一事务，中断即永久丢失，且「补发是安全的」（唯一键在用户维度）这个事实被误判成「不能补」。
5. **26-05 周榜分数失真**——含未实发的分、含非宿舍任务分、不按学校分组。冠军可能是「分数最高但实际没发出去」的宿舍。
6. **26-06 跳槽偷冠军**——无冷却期，周六退出、建单人宿舍、周一拿 30G。

放行路径：修完 26-01 ~ 26-06 后**可降级为「有条件上线」**（条件：26-07、26-08 在灰度期完成；补 4 条并发测试；`weekScores` 做缓存）。

**值得说清的一点**：这个模块的**后端质量是这一批 V3.1 功能里最高的**——三条硬规矩全部压在数据库约束上，注释解释了每个取舍，外部依赖全部容错。它的问题几乎全在「外围」：没页面、没校校验、没冷却、没补发、没测试。这些都比「重构核心逻辑」便宜得多。
