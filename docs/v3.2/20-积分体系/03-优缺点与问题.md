## 一、设计优点（为什么这么设计，好在哪）

1. **把"查余额 → 加 → 写日志 → 加成长值 → 判上限"收进一次调用**。十多个发分场景各写一遍必然对不上账，收口后业务侧只负责"该不该发、业务号是什么"——`PointsService.java:20-34` 的类注释把取舍写清了，代码也照做了。
2. **幂等交给数据库唯一键，而不是"先查再插"**。并发下"先查再插"必然穿透；`uk_task_idem(user_id,task_key,biz_key)` 是数据库级兜底 —— `PointsService.java:114-119`、`module-points-v31.sql:77`。
3. **扣分用条件更新，物理上不可能扣成负数**。`UPDATE ... WHERE balance >= cost` 一条语句解决"检查 + 扣减"的竞态 —— `PointsMapper.java:83-85`。
4. **"今天"用 `Asia/Shanghai` 硬编码，不依赖服务器时区**。签到、宠物、宿舍三处共用同一常量 —— `PointsService.java:40-41`、`SignService.java:35`、`DormService.java` 的 `BEIJING`。这类时区 bug 一旦上线极难复现，提前锁死是对的。
5. **任务目录 30 秒缓存 + 主动失效**。读多写极少的数据不值得每次查库，改完立刻 `evictCatalog()` 又避免"后台改了前台没变" —— `PointsService.java:46`、`PointsService.java:80-81`、`PointsService.java:271`。
6. **失败可观测**。每个发分场景都 `log.info` 打了 `task/ user / biz / result` 四要素（`AfterCommitPointsAwarder.java:50`），排障时能一眼看出是 `CAPPED` 还是 `ALREADY`。
7. **不碰钱**。全仓库无提现/转账/积分类支付接口，`POINTS_PER_YUAN` 只用于展示（`PointsService.java:43-44`、`pages/points/points.wxml:120`），这是准货币系统最重要的一条红线。

## 二、设计缺点与代价

1. **两本账（`task_log` 事实账 / `point_log` 金额账）没有对账机制**。设计上两者语义不同是对的（`docs/v3.1/积分体系-功能说明与测试手册.md:112`），但 `CAPPED` 时只写一本不写另一本（`PointsService.java:122-125`），且**没有任何巡检 SQL、没有管理端视图、没有告警**能把差额捞出来。准货币系统"账不平且无人知道"是结构性缺陷。
2. **日上限靠"插入后再数"，在多实例 / 高并发下不成立**。要真正卡住必须 `SELECT ... FOR UPDATE` 或用 Redis 计数，代价是锁等待；当前选择了性能，牺牲了上限。
3. **`spend()` 与 `award()` 两套幂等键**（`point_log.uk_user_biz` vs `task_log.uk_task_idem`），且 `spend()` 的 bizKey 由调用方拼、还会重复加模块前缀（`RewardService.java:107` 传 `redeem:12`，`PointsService.java:154` 再拼成 `redeem:redeem:12`）。对账时无法用同一规则把"兑换记录"与"扣分流水"关联起来。
4. **没有任何管理端读账能力**。客服问"我这 30 分哪来的"，运营只能进数据库。这是本轮排查里对商业上线影响最直接的一条（问题 20-05）。
5. **没有整域开关**。单个任务可停，但"积分体系整体出问题"时无法一键关停——而 `SearchService`/`PayController` 这类模块是有整域开关的（`FeatureFlags.java:37-41` 的用法）。
6. **`user_points` 行的创建依赖"第一次发分"**，不是注册时建行，于是 `me()` 有了 0 行分支（问题 20-04）。这是"懒建行"省一次写入换来的稳定性代价。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 决策 | 选了 | 没选 | 判断 |
|---|---|---|---|
| 账本表 | 复用 `user_points` + 扩 `point_log` | 新建 `points_account`/`points_ledger` | **对**。宠物域已在写这两张表，新建等于双钱包，历史余额还得迁移（`docs/v3.1/积分体系-功能说明与测试手册.md:111`）。 |
| 发放时机 | 同步、同事务 | 异步队列 | **半对**。同事务保证"发帖成功 ⇄ 加分"，但让积分模块的 SQL 缺失变成登录链路的 500（问题 20-01）。正解是"同事务发分 + 异常隔离到 REQUIRES_NEW"，现在只做了一半。 |
| 幂等键 | 数据库唯一键 | 业务代码判断"发过没有" | **对**。并发下业务判断必穿透。 |
| 日上限口径 | 次数 | 积分数 | **对**。次数能同时表达"签到 1 次""外卖 2 单"。但**缺全局日上限**：单任务限了次数，没限"一天总共能拿多少分"，多任务叠加后单日收益无天花板。 |
| 超上限处理 | 留痕不发分 | 回滚插入 | **值得商榷**。留痕的动机（`PointsService.java:123` 注释"避免刷上限的人反复试探"）成立，但代价是两本账永久不平，且没有对账工具兜住。 |

### 4.3 未列进清单但需知晓的三点

1. **没有全局日上限**：只有单任务 `daily_cap`，没有"单人单日总发分上限"。多任务叠加后单日收益无天花板（`PointsService.java:109-125` 只看单任务）。
2. **积分不清零、不过期**：`point_log` 只追加，`user_points.balance` 永不清零；这对用户友好，但平台的"未兑付负债"会单调增长，需在财务侧知道这件事。
3. **无积分转账/赠予**：全仓库无相关接口，这是对的（否则等于开放二级市场）；但反过来也意味着"补偿只能靠人工改库"（见 20-05）。

## 五、如果重做会怎么改

1. **账本先于功能**：先建 `admin_audit_log` 与"流水查询/人工调整"两个能力，再谈任务目录。准货币系统没有读账能力，等于没有客服。
2. **发分一律"同事务写事实 + 提交后发分"**：把 `award()` 拆成"写 `task_log`（同事务）"与"加余额（afterCommit + REQUIRES_NEW）"两步，天然免疫 20-01 这类"积分模块抖动打死登录"的问题，代价是允许 `task_log` 有事实而余额稍后到——但那时可以靠重试补跑，而不是靠人肉进库。
3. **日上限改成单语句原子插入**：`INSERT INTO task_log(...) SELECT ... WHERE (SELECT COUNT(*) FROM task_log WHERE ...) < cap`，一条 SQL 同时解决幂等与上限，不用两把锁。
4. **注册即建 `user_points`/`user_growth` 行**，把"懒建行"的分支全部消灭（覆盖 20-04）。
5. **任务目录与埋点做一致性校验**：启动时或 CI 里跑一条脚本，凡 `task_catalog` 里有、代码里无调用方的键，直接报红——20-06 这类"承诺了不给"的问题可以零成本防住。
