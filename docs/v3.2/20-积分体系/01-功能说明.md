## 一、这个功能解决什么问题

积分是全平台的**准货币**：签到、发帖、外卖、兼职、二手、宿舍、宠物八个模块都靠它发奖励，兑换池再把它换成外卖立减券。所以本功能真正要解决的不是"显示一个数字"，而是三件事：

1. **只有一个发放口**。`PointsService` 的类注释写死了纪律：`award()` / `awardCustom()` / `spend()` 三入口，别的模块只决定"该不该发、业务号是什么"——证据 `backend/src/main/java/com/campuslife/service/PointsService.java:20-34`。
2. **余额与流水必须能对上**。余额在 `user_points`，流水在 `point_log`，任务事实在 `task_log`，成长值在 `user_growth`，一次调用里五件事同事务——证据 `PointsService.java:114-134`。
3. **防刷**。幂等靠数据库唯一键（`task_log.uk_task_idem`），日上限靠当日计数，扣分靠条件更新——证据 `backend/src/main/resources/db/module-points-v31.sql:77-78`、`PointsService.java:145-166`。

映射器注释进一步声明"全仓库只允许 `PointsMapper` 对 `user_points`/`user_growth`/`point_log` 做写操作"（`backend/src/main/java/com/campuslife/mapper/PointsMapper.java:10-16`）。本次核对确认 `UPDATE user_points` 确实只有一处（`PointsMapper.java:75-85`），宠物域已改为只读（`backend/src/main/java/com/campuslife/mapper/PetMapper.java:29-41`）——这条纪律**当前成立**。

## 二、用户看到的样子（小程序端）

### 2.1 设计上的操作路径

`pages/points/points` → 余额卡「我的积分 / ≈¥0.63」→ 签到卡「签到 +1 积分」→ 段位卡（点开八段位说明）→ 今日任务列表 → 积分明细分页。数据来自三个接口，任一卡片失败不影响其他卡片——证据 `pages/points/points.js:96-185`。

### 2.3 未注册的后果（必须写清）

1. **真机不可达**。微信不允许 `wx.navigateTo` 到未在 `app.json.pages` 注册的路径，调用必然 fail（`errMsg: page "pages/points/points" is not found`）。所以积分页在真机上是**死链**，不是"藏得深"。
2. **引用关系是闭环死链**：`points` ↔ `points-redeem` 互相跳，`verify` 是唯一的外部引用者但它自己也没注册（`app.json:2-45` 无 `pages/verify/verify`）。四条 V3.1 新链路（积分、兑换、榜单、认证）在小程序侧等于没上线。
3. **不会报错到崩溃，只会静默失败**。`wx.navigateTo` 的 fail 回调在 `pages/points/points.js:242` 处没有处理，用户点了没反应，无 toast、无日志上报。
4. **静态检查发现不了**。`tools/check-all.js` 9/9 通过（见 `docs/v3.2/04-证据与复核台账.md:51-68`），但该套检查不校验"被引用页面是否注册"，所以"9/9 通过"与"页面能点开"是两件事。
5. **后端接口本身是通的**。`GET /api/points/me|tasks|logs`、`POST /api/points/sign` 均已实现（`backend/src/main/java/com/campuslife/controller/PointsController.java:39-65`、`SignController.java:26-31`），可用 curl/Postman 直接调通——**这是"后端已交付、端上没上线"的典型形态**。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 `award()` 的五个返回，业务侧必须分别处理

| 返回 | 触发条件 | 数据后果 | 证据 |
|---|---|---|---|
| `AWARDED` | 正常发放 | `task_log` +1 行、余额/成长值/流水各 +1 | `PointsService.java:127-134` |
| `ALREADY` | 同一 `(user,task,biz_key)` 已插过 | 什么都不改，幂等命中 | `PointsService.java:115-119` |
| `CAPPED` | 当日该任务次数 > `daily_cap` | **`task_log` 行已写入且提交**，只不发分；同 `biz_key` 之后永久 `ALREADY` | `PointsService.java:121-125` |
| `DISABLED` | 任务不存在或 `enabled=0` | 不写任何数据 | `PointsService.java:102-103` |
| `NOOP` | 计算出的 P=G=0 | 不写任何数据（不占日上限） | `PointsService.java:107` |

### 7.2 会拒绝的情况

- `userId` 为空或 < 1 → `IllegalArgumentException("用户无效")`（`PointsService.java:99`）。
- `taskKey` 为空 → `IllegalArgumentException("任务键无效")`（`PointsService.java:100`）。
- 扣分余额不足 → `spend()` 返回 `false`，调用方须自己抛业务异常（兑换场景见 `RewardService.java:109`）。
- 管理端改 P/G 为负、日上限为负、单次奖励 >1000 → 拒绝（`PointsService.java:265-267`）。

### 7.3 会补偿 / 不会补偿的情况

- **会补偿**：同一个 `biz_key` 重复调用不会重复发（`ALREADY`）；`ensurePointsRow`/`ensureGrowthRow` 用 `ON DUPLICATE KEY UPDATE` 兜底建行（`PointsMapper.java:69-73`）。
- **不补偿**：交易类发分走 `afterCommit`（`AfterCommitPointsAwarder.java:45-57`），发分失败只写 `log.warn`，**没有任何重试队列、没有补偿任务、没有人工补发接口**。官方取舍是"发分失败不影响主流程"，代价是这笔积分永久丢失且无告警（问题 20-05）。
- **不做**：积分不可提现、不可转账、无过期清零。前端合规文案写死"100 积分 = 1 元，仅作价值参考，不可提现"（`pages/points/points.wxml:120`），后端换算 `POINTS_PER_YUAN=100`（`PointsService.java:43-44`）。**全仓库无提现/转账接口**，这条红线当前成立。
