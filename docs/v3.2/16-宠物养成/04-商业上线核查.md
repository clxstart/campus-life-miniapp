## 一、合规与隐私

**结论：有条件通过（条件：宠物不面向未成年人做付费诱导；积分兑换需与礼包域合并审查）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 是否收集个人信息 | 通过：只存宠物状态与互动日志，无手机号/学号 | `module-pet.sql`、`module-pet-companion.sql` |
| 是否含未成年人付费风险 | 需登记：宠物是典型"养成 + 抽奖式奖励"设计，若后续加付费道具，未成年人保护必须前置 | `PetCompanionService.java:148-167`（当前购买只花积分，不花钱） |
| 是否涉及随机概率公示 | 有条件：派遣奖励是区间随机（`reward_min~max`），当前**未公示概率** | `module-pet-companion.sql:66-67`、`PetCompanionService.java:293` |

| 数据删除（注销时） | 未覆盖：未见清理 `user_pet`/`pet_dispatch`/`pet_interaction_log` | 需与 `19-个人中心与账号安全` 对齐 |

要点：宠物名 20 字、只校验长度不校验内容（`PetService.java:113`）。宠物名会出现在校园搭子首页，等于给了一个**不过审的展示位**。加一次 `checkText` 即可。

## 二、资金与对账

**结论：不通过（原因：发放侧缺少每日上限，构成准货币的无限产出）**

本功能不直接收付款，但它是**积分的产出与消耗端**，而积分可兑换券/礼包（`23-礼包兑换与券`），因此按"资金相关"对待。

| 检查项 | 结论 | 证据 |
|---|---|---|
| 是否直接收钱 | 不涉及 | 无支付调用 |
| 是否产出积分 | **是**：签到 5 分/天、派遣 20–200 分/次 | `module-points-v31.sql:99`、`:102` |
| 产出是否有日上限 | 签到**有**（cap=1）；派遣**无**（cap=0） | `module-points-v31.sql:99`、`:102`、`PointsService.java:122` |
| 是否有幂等 | 有：`bizKey=日期` / `dispatch:id` | `PetService.java:90`、`PetCompanionService.java:301` |
| 是否有并发保护 | 发分有（先插 task_log 唯一键）；互动次数无 | `PointsService.java:114-119`、`PetService.java:79-80` |
| 单用户理论日产出 | 派遣 ≈ 5760–8640 分（288 次 × 20–30） | 由 5 分钟任务推得（**推算，未实测**） |
| 兑换侧是否设上限 | 需与 `23-礼包兑换与券` 合并核查（本目录不覆盖） | — |

结论口径：**积分是准货币，发分口必须有日上限**。这一条不是"优化项"，与支付域的"退款必须有上限"同级。

## 五、性能与容量

**结论：通过（依据：全部为单行读写，无批量与聚合；未压测）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 互动 | 单次 1 读 + 1 写 + 1 日志 | `PetService.java:93-102` |
| 衰减 | 惰性计算，无定时任务 | `PetService.java:29-38` |
| 派遣 `markDue` | 每次请求调一次批量 UPDATE（把到期的 running 改 claimable）——**需确认是否有时间/范围限制** | `PetCompanionService.java:229`、`:281` |
| 索引 | `idx_pet_dispatch_user(user_id,status)`、`idx_pet_dispatch_end(status,end_at)` | `module-pet-companion.sql:85-86` |
| 压测 | **无** | 台账 3.2 |

风险点：`markDue()` 在每次 `dispatch`/`claim` 请求里都跑一次全表条件更新。若未加 `LIMIT` 或时间范围，派遣记录积累后会变成"每次打开派遣页都扫一遍"（**推测，未验证** —— 需读该 SQL 确认）。上线前建议补一次 `EXPLAIN`。

## 九、结论

**有条件上线（条件：1. `pet_dispatch.dailyCap` 设为有限值；2. 加 `pet.enabled` 开关；3. 宠物名过内容审核）**

- 技术上这是本仓库做得比较扎实的一块：积分单入口、发分幂等、派遣防重三层、进度不信客户端。这些优点让它不构成 P0。
- 但发分侧**缺一道上限**，而积分可兑换实物/券。在有兑换能力的前提下，这属于"资金侧的未闭合口子"，必须在开放兑换前修完（0.2 人日）。
- 若产品决定"宠物只是氛围功能、不接积分兑换"，则可以把 16-01 降为 P2；**但当前积分已与兑换池连通，不适用这个前提**。
- 无后台（16-04）不阻断上线，但会让这个板块的每次内容更新都要研发参与。
