## 一、设计优点（为什么这么设计，好在哪）

1. **积分只有一条通道。** 喂食扣分、衣柜扣分、签到加分、派遣加分，全部经 `PointsService.spend/award/awardCustom`（`PetService.java:14-15`、`PetCompanionService.java:29-30`）。宠物域自己**不碰余额表**，所以不会出现"宠物里能凭空多出积分"的经典漏洞。
2. **发分的幂等性做在最底层。** 先插 `task_log`（唯一键）再动余额，并发只有一个能插进去（`PointsService.java:114-119`）。这比"先查有没有发过、再发"可靠一个量级。
3. **派遣进度不信客户端。** 状态由 `start_at + end_at` 服务端计算，且 `markDue()` 与时间判断双重兜底（`PetCompanionService.java:229-244`）。改手机时间没用。
4. **领取做了三层防重**：状态检查、条件更新 `affected==1`、积分 `bizKey=dispatch:id`（`PetCompanionService.java:286-301`）。这是本仓库里防重复领取最完整的一处。
5. **同一时间只允许一个派遣。** `activeCount>0` 直接拒（`:255`），把"并发开 10 个任务"这条路堵死。
6. **惰性衰减替代定时任务。** 按小时扣饥饿/心情，不需要 `@Scheduled`（`PetService.java:29-38`）。少一个后台任务，少一类"任务没跑导致数据不动"的故障。
7. **每日次数限制覆盖三类互动**（喂 5 / 摸 10 / 签到 1，`PetService.java:74-76`）。签到还有积分域 `bizKey=日期` 的第二道幂等（`:90`）。
8. **扣分不会被扣成负数**，由 `spend()` 的条件更新保证（`PetService.java:82-87` 注释）。
9. **前端清理干净。** 动作定时器、气泡定时器在卸载时全部清除（`campus-home.js:215-219`），悬浮球用本地文案不发请求。小页面的健壮性做得比大页面好。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **派遣奖励没有日上限，而它给的是"准货币"。** 积分目录里 `pet_dispatch` 的 `dailyCap = 0`（`module-points-v31.sql:102`），`PointsService` 只在 `cap > 0` 时才限次（`:109`、`:122`）。最短任务 5 分钟给 20–30 分（`module-pet-companion.sql:97`）。串行反复做：理论上一天 288 次 ≈ **5760–8640 分**；按"100 积分 = 1 元"的展示换算（`PointsService.java:22`）约 **57–86 元/天**。积分能兑换礼包券（`23-礼包兑换与券`），所以这不是游戏分数，是可换物的资产。
2. **互动次数是"先查后写"，不是原子。** `countToday >= maxPerDay` 判完才写（`PetService.java:79-80` → `:102`）。并发连点能突破上限：多拿经验、多扣积分。它不会凭空造积分（喂食是扣分），所以危害小于 16-01，但"每天 5 次"这个承诺不成立。
3. **奖励金额取错了对象。** 领取时用 `latestDispatch(userId)` 的 `rewardMin/rewardMax` 算钱（`PetCompanionService.java:289-293`），而不是用"本次 dispatchId 对应任务"的区间。若用户先接 5 分钟任务、到点不领、再开 60 分钟任务，先前那单可能按 60 分钟任务的 140–200 分结算（**推测，未验证** —— 取决于 `activeCount` 是否把 `claimable` 也算作 active）。
4. **完全没有后台。** 后台 41 条路由无宠物页（`web/src/router/index.js`）。物品价格、任务时长、奖励区间、任务上下架**都只能改库**。运营想做个"中秋限定围巾"活动，要走研发排期。
5. **"领养"没有领养。** 宠物由首次 `GET /api/pet` 自动建行（`PetMapper.java:18`）。`pages/adopt` 只是一个外观选择器。对用户来说"我的猫是什么时候来的"没有仪式感；对运营来说"新增领养数"这个指标根本不存在。
6. **围巾的描述是假的。** `pet_item` 里 `acc_scarf` 写「领养时赠送的见面礼」（`module-pet-companion.sql:91`），但代码里没有任何发放逻辑（grep `acc_scarf` 在 Java 中零命中）。用户打开衣柜看到"未拥有"，描述与事实不符。
7. **对话页与宠物养成是两套东西。** `pages/companion` 是"与宠物聊天"，但它不写宠物状态、不给经验、不涨亲密度——聊完什么都不变。这会让人觉得"聊了也没用"。
8. **零测试。** 20 个测试类里没有一个覆盖宠物：次数上限、派遣幂等、积分扣减，全都靠人工点。
9. **无总开关。** 宠物域没有 `featureFlags` 条目，出问题（比如刷分被利用）只能发版下线。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 做法 | 为什么当前没选 | 代价/收益 |
|---|---|---|---|
| 给 `pet_dispatch` 设日上限 | 目录 `dailyCap = 5`（与喂食同量级） | 未评估 | 0.1 人日（改一条种子 SQL）；**必须做** |
| 互动次数用条件插入 | `pet_interaction_log` 加"每日每动作序号"唯一键，插入失败即超限 | 未评估 | 0.3 人日 |
| 建宠物管理后台 | 物品/任务 CRUD + 上下架 + 排序 | 未评估 | 2.0 人日；不做则所有运营动作都要研发 |
| 领养做成真实动作 | `POST /api/pet/adopt`：选物种 → 建行 → 发见面礼 → 记事件 | 未评估 | 0.5 人日；顺带修 16-05/16-06 |
| 任务奖励按任务自身区间 | `claimDispatch` 用 `dispatch` 行 JOIN `pet_task` 的区间 | 未评估 | 0.2 人日 |
| 对话影响宠物状态 | 聊天加心情/亲密度，按天限次 | 未评估 | 1.0 人日 |

## 五、如果重做会怎么改

1. **把"积分产出"当成资金系统对待。** 任何能发分的入口都必须有三件套：**每日上限（目录 `dailyCap > 0`）**、**业务幂等键**、**单用户速率限制**。派遣现在只有后两件半。先把 `pet_dispatch.dailyCap` 从 0 改成 5，成本 0.1 人日，收益是把一个可换钱的口子关掉。
2. **互动次数靠唯一键而不是靠 count。** 建 `pet_daily_action(user_id, action, stat_date)` 唯一键，`INSERT` 失败就是"今天做满了"。天然并发安全，也不需要额外锁。
3. **领养要有仪式。** 一个 `POST /api/pet/adopt` 接口：选物种 → 建行 → 发见面礼 → 记一条事件。它同时解决"围巾描述是假的"和"新增领养数算不出来"两个问题。
4. **宠物要有后台。** 物品与任务是运营素材（节日限定、限时任务），必须表驱动 + 后台可配。否则这个板块每次迭代都要研发参与。
5. **让聊天有后果。** 陪伴页每天聊一次 +心情/经验，把"陪伴"从纯展示变成有养成价值的动作，否则它只是一个动画页。
