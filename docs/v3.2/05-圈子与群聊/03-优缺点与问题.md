## 一、设计优点（为什么这么设计，好在哪）

1. **WebSocket 只做推送，不做写入。** 类注释一句话定了边界："WebSocket 只负责推送，不接收消息写入"（`CircleChatController.java:14`）。写入统一走 HTTP 意味着：限流、鉴权、审核、幂等只有一套实现，不存在"WS 通道绕过审核"的结构性漏洞。这个取舍比"WS 直接收消息"省掉了大量并发与审计问题。

2. **重连补量做了"先可用、再对齐"。** 先把最新一页渲染出来恢复交互，再在 8 秒 / 300 条预算内后台向前补齐缺口（`utils/chat-sync.js:1-7,65-104`）。补不完就丢掉缺口前的旧消息并允许上拉继续取（`:46-49`），避免"为了连续而卡住首屏"。这套纯函数有 9 条单测覆盖（`tools/acceptance/chat-sync.test.js`，本次 9/9 通过），是本次盘点里**唯一有可执行测试证据**的前端模块。

3. **火花的事实表设计干净。** `circle_activity_day(circle_id, active_date)` 唯一键 + `INSERT IGNORE` 返回值判断"今天是否第一次活跃"（`CircleStreakMapper.java:15-27`），并发安全不依赖应用层"先查再插"。连续天数的读改写用 `SELECT ... FOR UPDATE` 拿到最新已提交版本（`CircleStreakMapper.java:29-38`），注释还解释了 RR 隔离级别下普通 SELECT 会读到事务快照的坑——这是踩过之后写下的代码。

4. **火花展示层拒绝"拿库里的旧值骗人"。** `view()` 每次按"今天"重算：`last_active_date` 早于昨天就展示 0（`CircleStreakService.java:88-105`）。很多实现会直接展示 `streak_days` 列，结果是"断了 3 天的圈子还显示连续 12 天"。这里做对了。

5. **时区显式固定为 `Asia/Shanghai`。** 全部"哪天"的判断走 `today()`（`CircleStreakService.java:32,40-42`），既不吃服务器默认时区，也不信设备时间。校园产品跨时区部署（云服务器 UTC）时这一条能避免"每天的火花在早上 8 点断档"。

6. **消息幂等做到"重发不重复、错用要报错"。** 同一 `clientId` 重复提交返回同一条消息；如果 `clientId` 被复用到不同内容/不同圈，直接报"标识已被其他内容使用"（`CircleChatService.java:78-88`）。后者比"静默去重"更安全——它能暴露客户端 bug。

7. **群聊文本审核是"落库前 + fail-closed"。** 微信不可用时不放行，而是报"消息审核暂不可用"（`CircleChatService.java:142,146`），与论坛的 fail-open 相反。对群聊这种"一条消息瞬间扩散给 N 人"的场景，这个方向是对的。

8. **WebSocket 鉴权不是"连上再说"。** 连接建立即解析 JWT + 校验成员 + 校验圈子状态，失败发 `error` 帧并以 1008 关闭（`CircleWebSocketHandler.java:28-44,75-82`）。同用户同圈只保留一条连接，旧连接被踢（`:37-38`），避免"多端登录导致消息重复计未读"。

9. **在线名单有 TTL，不显示幽灵在线。** 心跳 30 秒、TTL 90 秒，掉线自动关连接并从名单摘除（`CircleWebSocketManager.java:31-32,107-125`）；注释明确说明节点崩溃后记录会自动过期。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **群聊是平台唯一一条"不可治理"的内容通道。**
   - 消息不进 `AuditService`（`CircleChatService.java` 全文无该依赖），不写 `audit_log`。
   - `circle_message` 表没有 `audit_status` 列（`db/module-circle-chat.sql:5-17`），连"标记为已审/已删"的字段都没有。
   - 审核台的 `chat` 类型查的是私聊表 `chat_message`（`AuditMapper.java:33-35`），`decideChat` 改的也是它（`AuditMapper.java:141`）。
   - 结论：群聊出现违规内容时，运营**看不到、审不了、下不掉**，只能写 SQL。

2. **审核力度在同一个仓库里自相矛盾。** 论坛 fail-open（`AuditService.java:204-207`），群聊 fail-closed（`CircleChatService.java:146`）。两套策略、两套词表、两套留痕方式。代价是：任何一个模块新增内容通道时，都要重新决定一遍"审核挂了怎么办"，而决定的结果没人知道。

3. **群聊的敏感词是另一套，而且只有 5 个。** `BLOCKED_WORDS = {赌博, 色情, 毒品, 诈骗, 暴恐}`（`CircleChatService.java:22`）。后台词库管理页里维护的 22 个校园诈骗词（`db/module-audit.sql:72-76`）对群聊**完全无效**。运营改了词库会以为群聊也被保护了——这是最容易产生"虚假安全感"的一处。

4. **圈子的两个状态字段可能互相矛盾。** 用户建圈固定 `status=0`（`CircleMapper.java:96`），但 `audit_status` 可能是 `passed`（文本审核直接过，`CircleService.java:147`）。结果：
   - 圈子列表查 `status=1`（`CircleMapper.java:22`）→ 看不到；
   - 审核台查 `audit_status='reviewing'`（`Audit.vue:146`）→ 也看不到；
   - 只有"圈子管理"页的 `isPending`（`status=0 && creator_id`）能捞到（`Circles.vue:245`）。
   - 代价：运营如果只看审核台，用户建的圈子会永远停在待审。

5. **火花在发现页是死数据。** 列表 SQL 不取火花三列（`CircleMapper.java:12-20`），`decorateStreak` 只能填 0（`CircleService.java:28-36`）。发现页的火花 UI 写了四态样式（`discover.js:35-47`），但永远走不到"点亮"分支。**做了 UI、做了数据、没接线。**

6. **推荐流绕过了学校隔离。** `recommend` 的 SQL 只有 `p.status=1`（`CircleMapper.java:145`），没有 `school_id` 条件。本仓库其它查询（`ForumService.java:15-18`、`CircleService.java:59-64`）都认真做了三档学校范围，推荐流漏了。

7. **群聊可用性完全绑在微信接口上。** 微信 `msg_sec_check` 抖动 → 全平台群聊发不出消息（`CircleChatService.java:142,146`），但历史消息仍能读（`history` 不调微信）。用户会看到"能看不能发"，且没有任何降级提示（提示只有"消息审核暂不可用，请稍后重试"）。

8. **事务边界过大。** `send()` 整体 `@Transactional`（`CircleChatService.java:61`），内部有微信 HTTP 调用（`:73`）与火花统计（`:105`）。一次群聊发送 = 1 个数据库连接被占用"网络往返时长"。火花统计失败还会把已发出的消息一起回滚。

9. **发现页一次拉 50 个圈子且不分页**（`discover.js:131`）。平台圈子超过 50 个之后，后面的圈子在发现页不可见——不是"加载慢"，是"看不到"。

10. **没有圈主治理能力。** `circle_member.role` 只有建圈时写的 `owner`（`CircleMapper.java:102`），全仓库没有任何按 `role` 判权限的地方。圈主不能删帖、不能踢人、不能禁言。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 原设计 | 替代方案 | 为什么当时没选（据代码与注释推断） | 代价留给了谁 |
|---|---|---|---|
| WS 只推送、写入走 HTTP | WS 双向收发消息 | 双通道意味着双份审核/限流/幂等，注释直接写明"只负责推送"（`CircleChatController.java:14`） | 延迟：多一次 HTTP 往返（实际影响小） |
| 群聊自建 5 词黑名单 | 复用 `SensitiveWordEngine` + 后台词库 | 群聊开发时可能想让"聊天别太容易被拦"，写死 5 个重罪词（`CircleChatService.java:22`） | 运营：词库管理对群聊无效；合规：刷单/押金类诈骗词在群聊完全不管 |
| 群聊 fail-closed | 与论坛一致 fail-open | 群聊消息扩散快、撤回难，宁可不可用（`CircleChatService.java:140-146`） | 用户体验：微信抖动时不能发言 |
| 用户建圈 `status=0` 待审 | 直接 `status=1` | 注释写"审核通过前不在圈子列表出现，避免群聊入口失控"（`CircleService.java:122`） | 运营：多一处待审队列，且与审核台不同源 |
| 火花冗余存 `circle.streak_days` | 每次用 `circle_activity_day` 聚合算 | 注释写"列表页不必每次聚合"（`db/module-circle-streak.sql:18`） | 一致性：列表 SQL 忘了取这三个字段，UI 恒 0 |
| 在线名单走 `CirclePresence`（集群读 Redis） | 只统计本节点 | 多实例下会显示幽灵在线（`CircleWebSocketManager.java:22-25` 注释） | 运维：多一个 Redis 依赖，故障时在线人数不准 |
| token 放 WS URL query | WS 首帧发 token 认证 | query 最简单，微信小程序 `wx.connectSocket` 支持自定义 header 但跨端兼容性差 | 安全：token 进 access log |

## 五、如果重做会怎么改

1. **内容通道统一抽象成 `ContentChannel`。**
   现在每条内容通道（帖子/评论/二手/兼职/私聊/圈名/群聊/活动）各自决定"审不审、怎么审、挂了好不好放行"。抽成一个接口：`audit(text, images) → {verdict, logId}` + `channel` 枚举，新增通道必须注册到审核台。做完之后 05-01/05-02/05-03 三个问题会同时消失。

2. **`circle_message` 必须有审核三列，且并入审核台 UNION。**
   表结构缺字段是根问题（`db/module-circle-chat.sql:5-17`），前端和运营再怎么补都绕不过它。

3. **圈子的状态只保留一个。**
   现在 `status`（业务可见）与 `audit_status`（审核态）双轨，导致 `status=0 + audit_status=passed` 这种没人能处理的组合。合并为单一 `lifecycle` 枚举：`draft/reviewing/active/rejected/dissolved`。

4. **火花从"冗余列"改成"派生值"，并统一在列表 SQL 里算。**
   `circle_activity_day` 是事实表，`circle.streak_days` 是缓存。缓存与 UI 之间断了一次线（`CircleMapper.java:12-20`）。要么列表也算一次（`LEFT JOIN` 聚合），要么在 `decorateStreak` 里对 `null` 显式抛错而不是填 0——让"没接线"在上线前就暴露。

5. **群聊的可用性与审核强度做成可调策略。**
   `circle_chat.strict_audit`（严格=微信不可用则拒发 / 宽松=入队待审继续发），交给运营按场景切。现在是一个写死的 fail-closed，微信抖动就全站不能聊天。

6. **WebSocket 鉴权换成一次性 ticket。**
