## 一、合规与隐私

**结论：不通过（原因：群聊内容完全不可治理 + 图片消息零审核）。**

|---|---|---|

| 群聊图片是否审核 | ❌ 完全不审 | `CircleChatService.java:70-73` |

| 圈子名/简介是否审核 | ✅ 是（同样受缺参静默放行影响） | `CircleService.java:142-143`，`AuditService.java:180-186` |

**上线级判断**：微信小程序审核要求"UGC 内容可举报、平台可处置"。群聊是全球 IM 类产品被抽查最狠的场景，而当前实现两条都不满足（不可举报、不可下架）。**这一维不通过，圈子功能整体不能上线。**

## 二、资金与对账

**结论：不涉及。**

依据：
- 圈子/群聊接口无任何金额字段（`CircleController.java:18-96`、`CircleChatController.java:24-59`）。
- 火花点亮不发积分、不触发权益（`CircleStreakService.java` 全文无 `PointsService`/`TierService` 依赖）。
- 建圈门槛是**段位**（成长值），不是付费（`CircleService.java:129-130`）——成长值由交易与任务产生，不构成直接购买。
- 无资金侧定时任务（`grep -rn "@Scheduled"` 的 3 个不在本模块，`04-证据与复核台账.md:44`）。

**附带风险（非资金但有价值等价）**：建圈名额"最多 1 个，待审也占名额"（`CircleService.java:131`，`CircleMapper.java:89-90`）。若审核误拒，用户的名额不会被释放——这是"权益被吞"，需在 05-05 修复时一并给运营"拒绝后释放名额"的动作。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：四个 SQL 按序执行；`circle_message` 结构升级需单独排期）。**

### 4.1 必须按序执行

```sql
-- 1) 圈子与成员表 + post.circle_id（发帖带 circleId 前必须先有这一列）
SOURCE backend/src/main/resources/db/module-circles.sql;
-- 2) 群聊消息表 + 已读表 + circle.last_message*（群聊功能前必须）
SOURCE backend/src/main/resources/db/module-circle-chat.sql;
-- 3) 火花事实表 + circle 三列
SOURCE backend/src/main/resources/db/module-circle-streak.sql;
-- 4) circle 的 audit_status 三列（依赖 1 已建 circle 表）
SOURCE backend/src/main/resources/db/module-audit.sql;
```

- 四份均为幂等脚本（`information_schema` 判存在后再 ALTER）。
- **顺序约束**：`module-circles.sql` 必须最先（`module-circle-chat.sql:28-42` 与 `module-circle-streak.sql:19-24` 都在 ALTER `circle` 表）。
- `module-circles.sql` 里包含**破坏性副作用**：会把 `tag LIKE '%游戏%'` 的历史帖批量归到圈子 1，`%学习%` 归到 2 等（`module-circles.sql:68-78`）。对已有生产数据这是**内容归属变更**，执行前必须备份 `post`。
- `module-circles.sql:81-86` 插入演示成员关系（用户 1~4 加入前 5 个圈），生产环境执行会造出假成员，需手工删。

### 4.2 回滚

```sql
-- 回滚一次误判的圈子解散
UPDATE circle SET status=1, audit_status='passed', audit_reason=NULL WHERE id=? AND status=0;

-- 回滚火花（某圈误重置）
UPDATE circle SET streak_days=0, last_active_date=NULL, spark_on=0 WHERE id=?;
DELETE FROM circle_activity_day WHERE circle_id=? AND active_date=?;

-- 回滚群聊一条已入库消息（无审核台时的唯一手段）
DELETE FROM circle_message WHERE id=? AND circle_id=?;

-- 结构回滚（整版回退时用，会丢全部火花与群聊）
DROP TABLE IF EXISTS circle_activity_day;
DROP TABLE IF EXISTS circle_read;
DROP TABLE IF EXISTS circle_message;
ALTER TABLE circle DROP COLUMN last_message_at, DROP COLUMN last_message,
  DROP COLUMN streak_days, DROP COLUMN last_active_date, DROP COLUMN spark_on,
  DROP COLUMN audit_status, DROP COLUMN audit_reason, DROP COLUMN audit_at;
-- circle / circle_member 若已产生业务数据，不要 DROP，改为导出备份
```

**现实约束**：群聊消息的"删除"只能写 SQL（没有后台入口），且删了之后对方的本地消息列表仍保留已渲染的副本。**没有撤回机制 = 违规内容删不干净。**

## 七、失败与降级（依赖挂了会怎样）

**结论：不通过（原因：微信抖动直接让全平台群聊失去发送能力，且无降级通道）。**

| 依赖 | 挂了会怎样 | 证据 | 可接受吗 |
|---|---|---|---|
| 微信 `msg_sec_check` 超时/5xx | 群聊**不能发**任何文字（含"在吗"），历史可读 | `CircleChatService.java:142,146` | ❌（没有降级） |
| 微信 `access_token` 取不到 | 同上 | `CircleChatService.java:165-167` | ❌ |
| `appid/secret` 未配 | 文字照发（只过 5 个写死词），图片照发 | `CircleChatService.java:129` | ❌（静默放行） |
| Redis / 限流计数不可用 | 发消息 503（fail-closed） | `RateLimiter.java:52-57` | ✅ 方向正确 |
| `ClusterBus`（跨节点广播）失败 | 只本节点投递，其它节点用户收不到实时消息（可刷历史补） | `CircleWebSocketManager.java:89-90` | ⚠️ 可接受（有 HTTP 兜底） |
| `CirclePresence`（在线名单）失败 | 在线人数异常，聊天不受影响 | `CircleWebSocketManager.java:122-123` | ✅ |
| WebSocket 断开 | 前端指数退避重连 + 断线补量 | `pages/circle-chat/circle-chat.js:97-108`，`utils/chat-sync.js:65-104` | ✅（有单测证明） |
| 数据库挂了 | 群聊全挂 | 无降级 | ⚠️ 常规 |

**方向性判断**：群聊对"内容安全"是 fail-closed（好），对"服务可用性"没有任何降级（差）。正确做法是**中间态**：微信不可用时把消息标记为 `pending` 入队待审、先让用户看到自己发的消息但不出圈——而不是直接拒绝，也不是直接放行。

## 九、结论

**不可上线。**

阻断项：

| 编号 | 等级 | 一句话 |
|---|---|---|
| 05-01 | P0 | 群聊图片消息零审核 |
| 05-02 | P0 | 群聊内容不进审核台、无 `audit_status`、无法下架 |
| 05-03 | P1 | 群聊只用 5 个写死词，后台词库无效 |
| 05-04 | P1 | 发现页火花恒为 0（增长机制死数据） |
| 05-05 | P1 | 用户建的圈在审核台看不到，可能永久待审 |
| 05-06 | P1 | 推荐流不按学校隔离 |
| 05-07 | P1 | WebSocket 任意 Origin + token 在 URL |
| 05-08 | P1 | 微信抖动导致群聊全站不能发言 |

解除条件：
- 05-01 + 05-02 + 05-03 是**同一条治理链**（"群聊进审核体系"），必须一起修，不能只做其中一项——只加审核不落下架手段，等于"审出来也没法处理"。
- 05-04 与 05-05 是**低成本高收益**（各 0.2~0.5 人日），没有理由留到上线后。
- 05-06 的定级取决于商务合同是否承诺"每校数据独立"；若承诺，升为 P0。
- 05-07 至少要把 Origin 白名单做上（成本 0.5 人日）。

**如果业务方坚持"先上圈子、群聊后置"**：可以按这个顺序拆——先上 `圈子发现 + 圈子详情 + 圈内帖`（屏蔽群聊入口），此时 05-01/05-02/05-08 不适用，阻断项只剩 05-04/05-05/05-06；这四个修完（约 1.2 人日）即可"有条件上线"。群聊单独作为下一期。
