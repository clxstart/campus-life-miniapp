## 一、合规与隐私

**结论：有条件通过（条件：课表属于学习行为数据，对外只用于本人展示；删除学期/课程需可恢复）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 收集内容是否必要 | 通过：课程名/教室/时间，是学生本人主动维护的信息 | `CampusService.java:51-67` |
| 是否收集他人信息 | 通过：无同学名单、无教师信息 | `course_schedule` 字段清单（`module-messages-academics.sql:30-35`） |
| 课表是否可被他人读取 | 通过：`/api/timetable` 在 `PRIVATE_READ_PREFIXES` 内，未登录 401；SQL 强制 `user_id=#{userId}` | `AuthInterceptor.java:74-84`、`CampusMapper.java:110` |
| 管理端能否窥探学生课表 | 部分不通过：无列表接口，但导入接口可指定任意 `userId` 写入；管理员可用它"探测某个学生课表是否存在"（返回值含 `total`） | `CampusController.java:113-119`、`CampusService.java:131-133` |
| 数据删除权（注销时） | 未覆盖：注销流程未见清理 `course_schedule` | 需与 `19-个人中心与账号安全` 对齐核实 |
| 学期/课程误删可恢复性 | **不通过**：硬删除，无软删、无备份 | `AdminModuleService.java:738`、`CampusMapper.java:127-128`、`:138-139` |

注：课表本身不算高敏数据，但它是"学生在校活动轨迹"，与考勤、住址（宿舍域）结合后价值升高。建议并入统一的数据删除清单。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：不通过（原因：导入路径会覆盖学生数据且无备份；删学期留下孤儿数据）**

执行顺序：

```bash
# 0) 前置：多校字段（academic_term.school_id 由它加）
mysql -u root -p campus_life < backend/src/main/resources/db/module-multischool-admin.sql
# 1) 消息 + 教务表（含演示种子）
mysql -u root -p campus_life < backend/src/main/resources/db/module-messages-academics.sql
# 2) 学校维度索引
mysql -u root -p campus_life < backend/src/main/resources/db/module-perf-index.sql
# 3) 核对
mysql -u root -p campus_life -e "
SELECT school, COUNT(*) c, SUM(active=1) actives FROM academic_term GROUP BY school;
SELECT COUNT(*) FROM course_schedule cs LEFT JOIN academic_term t ON t.id=cs.term_id WHERE t.id IS NULL;
SELECT COUNT(*) orphan_courses FROM course_schedule cs LEFT JOIN academic_term t ON t.id=cs.term_id WHERE t.id IS NULL;"
```

- 本次**未执行**，原因：无 MySQL 会话。
- 第 3 步第二条查询专门查"孤儿课程"：只要返回 > 0，说明历史上已经删过学期，数据已残留。

**上线前必须做的一次备份（因为 13-02 无回滚）**：

```bash
mysqldump -u root -p campus_life course_schedule academic_term > /backup/academics_$(date +%F).sql
```

回滚 SQL：

```sql
-- 危险：会丢全部课程
DROP TABLE course_schedule;
DROP TABLE calendar_event;   -- 已下线功能，可一并清
ALTER TABLE academic_term DROP COLUMN school_id;  -- 仅当确认回滚到无多校版本
```

⚠️ 没有任何"按学期回滚"的能力：一旦导入覆盖，只能靠 mysqldump 恢复整表。

## 五、性能与容量

**结论：有条件通过（条件：单学生课表规模很小，性能不是瓶颈；瓶颈在导入的 N 次往返）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 取课表是否 N+1 | 通过：1 次学期查询 + 1 次课程查询 | `CampusService.java:46` |
| 周次过滤是否走索引 | 通过：`idx_course_week(user_id,term_id,week_start,week_end)` | `module-messages-academics.sql:34` |
| 导入是否逐条写 | 是：N 行 = N 次 `upsertCourse`，无批量 | `CampusService.java:130` |
| 单次导入规模上限 | 无限制：CSV 全量进内存，`split` 后全存在 `preview` 列表 | `CampusService.java:102-126` |
| 大文件风险 | 万行 CSV 会构造万个 Map 并一次性循环写库（**推测，未压测**） | 同上 |
| 学期列表 | 通过：`idx_term_school(school_id,active)` | `module-perf-index.sql:51-55` |
| 压测 | **无** | 台账 3.2 |

容量判断：单学生课表通常 10–20 门、每周 20–30 格，数据量极小；真正的规模压力在"500 人 × 1 次导入"的运维成本，不在数据库。

**结论：不通过（原因：无任何开关；数据回滚只能整表恢复）**

| 项 | 现状 | 证据 |
|---|---|---|
| 课表功能开关 | 无（学生自建课表始终可用） | — |
| 导入开关 | 无（接口常开，任何有 admin token 的账号可调） | `CampusController.java:112` |

最小补齐（约 0.8 人日）：
1. `importTimetable` 加 `@Transactional`（13-02 最小解，0.2 人日）。
2. `replace=true` 时强制要求 `confirmToken`（先调一次拿 token 再执行），并自动把原课表 dump 到 `course_schedule_backup`。
3. 加 `campus.timetable.import.enabled` 开关，出问题能一键停。

## 九、结论

**不可上线（阻断项：13-02、13-03）**

- 13-02 阻断理由：写作规范第九节前置要求"涉及钱、数据、权限的功能，没有回滚方案就写不可上线"。导入会**删除学生数据**且无事务、无备份、无回滚——这正是该条款的场景。
- 13-03 阻断理由：跨校写学期（判级细则"数据可跨校 / 鉴权可绕过 → P0"）。
- 13-01（无 Web 入口）不阻断上线，但它意味着**首发时课表只能是空的或靠演示种子**；若产品口径是"支持课表"，则必须与本批一起修。
- 13-06（第 6 节起不渲染）不阻断，但一旦导入真实课表就会立刻暴露：学生会来问"我下午的课呢"。

## 十、上线前置清单（按执行顺序）

1. **（P0，0.2 人日）学期编辑加校域校验**

2. **（P0，0.5 人日）导入加事务 + 备份**
   - `importTimetable` 加 `@Transactional(rollbackFor = Exception.class)`。
   - `replace=true` 前把原课表 `INSERT INTO course_schedule_backup SELECT * FROM course_schedule WHERE ...`。
   - 验收：导入中途抛异常后，`course_schedule` 行数与导入前完全一致。

3. **（P1，0.5 人日）导入操作人与目标收紧**
   - `adminUserId` 改从 `AdminInterceptor.ADMIN_ID` 取（`UploadController.java:69` 已有同款写法）。
   - `target userId` 校验其 `school_id` 属于操作人校域（超管除外）。
   - 验收：校管导别校学生报 403。
