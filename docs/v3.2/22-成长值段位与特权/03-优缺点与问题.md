## 一、设计优点（为什么这么设计，好在哪）

1. **段位不落库是本功能最好的一个决定**。存 `user.tier` 就要维护"什么时候升级"，漏一处就永久不一致；推导永远自洽，且"改门槛后如何影响存量用户"变成可推演的问题而不是数据修复问题 —— `TierService.java:16-19`（注释）、`:72-113`。
2. **G 只涨不降，与 P 彻底分离**。`spend()` 不碰 `user_growth`，全仓库没有减 G 的语句，所以"花光积分掉段"这种产品事故在代码层就不可能 —— `PointsService.java:130`、`PointsService.java:145-166`。
3. **特权判定只有一个入口** `effectiveTierCode()`，业务侧不许各读 `user_growth`。注释把理由写得很直接："否则「显示白银但享受不到白银特权」" —— `TierService.java:20-21`、`:140-156`。
4. **三项特权都真的接在执行点上了**，不是只返回一个布尔：免审接在发帖写入（`ForumService.java:150-161`）、建圈接在校验链第一环（`CircleService.java:128-130`）、快速应答接在列表排序（`JobService.java:142-164`）。这一点比很多项目的"特权只做展示"强。
5. **管理端只读是有理由的取舍**，且注释写清了理由："改高后掉段的争议成本高" —— `AdminTierController.java:16-21`。把"不能改"作为设计决定写进代码，比默默不给入口好。
6. **`configForAdmin()` 把特权摘要文案收在后端**，前端不用自己拼（虽然前端没用对字段，见 22-07）—— `TierService.java:200-205`。
7. **9 个单测把边界钉死了**：59/60、199/200、超最后开放段、进度 floor、开关关闭、体验段位、过期段位、管理端口径 —— `TierServiceTest.java:62-154`。段位是纯函数，这类测试性价比最高。

## 二、设计缺点与代价

1. **三项特权只有两个开关**。`priorityReply` 没有 flag，`TierService.java:159` 的注释却说"开关关闭时对应特权一律 false"——注释与实现不一致。运营想"先关掉兼职置顶、看看数据变化"，做不到。
2. **"开关关闭后入口是否仍可用"这一列，三项特权答得不一致**：
   - 建圈：开关关 → 后端 403「圈子创建暂未开放」，入口仍在（符合设计稿 `:74`）✅
   - 发帖免审：开关关 → 后端走普通审核，前端无提示（用户不知道自己"从免审变不免"）⚠️
   - 快速应答：**没有开关**，只能改代码 ❌
3. **体验段位的时间语义依赖两个时钟**。写 `expires_at` 用 JVM 的 `LocalDateTime.now()`，读出来比较用 MySQL 的 `NOW()`；两者时区不同（生产 `DB_URL` 由环境变量给，`application-prod.yml:7` 只写 `${DB_URL}`，没有 `serverTimezone`）就会让"7 天体验"变成 7 天 ± 时差。这类 bug 上线后只会表现为"用户说体验突然没了"，极难查。
4. **段位配置的可运维性几乎为零**：无写接口、无校验、无审计、无版本、无快照。改门槛必须直连数据库，改错无法 diff 出"改之前是什么"。
5. **小程序把段位门槛硬编码**（`pages/points/points.js:18-27` 的 8 行常量），与 `tier_config` 双源。一旦后台改门槛（哪怕只是改库），弹层说明与段位卡进度会不一致。
6. **特权对用户完全隐形**：`privileges` 字段传到了端上却零消费（`utils/api/points.js:38-41` 只在演示数据里出现）。用户拿到白银后唯一能感知的是"兼职列表顺序好像变了"。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 决策 | 选了 | 没选 | 判断 |
|---|---|---|---|
| 段位存储 | 读时推导 | 落 `user.tier` 字段 + 升级任务 | **对**。省掉"升级一致性"这一整类 bug。 |
| 段位配置是否可改 | 管理端只读 | 后台可改门槛 | **方向对但做过头**。合理折中是"可改但需二次确认 + 全量快照 + 掉段补偿"，现在一刀切不给入口，反而把改动赶到改库这条无痕路径上。 |

### 4.3 一个必须回答的业务问题

**"段位门槛被后台误改"到底可不可能？** 本次核对结论是：**通过管理端不可能**（`AdminTierController.java:29-33` 只有 GET，且 `super` 硬判定），**通过改库完全可能且无痕**（无审计表、无校验、`evict()` 无调用方）。所以这条风险的正确表述不是"后台误改"，而是"任何有数据库权限的人都能在不留痕的情况下改变全平台的特权分配，且平台没有回滚手段"。修法不是给后台加编辑框，而是给配置表加变更记录与合法性校验。

## 五、如果重做会怎么改

1. **三项特权一律配开关**，且开关判定收在 `TierService` 里（现在 `priorityReply` 漏了），保证"权限判定只有一个入口"这条铁律也覆盖开关这一层。
2. **时间一律由 Java 算、由 Java 传**：所有 `expires_at > NOW()` 改成 `expires_at > #{now}`，DB 只存不判。仓库里 `SignService` 已经坚持"日期由服务端算"，段位这边应该统一。
3. **配置类表加"变更必须留痕"**：`tier_config` / `task_catalog` / `reward_item` 三张表共用一个 `config_change_log`，记录 before/after/operator/来源（后台 or SQL 工单）。
4. **段位说明不要硬编码**：段位名称、门槛、特权文案全部由后端返回，前端只负责渲染——顺带解决 Web 端两列恒空的问题。
5. **特权 UI 与特权判定同批次交付**：后端算了却没端上展示，等于白做；建议把"后端判定 + 端上提示"作为一条验收项写进 PRD。
