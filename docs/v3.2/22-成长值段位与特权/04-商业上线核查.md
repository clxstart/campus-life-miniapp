## 一、合规与隐私

**结论：有条件通过（条件：发帖免审的图片先发后审窗口需内容安全兜底；段位规则需在用户协议中明示）。**

- **免审是"机器审核通过后先发"，不是"免审核"**：`fastlane` 要求 `textAudit.pass() && !textAudit.reviewing()` 才成立 —— 证据 `ForumService.java:150-151`。命中词或"待人工复核"的内容仍走原流程（`ForumService.java:152-154`）。这个设计比"黄金用户直接放行"安全得多。
- **但图片是后审**：`fastlane` 成立时帖子 `status=1` 立即曝光，图片审核通过 `scheduleImagesAfterCommit` 异步执行 —— 证据 `ForumService.java:157`、`ForumService.java:160-161`。存在"违规图先曝光 N 秒~N 分钟"的窗口，属内容合规风险，需在营业前确认运营 SLA（发现即下架 + 通知）。
- **G 只涨不降**意味着段位是永久荣誉，不涉及用户付费购买（无"花钱买段位"接口），不构成虚拟财产交易 —— 证据 `PointsService.java:130`、`PointsService.java:145-166`（无减 G）。
- **隐私**：段位、成长值属"用户画像类"数据，`/me` 只对本人开放（`PointsController.java:33-37`）；段位在帖子/兼职列表是否对外展示 —— 兼职 `priority=true` 字段会随接口返回（`JobService.java:159`），但**不暴露 G 值本身**，风险低。
- **缺口**：段位规则（门槛、开放范围、特权内容）在 `docs/` 里有设计稿，但**没有面向用户的协议条款**；用户被"改高门槛后掉段"时平台无依据可引用（见 22-04）。

## 二、资金与对账

**结论：不通过（原因：段位本身不涉钱，但它决定"谁可以免费建圈子/免审/置顶"，属权益分配，且无任何分配留痕）。**

- **不直接涉资金**：本功能不扣积分、不发积分、不发券（G 由 `PointsService` 顺带写入）。
- **但间接涉钱**：
  - 「创建圈子」是稀缺名额（每人 1 个，`CircleService.java:131`），段位决定谁能拿到 —— 属资源分配。
  - 「免审」= 省掉一次审核成本 + 承担一次内容风险。
  - 「置顶」= 流量分配，会影响兼职发布的公平性。
- **无留痕**：段位配置无变更日志（22-04 已列），**无法回答"这个用户当年为什么是黄金"**。这正是对账维度的核心缺陷：权益分配链路缺少可审计的决策依据。
- **无反作弊**：G 只来自 `PointsService`，而 `PointsService` 的日上限可被并发绕过（见 20-02）→ 刷积分的同时也在刷 G → 刷段位。这是两个功能串联后的放大风险：**20-02 的可利用性在 22 上被放大成"免费获得黄金特权"**。
- 已有保障：G 不可被消费（无减 G 语句）、体验段位有到期时间且不可延长（`ON DUPLICATE KEY UPDATE expires_at = VALUES(expires_at)` 是覆盖而非累加，`TierMapper.java:43`）。

## 三、权限与越权

**结论：通过。**

- 段位配置只读且仅 super —— `AdminTierController.java:31-33`。
- 三项特权的判定全在服务端，前端只能"展示或不展示"，绕过 UI 直接调接口仍会被拦：
  - 建圈 403（`CircleService.java:129-130`）
  - 免审由服务端决定 `auditStatus`，客户端无法传参干预（`ForumService.java:150-157`，`fastlane` 完全由服务端算）
  - 置顶由服务端算，客户端无法指定（`JobService.java:144`）
- **无"前端隐藏当权限"**。
- 遗留：`privileges` 字段会随 `/me` 返回 `effectiveTierCode`，属用户自身信息，不构成越权。

## 四、数据与迁移

**结论：通过（脚本幂等、无历史数据迁移负担），但有一条检查项必须加进发布清单。**

| 顺序 | 脚本 | 依赖 | 回滚 |
|---|---|---|---|
| 1 | `db/module-feature-flag.sql` | 无 | `DROP TABLE feature_flag` |
| 2 | `db/module-points-v31.sql`（`user_growth`） | 已有 `user_points` | 见 20 篇 |
| 3 | `db/module-circles.sql`（`circle` 表） | 无 | 回滚前需先确认 `creator_id` 无业务依赖 |
| 4 | `db/module-tier-v31.sql` | **依赖 1（feature_flag）、2（user_growth）、3（circle）** | `DROP TABLE tier_config, user_privilege`；`ALTER TABLE circle DROP KEY idx_circle_creator, DROP COLUMN creator_id`；`DELETE FROM feature_flag WHERE flag_key IN ('post.fastlane.enabled','circle.create.enabled')` |

- 全部幂等：`CREATE TABLE IF NOT EXISTS` + `ON DUPLICATE KEY UPDATE`（`module-tier-v31.sql:13-32`、`:61-64`），扩列走 `information_schema` 判重（`:47-57`）。
- 无历史数据迁移：`user_growth` 由 `PointsService` 懒建行；段位不落库所以"存量用户自动获得段位"（按现有 G 推导，无 G 即青铜）。
- **必须加的检查项**：`module-tier-v31.sql` 的种子会 `INSERT feature_flag`，若生产 `feature_flag` 表不存在会直接报错中断——**先跑 `module-feature-flag.sql`**。
- **校验缺口**：脚本不校验"门槛递增/首个为 0/无重复"，靠人眼（见 22-05）。

## 五、性能与容量

**结论：通过。**

- 段位配置 30 秒缓存，单次推导是纯内存计算 —— 证据 `TierService.java:51-68`。
- 每次 `privileges()` 最多 2 次 DB 查询（`growth` + `activePrivileges`），开关走 `FeatureFlags` 的 30 秒缓存不查库 —— 证据 `TierService.java:161-178`、`FeatureFlags.java:37-41`。
- 唯一的热点是兼职列表：`injectPriority` 每请求调一次 `privileges()` + 一次 `users.selectById` —— 证据 `JobService.java:144-147`。属 P2 级开销（22-06）。
- 无批量/无定时任务，无容量风险。
- **未验证**：无压测。台账 `04:93` 已登记。

## 六、可观测与告警（日志、指标、错误上报、告警渠道）

**结论：不通过（原因：段位变更与特权发放全无日志）。**

- `TierService.grantTrial` 打了一条 `log.info`（`TierService.java:186`）—— 这是全类唯一的业务日志。
- **段位变化无日志**：段位是推导出来的，理论上不需要日志；但"用户从白银变黄金"这一事件对运营有价值（可用于私信激励），现在完全不可见。
- **配置变更无日志**：`configForAdmin` 只读；改库不留痕（22-04）。
- **无指标**：没有"各段位人数分布""体验段位在用人数""建圈被段位拒绝次数"任何 gauge —— 对比支付域有 `alerts.gauge`（`PayService.java:297`）。
- **无告警**：门槛被改坏（22-05）不会有任何信号，只会表现为用户投诉。
- 前端无上报：`privileges` 完全没被消费，连"特权未生效"这类前端异常都无从上报（22-03）。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

**结论：有条件通过（条件：补 `priority.reply.enabled`，并明确"关开关后的入口表现"）。**

| 动作 | 怎么关 | 生效延迟 | 证据 |
|---|---|---|---|
| 关免审 | `UPDATE feature_flag SET enabled=0 WHERE flag_key='post.fastlane.enabled';` | ≤30 秒（`isEnabled` 缓存） | `FeatureFlags.java:29`、`:37-41` |
| 关建圈 | `flag_key='circle.create.enabled'` 置 0 | ≤30 秒 | 同上 |
| 关快速应答 | **做不到**（无 flag） | — | 22-01 |
| 关体验段位 | 无接口；只能改 `user_privilege.expires_at` | 立即（下次查询） | `TierMapper.java:31-37` |
| 掉段/降段 | 改 `tier_config.g_threshold` 或 `user_growth.g_total` | 30 秒 | `TierService.java:31` |

- **数据回退**：段位不落库 → 改回门槛即"自动回退"，这是本功能最大的回滚优势（`TierService.java:16-19`）。
- **但已行使的特权不可回收**：已建的圈子、已免审发出的帖子不会因为关开关而消失；运营需要额外下架动作。
- **代码回滚**：`tier_config`/`user_privilege` 对旧代码无引用，回滚安全；`circle.creator_id` 留一列孤儿字段无害。
- **`evict()` 无人调用**：`TierService.java:49` 定义了缓存清理但全仓库无调用方 → 改库后必须等满 30 秒，且无主动刷新入口。

## 九、结论

**有条件上线（条件见下，共 5 条）。**

段位体系本身是本轮四个 V3.1 功能里**后端质量最高**的一个：纯函数推导、9 个单测钉边界、三项特权都真的接在执行点上、G 不可被消费。没有 P0，所以不阻断上线。但下面 5 条不满足，上线后运营会立刻踩坑：

1. **补 `priority.reply.enabled` 开关**（22-01）——三项特权里唯一没有止血手段的。
2. **统一体验段位的时间口径**（22-02）——否则"7 天体验"变成一个不可预测的时长。
3. **修 Web 段位表两列**（22-07）——运营唯一的可视化渠道现在是空的。
4. **加门槛合法性校验**（22-04/22-05）——门槛改错会让特权静默消失。
5. **明确"特权在端上如何呈现"再上线**（22-03）——后端算了不展示，等于用户拿不到任何激励。
