## 一、设计优点（为什么这么设计，好在哪）

1. **令牌里带范围，每个请求回查库。** `AdminJwtUtil` 把 `role/schoolId/shopId/tv` 写进 claim（`config/AdminJwtUtil.java:34-46`），`AdminTokenGuard` 每请求与库比对五项（`config/AdminTokenGuard.java:44-51`）。好处是「调权限立即生效」：把校管调到 B 校，他手上的旧 token 马上失效，不用等 8 小时。
2. **超管的「不限」用 `null` 显式表达，而不是用 0 或魔法值。** `scope(req)` 返回 `null` 表示全平台，返回具体 id 表示本校（`AdminModuleController.java:428-434`）。SQL 侧统一用 `(#{schoolId} IS NULL OR x.school_id = #{schoolId})` 表达（`mapper/AdminModuleMapper.java:11-20`），一套模板，不会写错方向。
3. **列表接口的范围收敛函数把「校管传别校 id」变成了 403，而不是静默忽略。** `effectiveSchool()` 在 `requestedSchoolId != own` 时直接抛 `ForbiddenException`（`AdminModuleController.java:446-449`）。静默忽略会让前端以为筛选生效了，实际看的还是本校——这是很多后台的通病。
4. **新建记录的归属不允许「无主」。** 校管强制写本校，超管必须显式指定，`resolveTargetSchool()` 的注释写明「超管必须显式指定」（`AdminModuleService.java:557-567`）；圈子创建还有专门一段「超管建圈必须指定学校，否则圈子会成为跨校无主数据」（`AdminModuleController.java:270-277`）。
5. **`assertSameSchool` 把「记录无学校」判成越权，而不是放行。** `longOr(rowSchoolId, -1)` 让 NULL 变成 -1，与任何正数 scope 都不等 → 403（`AdminModuleService.java:276-281`）。方向是对的：宁可拦错，不可放过。
6. **全局配置有明确的「第三档权限」。** 代码里有 6 处自己实现的 super 门（学校、管理员、功能开关、运营配置、任务目录、兑换商品池），且 `AppConfigController.java:22-26` 与 `AdminFeatureFlagController.java:38-40` 的注释都写清了「AdminInterceptor 只要求 super|school，这里必须更严」——说明作者知道「角色门」和「范围门」是两件事。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **隔离靠「记得调用校验函数」，没有任何机制强制。** 结果是 7 处漏掉：banner 改/删、活动状态、商品状态、圈子编辑、学期编辑、报名审核 approve/reject、报名设置。这些不是边角接口——活动上下架、二手下架都是日常运营动作。
2. **五套「取我该管哪个学校」的实现并存。** `AdminModuleController.scope()`（:428）、`effectiveSchool()`（:443）、`AdminModuleService.resolveTargetSchool()`（:557）、`AdminAuditController.scope()`（:107）、`AdminEnrollmentController.scopedSchool()`（:78）。语义大体相同，写新接口时挑一个用，很容易挑到不合适的那个（例如用了 `scope()` 却忘了 `assertSameSchool`）。
3. **`admin_log` 没有 `school_id`。** 日志靠 `admin_id` 归属（`AdminAuthController.java:116-118`）。校管离职换人后，历史日志的「哪个学校」信息丢失；超管查「B 校上周谁删了帖子」只能按人名猜。
4. **`meta.superOnly` 的语义被两层实现割裂。** 前端当它「菜单开关」，后端完全不知道它的存在。于是同一个概念要维护两份（`router/index.js:25-48` 与 6 个 controller 的 `requireSuper`），漏一处就出现「页面进得去、接口 200」的洞——AI 规则就是这样漏的。
5. **跨校内容（`school_id IS NULL`）成为治理盲区。** 校管列表看不到（严格等值过滤），单条操作会 403（`assertSameSchool` 把 NULL 判成越权），最终只有超管能处理。多校铺开后超管会成为内容审核瓶颈。
6. **历史数据用「一律归 1 号校」兜底。** `module-multischool-admin.sql:111-117` 把演示期数据全塞给内蒙古大学。这批数据在真实多校运营后无法自然消化，也不可追溯原归属。
7. **越权测试缺位。** 全仓 28 个测试类、197 个 `@Test`，没有一条「A 校管理员打 B 校资源」的用例（`grep -rln "ForbiddenException" src/test` 未命中管理端越权场景）。这类 bug 只有靠测试才能长期防住。

## 三、权衡过的替代方案

| 当前做法 | 替代方案 | 为什么当前更合适 | 代价 |
|---|---|---|---|
| 控制器手工传 `scope` 进 service | Service 层统一从 `RequestContext`（ThreadLocal）取范围 | 现在能从签名看出「这个方法要不要鉴权」；ThreadLocal 隐式，读代码看不出 | 漏传编译器不报错（已发生 7 次） |
| 手写 `assertSameSchool` | MyBatis-Plus 多租户插件（自动拼 `school_id`） | 插件对「先查后改」的两段式操作无效——你仍需先知道记录属于谁 | 引入插件与会话变量的复杂度 |
| `banner`/`activity`/`goods` 允许 `school_id IS NULL` = 跨校 | 强制 NOT NULL，跨校内容用单独一张「平台公告」表 | 现状省一张表 | NULL 语义分裂：列表看不到、单条改不了 |
| 角色只有 super/school/merchant/rider 四值 | 引入权限点（`content.moderate` / `finance.export` / `config.write`） | 四值模型简单，够当前团队规模 | 无法表达「能审核不能导出」，只能靠 controller 里逐个 if |
| 前端 `meta.superOnly` 隐藏菜单 | 后端返回当前账号的权限清单，前端按清单渲染 | 现状零接口改动 | 两份事实来源，必然漂移 |

## 五、如果重做会怎么改

1. **让「范围」成为不可绕过的参数。** Service 层所有「按 id 操作一条记录」的方法，签名统一为 `xxx(Long scopeSchoolId, Long id, ...)`，并在**框架层**用一个 `@SchoolScoped` 注解 + AOP 统一校验：进入方法前按 `id` 查一次 `school_id`，不符直接 403。这样就不依赖开发者记得调用。
2. **统一到一套范围解析。** 五套实现收敛成一个 `AdminScope` 值对象（`of(request)` → `{isSuper, schoolId, shopId, role}`），提供 `assertOwns(schoolIdOfRecord)`。现在五套并存是这 7 个 P0 的直接土壤。
3. **`admin_log` 加 `school_id`**，并强制所有写接口经过统一日志切面（现在 48 个管理端映射里只有 2 个控制器写日志，见 `28-管理后台与运营/`）。
4. **把 `meta.superOnly` 变成唯一事实来源**：后端 `GET /api/admin/profile` 返回 `permissions` 列表，前端菜单与路由都用它；后端仍按 controller 拦，但两边的「清单」由同一份配置生成。
5. **补越权回归测试**：至少 7 条用例，一一对应 02-01..02-07，用两个学校的 token 对打。这类 bug 一旦修好，没有测试就会再长回来。
6. **给跨校内容一个明确归属**：新增 `school_id=0` 表示「平台级」；或干脆禁止 NULL，把跨校公告迁到独立表。现状的 NULL 语义三方理解不一致（脚本注释、列表 SQL、单条校验），迟早出事。

## 六、7 条 P0 的共同根因与统一修法

这 7 条不是 7 个独立 bug，是**同一个结构缺口**的 7 次显形：`AdminModuleController` 里凡走 `scope(req)` 的接口，都指望被调用的 service 自己记得校验记录归属；而 7 个 service 方法没记、或收了参数没用。

统一修法（不用逐条打补丁）：

**第 1 步：给 service 定一条不可绕过的签名约定**

```java
// 现状（有洞的两种形态）
public void setActivityStatus(Long id, int status)              // 根本没给 scope
public void updateCircle(Long schoolId, Long id, Map body)      // 给了 scope 但没用

// 目标（两种形态都不允许存在）
public void setActivityStatus(Long scopeSchoolId, Long id, int status)
```

**第 2 步：把「取归属 + 比对」收成一个方法**，所有单条写操作第一行调用它：

```java
// AdminModuleService 内部
private void requireOwnership(Long scopeSchoolId, Object rowSchoolId, String what) {
    if (scopeSchoolId == null) return;                        // 超管不限
    long row = longOr(rowSchoolId, -1);
    if (row != scopeSchoolId) throw new ForbiddenException("无权操作其他学校的" + what);
}
```

**第 3 步：用测试锁死行为**。7 条 P0 各配一条集成测试（两个学校 + 两个校管 token），写进 `MultiSchoolIsolationTest`，纳入 CI。这类 bug 修完不测，三个月后一定长回来——因为它的成因是「新接口容易忘」，而不是「某一行写错」。

**第 4 步：让「忘」变成编译错误**。把「按 id 操作一条记录」的 service 方法统一改成接收一个 `AdminScope` 值对象（不是 `Long schoolId`），并在 `AdminScope` 里提供 `assertOwns(row)`。只要方法签名里有 `AdminScope`，开发者就必须面对它；现在传一个 `Long` 很容易被当成「可以忽略的参数」（`updateCircle` 就是这么被忽略的）。

按这个顺序做，7 条 P0 的实际代码改动约 3.5 人日，测试 1 人日，合计 4.5 人日——比逐条打补丁（也是 3.5 人日）多 1 天，但能防住第 8 条。
