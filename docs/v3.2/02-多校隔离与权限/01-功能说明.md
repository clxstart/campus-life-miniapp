## 一、这个功能解决什么问题

这是一个**平台方运营多所学校**的产品：一套代码、一个数据库、多个学校共用，靠 `school_id` 区分归属。它要解决三个问题：

1. **数据不能串校**——A 校管理员登录后，只能看、只能改 A 校的帖子/圈子/商品/活动/店铺/学期/报名。这是学校客户签约时的硬条款，也是这套系统唯一的商业模型。
2. **平台要能统管**——超管（平台方）必须能跨校切换、跨校对比、发全校公告。
3. **四类账号不能互相越界**——超管（全平台）、校管（本校）、商家（本店）、骑手（本校配送）。商家不能进后台改数据，骑手不能看财务。

隔离不是靠「前端隐藏菜单」，而是三层：

| 层 | 机制 | 是否真实生效 |
|---|---|---|
| 第 1 层：令牌携带范围 | 管理端 JWT 内含 `role` + `schoolId` + `shopId`，每请求查库比对 | ✅ 生效（`AdminTokenGuard.java:44-51`） |
| 第 2 层：接口取范围 | 控制器用 `scope(req)` / `effectiveSchool(req, schoolId)` 算出「我该看哪个学校」 | ✅ 列表接口生效 |
| 第 3 层：单条记录归属校验 | 改/删某条记录前，先查它的 `school_id` 与我的范围比 | 🟠 **只有部分接口做了** |

第 3 层是本功能的全部风险所在：列表看不见他校数据，但只要猜到/拿到一个他校记录 id，就能直接改。

## 二、用户看到的样子（小程序端）

学生侧的「校」是**筛选**，不是隔离——这是产品设计，不是漏洞：

1. 首页有「选学校」入口 → 列表来自 `GET /api/schools`（`utils/school.js:7-17`），选中态存 storage（`utils/school.js:11, 32-40`）。
2. 所有列表接口带上 `schoolId`：外卖 `GET /api/shops?schoolId=&schoolScope=local|all`（`BizController.java:35-39`）、二手（`:96-106`）、活动（`:140-149`）。
3. `schoolScope=local` 只看本校，`all` 看全平台（跨校广场）。学生可以自由切换——因为「看别校的帖子」不涉及权限。
4. 发帖/发商品的归属学校由当前选中学校决定；`post.school_id` 允许 NULL，NULL 表示「跨校可见」（`db/module-multischool-admin.sql:56`）。

学生看不到的部分才是隔离重点：任何「我的数据」接口都只认 token 身份（`AuthInterceptor.java:74-92`），与学校无关。

## 三、运营看到的样子（Web 端）

1. 登录后左侧菜单由 `AdminLayout.vue` 根据 `meta.superOnly` 过滤（`web/src/layouts/AdminLayout.vue:84-85`）：校管看不到「学校管理」「管理员」「AI 助手」「积分任务」「兑换商品」「校园评选」六项。
2. 页面右上角标题栏显示当前范围：超管「全平台管理权限」，校管「本校管理权限 · 学校 ID N」（`AdminLayout.vue:89`）。
3. 列表页（用户/帖子/圈子/商品/活动/店铺/学期/地点/Banner）都有一个「学校」筛选器：超管可选任意学校或「全部」，校管被强制锁定本校，传别校 id 直接被 403（`AdminModuleController.java:443-453`）。
4. 新建记录时：校管自动写本校；超管必须显式选学校，否则报「请指定所属学校」（`AdminModuleService.java:557-567`）。
5. 单条操作（下架帖子、审核圈子、删学期、改活动状态…）走各自服务的 `assertSameSchool` 校验（`AdminModuleService.java:276-281`）。

**关键事实**：菜单隐藏**不是**权限。`web/src/router/index.js:82-101` 的路由守卫不检查 `meta.superOnly`，校管手输 `#/schools` 能打开页面，只是数据请求会被后端 403。代码里已经有人明确写下这条原则（`AppConfigController.java:22-26` 注释：「Web 路由上的 meta.superOnly 只是前端隐藏，后端必须自己拦」）。

## 七、业务规则与边界

**会拒绝的情况**

1. 校管账号没有 `school_id` → 登录拒绝（`AdminAuthService.java:45-47`）；请求时 `scope()` 抛 403「当前账号未绑定学校」（`AdminModuleController.java:432`）。
2. 校管在列表接口传别校 `schoolId` → 403「只能查看本校数据」（`AdminModuleController.java:446-449`）。
3. 超管新建活动/圈子/店铺/地点/学期不指定 `schoolId` → 400「请指定所属学校」（`AdminModuleService.java:200-201, 274-277, 565-566, 678-679`）。
4. 改/删有校验的单条记录时，`school_id` 与自己的范围不符 → 403「无权操作其他学校的数据」（`AdminModuleService.java:277-281`）。
5. 商家 token 访问非 merchant 路径 → 403（`AdminInterceptor.java:59-62`）。
6. 骑手 token 访问管理端 → 403「骑手账号不能访问管理端」（`AdminInterceptor.java:63-66`）。
7. 管理员角色/学校/店铺被改后，旧令牌立刻 401（`AdminTokenGuard.java:48-50`）。

**会放行、但不应放行的情况（本功能的核心风险）**

1. 校管用他校 banner id 调 `PUT /api/admin/banners/{id}` → 直接改成功，还能顺手把 `schoolId` 改成自己的（`AdminModuleService.java:801-802`）。
2. 校管用他校 banner id 调 `DELETE` → 直接删（`:786`）。
3. 校管用他校活动 id 调 `POST /activities/{id}/status` → 下架/恢复成功（`:756`）。
4. 校管用他校二手商品 id 调 `POST /goods/{id}/status` → 上/下架成功（`:764`）。
5. 校管用他校圈子 id 调 `PUT /circles/{id}` → 改名、改描述、甚至把 `status` 改成 0（`:648-672`，`schoolId` 参数从未被引用）。
6. 校管用他校报名 id 调 approve/reject → 通过或驳回成功，还会给他校活动报名数 +1（`BizService.java:515-528`）。
7. 校管用他校学期 id 调 `PUT /terms/{id}` → 改学期起止日期，影响他校课表周次计算（`:698-709`）。

**跨校内容（`school_id IS NULL`）的特殊规则**

- 列表接口：`post.school_id = ?` 对 NULL 恒为 false，所以**跨校内容在任何「指定学校」的列表里都不出现**（管理端与小程序都一样，`AdminModuleMapper.java:32`、`ModuleMapper.java:26`）；只有小程序 `schoolScope=all`（即 `schoolId=null`，SQL 不加学校条件）时才看得到（`BizService.java:170-174`、`BizService.java:164-169` 的注释）。
- 也就是说：脚本注释说的「NULL = 进全校广场」，实际只在「全部」视图成立；一旦用户选了某个学校，这批跨校内容就消失了。
- 单条操作：`assertSameSchool(null 值)` 被解析成 `-1`，与任何 scope 都不等 → 403。结果是**校管既看不到、也管不了本校本校流里的跨校内容**，这部分内容实际变成「只有超管能管」。
- 证据：`AdminModuleService.java:277-281`（`longOr(rowSchoolId, -1)`）、`db/module-multischool-admin.sql:56`。
