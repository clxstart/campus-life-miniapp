## 一、鉴权与身份

### 1.1 身份只认 token（已修正，但要确认开关）

- **现象**：历史实现"解析失败也放行"，任何人把 `userId` 改成别人就能越权。现已改为 token 解析成功才写入 `userId`，写操作与"我的数据"读接口无有效 token 直接 401。
- **证据**：`backend/src/main/java/com/campuslife/config/AuthInterceptor.java:18-21`、`:107-118`、`:157`
- **残留风险**：`AuthInterceptor.java:45` 保留"关掉后回到谁传 userId 就代表谁"的调试开关；生产必须确认 `campus.auth.enforce`（或同类配置）为默认值。
- **影响面**：全部写接口（发帖、下单、投票、退款、发分）。
- **细节**：`01-登录与鉴权/`、`02-多校隔离与权限/`。

### 1.2 管理端权限在拦截器统一做，但"超管专属"只在前端隐藏

- **现象**：`AdminInterceptor` 统一校验 role（super / school / merchant / rider）与强制改密，角色边界清楚；但 `meta.superOnly` 只是前端菜单隐藏，后端是否每个接口都自查需逐条核。
- **证据**：`backend/src/main/java/com/campuslife/config/AdminInterceptor.java:59-65`、`:87-88`；`web/src/router/index.js` 的 `meta.superOnly`；`backend/src/main/java/com/campuslife/controller/AppConfigController.java:23-25`（注释已意识到该问题）
- **影响面**：学校、管理员、认证细则、AI 配置、评选、积分任务等超管专属写接口。
- **建议**：在拦截器增加一层"路径 → superOnly"映射，而不是依赖每个 Controller 自觉。
- **细节**：`02-多校隔离与权限/`。

### 1.3 私有上传接口允许匿名访问

- **现象**：`/api/admin/upload/private` 在拦截器里被显式豁免 token（用于商家入驻材料提交），等于**匿名可写私有目录**。
- **证据**：`backend/src/main/java/com/campuslife/config/AdminInterceptor.java:30`
- **影响面**：存储配额被刷、垃圾文件、违规内容入库；上传限流规则存在（`service/RateLimiter.java:40`，20 次/分钟）但需确认挂到了该路径。
- **建议**：改为一次性上传票据（先申请 token 再传），或至少对匿名额做 IP 限流 + 类型白名单 + 总量配额。

### 1.4 注销账号的 token 立即失效（已实现）

- **证据**：`AuthInterceptor.java:112-116`（`UserStatusGuard` 判定非激活即 401）
- **影响面**：注销用户不会继续发帖/下单。

## 二、多校隔离（本项目最大的系统性风险）

### 2.1 `schoolId` 来源可信，但**没有强制注入机制**

- **现象**：管理员 token 的 `schoolId` 在拦截器解析后放进 request attribute，之后完全靠**每个 Service 方法自己带 `schoolId`**。漏一处就是一个跨校越权缺口。
- **证据**：`backend/src/main/java/com/campuslife/config/AdminInterceptor.java:75-76`；全仓 `school_id` 仅出现在手写 SQL 与 mapper 参数中，没有统一的租户拦截器/MyBatis 插件。
- **影响面**：所有管理端列表、详情、导出、批量操作、审核动作。
- **建议**：两条路——(a) 加 MyBatis 租户插件强制拼 `school_id`；(b) 至少对"按 id 取详情/改状态"的接口统一加 `assertSameSchool` 断言。
- **细节**：`02-多校隔离与权限/`、各管理端相关功能文档。

### 2.2 跨校对象查询是否二次校验，需逐接口核

- **现象**：`GET /api/admin/xxx/{id}` 类接口若只按主键查，不校验 `school_id`，A 校管理员可读 B 校数据（订单、用户、帖子、报名材料）。
- **影响面**：订单、支付流水、用户、帖子、报名、认证材料。
- **状态**：逐条核对结果见各功能文档；本文件只登记"这是共性模式"。

## 三、金额与单位（两种口径混用）

### 3.1 同一实体里"元"和"分"并存

| 位置 | 字段 | 单位 |
|---|---|---|
| `backend/src/main/java/com/campuslife/entity/UserOrder.java:29-35` | `subtotal` / `packingFee` / `deliveryFee` / `discountAmount` / `couponDiscount` / `total` | 元（BigDecimal） |
| `backend/src/main/java/com/campuslife/entity/UserOrder.java:40` | `payAmountCents` | 分（Integer） |
| `entity/Coupon.java:20-21` | `valueCents` / `thresholdCents` | 分 |
| `entity/PaymentRecord.java:17`、`entity/RefundRecord.java:17` | `amountCents` | 分 |
| `entity/Job.java:53`、`entity/JobContract.java:31` | `payCents` / `payCentsSnapshot` | 分 |
| `entity/Shop.java:4`、`ShopGoods.java:4` | `minPrice` / `price` / `deliveryFee` | 元 |

- **风险**：一处换算错就是错账；`BigDecimal` 与 `Integer` 混用时四舍五入方向不统一（`JobService.java:957` 有 `feeCents` 换算函数可作参考）。
- **建议**：对外只暴露一种单位；换算集中到一个工具类，禁止在 Controller/前端做乘除 100。
- **细节**：`06-外卖点餐与订单/`、`07-支付与退款/`、`09-兼职生态/`。

### 3.2 客户端不能传金额（设计正确）

- **证据**：`backend/src/main/java/com/campuslife/dto/CreateOrderRequest.java:12-14`（客户端只传 `idempotencyKey` 与 `couponId`，金额由服务端算）
- **影响面**：外卖、券抵扣。

## 四、事务、幂等与并发

### 4.1 事务覆盖尚可，但"提交后发分"会丢

- **证据**：全仓 `@Transactional` 93 处 / 28 个 service；发分走 `service/AfterCommitPointsAwarder.java`（事务提交后异步/后置发放）。
- **风险**：主事务提交成功、发分失败 → 用户该得的分没到账，且没有补偿任务。积分是准货币，属于资金级缺口。
- **建议**：发分落"待发放"表 + 补偿任务（项目里已有 `PaymentCompensationService` 可照抄模式）。
- **细节**：`20-积分体系/`、`27-交易任务埋点/`。

### 4.2 幂等键只有一个入口

- **证据**：`dto/CreateOrderRequest.java:12`（`^[A-Za-z0-9_-]{8,64}$`）；其余写接口是否有幂等键需逐条核。
- **影响面**：下单、支付回调、退款、签到、抢单、兑换。

### 4.3 定时任务只有 3 个，漏跑无兜底

| 任务 | 位置 | 用途 |
|---|---|---|
| 支付对账 | `service/PayService.java:273` | 轮询未完成支付 |
| 支付补偿 | `service/PaymentCompensationService.java:63` | 补偿卡住的单 |
| 论坛榜单结算 | `service/ForumRankService.java:166` | 日/周榜 |

- **风险**：签到跨天、宿舍周榜、火花连续活跃、新榜补跑等**没有独立兜底任务**；服务重启错过 cron 只能人工补（榜单页有"重新结算"入口，属于人工兜底）。
- **细节**：`21-签到与连签/`、`24-论坛日榜周榜/`、`26-宿舍域/`。

### 4.4 并发热点集中在四处

下单（库存/券）、退款（重复退）、抢单（骑手/兼职）、发分（重复发）。各功能文档必须给出"并发下会不会重复/超发"的结论与证据。

## 五、内容安全

### 5.1 微信内容安全在参数缺失时**静默放行**（上线级风险）

- **证据**：`backend/src/main/java/com/campuslife/service/AuditService.java:180-184`（`appid`/`secret` 为空或 openid 以 `dev-` 开头 → `log.warn` 后跳过）
- **后果**：开发环境/配置漏配时，表现为"只有本地敏感词库在拦"，**以为在审其实没审**。
- **必须做**：生产配好参数后，发一条命中词文本验证真的被拦；把"审核跳过"做成可告警指标。

### 5.2 审核覆盖缺口（待各功能文档确认后汇总）

已知可能缺口：圈子群聊（WebSocket 实时推送）、昵称/头像修改、AI 聊天输入、活动报名材料、学习专区 UGC。逐条结论见 `29-内容治理与安全/` 与对应功能文档。

### 5.3 举报闭环

- **证据**：`service/ContentReportService.java`、`controller/ContentReportController.java`、`web/src/views/Reports.vue`
- **待核**：处理动作是否联动下架/删除内容并回写通知；同一对象多人举报是否合并；处理是否有审计日志。

## 六、消息触达

### 6.1 只有站内通知，没有订阅消息

- **现象**：通知只写 `notification` 表，用户不打开小程序就永远不知道（订单状态、审核结果、被回复）。全仓未见 `requestSubscribeMessage` 调用（以功能文档复核为准）。
- **影响面**：外卖、兼职、认证、活动报名、论坛互动。
- **建议**：先统一事件源，再挂订阅消息通道；一次性订阅必须用户主动授权，不能作为唯一触达手段。

### 6.2 未读数是高频争议点

- **证据**：`components/bottom-nav`（未读数缓存）、`service/CampusService.java`
- **待核**：已读/未读的写入时机、多端一致性、清零逻辑。

## 七、上传与私有文件

| 项 | 现状 | 证据 |
|---|---|---|
| 公开图片 | `/uploads/**` 映射到本地上传根 | `backend/src/main/java/com/campuslife/config/WebConfig.java:53-54` |
| 私有材料 | 写入「上传根/private/」，但**上传根本身被 `/uploads/**` 映射** → `/uploads/private/<name>` 可被直链下载 | `service/UploadService.java:47-53`、`ha/LocalObjectStorage.java:27,37`、`config/WebConfig.java:54` |
| 对象存储模式 | 私有前缀 `/private` 由业务层读取（`ObjectStorage.readPrivate`），本机模式下无第二道鉴权 | `ha/LocalObjectStorage.java:41` |
| 匿名上传口 | `/api/admin/upload/private` 无 token 放行 | `config/AdminInterceptor.java:30` |

- **结论（P0）**：私有材料（学生证、报名材料、认证照片）在本地磁盘模式下**通过静态映射可被直接下载**，URL 猜中即可。`19-个人中心与账号安全/`、`25-学生认证/`、`11-活动与报名审核/` 三份文档独立复现了同一问题。
- **待核**：对象存储（OSS/CDN）模式下私有前缀是否也公开可读；私有文件的鉴权预览链路（审核员怎么看图）。

## 八、可观测与告警

### 8.1 支付指标有计数器，但没有暴露与告警规则

- **证据**：`service/PaymentAlerts.java:28-30`（Micrometer `campus.pay.events`）+ `:21/:39`（30 秒限速日志）；`backend/pom.xml:36` 引入 actuator。
- **问题**：`application*.yml` 里**没有任何 `management.*` 配置**，Spring Boot 默认只暴露 `/actuator/health` → 计数器采集不到；仓库里也没有告警规则文件（`grep -ril "alert" backend/src/main/resources` 无结果）。
- **结论**：**"有指标、有日志、没有告警"**。上线前必须补暴露配置 + 告警规则（或至少日志关键字告警）。
- **细节**：`28-管理后台与运营/`、`07-支付与退款/`。

### 8.2 客户端错误上报已闭环

- **证据**：`app.js:16-73`（`reportClientError` → `/api/log/client`）；后端 `controller/ClientErrorController.java:28`（上报）、`:46`（列表）、`:54`（清理）。
- **结论**：这一条是**做得比多数项目好**的地方，可作为对外亮点。

### 8.3 审计日志

- `audit_log`（内容审核）与 `admin_log`（后台操作）两套，逐功能文档核对"高危操作是否都写了"。

## 九、离线兜底与生产配置

### 9.1 兜底规则设计正确

- **规则**：只有"网络不通"才用本地演示数据；服务端有响应但报错（401/403/409/500）必须原样抛出。
- **证据**：`utils/api/core.js:175-184`（`fallback`）、`:14-16`（`DEMO_USER_ID` 仅非生产）、`:45`（生产返回 0）
- **结论**：这是**值得保留的设计**，避免"假数据盖住真错误"。

### 9.2 生产域名仍是占位（P0，阻断发布）

- **证据**：`utils/config.js:9`（`PRODUCTION_ORIGIN = 'https://api.your-domain.example'`）、`:42-47`（占位/HTTP/localhost 一律判错）、`:70`（生产环境 `CONFIG_ERROR` 非空）
- **后果**：fail-closed 设计正确，但**发布版会直接阻断所有请求**——不改域名就上不了线。
- **必须做**：替换真实 HTTPS 域名 + 微信后台配置 request/uploadFile/downloadFile 合法域名。

### 9.3 开发默认值里有真实凭据样式

- **证据**：`backend/src/main/resources/application-dev.yml:7`（`${DB_PASSWORD:chang090011}`）、`:11`（JWT 默认密钥）
- **风险**：dev 配置随仓库分发；若生产 profile 未被正确激活，会带着弱凭据启动。生产 profile 强制环境变量（`application-prod.yml:9/:30/:32`）是正确做法，需要在部署文档里强调"必须 `--spring.profiles.active=prod`"。

## 十一、按影响面排的修复优先级（建议）

| 优先级 | 横切问题 | 影响功能数 | 为什么排这里 |
|---|---|---|---|
| 1 | 生产域名占位（9.2） | 全部（小程序侧） | 不改就发布不了 |
| 2 | 私有材料可直链下载 + 匿名可写私有目录（7） | 认证/报名/个人中心/商家 | 学号、证件照片直接泄露，属数据红线 |
| 3 | 内容安全静默放行（5.1） | 全部 UGC | 审核不通过 + 违规内容扩散 |
| 4 | 多校隔离无强制机制（2.1/2.2） | 全部管理端 | 一次越权就是事故 |
| 5 | 金额单位混用（3.1） | 外卖/支付/兼职 | 错账不可逆 |
| 6 | 发分无补偿（4.1） | 积分/埋点 | 准货币，用户会投诉 |
| 7 | 告警未打通（8.1） | 支付/退款 | 出事靠人翻列表 |
| 8 | 通知只落库（6.1） | 外卖/兼职/认证 | 体验，不阻断 |

> 这张表是"跨功能共性"的排序；单个功能的 P0 以 `01-上线风险总表.md` 为准。
