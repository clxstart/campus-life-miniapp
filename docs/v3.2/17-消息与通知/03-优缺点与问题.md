## 一、设计优点（为什么这么设计，好在哪）

1. **未读数在服务端一次算完，前端不做累加。** 会话列表的子查询把"对方发来的 + 给我的 + 未读 + 已过审 + 清空水位线之后"一次写进 SQL（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:28-29`）。比"前端边收边 +1"可靠，多端登录也不会重复计数。

2. **"清空"用水位线而不是物理删除。** `chat_preference.cleared_before` + `GREATEST()` 只增不减（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:78-80`），单方面清空不影响对方。这是私聊最容易做错的一处（很多实现直接 `DELETE`，把对方的记录也删了），这里做对了。

3. **发送幂等做了两层，且幂等键按发送人隔离。** 唯一键 `uk_chat_client(sender_id,client_id)`（`backend/src/main/resources/db/module-messages-academics.sql:9`）+ `ON DUPLICATE KEY UPDATE id=LAST_INSERT_ID(id)`（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:56-63`），service 层再回读比对 `receiverId`/`content` 防"同一 clientId 换了内容"（`backend/src/main/java/com/campuslife/service/CampusService.java:30`）。弱网重试这条最容易出重复消息的路径被堵住了。

4. **断网降级不撒谎。** 发送失败存本机，toast 明确写"已保存到本机演示记录，**未发送给对方**"（`pages/chat/chat.js:122`），文件头还有一条铁律注释（`utils/api/chat.js:1-4`）。比"本地显示已发送、其实对方收不到"诚实。

5. **已读更新用条件 UPDATE，天然防越权。** `WHERE receiver_id=#{userId} AND sender_id=#{peerId} AND id<=#{upToId}`（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:68-69`）——即使客户端传一个巨大的 `upToId`，也只能标记自己收到的、这个人发来的消息。

6. **emoji 面板只做 Unicode。** 70 个字符、5 类（`components/emoji-panel/index.js:2-8`），零图片资源、零版权风险、零审核成本。

7. **emoji 插入处理了中文输入法光标。** 只在插 emoji 时写 `inputCursor`，避免组词时 `setData` 抢光标（`pages/chat/chat.js:65-79` 注释解释了原因）。这是被真实 bug 咬过才会写的代码。

8. **拉黑在服务端双向阻断。** `blockService.blockedBetween(userId,peerId)`（`backend/src/main/java/com/campuslife/service/CampusService.java:20`）不区分谁拉黑谁，任一方拉黑则双方都发不出。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 通知"只落库"，六处写入点全部是"写进表就结束"

`notifyUser` 的实现只有一条 INSERT（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:95`）。全仓**没有**订阅消息、模板消息、WebSocket 推送、短信或邮件的发送代码（`grep -rn -i "subscribeMessage\|订阅消息\|templateId" backend/src/main pages/ utils/` 零命中）。

通知的完整生命周期只剩下：

```
帖子被赞 → INSERT notification → …… → 用户自己主动点开首页铃铛 → GET /api/notifications → 看到
```

中间没有"主动告诉用户"的任何一步。微信生态里这本该由**订阅消息**补上。缺失的代价是本功能的商业价值归零：一个没人知道存在的通知中心，等于没有通知。

### 2.2 铃铛入口无未读数，用户没有任何"有新消息"的视觉线索

`pages/index/index.wxml:38-40` 的铃铛只是图标，无 `wx:if` 计数节点。`app.json` 没有 `tabBar`（`node -e "require('./app.json').tabBar"` → `undefined`），全仓也没有 `setTabBarBadge` 调用。

所以即使服务端未读数算得准（第一节优点 1），**界面上也不显示**。这是 2.1 的加重项：推送没有、红点也没有，两层触达全部缺失。

### 2.3 私聊实时性靠 5 秒轮询，成本与体验双输

`pages/chat/chat.js:34` 每 5 秒拉一次 30 条完整消息并 `setData`。代价：

- **体验**：最快 5 秒才看到对方的话，接近"论坛回帖"；
- **成本**：每个打开私聊页的用户 = 每分钟 12 次请求 × 30 行。1000 人在线聊即 12,000 QPS 打在单表 `chat_message` 上；
- **不合理之处**：同仓库群聊有 WebSocket（`backend/src/main/java/com/campuslife/service/CircleChatService.java`，配套 `utils/chat-sync.js` 断开补量），**私聊反而没有**。技术栈不缺，是没接。

### 2.4 审核中的消息两头都不见，发送方却看到"发送成功"

`send()` 在审核返回 `reviewing` 时以 `audit_status='reviewing'` 落库（`backend/src/main/java/com/campuslife/service/CampusService.java:30`），而所有读取路径只认 `'passed'`（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:33,49`）。

- 发送方：接口 200，前端渲染气泡（`pages/chat/chat.js:119-121`）→ 以为发出去了；
- 接收方：永远看不到；
- 5 秒后的轮询重新拉服务端数据（`pages/chat/chat.js:127`），`reviewing` 不在返回里 → 发送方看到自己刚发的消息**凭空消失**；
- 会话可能整体消失：若这对用户之间所有消息都 `reviewing`，`MAX(x.id)` 为 NULL，`JOIN` 不成立（`CampusMapper.java:32-34`）→ 会话从列表里没了。

而 `reviewing` 的放行**只能靠管理员手工点**（`backend/src/main/java/com/campuslife/service/AuditService.java:454` 的 `decideChat`），没有超时自动放行、没有自动驳回、没有通知告知发送方"你的消息在审核中"。

### 2.5 私聊原文进管理端审核台，无用户告知

`AuditService.list(type="chat")` 返回每条消息的 `content` 与 60 字 `snippet`（`backend/src/main/java/com/campuslife/service/AuditService.java:386-387`），详情分支 `case "chat" -> auditMapper.chat(id, schoolId)`（`:467`）可直接取全文。

技术上这是"内容合规"所需，但产品上必须有三个前提，当前一个都没有：

1. 隐私政策明确告知"为履行内容安全义务，平台可能依法定程序查看你的私信"；
2. 审核员访问私聊留审计日志（谁能看、看了谁、看了哪条）；
3. 除 `reviewing` 状态外的私聊不出现在审核台列表里（当前 `list()` 的状态筛选由调用方传，传 `passed` 也能查）。

缺这三样，"能看私聊"就从合规能力变成合规风险。

### 2.6 会话内没有拉黑/举报入口，被骚扰的用户无自救路径

`more()` 只有三项（`pages/chat/chat.js:133`）。要拉黑对方，得先点"查看资料"进个人页——但 `pages/user-home/user-home.js` **也没有**拉黑/举报按钮（grep 无命中）；实际能拉黑的入口只有帖子详情（`pages/post-detail/post-detail.js:193`）和个人中心（`pages/profile/profile.js:380`）。

对一个正在被骚扰的用户，"去翻对方发过的帖子、从帖子详情页拉黑他"是一条荒谬的路径。消息级举报**完全不存在**（全仓唯一的 `reportContent` 调用是 `'post'` 类型，`pages/post-detail/post-detail.js:172`）。

### 2.7 通知去重键恒为 NULL，点赞/收藏可以反复刷通知

`notification` 表设计了 `uk_notification_seed(user_id, source_key)`（`backend/src/main/resources/db/module-messages-academics.sql:23`），种子数据也确实靠它去重（`:50` 的 `INSERT IGNORE`）。但业务写入的 `notifyUser` **不在 INSERT 列清单里包含 `source_key`**（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:95`）。

MySQL 唯一索引对 NULL 不做去重，所以：取消赞再点赞 → 又一条（`backend/src/main/java/com/campuslife/service/ForumService.java:165` 在 `liked` 为 true 时无条件通知）；取消收藏再收藏 → 又一条（`backend/src/main/java/com/campuslife/service/UserService.java:56`）；取关再关注 → 又一条（`ForumService.java:223`）。用户可以在几分钟内把别人的通知中心刷满。

### 2.8 无好友关系、无学校校验、无频控 —— 私聊是一条开放骚扰通道

`pair()` 的全部约束是：用户存在、不是自己、没有拉黑（`backend/src/main/java/com/campuslife/service/CampusService.java:20`）。`chat_message` 也没有 `school_id`。

配合 `user_id` 是连续自增（种子数据里就是 user 1/2/3/4，`backend/src/main/resources/db/module-messages-academics.sql:42-49`），遍历 id 就能给全平台任意用户发消息，且无频控（`backend/src/main/java/com/campuslife/controller/CampusController.java:17` 未注入 `RateLimiter`；对照发帖 `backend/src/main/java/com/campuslife/controller/ForumController.java:89` 有 `limiter.acquire`）。

对校园产品，"能私聊到任何人"可能是设计意图（二手交易需要），但**缺频控 + 缺举报入口 + 缺红点**三件凑在一起，就构成了完整可用的骚扰链路。

### 2.9 通知列表固定 100 条，超出的永久看不到

`ORDER BY id DESC LIMIT 100`（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:89`），无分页参数、无"加载更多"。一个活跃用户的通知中心从第 101 条起就是黑洞，且前端也没有任何提示（`pages/messages/messages.js:29` 只对返回的这批做统计）。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 现方案 | 替代方案 | 为什么没选（从代码能看出的原因） | 本方案的真实代价 |
|---|---|---|---|
| 通知只落库 | 微信订阅消息（一次性订阅 + 模板消息） | 全仓无相关代码，也没有模板 ID 配置项（`grep templateId` 零命中），可能是资质或排期问题 | 通知完全无效 |
| 铃铛无红点 | 自绘红点 / `setTabBarBadge` | `app.json` 根本没有 `tabBar`，红点无处可挂 | 未读数算了没人看 |
| 私聊 5 秒轮询 | 复用群聊的 WebSocket 通道 | 群聊已有 `CircleChatService` + WSS 基础设施 | 体验差、成本高 |
| 审核中消息对双方不可见 | 发送方可见自己 `reviewing` 的消息（带"审核中"标记），仅接收方不可见 | 当前 SQL 用一个 `audit_status='passed'` 同时管两边 | 消息凭空消失，用户信任受损 |
| 消息级举报 | 复用 `ContentReportController` 加 `chat` 目标类型 | `CONTENT_REPORT` 已有服务（`backend/src/main/java/com/campuslife/controller/ContentReportController.java`），只是前端不给入口 | 骚扰无法举报 |
| 通知去重靠唯一键 | 写入时带 `source_key`（如 `like:<postId>:<userId>:<天>`） | 字段和唯一键都建好了，只是没传值 | 通知可被刷 |
| 私聊无频控 | 复用 `RateLimiter` 的 `PUBLISH` 档或新增 `CHAT` 档 | 没做 | 骚扰零成本 |
| 消息保留策略 | 冷热分离 / 归档表 | 没做 | 单表无限增长 |

## 五、如果重做会怎么改

按"漏了什么能力"排序，不谈抽象原则：

1. **先补触达（最高优先）。** 两件事：一个 `/api/messages/unread-count` 聚合接口 + 首页铃铛红点；微信订阅消息（用户首次发起私聊/首次被评论时请求授权，服务端在通知落库成功后发模板消息）。约 3 人日。做完这条，现有的六处通知写入点才真正产生价值。

2. **把私聊从轮询换成 WebSocket。** 复用群聊已有的通道与 `utils/chat-sync.js` 的补量思路（先渲染最新一页，再后台补缺口）。轮询保留为 30 秒兜底。约 3 人日。

3. **审核态改造。** 发送方查询放行自己的 `reviewing` 消息并打"审核中"标记；加超时自动放行（如 10 分钟）；审核结论回写时给发送方一条通知。约 2 人日。

4. **自救路径。** 会话 `more()` 加"拉黑并举报"；`ContentReportController` 增 `chat` 目标；`user-home` 补拉黑入口。约 1.5 人日。

5. **通知去重与分页。** `notifyUser` 增 `sourceKey`；列表改游标分页。约 1.5 人日。

6. **频控与会话门槛。** `RateLimiter` 新增 `CHAT` 档；"首次会话"更严配额。约 1.5 人日。

7. **私聊可见性的合规改造。** 隐私政策条款 + 审核台私聊访问留痕 + 列表默认只查 `reviewing`。约 2 人日。

8. **建表脚本自洽。** 审核三列并入 `module-messages-academics.sql`，或出一份固定顺序的部署说明。约 0.5 人日。
