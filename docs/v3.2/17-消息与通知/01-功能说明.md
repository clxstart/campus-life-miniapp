## 一、这个功能解决什么问题

平台有两类"别处发生的事要告诉用户"：

1. **人对人**：二手交易谈价、约见面、圈子活动对接——需要一个**私聊会话**，能看历史、能免打扰、能清空自己那侧记录，且**未读数要准**。
2. **系统对人**：帖子被赞/被评论/被收藏、有人关注我、审核通过或下架、订单被取消——需要一个**通知流**，分类（赞和收藏 / 评论和回复 / 系统通知）展示。

代码里这两类被合在同一个模块：`CampusController` 的 `/api/conversations*`、`/api/notifications`、`/api/messages/read-all`，加小程序 `pages/messages`（消息页）与 `pages/chat`（私聊页）。

> **边界说明**：`CampusController` 同时托管课表段（`/api/timetable*`，`backend/src/main/java/com/campuslife/controller/CampusController.java:85-120`），课表归 `13-课表与教务/`，本文档只写消息/通知部分。同理 `utils/chat-sync.js` 是**圈子群聊**的重连补量工具，归 `05-圈子与群聊/`，本文档只在第七节说明它为什么不算私聊能力。

## 二、用户看到的样子（小程序端）

### 2.1 唯一入口：首页铃铛

`pages/index/index.wxml:38-40` 是一个 `notification-entry` 视图，`bindtap="openNotifications"`，图标 `/assets/icons/bell.svg`，**没有任何未读数或红点**。点击后 `wx.navigateTo({url:'/pages/messages/messages?tab=notice'})`（`pages/index/index.js:163-165`），直接落在"通知"tab。

`app.json` **没有配置 `tabBar`**（`node -e "require('./app.json').tabBar"` 返回 `undefined`），也没有 `custom-tab-bar` 目录，所以"消息"不是一个常驻底部入口，**只在首页有一个铃铛**。

### 2.2 消息页（`pages/messages`）

- 两个 tab：`chat`（聊天）与 `notice`（通知），默认 `chat`，带 `?tab=notice` 时默认通知（`pages/messages/messages.js:7-8`）。
- `onShow` 就拉一次数据：并发请求 `GET /api/conversations` 与 `GET /api/notifications`（`pages/messages/messages.js:9,16`）。**没有定时刷新、没有下拉之外的自动更新**（下拉刷新在 `:11`）。
- 未读汇总三处：`unreadTotal`（会话未读之和 + 通知未读数）、`likeUnread`（赞/收藏/关注）、`commentUnread`（评论）（`pages/messages/messages.js:29-31`）。
- **免打扰会话不计入未读**：`row.muted ? 0 : Number(row.unread)`（`pages/messages/messages.js:29`）。
- 通知筛选：`赞和收藏` → `like/favorite/follow`，`评论和回复` → `comment`，`系统通知` → `system`（`pages/messages/messages.js:28,56`）。
- "全部已读"按钮 → `POST /api/messages/read-all`，成功后本地把会话 `unread` 与通知 `unread` 全部清零（`pages/messages/messages.js:38-50`）。
- 点会话 → 跳 `pages/chat/chat?id=&name=&color=&avatar=`（`pages/messages/messages.js:51-54`）。
- 点通知 → 有 `postId` 就跳帖子详情（`pages/messages/messages.js:60-63`）。

### 2.3 私聊页（`pages/chat`）

- `onShow` 后**每 5 秒轮询一次**拉最新消息（`pages/chat/chat.js:32-34`）。
- 进页面即拉最近 30 条（`utils/api/chat.js:36`），返回后立刻 `markChatRead` 把 `last.id` 之前的对方消息标已读（`pages/chat/chat.js:55-56`）。
- 上拉加载更早消息，用 `beforeId` 游标（`pages/chat/chat.js:40,63`）。
- 输入框 + emoji 面板（`components/emoji-panel/index.js`，Unicode 字符，5 类 × 14 个 = 70 个，`components/emoji-panel/index.js:2-8`）。
- 发送失败会复用同一个 `clientId` 重试，避免重复发送（`pages/chat/chat.js:108-112`）；网络断了会存本机并明确告知"已保存到本机演示记录，未发送给对方"（`pages/chat/chat.js:122`、`utils/api/chat.js:46-59`）。
- 右上角 `more()` 只有三项：**查看资料 / 消息免打扰 / 清空聊天记录**（`pages/chat/chat.js:133`）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 会拒绝的情况

全部来自 `CampusService.pair()`（`backend/src/main/java/com/campuslife/service/CampusService.java:20`）：

| 条件 | 拒绝文案 | 证据 |
|---|---|---|
| `userId` 或 `peerId` 为 null / <1 | `用户参数无效` | `CampusService.java:19` |
| 用户不存在 | `用户不存在` | `CampusService.java:19` |
| 自己和自己聊 | `不能与自己聊天` | `CampusService.java:20` |
| 双方存在拉黑关系（任一方向） | `对方与你之间存在拉黑关系，无法聊天` | `CampusService.java:20`；`blockService.blockedBetween` |
| 分页游标 `beforeId < 1` | `分页游标无效` | `CampusService.java:23` |
| 已读游标 `upToId` 为 null / <1 | `消息游标无效` | `CampusService.java:31` |
| 消息内容为空 | `@NotBlank` 校验失败 | `backend/src/main/java/com/campuslife/dto/SendMessageRequest.java` |
| 消息超过 1000 字 | `@Size(max=1000)` → `消息不能超过1000字` | 同上 |
| 缺 `clientId` | `@NotBlank` 失败 | 同上 |
| 内容命中敏感词 / 微信判违规 | `rejectWithLog` 抛异常，整条不落库 | `backend/src/main/java/com/campuslife/service/CampusService.java:30`；`AuditService.java:168-173` |
| 同一 `clientId` 被不同内容复用 | `消息请求标识已被其他内容使用` | `CampusService.java:30`（回读后比对 `receiverId` 与 `content`） |

### 7.2 不会拒绝的情况（边界洞）

| 条件 | 实际行为 | 证据 |
|---|---|---|
| **对方从未与你聊过、也不认识你** | 照常发送成功。无好友关系要求、无"先打招呼"限制 | `CampusService.java:20` 只校验存在性与拉黑 |
| **跨校发给任意 userId** | 照常发送成功。`chat_message` 无 `school_id`，`pair()` 不校验学校 | `CampusService.java:20`；`module-messages-academics.sql:3-11`（无该列） |
| **高频发送** | 无限流。`CampusController` 未注入 `RateLimiter` | `CampusController.java:17`（唯一依赖是 `CampusService`） |
| **发图片** | 不支持（`type` 写死 `text`） | `backend/src/main/java/com/campuslife/mapper/CampusMapper.java:57-60` |

### 7.3 未读数的准确口径（逐条对齐）

会话未读 = 满足全部条件的消息数（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:28-29`）：

```sql
SELECT COUNT(*) FROM chat_message z
 WHERE z.sender_id = u.id            -- 对方发来的
   AND z.receiver_id = #{userId}     -- 给我的
   AND z.read_at IS NULL             -- 未读
   AND z.audit_status = 'passed'     -- 只算审核通过的
   AND z.id > COALESCE(p.cleared_before,0)  -- 清空水位线之后
```

这个口径本身是自洽的，问题出在三处外围：

1. **`audit_status != 'passed'` 的消息不计未读，也对双方不可见**——审核中的消息等于"发了但消失"（见 7.5）。
2. **会话可能整体消失**：会话列表用 `JOIN chat_message m ON m.id=(SELECT MAX(x.id) ... AND x.audit_status='passed')`（`CampusMapper.java:32-34`），如果一对用户之间**所有**消息都在审核中，`MAX` 返回 `NULL`，JOIN 不成立，**这个会话从列表里消失**。
3. **`muted` 会话的未读在前端被强制归零**（`pages/messages/messages.js:29`），但服务端仍在累加；一旦用户关掉免打扰，会突然出现一笔"陈年未读"。这是产品选择，不是 bug，但要有意识。

### 7.4 清空与已读的补偿边界

- `clear()`：取 `latestId(userId,peerId)` 作为 `cleared_before` 写进 `chat_preference`，随后把对方消息标已读（`CampusService.java:33`）。**只影响自己那一侧**，对方仍能看到全部记录——前端文案也是这么说的（`pages/chat/chat.js:137`：`只清空你看到的记录，不影响对方`）。
- `readAll()`：一次性 `readAllChats` + `readNotifications`（`CampusService.java:32`）；SQL 层不区分会话（`CampusMapper.java:72`：`WHERE receiver_id=#{userId} AND read_at IS NULL`）。语义上正确（"全部已读"就该是全部）。
- **没有补偿任务**：没有任何定时任务清理审核中滞留的消息、没有未读数重算、没有通知补发。

### 7.5 "发了但消失"的完整链路

`send()` 里内容审核返回 `reviewing` 时，消息以 `audit_status='reviewing'` 落库（`CampusService.java:30`），而所有读取路径都过滤 `audit_status='passed'`（`CampusMapper.java:33,49`）。谁来把它改成 `passed`？

- 图片帖有异步审核回调：`auditService.scheduleImagesAfterCommit(...)`（`ForumService.java:161`）；
- **文本消息没有等价机制**（`CampusService.java:30` 只调 `logTextResult`，不排任何异步任务）；
- 唯一出路是人工在管理端审核台点"通过"（`AuditService.java:454` 的 `decideChat`）。

所以：**一条被判"待人工审核"的私聊，在管理员点通过之前，发送方看到"发送成功"，双方都永远看不到它。** 详见 `03-优缺点与问题.md` 的 17-03。
