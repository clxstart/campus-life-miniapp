## 一、合规与隐私

**结论：不通过。** 原因：私聊内容明文入库且管理端可检索原文，用户协议无对应告知，审核员访问无私聊专属留痕。

| 检查项 | 结论 | 证据 |
|---|---|---|
| 私聊是否明文存储 | 🟠 是。`chat_message.content` 原样存储，无字段级加密 | `backend/src/main/resources/db/module-messages-academics.sql:6` |
| 谁能读私聊 | ❌ 管理员可通过审核台 `type=chat` 读原文与 60 字摘要 | `backend/src/main/java/com/campuslife/service/AuditService.java:386-387,454,467` |
| 是否告知用户"平台可查看私信" | ❌ 隐私政策页存在但未核对到私信条款 | `pages/agreement/agreement.js:6-7`（页面存在，条款文本**未逐句核对**，标为未验证） |
| 审核员访问是否留痕 | ❌ `list()` 只读不记日志 | `backend/src/main/java/com/campuslife/service/AuditService.java:377-390` |
| 会话对象身份可核实性 | 🟠 无实名/学生认证门槛，任意 `userId` 可聊 | `backend/src/main/java/com/campuslife/service/CampusService.java:20` |
| 骚扰/举报通道 | ❌ 消息级举报不存在 | `pages/post-detail/post-detail.js:172`（仅 `'post'` 类型） |
| 未成年人保护 | ❌ 无私聊限制、无年龄门槛 | 全仓无相关判断 |
| 内容安全 | 🟠 有敏感词 + 微信 `msg_sec_check`，但接口异常时 **fail-open** | `backend/src/main/java/com/campuslife/service/AuditService.java:168-205` |

**判断依据**："私聊可被平台人员读取"本身不是问题（内容安全是法定义务），问题是**没有告知、没有授权、没有访问审计**这三缺。三者任一缺失，被用户质疑或监管检查时无法自证已尽责。补齐后可降为"有条件通过"。

## 二、资金与对账

**结论：不涉及。** 依据：

- 三张表（`chat_message`、`chat_preference`、`notification`，`backend/src/main/resources/db/module-messages-academics.sql:3-24`）无金额、无余额、无流水字段。
- `CampusService` 全部依赖是 `CampusMapper`、`UserMapper`、`AuditService`、`UserBlockService`（`backend/src/main/java/com/campuslife/service/CampusService.java:16-17`），无 `PayService` / `WalletService` / `PointsService` 调用。
- 消息与通知不触发任何积分、成长值、优惠券。

> 一处间接关系：`notification` 里有"订单已取消"（`backend/src/main/java/com/campuslife/service/MerchantService.java:256`）。这条通知本身不涉及资金，但**如果发不出去，用户就不知道订单已被取消**，会以退款工单的形式出现在别的模块。即本功能的"通知不触达"会伪装成资金客诉。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：不通过。** 原因：`chat_message` 的审核三列在另一个脚本里，执行顺序没有文档化，漏跑直接导致发消息 500。

### 4.1 前置 SQL 与**强制执行顺序**

```sql
-- 第 1 步：建表（module-messages-academics.sql）
CREATE TABLE IF NOT EXISTS chat_message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  sender_id BIGINT NOT NULL, receiver_id BIGINT NOT NULL,
  type VARCHAR(8) NOT NULL DEFAULT 'text', content VARCHAR(1000) NOT NULL DEFAULT '',
  image VARCHAR(255), client_id VARCHAR(64) NOT NULL, read_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_chat_client(sender_id,client_id),
  KEY idx_chat_pair(sender_id,receiver_id,id), KEY idx_chat_receiver(receiver_id,read_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS chat_preference (
  user_id BIGINT NOT NULL, peer_id BIGINT NOT NULL,
  cleared_before BIGINT NOT NULL DEFAULT 0, muted TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY(user_id,peer_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS notification (
  id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id BIGINT NOT NULL,
  title VARCHAR(64) NOT NULL, content VARCHAR(1000) NOT NULL,
  category VARCHAR(16) NOT NULL DEFAULT 'system', tone VARCHAR(16) NOT NULL DEFAULT 'blue',
  post_id BIGINT NULL, source_key VARCHAR(64) NULL, read_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_notification_seed(user_id,source_key), KEY idx_notification_user(user_id,id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 第 2 步【必须】：给 chat_message 补审核三列（module-audit.sql:33-38）
--   漏跑这一步 → CampusService.send() 报 Unknown column 'audit_status'
ALTER TABLE chat_message
  ADD COLUMN audit_status VARCHAR(16) NOT NULL DEFAULT 'pending',
  ADD COLUMN audit_reason VARCHAR(200) NULL,
  ADD COLUMN audit_at DATETIME NULL;
UPDATE chat_message SET audit_status='passed' WHERE audit_status='pending';

-- 第 3 步：审核状态索引（module-audit.sql:58）
ALTER TABLE chat_message ADD INDEX idx_chat_audit_status(audit_status);
```

- 来源：第 1 步 `backend/src/main/resources/db/module-messages-academics.sql:3-24`；第 2、3 步 `backend/src/main/resources/db/module-audit.sql:33-38,58`。
- **反序会失败**：`module-audit.sql` 先用 `information_schema` 判断列是否存在，表不存在时判断为"列不存在"→ 执行 `ALTER` → 报 `Table doesn't exist`。属读码推断，**未实跑**。

## 五、性能与容量

**结论：不通过。** 原因：私聊 5 秒轮询 × 30 条/次，无压测数据，且未读数子查询无针对性索引。

| 检查项 | 结论 | 证据 |
|---|---|---|
| 会话列表查询 | 🟠 每行一个相关子查询（未读计数）+ 一个 `MAX(id)` 子查询，会话数 N 则为 2N 次子查询 | `backend/src/main/java/com/campuslife/mapper/CampusMapper.java:23-37` |
| 未读计数索引 | 🟠 依赖 `idx_chat_receiver(receiver_id, read_at)` | `backend/src/main/resources/db/module-messages-academics.sql:10` |
| 设计中的 `(receiver_id, created_at)` 索引 | 🟠 **永不生效**：`module-perf-index.sql:69-72` 按索引名判存在，而同名索引已由建表脚本创建（列不同） | `backend/src/main/resources/db/module-perf-index.sql:69-72` vs `module-messages-academics.sql:10` |
| 消息分页 | ✅ `beforeId` 游标 + `LIMIT`，走 `idx_chat_pair` | `backend/src/main/java/com/campuslife/mapper/CampusMapper.java:46-53` |
| 私聊轮询压力 | ❌ 每在线私聊页 12 次/分钟 × 30 行 | `pages/chat/chat.js:34`、`utils/api/chat.js:36` |
| 消息表增长 | ❌ 无归档、无 TTL、无冷热分离 | 全仓无相关任务（`grep @Scheduled` 仅 3 处，均非消息域） |
| 压测 | ❌ 未执行 | `docs/v3.2/04-证据与复核台账.md` 第四节第 8 项 |

**粗算**：1000 人同时在线私聊 = 1000 × 12 = 12,000 请求/分钟 ≈ 200 QPS，每次返回 30 行 → 约 6000 行/秒的读放大。单机 MySQL 不至于崩，但没有余量做增长，且这些流量 99% 是"没有新消息"的空轮询。

## 九、结论

**不可上线（阻断项：17-01、17-02）。**

1. **17-01 通知只落库不触达** —— 全仓零订阅消息、零推送、入口零红点（`backend/src/main/java/com/campuslife/mapper/CampusMapper.java:95`、`pages/index/index.wxml:38-40`）。这不是"体验差"，而是"通知功能不存在"。
2. **17-02 私聊原文进管理端审核台且无告知无留痕** —— `backend/src/main/java/com/campuslife/service/AuditService.java:386-387,454,467`。这是合规不通过。

补齐这两条后可重评为**有条件上线**，条件为：修 401 假已读（17-06）、审核中消息可见性（17-03）、会话内拉黑/举报入口（17-04）、私聊频控（17-05）、部署脚本顺序文档化（17-09）。

> 特别提醒：17-07（5 秒轮询）不阻断上线，但上线后每增加 1000 在线私聊用户就多约 200 QPS 的空轮询。用户量一起来必须换 WebSocket，否则扩容成本会被这个缺陷吞掉。
