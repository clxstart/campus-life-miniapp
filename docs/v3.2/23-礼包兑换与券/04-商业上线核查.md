## 一、合规与隐私

**结论：有条件通过（条件：虚拟商品不可退的规则必须写进用户协议/兑换规则页）。**

- 券只抵平台内外卖订单（`scope='takeout'`，`CouponService.java:41-42`），**不涉及现金提现、不可转赠、不可跨平台使用**，不构成预付卡/代金券发行（无需备案），但属"促销权益"，需在活动规则里写清有效期与使用范围。
- 「兑换后不可退」目前只有一句前端文案（`pages/points-redeem/points-redeem.js:128`），后端没有撤回接口也没有条款支撑 —— 单方面免责，用户投诉时平台站不住（23-11）。
- 「退款不退券」的选择有合理理由（防循环套利，`CouponService.java:82`），但同样需要条款明示。
- 隐私：兑换只涉及 `userId + item_key`，不采集新信息；券列表接口 `GET /users/{id}/coupons` 走 `requireSelf`（`UserController.java:80-82`），不会读到别人的券。
- **缺口**：券过期后 `status` 仍是 1（23-10），如果未来做"过期券折价回收"活动，会缺少区分依据；当前只影响展示口径，不构成合规问题。

## 二、资金与对账

**结论：不通过（原因：券的成本有一整条发放路径不进台账，且兑换支出无汇总视图）。**

- 券是**平台真实补贴**：用户用 100P 换 1 元券，商家按原价结算，1 元由平台出（`module-reward-v31.sql:117` 注释"平台补贴，商家收入不减"）。所以"发了多少券、核销了多少、作废了多少"必须能算。
- **台账缺口 1**：宿舍发券不写 `redeem_record`、不写 `point_log`、`source` 落成默认 `'seed'` → 宿舍线补贴完全不可统计（23-03）。
- **台账缺口 2**：没有"发放/核销/作废"三列汇总视图，也没有日终对账任务（4 个 `@Scheduled` 无一是券对账：`DormService.java:331`、`PayService.java:273`、`ForumRankService.java:166`、`PaymentCompensationService.java:63`）。
- **可被刷穿的口子**：限购可并发绕过（23-01）→ 单用户可清空某个商品的库存。`takeout_1` 200 张 × 1 元 = 200 元；`takeout_0_1` 500 张 × 0.1 元 = 50 元。金额不大，但"限量活动被一个人搬空"是运营事故。
- **做对的地方**：库存条件更新不超卖（`RewardMapper.java:37-38`）、锁定状态机防重复使用（`CouponService.java:53-61`）、退款作废防套利（`CouponService.java:83-88`）、抵扣被应付封顶（`BizService.java:640-645`）。
- **不可对账的另一个原因**：券面额有两个来源（23-04），算钱只能信 `value_cents`，但运营看的是 `coupon_amount`，两列不一致时无法判断"到底该赔多少"。

## 三、权限与越权

**结论：通过。**

- 用户侧只有 2 条接口，全部 `requireSelf()`，无 `userId` 入参 —— `RewardController.java:21-25`、`:27-38`。
- 兑换只发给自己：`coupon.setUserId(userId)` 来自 session，不接受客户端传入 —— `RewardService.java:86`。
- 管理端 `super` 硬判定，校管 403 —— `AdminRewardController.java:42-45`。
- 券的使用校验归属：`CouponService.usable()` 第一步就是 `!userId.equals(coupon.getUserId())` 直接拒 —— `CouponService.java:36`。
- 下单锁定带 `user_id` 条件，无法锁别人的券 —— `CouponService.java:56`。
- 无"前端隐藏当权限"的写法。

## 四、数据与迁移

**结论：有条件通过（条件：执行顺序 + 老券面额为 0 的用户公告）。**

| 顺序 | 脚本 | 依赖 | 回滚 |
|---|---|---|---|
| 1 | `db/module-food.sql`（`user_order`） | 无 | 回滚前需确认订单表无业务依赖 |
| 2 | `db/module-reward-v31.sql` | **依赖 `coupon`、`user_order`** | `DROP TABLE reward_item, redeem_record`；`ALTER TABLE coupon` 删 8 列 + 1 索引；`ALTER TABLE user_order DROP COLUMN coupon_id, coupon_discount` |
| 3 | `db/module-dorm-v31.sql` | **反向依赖 2 的 `reward_item`**（有 `information_schema` 守卫，缺失则跳过不报错） | `DROP TABLE` 宿舍相关表；`DELETE FROM reward_item WHERE item_key='milk_tea'` |

- 全部幂等：`CREATE TABLE IF NOT EXISTS`（`module-reward-v31.sql:13`、`:39`）+ `ON DUPLICATE KEY UPDATE item_key=item_key`（`:36`）+ `information_schema` 判重扩列（`:50-103`）。
- **老券兼容是明确的取舍**：`module-reward-v31.sql:105-106` 写"老数据不自动回填……按 0 元处理；需要使用的券一律由兑换/新人礼包重新发放，避免按文案猜面额"。这意味着**上线后所有历史券立即不可用**，必须公告或做一次性补发。
- **风险**：`module-dorm-v31.sql` 先于 `module-reward-v31.sql` 执行时，`milk_tea` 行会被跳过（守卫逻辑），后续跑完 reward 也不会自动补——需要人工重跑 dorm 脚本（它能重复执行）。
- 迁移量：`coupon` 8 列扩列在大表上有 DDL 锁风险，**未评估当前 `coupon` 行数**（台账未记录），上线窗口需确认。

## 五、性能与容量

**结论：通过（量级小，无热点）。**

- 兑换单次：`item` 查 1 → `countRedeem` 1 → `decreaseStock` 1 → `insert coupon` 1 → `insert redeem_record` 1 → `spend`（内部约 6 条）≈ 11 条 SQL，全部主键/唯一键或小范围更新 —— 证据 `RewardService.java:71-126`、`PointsService.java:145-166`。
- 商品池列表：5 个商品 = 1 + 5 次查询（`countRedeem` 每商品一次）—— 证据 `RewardService.java:43-61`。**商品数增长后是 N+1 隐患**，当前量级可接受。
- 券列表：`idx_coupon_user_state(user_id,status,expire_on)` 覆盖 —— 证据 `module-reward-v31.sql:99-103`。
- 热点：限购 COUNT 无锁、库存行更新（同一商品抢购）会在行锁上排队；量级小（200~500 库存），可接受。
- **未验证**：无压测。台账 `04:93` 已登记。

## 六、可观测与告警（日志、指标、错误上报、告警渠道）

**结论：不通过（原因：整条券链路几乎没有日志，只有兑换成功一条 info）。**

- 有日志：兑换成功 `log.info`（`RewardService.java:166` 是改商品，兑换成功**没有日志**——`redeem()` 全方法无 `log` 调用）。实际上本功能唯一的业务日志是"商品已更新"和"milk_tea 券不可用"（`DormService.java:406`、`:410`、`:422`）。
- **发券无日志**：兑换成功、宿舍发券成功都不打日志 → 用户说"我兑了没收到券"时无凭证。
- **无指标**：没有"今日兑换笔数 / 发券张数 / 核销张数 / 库存余量 / 限购拒绝次数"任何 gauge。对比支付域有 `alerts.gauge`（`PayService.java:297`）。
- **无告警**：库存归零不告警（运营直到用户投诉才发现活动结束）；`milk_tea` 库存 0 只打 `log.info`（`DormService.java:410`）。
- 前端无上报：兑换页未注册，`navigateTo` 无 fail 回调，打不开也没人知道（`pages/points/points.js:242`）。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

**结论：有条件通过（条件：补一个 `points.redeem.enabled` 开关）。**

| 动作 | 怎么关 | 生效延迟 | 证据 |
|---|---|---|---|
| 关整个兑换池 | 逐个商品 `enabled=0`（6 次 PUT 或 1 条 UPDATE） | 立即（无缓存，每次查库） | `RewardService.java:46`、`RewardMapper.java:19-26` |
| 关单个商品 | `PUT /api/admin/reward-item/{key} {enabled:false}` | 立即 | `AdminRewardController.java:33-40` |
| 停发宿舍奶茶券 | 把 `milk_tea.stock` 置 0 | 立即 | `DormMapper.java:232-237` |
| 停止核销/使用券 | 无开关；只能关外卖下单（`pay.enabled`） | — | — |

- **数据回退**：券一旦发出无法批量撤回；`coupon.status=0`（作废）是唯一手段，但要逐张改，且用户可见"券突然没了"。
- **代码回滚**：`reward_item`/`redeem_record` 对旧代码无引用，回滚安全；`coupon` 的新增列对旧代码无害（旧代码不查）。**回滚风险最低的一处**。
- **回滚障碍**：若已按新口径发券（`value_cents > 0`），回滚到旧代码后旧代码不认 `value_cents`（只认 `amount` 文案）→ **用户券会失效**。所以"发过券之后不要回滚代码"必须写进应急预案。

## 九、结论

**不可上线（阻断项：23-02、23-05、23-06；23-01 为上活动前必修）。**

- 23-05 让兑换页即使注册也空（字段错位），23-02/23-06 让"另一条发券路径"发出不可用的券——三者叠加后，本功能的**两条发券路径都不通**：
  - 兑换路径：页面打不开（未注册 + 字段错位）
  - 宿舍奖励路径：库存 0 发不出；即便发得出，券面额 0 也用不了
- 没有 P0（不涉及伪造支付、不涉及越权），但"活动上线即失败"在商业上等价于不可上线。
- 值得肯定：券的状态机与锁定超时释放是本功能质量最高的部分，`PayService` 那条对账兜底可以直接复用。
