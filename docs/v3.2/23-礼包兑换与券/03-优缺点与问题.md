## 一、设计优点（为什么这么设计，好在哪）

1. **券不是"发一张就完事"，而是完整状态机**。可用(1) → 锁定(2) → 核销(3)，取消释放回 1、退款作废为 0。类注释把为什么必须有"锁定"写清楚了：只在支付时校验会出现两个订单用同一张券，只在支付时扣会让"下单不付款"永久占券 —— `CouponService.java:17-23`。
2. **每个状态迁移都是条件更新**，并发下天然互斥：`lock` 带 `status=1`（`CouponService.java:53-61`）、`useByOrder` 带 `status=2`（`:64-70`）、`releaseByOrder` 带 `status=2`（`:73-80`）。没有"先查再改"。
3. **锁定的券有超时兜底**。支付对账任务每 60 秒扫未付单，超时关单并释放券；渠道不可达还有第二档强制关单 —— `PayService.java:305-352`。这道兜底让"券被永久占用"不成立，是设计上最值得保留的一处。
4. **四种失败都对齐了明确的业务语义**：积分不足、售罄、达限、下架，各有独立文案（`RewardService.java:74-80`、`:107-109`），前端可直接展示，不用自己猜。
5. **券抵扣额被订单应付封顶**，不会把订单抵成负数，也不会因为券面额过大而出现"负订单"——`BizService.java:640-645`。
6. **退款不退券**是有意识的选择，理由写进注释："平台补贴是真实支出，退券会造成循环套利" —— `CouponService.java:82`。这是防套利的关键决定。
7. **库存用条件更新**，`stock > 0 AND enabled = 1` 一条语句同时挡住超卖和"刚被下架"——`RewardMapper.java:37-38`。
8. **管理端权限收敛到 super**：商品池改价影响全平台，校级管理员连看都不给 —— `AdminRewardController.java:17-18`、`:42-45`。

## 二、设计缺点与代价

1. **"每人限购"只写在应用层**。`countRedeem` 是普通 COUNT，`redeem_record` 没有唯一键，`RewardMapper.java:11-14` 的注释却把它描述成数据库级约束。这是本功能最容易被利用的缺口：一个脚本并发 10 次就能把 200 张"外卖立减 1 元"券全部兑走（积分够的前提下）。
2. **两条发券路径两套口径**。兑换路径把 `value_cents/expire_on/scope/source` 全写（`RewardService.java:85-96`），宿舍路径只写 5 个字段（`DormMapper.java:244-249`）。同是"平台发的券"，一条能抵扣、一条不能；一条有 30 天有效期、一条永不过期。
3. **券的成本没有台账**。兑换路径有 `redeem_record` 可汇总，宿舍路径只有 `coupon` 行，没有 `source=dorm`（默认 `seed`）、没有美元金额留痕。做"本月补贴支出"报表时，两条路径算不到一起。
4. **面额有两个来源**。`value_cents` 决定真抵扣，`coupon_amount` 只是文案；后台两个都能改，且无一致性校验。用户可以手持"5.00 元"的券只抵 1 元 —— 这是投诉与合规双重风险。
5. **兑换不可退、退款不退券，全靠前端文案声明**。后端没有"撤回兑换"接口，用户协议里若没有对应条款，属单方面免责。
6. **没有兑换明细后台**。运营看不到"谁兑了什么、兑了多少、券用掉没有"，只能查库。
7. **券的过期状态不推进**。`status` 永远是 1，只靠查询时过滤 `expire_on`；`UserService` 甚至用了第二个"今天"（`LocalDate.now()` 无时区），与 `CouponService` 的 `Asia/Shanghai` 不一致。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 决策 | 选了 | 没选 | 判断 |
|---|---|---|---|
| 券的载体 | 复用老 `coupon` 表 + 扩列 | 新建 `voucher` 表 | **对**。用户已经在"优惠与权益"页看券，另立一套券列表是双份维护（`module-reward-v31.sql:4-6`）。 |
| 券状态字段 | 复用 `coupon.status` 的 1/2/3/0 | 新增 `state` 枚举列 | **可接受**。省一次迁移，代价是"0/1/2/3"含义要靠注释与文档传递。 |
| 面额口径 | `value_cents`（分，严格 1P=1 分） | 允许自定义折扣（如 8 折券） | **对**。折扣券会让"积分价值"不可计算，且平台补贴无上限。 |
| 限购实现 | `redeem_record` 计数 | `(user_id,item_key)` 唯一键 | **错在选了前者**。唯一键只能表达"限 1 件"，但项目要支持 limit=3/6/8/10，所以选了计数——那么就该在计数上做行锁或 `INSERT ... SELECT ... WHERE count < limit`。现在两头不靠。 |
| 奶茶券 | 复用 `reward_item` + `stock=0` 降级 | 直接发固定券 | **方向对**（"有商户库存才承诺"），但降级实现没走同一个发券函数，导致 0 面额 bug。 |

### 4.3 关于"券超发"与"库存超卖"的明确结论

- **库存超卖：不会。** `decreaseStock` 是 `UPDATE ... WHERE stock > 0 AND enabled = 1` 条件更新，并发下只有命中行的请求能继续（`RewardMapper.java:37-38`）；宿舍发券同样用条件扣减（`DormMapper.java:240-241`）。
- **券超发：会，但只在一个维度上。** 券的"张数"受库存约束，不会凭空多发；受突破的是"每人能拿几张"（23-01）——即**总量的天花板在，但分配规则可被单用户吃满**。
- **还有一个隐性超发口**：`updateItem` 允许运营把 `stock` 直接改大（无上限校验，`RewardService.java:148` 只校验非负）。若被误改为 99999，等价于取消库存约束。这一条已并入 23-07 的影响面，未单列。

## 五、如果重做会怎么改

1. **限购用单语句或行锁**，别用"COUNT 后再 INSERT"。这是最容易修、收益最大的一条（0.5 人日挡掉整类刷库存）。
2. **发券收敛成一个方法**：`CouponIssueService.issue(userId, source, bizKey, title, valueCents, thresholdCents, expireDays)`，兑换路径与宿舍路径都走它。现在两条路径各写一套，第一条写全了字段、第二条漏了一半——这就是 bug 的土壤。
3. **券面额只保留一个真值（`value_cents`）**，展示金额由前端算。凡是"同一事实存两处、允许人改一处"的地方，最终必然不一致。
4. **发行台账单独一张表**（`coupon_issue_log`），把"来源、业务号、面额、时间"记全，让"本月补贴多少"变成一条 SQL，而不是靠猜 `source` 默认值。
5. **兑换活动前先过一遍"三问"**：库存扣得动吗？限购挡得住并发吗？券能用吗？本次排查里前两问勉强、第三问在宿舍路径上是失败。
6. **虚拟商品的可撤销性写进协议**，不要只靠一句前端 toast 承担法律效力。
