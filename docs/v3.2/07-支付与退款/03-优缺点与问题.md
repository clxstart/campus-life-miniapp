## 一、设计优点（为什么这么设计，好在哪）

### 1. 只有一个入账口：`applyVerifiedPayment`

回调、对账查询、模拟支付三条完全不同的路径，最终都进 `PaymentLedgerService.applyVerifiedPayment`（`backend/src/main/java/com/campuslife/service/PaymentLedgerService.java:46-102`）。这一条把"什么算一笔有效支付"收敛成一个函数：必须验签或已向渠道确认过、必须金额一致、必须交易号唯一、必须用条件更新改订单。多入口系统最难修的 bug 就是"某条路径少做了一步校验"，这里从结构上排除了。

### 2. 验签失败不写数据库

`handleNotify` 在解析失败时**只计数 + 限速告警，一行记录都不落**（`PayService.java:126-131`）。历史版本会把未验签通知写成 `verified=0` 的行，攻击者可以预先占用真实交易号，这个坑在 `upsertVerifiedRecord` 里也补上了（`PaymentLedgerService.java:122-143` 的注释与实现）。这是"先想攻击者怎么做"的写法。

### 3. 网络调用一律在事务之外

退款被拆成四段：短事务领取（`RefundInitiationService.initiate`）→ 事务外调渠道（`MerchantRefundService.submitAfterCommit`）→ `REQUIRES_NEW` 短事务落账（`MerchantRefundStatusService.applyProviderResult`）→ 返回。注释里明写"绝不持有数据库事务或行锁"（`UserRefundService.java:23-32`）。对账同理（`PayService.java:270-272`）。这避免了"等微信 10 秒、锁住订单行 10 秒"的雪崩。

### 4. 三条退款路径共用一个确定性单号规则 + 一个状态机

用户退款 `RF{orderId}`、商家拒单 `MR{orderId}`、关单补偿 `PAC{exceptionId}`，都满足"重试永远生成同一个号"，再叠加 `refund_record.uk_refund_order`（每订单唯一）与 `uk_refund_out_no`。微信按单号去重，所以"重试导致退两次"在结构上不可能发生。状态机还做了终态单调（`MerchantRefundStatusService.java:130-132`）：迟到的 PROCESSING 不能把 success 拉回 pending。

### 5. 关单后到账有自动补偿，不一味转人工

`PAID_AFTER_CLOSE` 登记后由 `PaymentCompensationService` 每 2 分钟扫一次，自动调渠道退款，成功才置 `resolved`（`PaymentCompensationService.java:100-144`）。这类"钱收了但单没了"的场景是外卖业务最常见的资损源，做成自动补偿是对的。

### 6. 模拟支付做了三层防护

`simulate` 默认 false（`@Value` 默认值）、必须 `wxpay.enabled=false`、prod profile 直接抛异常、prod 配置写 true 会启动失败（`PayService.java:375-383` + `ProductionConfigValidator.java:56-58`）。注释里明确写了历史教训："以前只要 wxpay.enabled=false 就直接把订单标记成已付款，配置漏改就等于线上白送货"（`PayService.java:369-374`）。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 1. 退款有"工程严谨度"，没有"业务风控"

代码把"不重复退"做到了教科书水平，但对"该不该退"**一个判断都没有**：可退状态集合包含 `completed`（`RefundInitiationService.java:29-31`），没有时限、没有金额上限、没有频次限制、没有商家确认、没有人工审核。用户把餐吃完了，调一次接口就能全额退款。这是"把幂等当成风控"的典型代价——技术正确，业务不设防。

### 2. 异常单是"写得出、看不见"

`payment_exception` 表设计得很完整（5 种 kind、6 种状态、attempts、note、唯一键），`PaymentExceptionMapper` 连 `page()` 分页方法都写好了（`PaymentExceptionMapper.java:92`），但**没有接口、没有页面、没有调用方**。等于这套状态机只对机器可见，对人不透明。运营想知道"今天有几笔关单后到账"，只能进数据库敲 SQL。

### 3. 订单主状态与支付状态在"拒单退款"路径上分叉

商家拒单时先把订单改成 `cancelled`（`MerchantMapper.java:162-163`），再插退款单；退款成功后 `updateOrderStatusForRefund` 的来源集合**不含 `cancelled`**（`MerchantMapper.java:191-197`），所以订单主状态永远停在 `cancelled`，而 `pay_status` 变成 `refunded`。后果：管理端按"已退款"筛选会漏掉所有拒单退款单；`user_order.status` 与 `pay_status` 不再能互相解释。

### 4. `refunding` 是个没有出口的房间

`RefundInitiationService` 的注释声称"并发输家不会看到「refunding 但还没有退款记录」的中间态"（`:22`），但代码里没有任何机制在检测到这种状态时修复它：`existing()` 只会抛异常（`:85-87`），`PayService.cancel` 只接受 `created+unpaid`（`PayService.java:155`），`transitionStatus` 禁止直接写 `refunding/refunded`（`PayService.java:231-233`），补偿任务只处理 `payment_exception`。一旦进入，用户不能取消、不能退款、后台没有按钮能救，只能改数据库。库里现在就有 1 条这样的订单。

### 5. 告警只有"计数器 + 限速日志"

`PaymentAlerts` 用 Micrometer 计数器 + 30 秒去重的 `log.warn`，注释说"供 /actuator/metrics 与外部告警规则使用"（`PaymentAlerts.java:14-16`）。但整个仓库**没有配置任何告警规则、没有 webhook、没有短信、没有企微群**。等于把告警的责任推给了"以后会接的监控系统"，而现在没有人接。`alerts.warn("notify","verify_failed",...)` 一天响一万次也没人知道。

### 6. 小程序端把售后整块留给后台

支付侧接口齐全（pay/cancel/refund 三个），小程序只接了 pay。退款对用户来说等于不存在。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 做法 | 为什么本仓库没选（从代码能看出取舍） |
|---|---|---|
| 退款走"申请—审核—打款"三段 | 用户申请后进入待审核，运营批了才调渠道 | 现在是一步直达。推测原因（未验证）：为了少写一个审核状态机。代价是资损无门槛。退款状态值里其实已经预留了 `pending`，改成三段并不需要动表结构 |
| 用微信退款查询做唯一真相 | 不落本地退款账本，每次查微信 | 会丢失"谁在什么时候为什么申请"的业务信息，且渠道查询有频率限制。本地账本 + 渠道核验是更好的选择，这个取舍是对的 |
| 支付回调时同步 HTTP 通知业务系统 | 交易系统间同步调用 | 回调本身要快速 ACK，同步调业务会拉长响应并放大故障。本仓库用 `payment_exception` 表解耦，方向正确——只是没做完"人能看见"那一半 |
| 商家拒单不退款、只关单 | 让用户自己申请 | 会被投诉。当前"拒单即自动退"是最省事的正确做法，问题只出在状态回写 |
| 模拟支付靠环境变量关掉 | 只留 `campus.pay.simulate` | 已经这么做了，且加了 prod 启动校验。更进一步的做法是"prod 启动时断言 `wxpay.enabled=true` 或 `simulate=false` 二者必有其一"，现在只有后者被断言 |
| 异常单自动退款失败一律转人工且不再重试 | 简单 | 已否决：`MAX_ATTEMPTS=6` 后转人工（`PaymentCompensationService.java:41`），之前会一直查，方向正确 |

### 4.1 关于"模拟支付开关"这条为什么不是 P0

任务要求重点核查模拟支付。结论是：**开关本身收得住**——`@Value` 默认 false、要求 `wxpay.enabled=false`、prod profile 抛异常、prod 配置写 true 会导致启动失败（`PayService.java:375-383` + `ProductionConfigValidator.java:56-58`）。这四层防护是成立且可验证的。

真正剩下的缺口是"**基础配置把默认值写成了 true**"（`application.yml`），使得"非 prod profile"等于默认开模拟支付，而 prod 之外的 profile 没有任何启动校验。这一条被定为 P1 而不是 P0，因为它需要一个明确的配置动作（用 dev/test profile 部署）才会成立；一旦那个动作发生，它的实际后果等同于 P0（资金可伪造）。修法是 0.5 人日的默认值 + 一条正向断言，建议无论如何都做。

## 五、如果重做会怎么改

1. **把退款拆成"申请"和"出款"两个状态**。`refund_record.status` 加 `awaiting_review`，任何退款先进待审，运营/规则引擎批了才提交渠道。这一步同时解决 07-01 与部分风控问题，且不需要改表结构（`status` 是 VARCHAR）。
2. **异常单是一等公民**。凡是平台自己登记了"需要人处理"的数据，就必须有对应的列表页与处理动作——否则那张表只是给机器看的日志。可以定一条规：任何 `status` 里含 `manual` 的表，必须有管理端入口。
3. **状态一致性的最终裁决者是数据库**。`user_order.status` 与 `pay_status` 的组合目前靠四处代码各自小心维护。加一条 `CHECK`（或定时核对任务）断言"`pay_status='refunded'` 时 `status IN ('refunded','cancelled','closed')`"，让不一致在写入时暴露，而不是在财务对账时暴露。
4. **状态机不允许出现无出口的节点**。`refunding` 没有出口是设计缺陷：任何一个"进行中"状态都必须有超时回收（自愈任务），否则进程被 kill 一次就产生一个永久卡单。
5. **告警出口与告警规则一起交付**。现在的 `PaymentAlerts` 只做了一半（发出信号），没做另一半（人收到）。最小可用的做法是 webhook + 一条"哪些指标必须打电话"的清单。
