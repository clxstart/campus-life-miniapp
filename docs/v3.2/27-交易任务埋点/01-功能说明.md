## 一、这个功能解决什么问题

积分体系需要一个「真实交易行为 → 积分奖励」的通道，让用户在主业务里做事就能拿到分，而不是只在论坛发帖。`task_catalog` 里配了三条交易类任务（`db/module-points-v31.sql:93-95`）：

| task_key | 名称 | P | G | daily_cap |
|---|---|---|---|---|
| `food_order` | 外卖点单完成 | 10 | 20 | 2 |
| `job_settle` | 兼职结算 | 5 | 15 | 2 |
| `market_trade` | 二手成交 | 5 | 12 | 2 |

这三条任务要真的发得出去，必须解决一个工程问题：**发分不能影响主交易**。

- 外卖订单已完成、兼职已结算、二手已成交——这些是用户的钱/劳务/物权，不能因为「积分服务抖了一下」就回滚。
- 反过来，发分失败也不能静默丢失。

所以有了 `AfterCommitPointsAwarder`（`AfterCommitPointsAwarder.java:9-27`）：

> 1. **提交之后才发**：发分失败不能把外卖订单完成 / 兼职结算一起回滚。
> 2. **必须单开新事务**：`afterCommit` 回调执行时，外层事务虽已提交，但连接与事务同步资源仍绑定在当前线程；直接调 `@Transactional(REQUIRED)` 的 `PointsService` 会「加入」那个已经提交的事务，语句可能被丢弃。这里用 `REQUIRES_NEW` 挂起外层、单开一个短事务。

这个设计**是对的**，而且理由写得比多数生产代码清楚。问题在于：它只被一个场景用了。

## 二、用户看到的样子（小程序端）

三个场景，三条不同位置的断点：

### 2.1 外卖点单完成 —— 用户能下单能完成，但拿不到分

- 用户侧：`pages/food-list` → `pages/food-shop` → `pages/food-order` → `pages/food-orders` / `pages/food-order-detail`（链路完整，`pages/food-orders` 等均在 `app.json` 注册）。
- 订单完成动作由**商家自配送**（`MerchantService.java:283-287`）或**骑手送达**（`RiderService.java:97`）触发，用户侧不点「完成」。
- **埋点：不存在。** `MerchantService` 与 `RiderService` 都没有 `AfterCommitPointsAwarder`/`PointsService` 依赖；全仓 `grep -rn "food_order" backend/src/main/java` 只命中 `AfterCommitPointsAwarder.java:21` 的注释。

后果：订单完成 → `food_order` 任务永远不触发 → 用户永远拿不到 10P/20G。

### 2.2 兼职结算 —— 整条链路都通，只差最后一步发分

- 用户在 `pages/job-mine` 提交/确认计价数量：`job-mine.js:226-240` → `api.submitJobHours` / `api.confirmJobHours`（`utils/api/market.js:239-244`）。
- 后端：`JobService.confirmHours`（`:538-541`）→ `writeHours`（`:544-577`）→ 双方数额一致时 `settleContract`（`:881-897`）→ 写履约账单。
- **埋点：不存在。** `settleContract` 只写 `earnings_ledger`，全程无 `award`；`JobService` 全文无 `PointsService` 依赖。

后果：兼职结算成功后，`job_settle` 任务永远不触发 → 双方永远拿不到 5P/15G。**这是三个场景里最扎眼的一个：前端到位、后端到位、结算逻辑完整，唯独没有那一行 `award`。**

### 2.3 二手成交确认 —— 后端埋点写好了，但前端没入口

- 后端：`MarketTradeService.confirm`（`:111-148`）→ 条件更新成交 → 商品置已售 → `awardBothAfterCommit`（`:198-214`）→ `afterCommit` 里双方各发一次 `market_trade` 分（`:200-201`）。
- 接口：`POST /api/market/{goodsId}/trade`、`POST /api/market/trade/{id}/confirm`、`POST /api/market/trade/{id}/cancel`、`GET /api/market/trades/mine`（`MarketTradeController.java:33-52`）。
- 小程序 API 层：`startMarketTrade` / `confirmMarketTrade` / `cancelMarketTrade` / `getMyMarketTrades`（`utils/api/points.js:213-242`）。
- **页面调用：零。** `grep -rn "confirmMarketTrade\|startMarketTrade\|getMyMarketTrades" pages/` 空。

后果：这是唯一接上的埋点，但它**没有触发入口**——用户在二手交易页（`pages/market-detail`、`pages/market-list`）看不到「我买到了」「确认成交」任何按钮。

### 2.4 汇总：三条链路各断一处

| 场景 | 前端入口 | 后端埋点 | 端到端可用 |
|---|---|---|---|
| 外卖完成 | ✅（订单链路完整） | ❌ **没有** | ❌ |
| 兼职结算 | ✅（`job-mine` 提交/确认计价数量） | ❌ **没有** | ❌ |
| 二手成交 | ❌ **没有** | ✅（`afterCommit` 发分） | ❌ |

**没有一条端到端能用。** 这就是 27-01 与 27-02 的由来。

## 五、数据表与字段

本功能**不新增任何表**。它读写的是既有表：

| 字段 | 用途 | 证据 |
|---|---|---|

### 5.2 `market_trade`（二手成交状态机）

| 字段 | 用途 | 证据 |

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 外卖完成（**未实现，以下为应有行为，无代码可依**）

按 `task_catalog` 配置：完成后双方（下单用户）得 10P/20G，日限 2 单。当前无实现，无代码可引用——**这一节是「缺失」本身，不是规则**。

### 7.2 兼职结算（**未实现**）

应有行为：双方计价数量一致 → `settleContract` → 结算成功 → 双方得 5P/15G，日限 2 次。当前 `settleContract` 只写账单（`JobService.java:881-897`），无发分。

### 7.3 二手成交确认（**已实现，规则完整**）

| 规则 | 行为 | 证据 |
|---|---|---|
| 只有卖家能确认 | 403「只有卖家可以确认成交」 | `MarketTradeService.java:118-120` |
| 已确认的重复确认 | 幂等返回 `alreadyConfirmed=true`，不重复发分 | `:122`、`:132-137` |
| 已取消的不能确认 | 400「该成交已取消」 | `:123` |
| 不能买自己的商品 | 400「不能购买自己发布的商品」 | `:67` |
| 一件商品只有一笔成交 | `uk_trade_goods` 兜底并发 | `MarketTradeMapper.java:21-26`、`MarketTradeService.java:93-98` |
| 同一对用户 7 天内只计一次分 | 判定命中时**成交照样成功、商品照样置已售**，只是不发分并记 warn | `MarketTradeService.java:128-129`、`:141-146` |
| 7 天判定含角色对调 | `(buyer=A AND seller=B) OR (buyer=B AND seller=A)` | `MarketTradeMapper.java:66-67` |
| 日限 2 笔 | `task_catalog.market_trade.daily_cap=2` | `db/module-points-v31.sql:95` |
| 发分在提交后、单开新事务 | `afterCommit` + `REQUIRES_NEW` | `MarketTradeService.java:203-214`、`AfterCommitPointsAwarder.java:34-38` |
| 发分失败不影响成交 | `catch (RuntimeException)` 只记 warn | `AfterCommitPointsAwarder.java:52-56` |

**这句要专门表扬**：「同一对用户 7 天内已经成交过，这一笔照样确认成功、商品照样置已售，只是不发分」（`MarketTradeService.java:107-109` 注释）。把「反作弊判定」与「业务是否成立」分开，是正确的边界——反作弊不该阻断正常交易。

### 7.4 补偿规则

| 场景 | 现状 | 结论 |
|---|---|---|
| 发分失败（积分服务异常） | 只记 warn，**无补偿任务、无巡检** | 缺口（27-03） |
| 发分成功但事务提交失败 | `REQUIRES_NEW` 自身回滚 → 无分无日志（只有 warn） | 缺口 |
| 交易回滚但发分已注册 | `afterCommit` 只在提交后触发 → 不会发 | ✅ 正确 |
| 命中日上限 | `CAPPED`，`task_log` 留痕但不发分，且**永不重试** | 缺口（与 24-02 同源） |
| 任务被后台停用 | `DISABLED`，不发分 | ✅ 可接受（配置问题） |

### 7.5 事务边界的正确性（本功能的核心价值所在）

`AfterCommitPointsAwarder` 的两个设计点都成立：

1. **提交后才发**：`TransactionSynchronization.afterCommit` 只在主事务提交成功后回调（`MarketTradeService.java:203-209`）。主事务回滚时回调不会执行。
2. **必须 `REQUIRES_NEW`**：注释解释了原因（`AfterCommitPointsAwarder.java:15-18`）——`afterCommit` 执行时连接仍绑定在当前线程，直接调 `@Transactional(REQUIRED)` 会加入一个已提交的事务，语句可能被丢弃。这是 Spring 事务传播的一个真实陷阱，代码里明确指出了。

**这一处是本模块唯一「做对了而且能当范例」的地方。**

但有残余风险：

- `catch (RuntimeException e)` 不覆盖 `Error`（如 `OutOfMemoryError`）——会穿透到 `afterCommit`，导致主交易已提交但 HTTP 返回 500（27-05）；
- `afterCommit` 中申请 `REQUIRES_NEW` 会**再要一个连接**，而外层连接尚未释放；连接池打满时会出现「互相等待」直到超时（27-05）。
