## 一、设计优点（为什么这么设计，好在哪）

### 1.1 把「发分」和「主交易」用事务边界彻底隔开

`AfterCommitPointsAwarder.java:9-26` 的两个要求，恰好是这类需求最容易做错的两个地方：

> 1. **提交之后才发**：发分失败（积分表锁等待、连接抖动……）不能把外卖订单完成 / 兼职结算一起回滚。
> 2. **必须单开新事务**：`afterCommit` 回调执行时，外层事务虽然已提交，但连接与事务同步资源仍绑定在当前线程上；此时直接调 `@Transactional(REQUIRED)` 的 `PointsService` 会「加入」那个已经提交的事务，语句可能被丢弃、或在连接清理时被回滚。这里用 `REQUIRES_NEW` 挂起外层、单开一个短事务。

第 2 条是**真正的坑**：绝大多数人只知道「放在 afterCommit 里」，然后就被「语句被丢弃」这种灵异问题折磨。这里不但用了 `REQUIRES_NEW`，还在注释里写清了原因（`:15-18`），并指明了同款先例（`DispatchService.autoDispatch`）。

**这一处可以直接当团队范例。**

### 1.2 发分仍然只有一个出口

`AfterCommitPointsAwarder` 自己不算分、不动余额，只负责「什么时候发、用哪个事务发」（`:25`）。真正的发分还是走 `PointsService.award`（`:48-49`）。

这保持了 `PointsService.java:20-34` 的纪律：「V3.1 有十余个发分场景……这里把『幂等 + 日上限 + 余额 + 成长值 + 流水』五件事收在一次调用里」。桥接器没有破坏它。

### 1.3 `CAPPED`/`DISABLED` 的语义在这条链路上是清晰的

`PointsService.doAward` 返回五种结果（`PointsService.java:48-59`），桥接器把 `AwardResult` 原样返回（`AfterCommitPointsAwarder.java:51`），调用方可判断。这比「返回布尔」信息量大得多。

（虽然 `MarketTradeService` 实际丢弃了返回值——那是调用方的问题，不是设计问题，见 27-04。）

### 1.4 二手成交的反作弊是三机制叠加，且与业务分离

| 机制 | 实现 | 拦住什么 |
|---|---|---|
| 一件商品一笔成交 | `uk_trade_goods` | 同一商品反复成交刷分 |
| 7 天同对用户只计一次 | `countRecentPair`（含角色对调） | 两个账号互相买卖刷分 |
| 日限 2 笔 | `task_catalog.daily_cap=2` | 短时间高频刷分 |
| 不能自买自卖 | `sellerId == buyerId` 直接拒 | 单账号自导自演 |

最关键的是**它们都不阻断业务**：`MarketTradeService.java:107-109` 注释明确「同一对用户 7 天内已经成交过，这一笔照样确认成功、商品照样置已售，只是不发分并记 warn——产品规则是『同一对用户 7 天内只计一次积分』，不是『7 天内不许再交易』」。

**把反作弊判定与业务是否成立分开，是对的产品判断。** 反过来（命中反作弊就拒绝成交）会让真实用户被误伤，且无法申诉。

### 1.5 `countRecentPair` 处理了角色对调

`MarketTradeMapper.java:66-67`：

```sql
AND ((buyer_id = #{buyerId} AND seller_id = #{sellerId})
  OR (buyer_id = #{sellerId} AND seller_id = #{buyerId}))
```

只写前半句是最常见的疏漏：A 买 B 的 → B 买 A 的，两笔都会被当成「新的一对」。这里写全了。

### 1.6 幂等键的设计粒度正确

- 二手成交：`trade:{tradeId}:{userId}` —— 一笔成交里买卖双方**各算一次**（`MarketTradeService.java:216-219`）；
- 而不是 `trade:{tradeId}` —— 那样第二个人就会被幂等挡掉。

这个粒度选对了，注释也写了理由（`:216`）。

### 1.7 条件更新而不是「先查后改」

`MarketTradeMapper.java:42-47` 的 `UPDATE ... WHERE id=? AND seller_id=? AND status='pending'`，配合服务层「返回 1 才算成功，否则重新查一次判断是不是别人先确认了」（`MarketTradeService.java:132-137`）。

并发下不会出现「两个请求都以为自己确认成功」。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 代价一：桥接器只有一个用户，而那个用户没有入口

- `AfterCommitPointsAwarder` 的调用方只有 `MarketTradeService`（`grep -rln` 确认）；
- `MarketTradeService` 的入口在小程序里不存在（`confirmMarketTrade` 等 4 个 API 零页面调用）。

于是：**唯一接上的埋点，触发不了。**

这不是「没写完」，是「写了但没人接」——和功能 26 的宿舍（后端全、前端无）、功能 24 的榜单（页面全、未注册）是同一类失败模式：**这个项目缺的不是实现能力，是「端到端接通」的责任人。**

### 2.2 代价二：注释描述的是目标，不是现状

`AfterCommitPointsAwarder.java:20-23`：

> 交易侧的三个发分场景都经过这里：
> `food_order` 外卖订单完成 `order:{orderId}`
> `job_settle` 兼职合约结算成功 `contract:{contractId}`
> `market_trade` 二手成交确认 `trade:{tradeId}:{userId}`

用现在时写，读起来像已经接上了。实际只有第三条。而 `food_order` / `job_settle` 这两个**看起来像存在**的字符串，正是让 grep 结果「命中」从而误判的原因——`grep -rn "food_order" backend/src/main/java` 会返回一行，但那行是注释。

**这是本功能最大的隐性代价**：注释给出了虚假的完成感，让排查的人以为「只是没测」，实际是「没写」。

### 2.3 代价三：任务目录已经上架，用户会被承诺做不到的事

`db/module-points-v31.sql:93-95` 三条任务都已 `enabled=1`；`PointsService.tasks()` 把**所有 enabled 目录行**返回给用户（`PointsService.java:213-237`），而且 `available` 的计算只看日上限（`:234`），完全不检查「这个任务有没有实现」。

所以一旦 `pages/points` 注册上线（当前未注册，属功能 20/24 的问题），用户会在任务列表里看到：

> 外卖点单完成 +10
> 兼职结算 +5

两条都标着可完成，实际永远完不成。**这比「没这个任务」更糟**：用户会为了拿分去点外卖、去接兼职，然后发现没分。

### 2.4 代价四：反作弊只覆盖了二手成交，另两处是裸奔设计

- 外卖：`food_order` 日限 2 单，但没有「同一设备/同一收货地址/同一支付账号」的判定。外卖本身有实付金额与配送履约，刷单成本较高——这是可接受的，但**一旦接入模拟支付（`campus.pay.simulate=true`）就等于零成本刷单**。
- 兼职：`job_settle` 日限 2 次，但兼职合约的「双方提交一致计价数量即结算」是一个**纯双人协作动作**，没有资金流校验（`JobService.java:544-577`、`:881-897` 只写履约账单，没有真实支付）。两个账号互相发包、互相确认 1 小时、结算成功 → 各拿 5P/15G，每天 2 次。

也就是说：**兼职埋点一旦按设计接上，会立刻变成一个可自刷的发分口**。设计里没有为它准备任何反作弊（对比二手成交的三层机制）。

### 2.5 代价五：`REQUIRES_NEW` 在 afterCommit 里会多占一个连接

`AfterCommitPointsAwarder.java:37-38` 用的是 `REQUIRES_NEW`，而 `afterCommit` 执行时**外层连接还没释放**（回调发生在连接清理之前）。所以每次成交通知会同时占用 2 个连接（外层 + 新事务）。

连接池大小未在本次核查范围内确认；如果池是默认的 10，10 个并发 confirm 就会互相等待，直到超时（默认 30s）。超时后 `award` 失败被 catch，主交易已提交——**用户成交了但没拿到分，且只留一条 warn**。

这是个低概率但会放大成批量的风险：一笔热点商品的成交潮就能触发。

### 2.6 代价六：失败没有任何补偿与巡检

| 失败 | 现状 | 后果 |
|---|---|---|
| 发分抛异常 | `catch (RuntimeException)` → warn，返回 null | 用户拿不到分，无人知道 |
| 发分返回 `CAPPED` | 返回值被调用方丢弃 | 同上，且 `task_log` 已留痕，永不重试 |
| 发分返回 `DISABLED` | 同上 | 同上（配置问题，但没有告警） |
| 进程在 afterCommit 前挂 | 无 | 成交已提交、无分、无日志 |

没有补偿任务、没有对账、没有「交易成功但发分失败」的巡检。对比论坛榜至少有 `POST /resettle` 这个补跑入口——交易埋点连这个都没有。

### 2.7 代价七：7 天窗口用 MySQL `NOW()`

`MarketTradeMapper.java:64`：`confirmed_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)`。

全仓库其他地方都在强调「时间一律由 Java 按 Asia/Shanghai 算好再传，不依赖数据库时区」（`ForumRankMapper.java:32-34`、`DormMapper.java:24-25`、`DormService.java:38`）。这里是唯一一处破例。

如果目标库 `time_zone` 不是 `+08:00`，7 天窗口会整体偏移 8 小时——影响不大（7 天判定本就是粗粒度），但**与纪律不一致**，且这种不一致会在排查时误导人。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 优点 | 代价 | 为什么没选（依据代码/注释） |
|---|---|---|---|
| **在主事务里直接发分** | 简单、强一致（成交与发分同生共死） | 积分服务抖动会把成交/结算一起回滚；用户付了钱却看不到订单 | 明确否决，`AfterCommitPointsAwarder.java:13-14` |
| **`afterCommit` 里直接调 `@Transactional(REQUIRED)`** | 少写一行传播级别 | 语句可能被丢弃或回滚（Spring 事务同步的真陷阱） | 明确否决，`AfterCommitPointsAwarder.java:15-18` |
| **异步消息/MQ 发分** | 彻底解耦，可重试 | 需要引入 MQ 与消费幂等；当前架构无 MQ | 未选。若将来发分场景增多，这是正确方向（能同时解决 27-03 的无补偿问题） |
| **定时任务扫「已成交但无 point_log」补偿** | 无需 MQ，能兜住所有失败 | 有延迟；需要一个可靠的对账维度 | **未做**，这是 27-03。技术上很便宜（`market_trade.confirmed_at` vs `point_log.biz_key` 即可对账） |
| **命中反作弊就拒绝成交** | 从源头挡住刷分 | 真实用户会被误伤且无法申诉 | 明确否决，`MarketTradeService.java:107-109`。这是对的 |
| **`bizKey = trade:{tradeId}`（不区分用户）** | 一个键搞定 | 第二个人会被幂等挡掉，只有一方拿分 | 明确否决，`MarketTradeService.java:216-219` |
| **二手成交不设 7 天限制，只靠日限 2** | 简单 | 两个账号每天互刷 2 笔，一周 14 次 | 否决，三层叠加（`MarketTradeMapper.java:61-70`） |
| **兼职结算加真实资金流校验** | 从根上防自刷 | 需要接入支付/担保交易（设计稿 §七 明确不做） | 未做。**但发分埋点仍按设计准备接上**，这就是 2.4 的隐患 |

### 4.1 判级说明

- **27-01 P0**：这不是「体验不好」，是**承诺的能力不存在**。`task_catalog` 已把两条任务上架、`PointsService.tasks()` 会把它们返回给用户、`pages/points` 的任务列表会展示它们——用户会为了拿分去点外卖、去接兼职，然后发现没分。这是「误导用户去做无回报的事」，性质接近虚假宣传，比纯功能缺失更严重。按 `00-写作规范.md` 4.2「主链路不可用 = P0」判级。
- **27-02 P1**：唯一能工作的埋点无法被触发。不阻断（因为本来 2/3 就没实现，功能整体不可用），但修 27-01 之后它立刻变成阻断项——**修法必须在同一轮里做完**，否则会出现「三处埋点全接上了，两处能触发、一处不能」的怪状态。
- **27-03 P1**：无补偿 = 静默丢分。交易发分是用户可感知的权益，丢了必须有补偿路径。
- **27-04 ~ 27-07 P2**：一致性、健壮性、可维护性问题。

## 五、如果重做会怎么改

1. **把埋点做成「业务事件」而不是「散落的调用」**。现在三处埋点写在三个 service 里，没有任何机制保证「新增一个交易任务时会被接上」。建议：
   - 定义 `TradeEvent{type, bizId, userId, amount}`，在交易服务里发布；
   - 一个监听器统一处理 `task_catalog` 里的交易类任务；
   - 新任务只需在目录里加一行，不需要改三个 service。
   
   这样 27-01 这类「目录上架了但没接」的情况在架构上就消失了。

2. **补偿任务必须有**。既然 `task_log` 的 `biz_key` 已经是幂等键，补发天然安全。一个每小时跑的「已成交但无 `point_log`」扫描任务，成本极低，能兜住 27-03、27-05 以及所有未知失败。

3. **`afterCommit` 发分改成异步**。`REQUIRES_NEW` 在 `afterCommit` 里占用两个连接是结构性风险。用一个小线程池（单线程也行，配合幂等与补偿）把发分移出请求线程，既解决连接池问题，也让响应更快。

4. **`catch` 到 `Throwable`**。`Error` 不该让主交易「已提交却返回 500」。

5. **加一致性巡检告警**：「`task_catalog.enabled=1` 但近 7 天 `task_log` 为 0」——这一条告警能在第一时间发现所有「任务上架但埋点没接」的情况。27-01 之所以能活到现在，就是因为没有这条告警。

6. **兼职结算埋点接上之前先补反作弊**。设计里 `job_settle` 没有任何反作弊（对比二手成交的三层），而兼职结算是一个纯双人协作动作、无真实资金流。直接接上会立刻变成一个可自刷的发分口。建议至少加：同对用户 7 天只计一次（复用 `countRecentPair` 思路）+ 单账号每周上限。

7. **把注释里的「三个场景都经过这里」改成时态正确**。现在这句让 grep 结果产生虚假命中，是 27-01 被长期忽略的直接原因之一。
