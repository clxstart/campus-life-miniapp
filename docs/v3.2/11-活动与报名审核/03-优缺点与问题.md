## 一、设计优点（为什么这么设计，好在哪）

1. **模式做在活动级，不是全站开关。** 「周末跑步」点一下、「歌手大赛」要材料，同一套代码两种行为，老活动不受影响（`module-activity-enroll.sql:5-7`、`:37` 默认 `approved`）。这是对产品真实差异的正确抽象。
2. **报名数只在通过后 +1。** 材料模式落 `pending` 时明确不加人数（`BizService.java:482` 注释），所以"已报名人数"口径是"已通过人数"，对外报数不会虚高。
3. **状态机用条件 UPDATE 做幂等。** `WHERE id=? AND status='pending'`（`ModuleMapper.java:295`）+ 服务层先查再改（`BizService.java:518`），两个管理员同时点通过只会有一个生效。这比"先查后写"单保险更硬。
4. **重复报名双保险。** 服务层查重给友好提示 + 数据库唯一键兜底并发（`BizService.java:429-431`、`module-market-jobs-activities.sql:63`）。异常被翻译成"已经报名过啦"，而不是 500。
5. **材料功能有降级开关。** 材料通道出问题时整体降级为一键报名，而不是让活动完全不能报名（`BizService.java:418-424`）。活动报名是时效性极强的场景，"能报名"优先于"报得全"。
6. **材料地址做前缀白名单。** 只接受 `/uploads/` 或 `http`（`BizService.java:462-464`），挡住 `javascript:`、`file:` 这类注入。方向对。
7. **管理端列表把材料一次性带出。** 列表里每个报名补一次 `enrollMaterials`（`BizService.java:503-506`），运营不用点进去再点一次。
8. **审核列表按校域过滤写在 SQL 里。** `JOIN campus_activity a` 后按 `a.school_id` 过滤（`ModuleMapper.java:267`），不是查完再在内存里筛。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **材料存进了公开目录。** `submitMaterialEnrollment` 只接受 `/uploads/` 前缀（`BizService.java:462`），而 `/uploads/**` 是无鉴权静态映射（`WebConfig.java:50-55`）。系统里明明有私有通道（`UploadController.java:49-57`），但它只给管理端用，学生调不到。于是：学生证、身份证、报名表、作品全在公开可枚举的路径下。URL 一旦被转发、被日志采集、被截图分享，就等于泄露。
2. **审核权力没有边界。** 列表按校过滤（读），但审核不按校过滤（写）。A 校管理员只要知道一个报名 id（连号很容易猜），就能通过或驳回 B 校学生的报名。这是最典型的"读做了隔离、写忘了"的漏洞。
3. **没有名额这个概念。** 表里没有字段，代码里没有校验。这不是"超卖"，是"卖不了"——任何需要限流的活动（教室 60 人、演出票 200 张）只能靠人肉盯着列表手动驳回。而审核列表没有"当前已通过 X / 上限 Y"的显示，运营也没法盯着。
4. **人数只增不减。** `enrolled` 全仓库只有一处 `+1`（`ModuleMapper.java:300`），没有 `-1`。加上没有取消功能，一次误通过就永久污染这个数字。
5. **学生端闭环断在最后一环。** 后端把 `myEnrollStatus` 返回了（`ModuleMapper.java:184`），小程序就是不渲染（`pages/activities/activities.js` 全文无引用）。学生提交完材料 → 页面跳回列表 → 按钮变灰 → 没有任何文字说明现在是什么状态、为什么、什么时候出结果。这是功能可用性上的致命伤：**用户不知道自己在排队还是被拒了**。
6. **被驳回无法重来。** `countEnrollment` 不去分状态（`ModuleMapper.java:233-236`），所以"驳回"实际上等于"永久拉黑这个活动"。而驳回原因本来是让学生"补材料再交"的。
7. **活动本身不审核。** 任意登录用户 `POST /api/activities` 即可发布，`campus_activity` 没有 `audit_status`，`status` 默认 1，立刻对全校可见。同时首页「季节活动」入口直通列表。UGC 无审核 + 无举报入口 = 内容治理缺口。
8. **审核动作没有审计日志。** 通过/驳回是本域最有权力的两个写操作，却不像学期、banner 那样留 `log(...)`。出了"谁把这个人放进来的"问题，查不到。
9. **材料格式与现实不匹配。** 歌手大赛要 mp3，`wx.chooseMedia` 选不了；PDF 报名表也传不了。旧文档自己承认了（测试手册 `:233`），半年没动。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 做法 | 为什么当前没选 | 代价/收益 |
|---|---|---|---|
| 材料走私有通道 | 学生端也开 `POST /api/upload/private`，落 `uploads/private/`，读取走带鉴权接口 | 私有接口只挂在 `/api/admin/**` 下，学生拿不到 token；改动涉及新接口 + 管理端读文件接口 | 约 1.5 人日；这是 11-01 的唯一解法 |
| 加名额字段 + 条件 UPDATE | `campus_activity.quota` + `UPDATE ... SET enrolled=enrolled+1 WHERE enrolled < quota`（兼职域已有同款写法：`JobService.java:444`） | 未评估 | 约 1 人日；直接消灭 11-03、11-04 |
| 驳回后可重报 | `countEnrollment` 排除 `rejected`，或允许把 `rejected` 改回 `pending` | 未评估（旧文档把"撤回"列为待办，但没提"重报"） | 约 0.5 人日 |
| 材料改 `wx.chooseMessageFile` | 支持 mp3/zip/pdf | 旧文档给了方案 B（半天），业务方没点头 | 0.5 人日 + 上传白名单扩类 |
| 活动发布即审核 | `campus_activity` 加 `audit_status`，复用内容审核台 | 未评估 | 约 1.5 人日；不做则学生可发布任意活动 |
| 报名成功/驳回发通知 | 复用 `notifyUser` | 旧文档列为"下一步 2" | 0.3 人日 |

## 五、如果重做会怎么改

1. **材料从一开始就走私有通道。** 上传接口按"业务用途"分流（`purpose=activity_material`），落 `uploads/private/`，DB 存站内路径，读取必须走 `GET /api/admin/enrollments/{id}/materials/{mid}` 且校验管理员校域。这样 URL 本身无意义，泄露也不可读。
2. **每个写操作都带校域参数。** 不是"列表过滤了就行"，而是 `decideEnrollment(scopeSchoolId, enrollId, ...)` 签名里就有它。签名里没有的，就是不会校验的。
3. **名额是活动的一等属性。** `quota INT NOT NULL DEFAULT 0`（0=不限），报名走条件 UPDATE。兼职域已经有正确写法（`JobService.java:444`），直接照抄，不要重新发明。
4. **状态机补两个状态：`cancelled`（学生撤）、`expired`（活动结束未处理）**，并把"驳回"定义为可重投，而不是终态。
5. **学生端加「我的报名」页**：一条列表解决"我在排队/被拒/该补什么"，比在活动列表里塞角标更清楚。
6. **活动发布进审核台。** UGC 一律 `audit_status='reviewing'` 起步，和帖子、二手商品同一套流程，运营只需维护一个审核队列。
