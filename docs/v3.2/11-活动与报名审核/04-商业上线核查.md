## 二、资金与对账

**结论：不涉及（依据：`campus_activity` 无价格/费用字段，报名接口无任何支付调用，`BizService.enrollActivity` 全路径不碰 `pay`/`order`）**

需要登记的一条边界：报名**收不了费**。若将来办收费活动（培训、演出票），当前链路没有下单-支付-退款，只能线下收款 + 平台记账外。届时"取消报名退款"必须重新设计，不能在这个状态机上硬加：现在 `enrolled` 只增不减（`ModuleMapper.java:300`），没有退款对应的名额回收。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：依赖 `module-multischool-admin.sql` 先跑完并回填 `campus_activity.school_id`）**

执行顺序：

```bash
# 0) 前置：多校字段（campus_activity.school_id 由它加，并回填为 1）
mysql -u root -p campus_life < backend/src/main/resources/db/module-multischool-admin.sql

# 1) 报名域迁移（幂等）
mysql -u root -p campus_life < backend/src/main/resources/db/module-activity-enroll.sql

# 2) 核对
mysql -u root -p campus_life -e "
SELECT COUNT(*) AS null_school_activity FROM campus_activity WHERE school_id IS NULL;
SELECT status, COUNT(*) FROM activity_enroll GROUP BY status;
SHOW COLUMNS FROM activity_enroll LIKE 'status';
SHOW TABLES LIKE 'activity_enroll_material';"
```

- 本次**未执行**，原因：无 MySQL 会话。
- 关键风险：若 `campus_activity.school_id` 仍为 NULL，校管的报名列表会**看不到任何数据**（`a.school_id=#{schoolId}` 对 NULL 不成立），运营会以为"没人报名"。

回滚 SQL：

```sql
ALTER TABLE activity_enroll DROP INDEX idx_enroll_status;
DROP TABLE activity_enroll_material;
ALTER TABLE activity_enroll
  DROP COLUMN status, DROP COLUMN real_name, DROP COLUMN student_no, DROP COLUMN phone,
  DROP COLUMN remark, DROP COLUMN audit_reason, DROP COLUMN audited_at, DROP COLUMN audited_by;
ALTER TABLE campus_activity DROP COLUMN enroll_mode, DROP COLUMN enroll_hint, DROP COLUMN enroll_max_files;
```

⚠️ 回滚会丢全部审核状态（`status` 列删除后老数据回到"默认 approved"语义）、全部材料记录与表单字段。**材料文件本身不会删**，会变成孤儿文件（可用 `GET /api/admin/uploads/orphans` 清理，`UploadController.java:60-65`）。

## 七、失败与降级（依赖挂了会怎样）

| 依赖 | 挂了会怎样 | 判定 |
|---|---|---|
| MySQL | 报名 500；列表空；前端 toast | 可接受（局部） |
| `enroll.material.enabled` 关闭 | **静默降级为一键报名**：学生以为交了材料，实际只写了一条无材料的报名 | **不可接受**（11-08 变体：降级对用户不透明） |

特别提示「静默降级」这一条：`BizService.java:422-424` 在开关关闭时把材料报名当一键报名处理，只留一行 `log.warn`。学生提交了 3 份材料，结果是 `status=approved`、材料**不落库**（走的是 `insertEnrollment` 单字段版本）。这是数据丢失级的降级，必须改成"明确报错：材料通道暂不可用"。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

**结论：不通过（原因：只有一个材料开关，且它的降级语义是错的；没有任何"停止报名"的能力）**

| 项 | 现状 | 证据 |
|---|---|---|
| 材料模式开关 | 有：`enroll.material.enabled`（全局） | `BizService.java:419` |
| 按活动关闭报名 | 只能把活动 `status` 置 0（下架整场活动） | `ModuleMapper.java:300` |
| 关闭单个报名 | 无 | — |
| 审核误操作的撤销 | 无（`WHERE status='pending'` 挡住重复处理，也没有反向操作） | `ModuleMapper.java:295` |
| 代码回滚 | 整包回滚；但若已产生材料数据，回滚后旧代码不认识 `status` 列 → 报名全部按"已报名"处理 | 需先跑第四节回滚 SQL |
| 数据回滚 | 见第四节，材料文件变孤儿 | 不可恢复 |

最小补齐（约 0.5 人日）：
1. `enroll.material.enabled=false` 时**不要降级**，直接返回「材料报名通道维护中，请稍后再试或联系主办方」。
2. 每个活动加 `enroll_open`（或复用 `status`）作为"仅停报名不停活动"的开关。

## 九、结论

**不可上线（阻断项：11-01、11-02）**

- 11-01 阻断理由：报名材料是学生主动交给平台的敏感文件（身份证、学生证、作品）。当前形态是"上传到公开可读目录 + 后台裸链接展示"，属于判级细则中"数据可跨用户读取（私有材料）→ P0"。这不是"以后优化"，是必须在上线前改完。
- 11-02 阻断理由：跨校审核是判级细则中"鉴权可绕过/越权写 → P0"。多校 SaaS 客户做安全评审时，这是第一个会被问的点。
- 11-03/11-04 不阻断，但**任何限人数活动都不能上线使用**（教室承载、票务）。若首发活动不含限额场景，可推迟。
- 11-05 不阻断但体验致命：学生报完名不知道结果，客服必然被打爆。建议同批修。
