## 一、设计优点（为什么这么设计，好在哪）

### 1. 定价权完全收在服务端，客户端拿不到任何金额入口

`CreateOrderRequest` 里没有 `total / price / amount / discount` 任何一个字段（`backend/src/main/java/com/campuslife/dto/CreateOrderRequest.java:3-16`）。客户端只能报"我要哪几样、各几份"。这是外卖类系统最容易被刷的地方，本仓库从一开始就堵死了：改包、改 JS、改本地缓存都无法影响实收金额。对照 `docs/v3.1/` 里其他功能还在讨论"前端传金额后端校验"，这一条是本功能做得最干净的地方。

### 2. 价格与商品信息在下单瞬间快照，商家改价不影响历史单

`BizService.java:627-632` 把 `{goodsId,name,price,count}` 写进 `user_order.items`（JSON），`subtotal` 与 `total` 同时落库。商家后续改菜价、下架菜品，已经产生的订单金额与明细都不会漂。这是"钱不能变"的基本功，做到了。

### 3. 幂等键 + 唯一索引 + 当前读，三层兜住"重复提交"

`idempotency_key` 有唯一键 `uk_order_user_idem`（`module-commerce-consistency.sql:47-50`），并发首提撞键后改用 `FOR UPDATE` 当前读回对方订单（`UserOrderMapper.java:90-96`），已经关闭的订单明确报错让前端换键（`BizService.java:604-606`）。小程序侧同一次结算复用同一个键并用 `sig`（店铺+商品+地址）绑定内容变化（`pages/food-order/food-order.js:76-88`）。这是本功能里设计层次最高的一段。

### 4. 券的四态机与"平台补贴"分账

`CouponService` 把"可用(1) → 锁定(2) → 核销(3) / 作废(0)"做成条件更新（`CouponService.java:53-88`），锁券失败整单回滚（`BizService.java:667-669`）。更关键的是退款时**券作废不退**、商家收入不扣券、平台单独记一条 `platform_subsidy` 账（`PaymentLedgerService.java:110-120`）。这避免了"退券造成循环套利"和"商家替平台打折"两个真实坑。

### 5. 状态机集中定义、非法边直接抛

`OrderStatus.canTransit()` 用 `EnumSet` 把 10 个状态的所有合法边写死（`OrderStatus.java:29-47`），`transitionStatus` 还额外禁止直接改 `refunding/refunded`（`PayService.java:231-233`）。分散在各 service 里写 `if (status.equals(...))` 是这类系统的通病，这里没有。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 1. 同一个业务概念有两套数据源，这是本功能所有金额问题的根

"满减"同时存在为：
- 展示文案 `shop.discount`（VARCHAR(32)，人情字符串，如「满20减8」）；
- 参与计算的两列 `shop.discount_threshold` / `shop.discount_amount`（DECIMAL）。

而**写入口分成两条，一条只写文案、一条只写数值**：
- 管理端 `web/src/views/Shops.vue:99-101` + `AdminModuleMapper.java:455-470` → 只写文案；
- 商家端 `MerchantMapper.java:119-127` → 写数值（也写文案，但两个字段可以让商家自己填不一致的值）。

代价：只要运营用管理端建店或改优惠，展示与实收必然分叉，且**没有任何一致性校验、没有任何数据库约束、没有一条测试**。

### 2. 客户端复制了一份满减算法

`utils/food.js:6-7` 用正则从文案里解析「满X减Y」自己算一遍，而后端读数值列。两套算法同源不同实现，一旦文案与数值不一致，用户在结算页看到的是**客户端的算果**、扣款用的是**服务端的算果**。这是"体验层复制业务规则"的典型代价：看起来只是前端小工具函数，实际是第二套定价逻辑。

### 3. 小程序端把"售后"整块留给了后台

取消、退款两个接口后端写得相当讲究（渠道先查后关、已付款则拒绝取消并引导退款，`PayService.java:152-169`），但小程序端一个按钮都没有。代价是：**用户想取消一笔下错的单，唯一路径是打电话给运营**。运营再在 Web 订单页操作。这种"能力有、入口无"的半成品比"完全没做"更难排查，因为接口测试是通过的。

### 4. 学校隔离在读侧是"可绕过"的软约束

`resolveSchoolId()` 三档优先级里，`explicitSchoolId` 与 `schoolScope=all` 都能越过"用户所属学校"（`BizService.java:170-174`），并且这个参数是**匿名可传**的（`GET /api/food/shops` 属公开读）。对店铺/菜品这类公开信息这不算漏洞，但它意味着"按校隔离"不能作为数据安全的依据；一旦哪天有人把敏感字段塞进店铺返回体，隔离会立刻失效。当前返回体已经带 `contactPhone` 与 `address`（`BizService.java:75`）。

### 5. 订单状态在四个地方各自维护一份文案表

`OrderStatus`（后端 10 态）、`Orders.vue`（Web 7 项）、`food-order-detail.js`（8 态）、`food-orders.js`（9 态，含 `unpaid/pending_payment` 这两个后端根本不产生的值）。每加一个状态要改四处，漏一处就是"状态更新中"。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 做法 | 为什么本仓库没选（从代码能看出的取舍） |
|---|---|---|
| 满减只存数值，文案由后端生成 | 删掉 `shop.discount`，列表接口返回 `满{threshold}减{amount}` 拼串 | 商品/店铺卡片文案风格不统一（有的要写"第二杯半价"），运营想自定义文案；作者选了"文案自由 + 数值另存"，代价是一致性靠人 |
| 满减只存文案，后端也解析 | 后端复用 `utils/food.js` 的正则 | 字符串解析在服务端做定价属于不可接受的做法（改一个字就能改价格），所以后端坚持读数值列——这个选择是对的，问题出在没人写数值列 |
| 券抵扣前端算好传后端 | 前端传 `couponDiscount`，后端校验 | 已被明确否决，证据：`CreateOrderRequest.java:13` 注释「抵扣额由服务端按券面额与门槛计算，客户端不能传金额」 |

| 停用店铺用 `status=0` 软删 | 当前做法 | 结果：`AdminOrderService.java:79` 用 `status=1` 过滤店铺集合，停用后历史订单在后台消失。更稳的做法是"订单查询不按店铺状态过滤，只在店铺选择器里过滤" |

### 4.1 为什么是这 9 条

本功能代码量不小（`BizService` 679 行、`CouponService` 103 行、`ShopGoods/Shop/UserOrder` 三个实体、6 个 SQL 脚本、5 个小程序页、2 个 Web 视图、12 个商家端接口），9 条已按"能验收"的标准筛过一轮：凡是给不出 `path:line` 或给不出复现方式的观察都写进了 02-实现现状，不列进问题清单。

## 五、如果重做会怎么改

1. **满减只留一份数据**。数据库只存 `discount_threshold / discount_amount`，`shop.discount` 要么删除、要么改成 `GENERATED COLUMN`，让"展示文案"在物理上不可能与实收不同源。这条改完后 06-01 整类问题永久消失。
2. **前台不复制定价规则**。`utils/food.js#bill` 只做展示用估算，页面要明确标注"以结算页为准"，真正的 total 由 `POST /api/orders` 返回值覆盖页面（当前结算页是自己算完直接展示，提交后拿 `result.total` 但没回写展示）。更彻底的做法是加一个 `POST /api/orders/preview`，结算页所有金额都来自服务端。
3. **订单查询与店铺生命周期解耦**。订单是财务凭证，它的可见性不该取决于店铺是否在营业。
4. **售后入口跟接口一起交付**。凡是后端有 `cancel/refund` 的能力，前端必须同时有入口，否则接口就是没有用户的接口；同理凡是前端有入口，后端必须有对应实现。用一条静态检查（类似 `tools/check-api.js`）断言"关键写接口必须被至少一个页面调用"。
5. **状态字典单一来源**。把 10 个状态的中文名与前端的颜色/文案集中在 `utils/constants`，四个页面引用同一份，加状态只改一处。
