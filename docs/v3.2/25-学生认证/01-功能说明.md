## 一、这个功能解决什么问题

平台上有「只能本校学生做」的事：接有偿兼职（`VerificationService.java:29-30`）、创建宿舍（`DormService.java:499-504`）。这些人身相关的权限需要一个可信的身份结论，所以要有学生认证。

它要回答三个问题：

1. **这个人是不是真学生**——收学校、学院、真实姓名、学号四项文本材料，人工核验（`VerificationService.java:31-32`）。
2. **结论能不能被信任**——没有可信核验源时**绝不伪造「已认证」**：默认全员 `none`，状态只能由管理端人工核验写入，或开了 `auto` 规则后由学号正则命中写入（`VerificationService.java:26-30`）。
3. **结论能不能被消费**——下游通过 `status()` 的 `verified` / `canTakePaidJob` 两个布尔量判断，而不是各页面自己拼状态（`VerificationService.java:100-114`）。

明确**不做**的事（读码可见）：

- **不采集证件影像**。只存四项文本，`user_verification` 表里没有图片列，`apply` 接口也不接收文件（`VerificationService.java:31`、`UserVerification.java:12-17`、`VerificationController.java:60-66`）。
- 不接入第三方身份接口，不做学信网/教务系统对接（`VerificationService.java:27-28`）。
- 不做多校差异化规则：规则存 `app_config`，平台一套（`module-app-config-verification.sql:3-6`）。

3. 表单字段按后端 `require` 动态渲染，不写死四项必填（`verify.js:74-75`、`:22-28`）。

5. 提交 `POST /verification/apply`，成功后就地切「审核中」（`verify.js:167-190`）。

**B. 认证规则配置**

1. 读写 `app_config` 里的 7 个键（`Verification.vue:213-219`）：4 个 `verification.require.*`、`student_no_pattern`、`review_mode`、`daily_limit`。

### 4.1 私有上传：设计意图 vs 实际行为（先说清，问题见 03）

设计意图（两处注释）：

- `UploadController.java:49-50`：「私有上传：学生证等敏感图片。存到 `uploads/private/`，**不走 `/uploads/**` 静态映射，因此无法被直接访问**；需要时由带鉴权的接口读取。」
- `UploadService.java:93-95`：「私有文件不给完整 URL，避免被直接访问；调用方存站内路径，读取时再走鉴权接口」，返回 `{path:"/private/xxx", url:""}`。

实际行为（三处代码）：

- `LocalObjectStorage.java:27`：`privateDir() = root.resolve("private")` → 即 `<uploads>/private`，**在公开根目录里面**。
- `WebConfig.java:48-54`：`/uploads/**` 映射到 `localRoot`（= `<uploads>`），所以 `GET /uploads/private/<name>` 会被静态资源处理器直接返回文件。
- `AdminInterceptor.java:29-30`：`/api/admin/upload/private` 在**没有 token** 时直接放行。

即：**「私有上传」既不私有、也不鉴权**。这是 25-01。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 `apply` 的校验顺序（顺序本身是设计，`VerificationService.java:199-205` 注释说明）

1. **先看总闸门**：`verification.student.enabled` 关着直接 403「认证申请暂未开放」，连字段都不校验——避免把「暂未开放」说成「学号格式不对」（`VerificationService.java:211-212`）。
2. 读配置，算出哪几项必填（`:214-218`）。
3. 校验学校存在且启用：`schoolExists(schoolId) >= 1`（`:224-226`、`UserVerificationMapper.java:59-60`）。
4. 必填项非空 + 格式（`:228-237`）：姓名 2–20 字只含中文/字母/`·`；学号 4–20 位字母数字；学院 2–32 字。
5. 审核中不许重复提交（`:242-245`）：「正在审核中，请耐心等待」。
6. 已认证不许重复提交（`:246-248`）。
7. **最后才动限频计数**（`:250-253`）——注释解释：先记次数会让「填错一个字就白白消耗一次机会」（`:202-203`）。

### 7.2 会拒绝的情况

| 情况 | 提示 | 证据 |
|---|---|---|
| 入口未开放 | 403「认证申请暂未开放」 | `VerificationService.java:212` |
| 未选学校 / 学校不存在或停用 | 400「请选择学校」 | `:224-226` |
| 姓名缺失/格式错 | 400「请填写真实姓名」 | `:228-231` |

### 7.3 驳回后能否重提

**能。** 拦截条件只有 `pending` 与「双 verified」（`VerificationService.java:242-248`），`rejected` 不在拦截范围内；重提会覆盖同一行、清空 `reject_reason`、`source` 置回 `self`（`:265-279`）。

但有代价：`submit_count` 不会因为驳回而重置，一天最多 `daily_limit` 次（默认 3）。

### 7.4 `auto` 模式的三条铁律（都写在代码里）

1. **空正则 + auto = 谁都能过**：`auto` 必须同时满足「正则非空」且「能编译」，否则强制回落 `manual` 并记 `warn`（`VerificationService.java:162-185`）。这条是本模块最硬的一处防线，`effectiveReviewMode` 有单测可覆盖。
2. **改严不追溯**：`status()` 只读状态列、不读配置——把学院从选填改成必填，已通过的老用户不会被重新判成未通过（`VerificationService.java:41-42`、`:96-127`）。
3. **平台一套 ≠ 永远一套**：`auto` 只适合当前单校阶段，提示写在 `app_config.remark` 里（`module-app-config-verification.sql:22`）。

### 7.5 下游如何消费（这是本功能的出口价值）

| 消费方 | 判断 | 证据 |
|---|---|---|
| 有偿接单 | `canTakePaidJob = verified && job.paid.enabled`，两者都满足才放行；`requireVerifiedForPaidJob` 只判「人」 | `VerificationService.java:113-114`、`:292-296` |
| 创建宿舍 | `verification.status(userId).verified` 必须 true | `DormService.java:499-504` |
| 个人中心展示 | 接口失败时保持「未认证」，绝不乐观展示已认证 | `pages/profile/profile.js:44` |
