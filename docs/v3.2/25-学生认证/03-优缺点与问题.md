## 一、设计优点（为什么这么设计，好在哪）

### 1.1 「不伪造已认证」是写进代码的，不是写在文档里的

`VerificationService.java:26-27`：「没有可信核验源时**不伪造"已认证"**：默认全员 none，状态只能由管理端人工核验写入」。`status()` 对没有记录的用户返回全 `none`（`:96-99`），前端也同口径：「接口失败时保持未认证，绝不乐观展示已认证」（`pages/profile/profile.js:44`）。

在一个大量使用 mock 兜底的仓库里（参见功能 24 的 `demoRank`），认证这一块**没有一处假值**。这是取舍正确的地方：身份状态一旦造假，下游所有权限判断（接有偿兼职、建宿舍）都会跟着错。

### 1.2 auto 模式的「空正则 = 谁都能过」防线

`effectiveReviewMode`（`VerificationService.java:166-185`）做了两件事：

1. `auto` 必须同时满足「正则非空」**且**「正则可编译」，否则强制回落 `manual` 并 `log.warn`；
2. 告警只打一次（`lastAutoFallbackWarn` 去重），不会把日志刷爆。

注释把后果说得很直白：「系统不允许被配置成『任何学号都通过』——那等于认证入口不存在」（`:163-165`）。

**这是本项目里设计得最讲究的一段防御性代码**：它防的不是攻击者，是运营自己的一次误配置。

### 1.3 「改严不追溯」——配置变更不影响历史结论

`status()` 只读状态列、不读配置（`VerificationService.java:41-42`、`:96-127`）。把「学院」从选填改成必填，已通过的老用户不会被重新判成未通过。

这条很容易被忽略但极其重要：如果状态是「实时按配置算」的，那么一次配置变更会让一批已认证用户突然失去接单权限，而且无法解释。做成「结论落库 + 配置只影响入口」是对的。

### 1.4 校验顺序：先查闸门 → 再校验材料 → 再查状态 → 最后动计数

`VerificationService.java:199-205` 的注释解释了为什么：「如果先记次数再校验，用户填错一个字就白白消耗一次机会，第二天来又要等。」

这个顺序不是随手写的——它同时解决了三个体验问题：

- 入口关闭时不会误导成「格式错误」（`:211-212` 的注释）；
- 填错不消耗次数（`:250` 在所有校验之后）；
- 审核中/已认证的重复提交被拦在计数之前（`:242-248`）。

### 1.5 管理端审核台补上了「审核员看得见」这个断点

`AdminVerificationController.java:29-34` 注释点明：「没有这些字段，审核员看到的只是一个『待审核用户 7』」。现在列表返回学校名、学院、姓名、学号、提交时间（`UserVerificationMapper.java:26-50`），并且学校过滤写在 SQL 里而不是内存过滤（`:38`）。

### 1.6 越权判定与审计都做了

- 校管只能审本校用户（`VerificationService.java:309-311`）；
- 未绑定学校的校管直接拒绝（`AdminVerificationController.java:77`）；
- 审核写管理端审计日志，含 before → after 与原因（`VerificationService.java:336-337`）；
- 状态值白名单（`:354-358`），不会写入非法状态。

### 1.7 规则配置的权限被收紧到超管

`AppConfigController.java:47-57` + `:63-67` 的 `requireSuper`。`module-app-config-verification.sql:8-10` 注释记录了历史问题：「以前 AppConfigController 没有任何角色校验，校管也能写全局 app_config —— 那只是二维码和文案；一旦装上『学号正则』和『审核方式』，任何一个校管都能改掉全平台的认证规则。」

**他们意识到了「同一个接口在不同配置项上风险等级不同」这件事**，并事后补了权限。这是很成熟的一次反思。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 代价一：「私有上传」这个基础设施是坏的，而且注释在骗人

三处注释都声称私有文件不可直接访问（`UploadController.java:49-50`、`UploadService.java:93-95`、`LocalObjectStorage.java` 的 `putPrivate` 语义），但三处代码否定了它：

1. `LocalObjectStorage.java:27`：`privateDir() = root.resolve("private")`——私有目录**在公开根目录里面**；
2. `WebConfig.java:48-54`：`/uploads/**` 映射到 `root`，所以 `GET /uploads/private/<uuid>.jpg` 会被静态资源处理器直接吐回来；
3. `AdminInterceptor.java:29-30`：`/api/admin/upload/private` 在**没有 token** 时 `return true`。

第 3 条的注释解释了原因：「License files use private storage while application submission remains public」（商家入驻资质要匿名提交）。这个业务理由可以理解，但它用一个**路径级的放行**解决了一个**业务级的例外**——结果是任何人都能往私有命名空间写文件，而私有命名空间同时是公网可读的。

组合起来的后果不是「学生证泄露」（认证流程根本不收影像），而是：

- **任意人可上传任意图片并获得长期公网 URL**（`url` 字段虽为空，但 `/uploads/private/<name>` 可直读）；
- 私有目录 = 公开图床，容量与内容都不受控；
- 一旦将来真往这个目录存学生证，就是**明文证件照公网可读**，没有任何代码需要改，事故自动发生。

### 2.2 代价二：认证页是个「只有大脑没有身体」的页面

`pages/verify/verify.js` 有 8027 字节的完整交互逻辑（四态推导、动态表单、校验、提交、重填），但：

- 没有 `.wxml`（模板）→ 没有任何 UI；
- 没有 `.json` → 没有页面配置；
- 没有 `.wxss` → 没有样式；
- 未注册 `app.json` → 微信不打包；
- 无入口 → 即使注册也没人能找到。

**5 个环节全断**。而静态检查 9/9 通过，因为检查只遍历 `app.pages`（`tools/check-static.js:13-20`）。

这说明流程上缺一个动作：**「新页面交付」的完成定义里没有「真机能打开」这一条**。

### 2.3 代价三：材料清单是「三端三个版本」

| 位置 | 是否有 phone |
|---|---|
| 配置（`VerificationService.java:148`） | 有，且可设必填 |
| Web 配置页（`Verification.vue:216`） | 有，可勾选 |
| 小程序表单（`verify.js:161`） | 有，必填时校验 `1[0-9]{10}` |
| 小程序提交（`utils/api/points.js:150`） | 有，发到后端 |
| 控制器（`VerificationController.java:60-66`） | **丢弃** |
| Service 签名（`VerificationService.java:208-209`） | **没有该参数** |
| 实体（`UserVerification.java:22-47`） | **没有该字段** |
| 建表脚本（`module-verification-v31.sql:24-78`） | **没有该列** |

脚本自己的备注写着「本期无对应表单字段，仅预留」（`module-app-config-verification.sql:20`），但前端已经做了。**这是一次典型的「配置先行、实现滞后、前端抢跑」**，代价是：运营把手机号设为必填后，用户必须填、填了丢掉、审核员永远看不到——而系统没有任何提示说它是无效配置。

### 2.4 代价四：限频数字看着严谨，实际可以被并发绕过

`VerificationService.java:250-253` 是标准的「读 → 判 → 写回」：

```java
int used = row != null && today.equals(row.getSubmitDate()) ? nvlInt(row.getSubmitCount()) : 0;
int limit = dailyLimit();
if (used >= limit) throw ...;
// ... 后面才 row.setSubmitCount(used + 1)
```

没有 `SELECT ... FOR UPDATE`、没有乐观锁、没有 `@Version`，也没有 `RateLimiter`（对比发帖/评论都加了 `RateLimiter.PUBLISH`，见 `ForumController.java:89`）。

同一用户并发发 N 个请求，每个都读到 `used=0`，每个都写 `submit_count=1`——**上限形同虚设**，审核队列可被打爆。而这条链路的成本是零：一个 `curl` 循环就行。

### 2.5 代价五：认证的「社会价值」没交付

学生认证在校园产品里的核心价值有两块：**准入门槛**（能接有偿活）与**社会证明**（这个人真的是某校学生）。第一块做了，第二块完全没做：

- 用户主页看不到认证标识；
- 帖子/评论列表看不到；
- 只有自己在「我的」页能看到。

`grep -rn "verified" pages/user-home/ pages/post-detail/ pages/community/` 零命中；后端也没有任何「返回他人认证状态」的接口字段。所以认证用户与非认证用户在内容社区里**毫无区别**，激励闭环缺一半。

### 2.6 代价六：学校这个维度是「用户自选 + 审核按用户表判」的混合体

- `apply` 时 `schoolId` 由用户从下拉里自选，只校验「学校存在且启用」（`VerificationService.java:224-226`），不比对 `user.school_id`；
- `adminList` 过滤用 `u.school_id`（用户表）但展示 `v.school_id`（申请填的）（`UserVerificationMapper.java:31-38`）；
- `review` 越权判定用 `target.getSchoolId()`（用户表）（`VerificationService.java:309-311`）。

三者不是同一个字段，于是出现两种错配：

1. 用户 `u.school_id=A` 但申请填 `school_id=B` → 校管 A 能审（因为用户属 A），审出来的结论却是「B 校已认证」；
2. 用户 `u.school_id=B` 但申请填 `school_id=A` → 校管 A 在列表里**看不到**这条（被 `u.school_id=B` 过滤掉），校管 B 看得到并审了一条申报 A 校的材料。

这是 25-03，属越权边界的实际破口。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 优点 | 代价 | 为什么没选（依据代码） |
|---|---|---|---|
| **接入学信网/教务系统做真核验** | 结论可信、可自动化 | 需要资质与对接；单校阶段不现实 | 明确不做，`VerificationService.java:27-28`：「不接入任何未经验证的自助认证或第三方身份接口」 |
| **不认证，直接放开权限** | 零开发量 | 有偿兼职/宿舍对所有人开放，风险更高 | 否决，`DormService.java:499-504` 坚持要认证 |
| **默认全员「已认证」** | 体验最好，无审核成本 | 身份造假，下游权限全错 | 明确否决，`VerificationService.java:26-27`。这条是本模块的底线 |
| **按学校一套认证规则（`school.verify_config`）** | 多校天然隔离 | 单校阶段过度设计 | 现在用平台一套，`module-app-config-verification.sql:3-6` 明确了将来切换路径 |
| **状态实时按配置算** | 改配置立即生效 | 改严会把老用户打成未认证 | 否决，`VerificationService.java:41-42` 的「改严不追溯」 |
| **采集证件影像** | 人工核对更准 | 合规风险（证件影像属敏感个人信息）、存储成本、泄露代价 | 明确不做，`UserVerification.java:12-17`、`VerificationService.java:31`。这个取舍**是对的**，见 2.1：私有上传基础设施现在是坏的，不收影像反而避开了最大风险 |
| **限频用 Redis/RateLimiter** | 多实例一致、并发安全 | 多一个依赖 | **未选，这是缺陷**（25-05）：发帖评论都用了 `RateLimiter`，认证没用 |
| **认证材料单独历史表** | 审核可追溯 | 多一张表 | 未选（25-09）：单行覆盖，驳回重提后旧材料不留痕 |

## 五、如果重做会怎么改

1. **认证材料与私有存储分开设计**。材料（文本）进 `user_verification`，影像（若将来要做）进独立私有桶，读取走**带鉴权的签名 URL**（`ObjectStorage` 已有 `readPrivate`，缺的是「按业务对象鉴权」的读接口，目前只有 `MerchantAuditController.java:53` 一处在用）。绝不能让私有目录落在静态映射根下。
2. **`/api/admin/upload/private` 去掉路径级放行**。商家资质匿名提交应该是**单独一个公开接口**（如 `POST /api/merchant/license`），而不是把管理端私有上传的鉴权整个关掉。
3. **学校归属只保留一个字段**。建议以 `user.school_id` 为唯一真相：`apply` 时若传了不同学校就更新它（并有审计），列表/展示/越权判定全部读同一处。现在的三字段混用必然长出 25-03 这类 bug。
4. **材料清单由配置驱动但必须可验证**。给 `verification.require.*` 加一层「配置项是否被后端实现」的自检：启动时对未实现的键打 `warn`，或干脆把 phone 从配置里删掉直到实现——「可设必填但静默丢弃」比「没这个功能」更糟。
5. **限频上移为通用能力**。认证、发帖、上传三处都要限流，现在只有两处有（`ForumController.java:89/121`、`UploadController.java:35/45/55`）。把 `RateLimiter` 做成注解或用例，避免「新功能忘了加」。
6. **补测试**（现在 0 个）：`effectiveReviewMode` 空正则回落、并发限频、驳回重提、跨校审核 403、auto 通过后状态不被前端覆盖。这五条是本模块的全部关键分支。
7. **「新页面」的完成定义加两条**：①`app.json` 已注册；②`tools/check-static.js` 增加「未注册目录 / 缺文件」检查（当前只遍历 `app.pages`，天然漏检）。
