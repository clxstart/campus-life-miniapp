## 二、资金与对账

**结论：不涉及资金（依据：本功能不发不扣任何积分/成长值，也不经手任何金额）**

| 检查点 | 结论 | 依据 |
|---|---|---|
| 是否直接发/扣积分 | 不涉及 | `grep -n "award\|spend\|point" VerificationService.java` 零命中 |
| 是否作为其他发分的凭证 | **间接相关**：认证是「接有偿兼职」的前置条件（`requireVerifiedForPaidJob`），而兼职结算是功能 27 的发分场景之一 | `VerificationService.java:292-296`、`DormService.java:499-504` |
| 是否涉及真实货币 | 不涉及：无支付、无退款 | 全文无 `PayService`/`BigDecimal` 依赖 |
| 认证费用 | 不涉及：免费 | 同上 |

**但有一条必须记**：认证状态是**下游资金类操作的准入闸门**（有偿兼职、宿舍奖励）。一旦认证被越权通过（25-03），下游的「有偿」资格就跟着被绕过。所以本功能的「资金影响」是**间接但实质的**——它决定了谁能进入资金链路。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：按顺序执行 + 补 `user_id` 唯一键）**

### 4.1 前置 SQL 与执行顺序

```text
1) backend/src/main/resources/db/module-verification.sql       -- 基线表 user_verification（旧脚本，需确认已跑）
2) backend/src/main/resources/db/module-verification-v31.sql   -- 扩 8 列（学校/学院/姓名/学号/提交时间/来源/限频计数）+ 1 索引
3) backend/src/main/resources/db/module-app-config-verification.sql -- 7 个配置键种子
4) backend/src/main/resources/db/module-feature-flag.sql       -- 需含 verification.student.enabled / job.paid.enabled 两行开关
```

顺序理由：`module-verification-v31.sql` 用 `ALTER TABLE user_verification` 扩列，**表必须已存在**（`db/module-verification-v31.sql:24-28`），故基线脚本必须先跑；`module-app-config-verification.sql` 依赖 `app_config` 表存在。

### 4.2 幂等性

| 脚本 | 可重复执行 | 依据 |
|---|---|---|
| `module-verification-v31.sql` | 是：每列前查 `information_schema.COLUMNS`，已存在则 `SELECT 1` | `:24-78` |
| `module-app-config-verification.sql` | 是：`ON DUPLICATE KEY UPDATE config_key = config_key`（不覆盖后台改过的值） | `:24` |
| 索引 `idx_verif_pending` | 是：查 `information_schema.STATISTICS` | `:73-78` |

### 4.3 缺失的约束（建议在迁移中一并补）

```sql
-- 代码用 selectOne(user_id) 语义，必须有唯一键，否则并发首提会插入两行（25-10）
ALTER TABLE user_verification ADD UNIQUE KEY uk_verif_user (user_id);

-- 若决定支持手机号（25-04 方案①）
ALTER TABLE user_verification ADD COLUMN phone VARCHAR(20) NOT NULL DEFAULT '' COMMENT '联系方式，人工核验回访用';
```

### 4.4 回滚

```sql
-- 回滚发放入口（保留数据，最小破坏）
UPDATE feature_flag SET enabled = 0 WHERE flag_key = 'verification.student.enabled';

-- 回滚配置项（恢复到「全部人工审核 + 默认必填项」）
UPDATE app_config SET config_value = 'manual' WHERE config_key = 'verification.review_mode';
UPDATE app_config SET config_value = '1'      WHERE config_key = 'verification.require.real_name';
UPDATE app_config SET config_value = '1'      WHERE config_key = 'verification.require.student_no';

-- 让已发出去的「已认证」失效（谨慎：会影响宿舍与有偿兼职）
UPDATE user_verification SET real_name_status = 'none', student_status = 'none', verified_at = NULL;
```

**注意第三条**：把已认证用户批量打回 `none`，会让「已建的宿舍」「已在做的有偿兼职」瞬间失去合法性（`DormService.java:499-504`、`VerificationService.java:292-296`）。真要做必须先确认下游有容忍逻辑，否则会造成比问题更严重的事故。这也是本维度判「有条件通过」而非「通过」的原因：**回滚有副作用，需要剧本而不是一行 SQL**。

## 九、结论

# 不可上线（阻断项：25-01、25-02、25-03、25-04、25-05）

逐项说明：

1. **25-01 私有上传匿名可写 + 公网可读**——这是安全问题，不是功能问题。当前它暂时没被用来存证件照（认证不收影像），但基础设施已经处于「一碰就炸」的状态，且代码注释在误导后来者相信它是安全的。**必须先修**。
2. **25-02 认证页只有 .js**——学生认证在小程序端 0 用户可达，而它是有偿兼职与建宿舍的前置条件。等于三个功能一起废掉。
3. **25-03 学校三字段混用**——校管可越权审出「别校已认证」，直接绕过下游资金类操作的准入门槛。
4. **25-04 手机号静默丢弃**——运营配了必填、用户填了、审核员看不到。这是「配置说谎」，会让运营基于错误信息做决策。
5. **25-05 限频可并发绕过**——审核队列可被单账号打爆，是整个认证体系可用性的单点。

放行路径：修完 25-01 ~ 25-05 后**可降级为「有条件上线」**（条件：25-06、25-07 在灰度期完成；补 `user_id` 唯一键；补 5 条关键测试）。

值得肯定的一点：**这个模块的「不伪造已认证」「改严不追溯」「auto 空正则回落」三条设计，是全仓库最经得起追问的部分**。它的问题不在思路，在落地完整性。
