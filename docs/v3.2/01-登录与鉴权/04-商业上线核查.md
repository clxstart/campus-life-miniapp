- 与支付相关的资金口径不在此文档，见 `07-支付与退款/`。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：必须按下面顺序执行，且 `token_version` 列缺失会让管理端每请求 503）。**

执行顺序（缺一步都会出问题）：

```sql
-- 1) 管理员/学校/日志基础表（必须先于 2）
--    db/module-multischool-admin.sql
-- 2) token_version 列（AdminMapper.tokenState 直接 SELECT 它；缺列 = 所有管理端请求 503）
--    db/module-commerce-consistency.sql:55-56
-- 3) user.status / deleted_at（注销功能依赖）
--    db/module-account-delete.sql:12-24
-- 4) 仅在本地演示时执行，生产禁止
--    SET @ALLOW_DEMO_SEED='YES'; 再跑 db/module-admin-seed.sql
```

回滚：

```sql
-- 回滚 2)：先确认没有代码在引用该列，再执行
ALTER TABLE admin_user DROP COLUMN token_version;
-- 回滚 3)：
ALTER TABLE `user` DROP COLUMN status, DROP COLUMN deleted_at;
-- 回滚 1)：不要 DROP，直接改代码回旧版本；admin_user 里已有运营账号
```

**风险点**：`AdminMapper.java:90` 的 `token_state` 查询是硬依赖，`module-commerce-consistency.sql` 漏跑时表现为「登录成功但每个接口 503」，且 `AdminInterceptor.java:48-51` 会把它归类为「鉴权服务暂不可用」，运维不易定位。**上线前置里必须有一条「跑完 SQL 后登录管理端点一次看板」的验收动作。**

## 五、性能与容量

**结论：有条件通过（条件：单实例下可支撑；`cluster` 模式必须先建 `scheduler_lock`）。**

| 项 | 数据 | 证据 | 判断 |
|---|---|---|---|
| 管理端每请求多查一次库 | 1 次主键查询/请求 | `AdminTokenGuard.java:34-52` | 后台 QPS 低，可接受 |
| 用户请求的用户状态校验 | 60 秒本地缓存，命中率接近 100% | `UserStatusGuard.java:27-53` | 可接受 |
| 单实例 vs 集群 | `campus.ha.mode=single` 时限流/在线数/任务锁都在进程内 | `application.yml`（`campus.ha.mode`） | 多实例会把限流额度放大 N 倍 |
| 集群模式前置 | 缺 `scheduler_lock` 表直接启动失败 | `ha/HaConfiguration.java:28-34` | 设计正确（fail-fast） |
| 数据库连接池 | 25（`hikari.maximum-pool-size`） | `application.yml` | 按注释推算 ≈1250 QPS 上限，登录不是瓶颈 |
| 登录接口本身 | 无缓存，每次走微信接口 | `AuthService.java:106-121` | 微信接口 RT 是外部依赖，未压测 |

**未验证**：登录 QPS 上限、微信 `jscode2session` 的可用性与限频——`04-证据与复核台账.md` 第四节未登记这一项，属于漏登记。

## 七、失败与降级（依赖挂了会怎样）

| 依赖 | 挂了的表现 | 是否可接受 | 证据 |
|---|---|---|---|
| 微信 `jscode2session` | 登录返回 503「微信登录服务暂时不可用」，前端重试；**不降级到 dev-login** | 可接受（生产） | `AuthService.java:115-120` |
| 微信参数未配置 | 登录 503「微信登录未配置，请联系管理员补齐」 | 可接受（但说明部署失败） | `AuthService.java:84-86` |
| MySQL（管理端鉴权） | 每个管理端请求 503「鉴权服务暂不可用」——**管理端整体不可用**，这是有意的 | 可接受（宁可不可用不可越权） | `AdminInterceptor.java:48-51` |
| MySQL（用户状态） | 按「可用」放行（fail-open），已注销用户的 token 可能再活最多 60 秒 | 有条件可接受，需知会 | `UserStatusGuard.java:45-47` |
| Redis（cluster 限流） | 429 之外的 503，除非显式 fail-open | 可接受 | `RateLimiter.java:52-57` |
| Redis（用户状态？） | 用户状态不用 Redis，纯本地缓存 | — | `UserStatusGuard.java:33` |

**最需要补的降级**：小程序侧对 503（服务不可用）与 401（未登录）的提示是同一个 `error.message` 透传（`utils/api/core.js:71-78`），用户看到的是「服务繁忙」却可能以为要重新登录。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

| 开关 | 默认 | 生产可否改 | 效果 | 证据 |
|---|---|---|---|---|
| `campus.auth.enforce` | true | **不可**（prod 配 false 直接拒绝启动） | 关掉 = 任何人可冒充任意用户 | `ProductionConfigValidator.java:53-55` |
| `campus.auth.dev-login-enabled` | false | **不可**（prod 配 true 拒绝启动） | 关掉 = 无本地后门 | `ProductionConfigValidator.java:47-49` |
| `campus.auth.dev-login-any-user` | false | **不可** | 同上 | `ProductionConfigValidator.java:50-52` |
| `campus.jwt.admin-ttl-seconds` | 28800（8h） | 可（改配置需重启） | 缩短 = 更安全更频繁重登 | `application.yml` |
| `campus.jwt.ttl-seconds` | 604800（7d） | 可（需重启） | 缩短 = 泄露窗口变小，但老 token 仍按旧 TTL 走完 | `application.yml` |
| `campus.production-guards.enabled` | true | 可（**不建议**） | 关掉 = 不再拦截已泄露口令账号 | `ProductionDemoAccountGuard.java:23` |

**回滚方案**

1. **代码回滚**：登录/鉴权是纯代码能力，回滚到上一个 tag 即可，无数据结构副作用（`token_version` 列保留不影响旧代码）。
2. **令牌全量作废**（紧急处置手段）：改 `CAMPUS_JWT_SECRET` 并重启 → 所有用户与管理员 token 同时失效，所有人需重新登录。这是当前**唯一**的「一键踢所有人」手段，上线前必须写进应急预案。
3. **数据回退**：`user.status=0` 可改回 1 恢复账号（但 `openid` 已被置空，恢复后账号无法再用原微信登录，见 `UserService.java:127-134`）——**注销是不可逆操作，没有真正意义上的回退**。
4. **管理员被锁死的自救路径**：只能改数据库 `admin_user.must_change_password=0, status=1, locked_until=NULL`。没有自助找回密码（无邮件/短信验证码通道）；唯一的重置接口是管理端重置**骑手**密码（`RiderAdminController.java:73`），管理员与校管没有对应入口。

## 九、结论

**不可上线。**

阻断项：

- **01-01（P0）**：`utils/config.js:9` 的 `PRODUCTION_ORIGIN` 仍是 `https://api.your-domain.example`，release/trial 包的任何请求在本地就被 `reject`，登录链路整段不可用。这是「一票否决」项，不修完后面所有检查都没有意义。

修完 01-01 后转为**有条件上线**，条件为：01-02、01-03、01-05 三条 P1 必须先修（限流键伪造 / 管理端无限流 / 无服务端登出）。
