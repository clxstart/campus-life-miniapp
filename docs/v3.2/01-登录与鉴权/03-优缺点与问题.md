## 一、设计优点（为什么这么设计，好在哪）

1. **两套密钥彻底隔离，小程序 token 冒充不了管理员。** 管理端密钥 = 用户密钥 + `-admin-scope` 后缀（`config/AdminJwtUtil.java:20-27`），同一个 `campus.jwt.secret` 派生出两把不可互换的 key。比「同一个 key + 一个 role claim」安全：即使 role 判断写错，签名也对不上。
2. **管理端不是「无状态 JWT」，而是「JWT + 每请求查库」。** `AdminTokenGuard` 每次请求比对 status / token_version / role / schoolId / shopId 五项（`config/AdminTokenGuard.java:48-50`）。改密、停用、调校区都会让旧令牌即时失效，而且**查库失败返回 503 而不是放行**（`AdminInterceptor.java:48-51`）。管理端 QPS 低，这个代价换得的值。
3. **「首次登录必须改密」是服务端拦的，不是前端跳转。** `AdminInterceptor.java:68-72` 对 `must_change_password=1` 的账号只放行改密、profile、logout 三个路径，注释直接写了「否则前端跳过改密页仍能直接调业务接口」。同类系统最常见的漏洞（只在前端跳）这里没有。
4. **生产配置闸门在启动阶段就拒绝，而不是第一笔请求才炸。** `ProductionConfigValidator` 检查 profile 必须显式、微信参数真实、`dev-login` 关闭、`enforce=true`、`pay.simulate=false`、JWT 密钥长度与特征、CORS 与上传域名（`config/ProductionConfigValidator.java:32-89`）。这几条恰好是历史上真出过事的地方（注释里点名「以前只看 AppID 是否为空，生产漏配时所有 code 都会解析成同一个 dev-1 账号」）。
5. **已泄露的演示口令按哈希拦截启动。** `ProductionDemoAccountGuard.java:27-32` 把仓库历史里出现过的 4 个 BCrypt 哈希列成黑名单，生产库里只要还有启用账号用它们就拒绝启动。按哈希而不是按用户名判断，真实运营账号只要换过密码就不受影响。
6. **限流存储故障 fail-closed。** `RateLimiter.java:52-57`：共享计数不可用时抛 503，除非显式打开 `rate-limit-fail-open`。注释写明「一次 Redis 抖动就等于所有限流形同虚设」。
7. **小程序 401/403 语义分得清。** 401 清登录态（真的没身份），403 只报错（已登录但无权，例如动别人的订单），`utils/api/core.js:74-77`。很多项目在这里一律清 token，导致用户被莫名踢下线。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **两套身份体系没有统一抽象。** 小程序用户走 `JwtUtil`+`AuthInterceptor`，管理端/商家/骑手走 `AdminJwtUtil`+`AdminInterceptor`，`AuthInterceptor` 用路径前缀把 `/api/admin|merchant|rider` 整段「委托」出去（`AuthInterceptor.java:130-135`）。这套委托判断只要有一条新路径没被三个拦截器之一覆盖，就是匿名可达。当前 `/api/admin/upload/private` 就是这么放的（`AdminInterceptor.java:30`）。
2. **用户令牌只有「过期」没有「撤销」。** 7 天 TTL（`JwtUtil.java:22-23`），唯一提前失效途径是注销账号（`UserStatusGuard`）。没有 jti 黑名单、没有用户级 token_version。手机丢失、token 被日志带出、换设备，都无法主动踢掉。
3. **登录限流把「客户端可控的头」当身份。** `AuthController.java:45-49` 取 `X-Forwarded-For` 首段做限流键。这个头由客户端随意设置，等于限流形同虚设；同时它也污染日志里的 IP 字段（`AdminAuthController.java:142-145` 同样取值）。
4. **管理端登录完全没有 IP 维度限流。** 只有「按账号 5 次锁定」（`AdminAuthService.java:21-22`）。密码喷洒（一个弱口令打 N 个账号，每账号只试 1-2 次）不受任何限制。
5. **密码策略只有长度。** 8-72 位，不校验复杂度、不校验常见弱口令、不校验与用户名相似（`AdminAuthController.java:77`、`AdminAuthService.java:73-76`）。`TemporaryPasswords` 这个 12 位随机生成器已经写好了，却只给商家/骑手用。
6. **没有服务端登出。** `AdminInterceptor.java:88` 把 `/api/admin/logout` 当成合法放行路径，但**这个接口不存在**；前端「退出」只清 localStorage（`web/src/stores/auth.js:49-53`）。共用电脑场景下，点了退出的人会以为会话结束了。
7. **`/api/auth/status` 公开泄露部署信息。** 匿名可查「是否开了 dev-login」「微信是否配好」（`AuthController.java:37-43`），给攻击者一个免费的探测口。

## 三、权衡过的替代方案

| 当前做法 | 替代方案 | 为什么当前更合适 | 代价 |
|---|---|---|---|
| 管理端每请求查一次 admin_user | 令牌内自带权限 + 短 TTL（15 分钟）+ refresh token | 后台 QPS 低，查库成本可忽略；换来「改权限立即生效」这种运营真正需要的能力 | 多一次主键查询；数据库故障时管理端直接不可用（有意为之） |
| 用户 token 7 天无刷新 | 双 token（access 15 分钟 + refresh 30 天） | 小程序冷启动体验优先，学生不能容忍频繁重登 | 无法主动吊销，泄露窗口 7 天 |
| 管理端与用户端共用 `campus.jwt.secret` 派生 | 两套完全独立的密钥配置项 | 少一个必须配的环境变量，降低部署漏配概率 | 密钥轮换必须同时换两端 |
| 路径前缀委托鉴权 | 每个控制器标注所需角色注解（`@RequiresRole`） | 拦截器方案改动集中、不侵入业务代码 | 新增路径容易漏，靠人记（已发生：private upload） |

## 五、如果重做会怎么改

1. **把「身份」抽象成一套**：`UserPrincipal`（id, type, role, schoolId, shopId, tokenVersion），三个拦截器只负责解析与装载，鉴权决策统一交给一个 `Authorizer`。现在的问题不是拦截器写得差，而是「谁该被谁拦」靠路径前缀字符串约定。
2. **所有安全相关的时间与 IP 都从服务端可信源取**：配置 `server.forward-headers-strategy` + 可信代理白名单，代码里不再手工解析 `X-Forwarded-For`（当前有 4 处重复实现：`AuthController.java:45-49`、`AdminAuthController.java:142-145`、`AdminModuleController.java:467-470`、`ClientErrorController.java:59-63`）。
3. **用户令牌加 `token_version`**，与 `admin_user` 对齐。已有 `AdminTokenGuard` 的成熟实现，复制到用户侧的成本远低于未来被冒用一次的成本。
4. **把限流做成横切能力**：注解 `@RateLimited(scene, keyExpr)`，而不是每个 controller 自己拼 key。当前 4 个场景（登录/发布/AI/上传）散落在各处，新增接口极易漏掉。
5. **生产配置闸门加一条**：`utils/config.js` 的 `PRODUCTION_ORIGIN` 必须与后端 `CAMPUS_WEB_ORIGINS`/`CAMPUS_UPLOAD_BASE_URL` 同域校验，纳入 `tools/check-all.js` 的发布前门禁（现在只是运行时阻塞，能上线一个「点了就报错」的包）。

## 六、本章不覆盖、但与本章强耦合的三处

写这份文档时必须划清边界，否则「登录鉴权」会被当成万能背锅位：

| 事项 | 为什么不在本章 | 在哪一份 |
|---|---|---|
| `/api/admin/upload/private` 匿名放行 | 属文件边界，不是身份边界；拦截器放行是**有意**为商家入驻开的 | `19-个人中心与账号安全/` 19-02 |
| 校管能看到全平台数据 | 属多校隔离（第 3 层记录归属校验），不是登录能管的 | `02-多校隔离与权限/` |
| 退款/导出等后台高危动作无审计 | 属运营审计能力，登录只管「谁能进来」 | `28-管理后台与运营/` 28-01、28-02 |

**反过来说**：02 的 7 条跨校越权、19 的私有文件直链、28 的审计缺失，三者都建立在「登录鉴权已可信」这个前提上。本章的 01-01（发布版域名占位）是这三者的前置——**登录发不出去，后面所有权限设计都无从验证**。
