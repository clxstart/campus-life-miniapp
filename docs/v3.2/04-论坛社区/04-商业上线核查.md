## 一、合规与隐私

**结论：不通过（原因：内容安全在缺参时静默放行，且举报入口覆盖不全）。**

| 核查点 | 结论 | 证据 |
|---|---|---|
| 用户内容是否有审核 | ❌ 形式上有，实际可能完全不生效 | `AuditService.java:180-186`（缺 appid/secret 或 `dev-` openid → `pass`）、`:204-207`（异常 → `pass`）、`:317-321`（图片异常 → `pass`） |
| 审核是否留痕 | ⚠️ 留痕但可失真 | `AuditService.java:213-215` 在没调微信的情况下也写 `source=wechat/result=pass` |
| 用户能否举报 | ⚠️ 能，但只有帖子 | `pages/post-detail/post-detail.js:172` 固定 `targetType='post'`；评论无举报入口 |
| 举报是否有回执 | ❌ 无 | `ContentReportService.java:60-62` 只返回 `{reported:true}`，处理结果不回推 |
| 隐私政策 / 用户协议 | 本功能不采集新个人信息；发布内容会公开昵称与头像 | `ForumService.java:120`（`authorNickname`/`authorAvatar` 随列表返回） |
| 未成年人保护 | ❌ 无年龄门槛、无未成年人内容分级 | 全仓库 `post` 表无相关字段（`db/module-audit.sql:8` 仅审核三列） |
| 被下架内容是否真的不可见 | ✅ 列表与详情都要求 `status=1` | `ForumService.java:12,124` |

**上线级判断**：微信小程序审核会验"用户可举报 + 平台可处置"，这两项代码都在；但"审核真的在跑"这件事在 dev 环境是假的（台账 `04-证据与复核台账.md:77` 已登记为未验证项）。**这一维不签字，论坛不能对外。**

## 二、资金与对账

**结论：不涉及。**

依据：
- `ForumController` 16 条映射中没有任何金额入参或出参（`ForumController.java:21-174`），`CreatePostRequest`/`CommentRequest` 无金额字段（`ForumService.java:132-166` 只读 `title/content/image/tag/learnCategory/schoolId/crossSchool/location/circleId`）。

| 管理端鉴权 | ✅ `/api/admin/**` 由拦截器强制校验 token + 角色 + 令牌版本 | `config/AdminInterceptor.java:36-70` |

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：三个 SQL 必须先跑且顺序正确；回滚需要人工 SQL，无工具）。**

### 4.1 必须按序执行的 SQL

```sql
-- 1) 先建审核列（post/comment/goods/job/chat_message/circle 六张表 + 索引 + 词表 + 审核日志）
SOURCE backend/src/main/resources/db/module-audit.sql;
-- 2) 评论点赞明细表 + comment.like_count
SOURCE backend/src/main/resources/db/module-comment-like.sql;
```

- 均为幂等脚本（`information_schema` 判存在后再 ALTER，`module-audit.sql:6-9`、`module-comment-like.sql:14-17`），可重复执行。
- **顺序不可颠倒**：`module-comment-like.sql:14-17` 依赖 `comment` 表存在；`module-audit.sql` 的 `audit_status` 列必须早于首次发帖，否则新内容会落到默认 `pending`（`module-audit.sql:8`），而审核台看不到 `pending`（04-04）。
- 第一次跑 `module-audit.sql` 时会把历史行从 `pending` 提为 `passed`（`module-audit.sql:10,17`）；**重复跑不会重提**，这是正确的幂等设计。

### 4.2 与圈子/发布页 SQL 的关系

- `module-circles.sql`（`post.circle_id` 列 + 索引）：发帖带 `circleId` 时需要，否则 `postMapper.insert` 会因未知列失败。必须早于论坛上线（`db/module-circles.sql:38-50`）。
- `module-publish.sql`：与论坛帖无关，属发布页另外三种类型（`module-publish.sql:8-48`）。
- `module-hotness.sql`：属首页推荐/二手/外卖热度，不参与论坛排序（`module-hotness.sql:4-57`）。

### 4.3 回滚

```sql
-- 回滚一次误审（把误判 rejected 的帖子放回）
UPDATE post SET audit_status='passed', status=1, audit_reason=NULL, audit_at=NOW()
WHERE id = ? AND audit_status='rejected';

-- 回滚一次被异步图片审核误下架的帖子
UPDATE post SET audit_status='passed', status=1, audit_reason=NULL
WHERE id = ? AND audit_status='rejected' AND audit_reason LIKE '%图片%';

-- 结构回滚（谨慎：会丢审核状态，仅回滚整版时用）
ALTER TABLE post DROP INDEX idx_post_audit_status, DROP COLUMN audit_status,
  DROP COLUMN audit_reason, DROP COLUMN audit_at;
ALTER TABLE `comment` DROP INDEX idx_comment_audit_status, DROP COLUMN audit_status,
  DROP COLUMN audit_reason, DROP COLUMN audit_at;
```

**回滚的现实约束**：`audit_log` 没有"批量撤销"能力，`Restore` 只能一条一条点（`AuditService.java:441-446`）。如果一次误操作批量拒绝了 200 条，回滚需要 200 次点击或 1 次手写 SQL。**没有回滚工具 = 上线后第一次误操作就会变成数据事故。**

## 六、可观测与告警（日志、指标、错误上报、告警渠道）

**结论：不通过（原因：审核"是否真的执行"完全不可观测，没有指标也没有告警）。**

| 核查点 | 结论 | 证据 |
|---|---|---|
| 审核跳过是否有日志 | ⚠️ 有 `log.warn`，但没有计数指标 | `AuditService.java:184,264,298,318` |
| 审核跳过是否会被运营看到 | ❌ 不会。管理端首页与审核台都不展示"跳过次数" | `AuditService.java:398-402`（stats 只有 today/reviewing/rejected/words/blocked） |
| 是否存在"假装已审"的日志 | ❌ 存在 | `AuditService.java:213-215` |
| 审核队列积压是否有告警 | ❌ 无。只有 `reviewing` 计数，无阈值告警 | `AuditMapper.java:89-94` |
| 微信 token 获取失败是否有告警 | ❌ 只抛异常被上层吞掉（`checkText` 的 catch） | `AuditService.java:350-358` → `:204-207` |

## 七、失败与降级（依赖挂了会怎样）

**结论：不通过（原因：五条依赖失败路径全部指向"内容照常上线"，且没有一条会通知运营）。**

| 依赖 | 挂了会怎样 | 证据 | 可接受吗 |
|---|---|---|---|
| 微信 `appid/secret` 未配 | 内容照发，只有本地词库在拦，日志写 `wechat/pass` | `AuditService.java:180-182,213-215` | ❌ |
| 微信 `msg_sec_check` 超时/5xx | 捕获后放行 | `AuditService.java:204-207` | ❌ |
| 微信 `access_token` 拿不到 | 同上（异常被同一 catch 吞掉） | `AuditService.java:350-358` | ❌ |
| 微信 `img_sec_check` 挂了 | 图片直接通过 | `AuditService.java:317-321` | ❌ |
| 审核线程池队列满 | 图片直接通过 | `AuditService.java:260-267` | ❌ |
| 敏感词表读不到 | 用内置 23 个兜底词（`FALLBACK_WORDS`），不阻断发帖 | `AuditService.java:89-105` | ⚠️ 可接受（有兜底） |
| 敏感词引擎自身抛异常 | `match()` 返回空 → 视为未命中 → 放行 | `SensitiveWordEngine.java:90-93,116-118` | ❌ |
| 数据库挂了 | 帖子列表 500；发帖 500 | 无降级设计 | ⚠️ 常规 |
| Redis/限流计数挂了 | fail-closed，发帖返回 503 | `RateLimiter.java:52-57` | ✅ 方向正确 |

**方向性建议**：限流用了 fail-closed（`RateLimiter.java:52-57`，注释写"绝不静默退回进程内计数"），审核却用了 fail-open。同一仓库两种相反的取舍，**说明审核的 fail-open 不是深思熟虑的决策，而是顺手写的**。上线前把审核改成"失败即待审 + 告警"，代价是用户在微信抖动时看到"内容待审核"，收益是不会出现"以为在审其实没审"。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

**结论：有条件通过（条件：止血开关能关"发帖"，关不掉"已发内容"；数据回退需手写 SQL）。**

| 能力 | 有没有 | 证据 |

## 九、结论

**不可上线。**

阻断项：

| 编号 | 等级 | 一句话 |
|---|---|---|
| 04-01 | P0 | 缺 appid/secret 或 `dev-` openid 时，内容安全静默放行，且日志写成已审 |
| 04-02 | P1 | 微信异常时捕获后放行 |
| 04-03 | P1 | 假审核日志让事后追责失去基准 |
| 04-04 | P1 | `pending` 内容无任何审核台入口，异常时永久不可见 |
| 04-05 | P1 | 黄金段位免审默认开启，存在合法的审核绕过通道 |
| 04-06 | P1 | 拉黑对评论/详情/群聊无效 |
| 04-08 | P1 | 发帖成功提示与真实审核状态不一致 |
| 04-14 | P1 | 跨校帖任何校管都无法处置 |

解除条件：04-01 与 04-03 必须合并修掉（同一处代码），04-04/04-05/04-14 必须在上线前完成，04-02/04-06/04-08 至少给出明确的运营 SOP 兜底（例如：上线期强制关闭免审、客服话术覆盖"评论审核中"）。
