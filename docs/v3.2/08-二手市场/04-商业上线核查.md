## 二、资金与对账

**结论：不涉及（依据：本功能全程不经手资金）。**

| 判断依据 | 证据 |
|---|---|
| 无支付接口调用 | 二手链路的全部接口在 `BizController.java:93-126` 与 `MarketTradeController.java:33-54`，无一处调用 `PayService` |
| 无金额字段落库结算 | `market_trade` 表 7 列全是 id/状态/时间，无金额（`module-market-trade-v31.sql:19-36`） |
| 无退款/结算代码 | 全仓 `PayService` / `RefundInitiationService` / `PaymentCompensationService` 无二手引用 |
| 商品价格只是展示字段 | `goods.price` 只被列表/详情读出展示（`ModuleMapper.java:18`），不参与任何扣款 |

**但需要记录一个间接的资金相似物**：成交会给双方发积分（5P/12G，日限 2 笔）。积分可兑换成券，券可抵扣外卖订单金额（见 06/07）。所以"刷二手成交"等价于"刷券"，等价于"平台补贴"。当前三层防刷（一件商品一笔、7 天同对、日限 2 笔）把单人日收益压到 10 分 ≈ 0.1 元，风险可接受；但**这套防护完全没有测试**（见 02-第六节）。

**结论：通过（脚本幂等、可重复执行）；回滚有条件通过。**

`module-market-trade-v31.sql` 头部注释写明"只对本地 dev 库执行、全部 `CREATE TABLE IF NOT EXISTS`、可重复执行"（`:8-9`）。

```sql

-- 收藏表属于热度域，不建议删（会丢真实热度）
```

## 九、结论

**有条件上线。**

先说清一件事：**"有条件的条件"不是修 bug，而是补齐 V3.1 承诺的交付**。二手市场的浏览/发布/私聊这条主链是可用且相对干净的（无 P0、越权全收口、审核双通道齐备）。真正的问题在于：

F10 成交确认这项能力，后端做完了（279 行 service + 4 个接口 + 一张表 + 三层防刷 + 事务后发分），**三端一个入口都没有**。`market_trade` 至今 0 行。这意味着：

- 如果对外宣称"二手成交已完成"——不成立；
- 如果按现状上线——用户能买卖，但平台不知道、也没法确认，`market_trade` 永远是空表，为它写的积分任务配置也是空转。

因此分两种口径给结论：

| 口径 | 结论 |
|---|---|
| **把二手市场作为"发布 + 浏览 + 私聊"的撮合功能上线** | 可上线（需先修 08-04 举报入口，0.5 人日） |
| **把二手市场作为含"成交确认"的功能上线（V3.1 设计口径）** | 不可上线（阻断 08-01、08-02） |

建议按第一种口径先上，同时并行补 08-01/08-02/08-03。

必须在上线前完成：

1. **08-04（P1）举报入口**：0.5 人日，后端已全部就绪，只差一个按钮。违规商品无举报入口，在校园场景会直接引发投诉。
2. **08-01（P1）成交确认三端补齐**：如果这一版要宣称成交能力，必须补；不补就要在对外材料里把"成交确认"从已完成清单里拿掉。
3. **08-02（P1）成交撤销**：与 08-01 同批交付，否则第一笔误点确认就会产生一个永久死掉的商品。
4. **08-03（P1）收藏读路径**：1.5 人日。收藏了看不到，是"功能存在但无效"的典型，用户会反复收藏同一件东西。

P2 六项可上线后迭代，其中 08-05（已售商品 404）建议跟着 08-01 一起修，因为成交一旦可用，这个 404 会立刻变高频。
