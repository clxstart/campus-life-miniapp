## 一、设计优点（为什么这么设计，好在哪）

### 1. 一件商品只允许一笔成交，用唯一键把"重复成交"变成数据库层面的不可能

`market_trade` 上有 `UNIQUE KEY uk_trade_goods (goods_id)`（`backend/src/main/resources/db/module-market-trade-v31.sql:31`）。这一个约束同时解决了三件事：一件商品不会被两个买家同时"买走"、卖家不能对同一件商品重复发分、历史成交可追溯。很多 C2C 系统在这一层靠应用逻辑判断，本仓库直接用数据库兜住。

### 2. "被取消后还能再发起"用复用同一行解决，而不是新插行

唯一键会挡住"被拒后再卖"这条产品规则。代码的处理是：`cancelled` 状态下 `UPDATE` 同一行、重置买家与时间（`backend/src/main/java/com/campuslife/mapper/MarketTradeMapper.java:51-58`），并注释说明并发下只有一条 UPDATE 能命中。这比"删掉旧记录"或"给唯一键加 status"都更稳。

### 3. 发分与成交解耦，且放在事务提交之后

`awardBothAfterCommit` 用 `TransactionSynchronization.afterCommit()` + `REQUIRES_NEW`（`backend/src/main/java/com/campuslife/service/MarketTradeService.java:194-214`）。积分服务挂了不会把"成交成功、商品已售"回滚掉。对"主流程不能被激励系统拖累"这个判断是对的。

### 4. 三层防互刷，且每层解决不同问题

| 层 | 拦什么 | 证据 |
|---|---|---|
| `uk_trade_goods` | 一件商品反复成交 | `module-market-trade-v31.sql:31` |
| `countRecentPair` 7 天 | 同一对用户来回刷 | `MarketTradeMapper.java:80-89` |
| 积分任务日限 2 笔 | 多开小号刷 | `MarketTradeService.java:36-37` |

三层叠加后，单人每天能刷到的积分上限被压到 10 分（2 笔 × 5P），成本大于收益。

### 5. 视觉设计上刻意不引入"担保交易"

不碰钱意味着不需要商户号、不需要对账、不需要退款、不需要资金合规。对于校园闲置这种"当面看货当面付"的场景，这是正确的取舍——它把一个需要金融资质的重系统降级成撮合系统。

### 6. 发布侧防脏数据做得细

图片必须是服务端可访问地址，`wxfile://tmp_xxx` 与 `http://tmp/xxx` 被显式识别并拒绝（`BizService.java:151-159`）。这是微信小程序最典型的坑（本地临时路径存进库后图片永远打不开），代码里连注释都写了原因。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 1. 后端比前端超前了整整一个版本

F10 的 279 行 service、4 个接口、1 张表、三层防刷、事务后发分——全部就绪。而小程序端连一个按钮都没有，API 封装写好放在 `utils/api/points.js:213-233` 却无人调用。这是一个"只做了一半、而且是用户看不到的那一半"的功能。代价：`market_trade` 至今 0 行，所有为它写的代码、表、索引、积分任务配置都是纯负债。

### 2. 成交是终态，没有回路

`confirmed` 之后：不能取消（`MarketTradeService.java:166`）、不能再发起（`:75`）、商品 `status=2` 且 `selectGood` 只查 `status=1`。若卖家误点确认，或买家口头答应后反悔，这件商品就永久废了。系统里**没有任何一条路径**能让它重新可售——因为 `uk_trade_goods` 只允许一行，而那一行是 `confirmed`。这不是"设计取舍"，是缺一个 `confirm → cancelled` 的纠错边。

### 3. 收藏有两套存储、却没有一条读路径

服务端有 `goods_favorite` 表、有 `addGoodsFavorite` / `removeGoodsFavorite` / `syncGoodsFavorite`，红心状态的来源却是本地 `wx.getStorageSync('goods_favorites')`（`utils/api/market.js:119-121`）。而"我的收藏"页面读的是 `GET /api/users/{id}/favorites`，那个接口只返回**帖子**收藏（`UserService.java:43-45` 查 `favorite` 表的 `post_id`）。结果：用户的收藏写进了数据库，但他自己永远看不到。

### 4. Web 端把"已售出"当成"已下架"

`Business.vue:312-324` 只判断 `status===1`。`status=2`（已售出）落到 else 分支显示"已下架"，并且「上架」按钮会把它改回 1。于是运营点一下就能制造一件"列表里能看到、但谁买都会被告知已有成交记录"的商品。

### 5. 举报入口缺席

后端 `ContentReportService` 明确支持 `targetType` 含 `goods`（`backend/src/main/java/com/campuslife/service/ContentReportService.java:29`），小程序也有 `api.reportContent()`（`utils/api.js:177-178`），但**只有帖子详情页在用**（`pages/post-detail/post-detail.js:146-172`）。二手商品详情页没有任何举报入口。结果是：违规二手商品只能等审核/运营发现，用户参与不了治理。

### 6. 商品一旦发布就不能改

用户侧只有 `POST /api/goods`（发）与 `DELETE /api/goods/{id}`（删），没有 `PUT`。想改价格只能删了重发——重发会丢浏览数、收藏数、咨询数，也会丢掉已有的 `market_trade` 关联（物理删除，`market_trade` 无外键）。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 方案 | 做法 | 为什么本仓库没选（从代码能看出取舍） |
|---|---|---|
| 引入担保交易 | 买家付款到平台，确认收货再打给卖家 | 需要支付资质、资金存管、对账系统；校园闲置客单价低、面交率高，投入产出不成立。代码注释直接写明"只做确认，不涉及资金"（`MarketTradeService.java:29`） |
| 成交记录每件商品多行（流水式） | `market_trade` 不设唯一键，保留全部历史 | 会引入"哪一条是当前有效"的判断；当前用"一行 + 复用"更简单，代价是没有历史可查 |
| 取消成交也发分 | 让卖家有动力点"没有成交" | 会被刷。现在只有 confirmed 发分，正确 |
| 收藏状态从服务端读 | 详情接口返回 `favored` 字段 | 未做。推测原因（未验证）：详情接口是公开的，加 `favored` 需要带用户身份，作者选择了前端本地缓存省事 |
| 商品软删除 | `status=3` 或 `deleted_at` | 未做。物理删除导致 `market_trade` 可能指向不存在的商品（虽然 `LEFT JOIN` 不会报错，但成交记录会变成孤儿数据） |
| 已售商品仍允许看详情 | 详情查询放宽到 `status IN (1,2)` 并显示"已售出" | 未做。当前 404 让"我的收藏里点进去"直接变错误页 |

### 4.1 为什么 P0 是 0 条

按 README 第六节的 P0 定义（资金损失 / 数据泄露 / 越权 / 合规不通过 / 主链路不可用），本功能逐条对照：

- **资金**：二手全程不经手钱（`MarketTradeService.java:29` 注释明确"不涉及资金：没有担保交易、没有线上支付、没有评价"），没有支付、退款、结算代码，因此不存在资金类 P0。
- **数据泄露**：详情接口只透出 `sellerId` 与 `sellerNickname`（`ModuleMapper.java:66`），无手机号、无学号、无地址；成交接口全部要求登录且校验买卖双方身份（`MarketTradeController.java:56-60`）。跨校可读是产品设定（`schoolScope=all`），不是越权。
- **越权**：`POST /api/goods` 的 `userId` 被 token 覆盖；`DELETE` 与成交三接口都以 token 为准。08-10 的 `1L` 兜底只在 `enforce=false` 时可达，因此定 P2 而非 P0。
- **合规**：无支付资质要求（不经手钱），但内容治理缺举报入口（已列 08-04 P1）。
- **主链路不可用**：列表/详情/发布/删除全部可用。

结论：本功能没有 P0，但"成交确认"这个 V3.1 主打能力**实际上等于没交付**，因此不适合作为"已完成功能"上报。

## 五、如果重做会怎么改

1. **前后端同一次提交**。凡是"后端有接口、前端无入口"的功能，验收时应该判为未完成。可以用一条静态检查（扩展 `tools/check-api.js`）断言"每个写接口至少被一个页面调用"，这类"代码先行、界面滞后"的负债就不会积累。
2. **状态机的每个终态都要有纠错边**。`confirmed` 没有反向边，是 08-02 的根因。规则可以是"终态必须有一个人工可触发的回退动作，并留审计日志"。
3. **一件商品允许多条成交历史，但只有一条有效**。把 `uk_trade_goods` 换成 `(goods_id, active)` 或给 `market_trade` 加 `superseded_by`，既保住唯一性，又留下可追溯的重新上架历史。
4. **收藏这种"只增不减、用户预期能看回来"的数据，读路径必须跟写路径一起交付**。
5. **内容治理入口按"内容类型"统一铺开**，而不是只在帖子详情页做。`ContentReportService` 已支持 5 种 targetType，前端只接了 1 种。
6. **二手详情页对已售出/已下架商品给"状态页"而非 404**。404 对用户是"东西没了"，状态页是"东西卖掉了"，信息量完全不同。
