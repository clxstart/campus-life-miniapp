## 一、设计优点（为什么这么设计，好在哪）

1. **SQL 注入这条红线守住了，而且是干净的守。** 7 个查询全部 `#{like}` 参数绑定，没有一处 `${}` 拼接（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:16-107`），文件头还专门写了"所有关键词均为参数绑定，不做字符串拼接"（`:8`）。用户传 `' OR 1=1--` 只会被当成字面量去 LIKE。这一条是本功能最值得肯定的地方——很多同类项目在这里翻车。

2. **一次请求给出全部分类计数，tab 上的数字不用二次请求。** `counts()` 用一条 SQL 完成 6 类计数（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:14-24`）。用户不用点进每个 tab 才知道哪类有结果，这直接决定了多域搜索的可用性。

3. **混排的类间顺序有产品主张。** 固定 `post → circle → goods → activity → job → food`，代码注释写明"先内容后服务"（`backend/src/main/java/com/campuslife/service/SearchService.java:82-83`）。比按命中数纯机械排序更符合校园场景的心智——用户先想看同校同学说了什么，再看能买什么。

4. **单类分页是真分页，不是假无限滚动。** `LIMIT/OFFSET` + 后端返回 `total`，前端用 `merged.length < total` 判断是否还有下一页（`pages/search/search.js:165`），并且请求带 `_seq` 防竞态（`:145,152`）。快速切 tab 不会被旧响应覆盖。

5. **空态与错误态都做了，文案是人话。** `没有找到相关内容，试试其他关键词吧`（`pages/search/search.wxml:30`）、错误时给"重新加载"（`:54`）。对比很多页面在无结果时给一片空白，这里合格。

6. **离线兜底复用同一套匹配语义。** `localSearchAll()` 用 `keywordMatcher` 在前端 mock 数据上重放分类逻辑（`utils/api.js:106-136`），且数据源切换时会重置列表避免真假混排（`pages/search/search.js:154-155`）。降级路径是设计过的，不是随手写的。

7. **URL 参数解码做了失败兜底。** `safeDecode` 解码失败退回原串而不崩（`pages/search/search.js:8-16`），注释还解释了为什么页面内输入的关键词不走这条路（`:116-117`）。

8. **活动/兼职没有详情页就老实回列表页，不假装。** `pages/search/search.js:58,65` 直接给列表页 URL，注释也写明原因（`:180`）。没有为了让每条结果都能点而造一个假详情页。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 "把 status 当关键词搜"——一个字段两个用途的典型事故

兼职的查询条件是：

```sql
WHERE title LIKE #{like} OR location LIKE #{like} OR status LIKE #{like}
```

（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:79`）

而 `job.status` 是中文文本 `VARCHAR(8) DEFAULT '招聘中'`（`backend/src/main/resources/db/module-market-jobs-activities.sql:38`）。这意味着：

- 搜"招聘"→ 命中所有正在招聘的岗位（用户以为搜的是岗位名）；
- 搜"日结"→ 如果 status 值恰好是这两个字，也会命中；
- **搜任何词都没有排除已关闭岗位**，因为根本没有 `status` 过滤条件，只有 `LIKE`。

更糟的是新兼职体系已经把生命周期迁到 `workflow_status` 英文枚举上了（`open|taken|recruiting|working|pending_confirm|settled|disputed|refunded|cancelled`，`backend/src/main/resources/db/module-jobs-marketplace.sql:95`），而搜索还在看旧字段。所以一个已经 `cancelled` 的岗位，只要标题里有关键词，就照样出现在搜索结果里，且卡片上不显示状态（`pages/search/search.js:61-67` 的 `meta` 只拼日薪与结算方式）。

### 2.2 外卖店铺不过滤 `status`，下架店铺可被搜到并点进点餐页

`shop` 表有 `status TINYINT NOT NULL DEFAULT 1`（`backend/src/main/resources/db/module-food.sql:4-7`），但搜索查询是：

```sql
WHERE s.name LIKE #{like} OR s.category LIKE #{like} OR s.notice LIKE #{like}
```

（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:90`）

没有 `s.status = 1`。而搜索结果里店铺卡片点进去是点餐页（`pages/search/search.js:73`）。后果：商家被停用后，用户在搜索里仍能看到它、点进去、看到菜单、尝试下单，直到下单环节才失败。

### 2.3 8 次全表扫 + 匿名可调 + 无限流

一次 `/api/search/all` 请求的实际 SQL 数量：

| 查询 | 次数 | 形态 | 证据 |
|---|---|---|---|
| `counts()` | 1 | 一条 SQL 含 6 个相关子查询 | `SearchMapper.java:14-24` |
| 各类 list | 混排 6 次 / 单类 1 次 | 每个都是 `LIKE '%kw%'` | `SearchService.java:74`（单类）、`:88`（混排循环） |

即：混排一次 = 1 次 counts（内含 7 个全表 COUNT）+ 6 次分页查询 = **至少 13 次全表扫描**。而 `LIKE '%keyword%'` 是前置通配，**任何 B-Tree 索引都用不上**，全库也没有一个 FULLTEXT 索引（`grep -rn -i "fulltext" backend/src/main/resources/db/*.sql` 零命中）。

再叠加两个放大条件：

- 接口是公开 GET，**匿名可调**（不在 `PRIVATE_READ_PREFIXES`，`backend/src/main/java/com/campuslife/config/AuthInterceptor.java:76-86`）；
- **无限流**（`backend/src/main/java/com/campuslife/controller/ForumController.java:74-83` 未注入 `RateLimiter`，而同文件的发帖接口有 `limiter.acquire`，`:88`）。

一个脚本反复打这个接口，就能把数据库 CPU 打满。这是本功能最需要在上线前处理的一项。

### 2.4 `%` 和 `_` 被有意保留为通配符

`likePattern()` 对 `%` 与 `_` 不做转义（`backend/src/main/java/com/campuslife/service/SearchService.java:37-40`），只转其他字符。注释说这是为了"与前端 `keywordMatcher` 语义保持一致"（`:28-30`）。

代价：用户输入 `%` 得到 `LIKE '%%%'`，7 张表全命中；配合 2.3 的全表扫，一次请求就能生成一个"全表结果集"的分页统计。虽然单次结果被 `LIMIT` 限制，但 `counts()` 的 `COUNT(*)` 是**真的数全表**。

语义一致这件事本身是对的（前后端匹配规则不能不一致），但"一致性"应该靠在**两端都把通配符转义**来实现，而不是让用户输入的通配符生效。

### 2.5 "共 N 条结果"与可见内容不符

- 混排每类取 `per = Math.max(2, size/3)`（`backend/src/main/java/com/campuslife/service/SearchService.java:84`），`size=10` → 每类 3 条，7 类最多 21 条；
- `total` 是各类计数**之和**（`SearchService.java:95`）；
- `hasMore` 硬编码 `false`（`SearchService.java:96`）。

页面顶部写"共 137 条结果"（`pages/search/search.wxml:28`），列表只有 21 条，滑到底没有任何反应（`pages/search/search.js:165` 逻辑上就不可能加载）。用户的第一反应是"搜索漏了数据"。

### 2.6 零持久化：没有日志、没有热词、没有历史

`SearchMapper.java` 全文件只有 `@Select`，无一条写入；全库无搜索相关表（`grep -rn -i "search" backend/src/main/resources/db/*.sql` 零命中）；小程序端也没有 `wx.setStorage` 记录历史（`grep -n -i "history\|历史\|热门\|hot" pages/search/` 零命中）。

代价按商业价值排：

- **做不出热词**：不知道用户在搜什么，运营没有选品/选题依据；
- **做不出无结果分析**：不知道哪些词搜不到东西，无法发现内容缺口（比如"电瓶车充电"搜不到，说明缺这个需求）；
- **做不出历史**：用户每次都要重新输入，复访成本高；
- **做不出效果评估**：改了排序、加了内容，无法证明搜索质量变好。

### 2.7 跨校边界不存在

7 个查询全部无 `school_id`（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:16-22,26-107`）。多校 SaaS 下，A 校用户能搜到 B 校的二手商品（含卖家昵称，`:56`）、岗位、店铺，并可点进 B 校的外卖点餐页。

这是产品定位问题而非纯粹的技术缺陷：如果平台定位就是"一个城市的校园集市"，跨校是可接受的；如果卖给每个学校做独立 SaaS，这是跨租户内容混出，客户会当场提出来。当前代码没有能力在两者之间切换（无开关、无 `school_id` 条件）。

### 2.8 匿名访问的个性化标记一律按"用户 1"算

`SearchService.search()` 里 `Long uid = (userId == null || userId < 1) ? 1L : userId;`（`backend/src/main/java/com/campuslife/service/SearchService.java:55`），控制器侧也有 `Math.max(CurrentUser.resolve(request, userId), 1)`（`backend/src/main/java/com/campuslife/controller/ForumController.java:81`）。

后果：游客（或 token 失效的用户）看到的帖子里 `liked` 标记、活动里 `enrolledByMe` 标记、圈子里 `joined` 标记，全部等于"用户 1 的状态"。如果用户 1 点过赞，游客会看到一个已点赞的按钮图标。这是展示错误，不是数据泄露（不会暴露用户 1 的身份），但对个人中心与分享落地页的体验有影响。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 现方案 | 替代方案 | 为什么没选（从代码能看出的原因） | 本方案的真实代价 |
|---|---|---|---|
| `LIKE '%kw%'` 全表扫 | MySQL FULLTEXT 索引 + `MATCH ... AGAINST` | 全库零 FULLTEXT，也没写中文分词配置（`ngram` parser） | 13 次全表扫/请求，无法扩量 |
| 无学校过滤 | 给 7 个查询加 `school_id` 条件 | 未做，也没有开关 | 多校 SaaS 下跨租户混出 |
| 混排不可翻页 | 统一游标分页，混排也用 `beforeId` | 混排是"每类取 N 条拼接"，天然无法用单游标分页——架构上就没为混排翻页设计 | "共 N 条"与可见条数不符 |
| 无相关性排序 | 简单加权：标题命中 > 正文命中，前缀命中 > 中间命中 | 未做。当前是各表原生排序直接透出 | 搜"台灯"可能先看到只是正文提一句的帖子 |
| `%`/`_` 保留为通配符 | 两端都转义（`keywordMatcher` 也当字面量） | 选了"让用户输入生效"这条一致性方案 | 一次输入 `%` 就触发全表 COUNT |
| 无搜索日志 | 加 `search_log(keyword, user_id, hit_count, created_at)` | 未做，可能因"要加表、要排期" | 运营完全看不到搜索需求 |
| 匿名回落到用户 1 | 匿名时返回全 false 的个性化标记 | `CurrentUser.resolve` 的默认值就是 `1L`，沿用了这套约定 | 游客看到别人的已点赞状态 |
| 兼职搜 `status` 字段 | 只搜 `title`/`location`，用 `workflow_status` 过滤 | 未做。可能是为了"能按状态搜"，但实现成了 LIKE | 搜"招聘"命中全部岗位，且死岗位混入 |

## 五、如果重做会怎么改

按"漏了什么能力"排序，不谈抽象原则：

1. **先修两个"搜到死数据"的过滤缺失。** 兼职去掉 `status LIKE` 并加 `workflow_status` 白名单；店铺加 `s.status = 1`（`counts()` 内的 food 子查询同步改）。这两处是 0.7 人日就能做完、且用户立刻能感知的修复，优先级高于任何架构改造。

2. **加限流，把匿名全表扫的风险先摁住。** 复用已有 `RateLimiter`（同文件发帖接口就是这个写法，`backend/src/main/java/com/campuslife/controller/ForumController.java:89`），给 `/search/all` 加一个 `SEARCH` 档（如 30 次/分钟/IP）。0.5 人日。**不做这一步，2.3 节的性能问题会在任何一次小规模攻击下变成事故。**

3. **上全文索引，把 LIKE 全表扫换掉。** MySQL 8 的 `ngram` parser + FULLTEXT 索引，对中文可用；`MATCH ... AGAINST` 同时天然带相关度分数，可以一次解决 18-04 与 18-09。给 `post(title,content)`、`goods(title,description)`、`circle(name,description)`、`job(title,location)`、`shop(name,notice)`、`shop_goods(name)` 建索引。约 3 人日（含中文分词调优与回填）。

4. **把 `total` 与可见数对齐。** 混排要么实现真分页，要么把顶部文案改成"每类 Top3，点 tab 看全部"。后者 0.5 人日、零风险，建议先做。

5. **补搜索日志。** 建 `search_log`，写入关键词 + 分类 + 命中数（不存 userId 明文，存哈希更稳）。有了这张表，热词、无结果榜、搜索质量趋势才都成立。约 2 人日（含管理端一个只读页）。

6. **两端统一转义通配符。** `keywordMatcher` 与 `likePattern` 同时改成"用户输入一律按字面量"，保住语义一致这个设计初衷。约 0.5 人日。

7. **学校边界做成显式开关。** 若要卖多校 SaaS，加 `school_id` 过滤 + 一个"跨校搜索"开关；若定位单校集市，则在文档里写明"搜索是全局的"，避免每条缺陷都被当成 bug 报。约 2 人日。

8. **匿名个性化标记归零。** `uid` 匿名时传 `null`。约 0.3 人日。

合计约 11 人日。其中第 1、2 项（0.7 + 0.5）建议在下一个迭代内完成；第 3 项是量级门槛，用户数过千就必须做。
