## 一、这个功能解决什么问题

校园平台内容分散在 7 个业务域里（帖子、圈子、二手商品、活动、兼职、外卖店铺、外卖菜品）。用户的心智是"我知道有个东西叫什么，帮我找到它"，而不是"先选对业务域再浏览"。

搜索要解决的就是这一件事：**一个关键词，跨 7 个域一起找，并按域给出命中数让用户知道自己该去哪个 tab。**

代码把这个诉求实现成"一次请求返回各类计数 + 混排列表 + 单类分页列表"的形态（`backend/src/main/java/com/campuslife/service/SearchService.java:53-98`），共 7 个分类：`all / post / circle / goods / activity / job / food`（`SearchService.java:19`）。

**它不解决的问题**：不搜用户、不搜课程、不搜通知、不搜聊天记录。全站搜索只覆盖内容与商品。

## 二、用户看到的样子（小程序端）

### 2.1 入口（两处）

| 入口 | 行为 | 证据 |
|---|---|---|
| 首页搜索框提交 | 跳 `/pages/search/search?keyword=xxx`（不带类型，落"全部" tab） | `pages/index/index.js:144-148` |
| 圈子页搜索 | 跳 `/pages/search/search?keyword=xxx&type=circle`（直接落"圈子" tab） | `pages/discover/discover.js:208` |

页面已在 `app.json:39` 注册（`pages/search/search`）。

### 2.2 结果页结构

- 7 个 tab：`全部 / 帖子 / 圈子 / 闲置 / 活动 / 兼职 / 外卖`（`pages/search/search.js:19-27`）。
- 顶部结果说明：`“{keyword}” · 共 {total} 条结果`（`pages/search/search.wxml:28`）。
- 卡片形态按类型分流：圈子（成员数+帖子数）、闲置（价格+出售/求购+成色）、活动（时间+已报名）、兼职（日薪+结算方式）、外卖店铺（评分+月售+起送）、外卖菜品（来自哪家店+月售）、帖子（作者+时间+赞评数）（`pages/search/search.js:37-92`）。
- 点击跳转：圈子→圈子详情；闲置→商品详情；活动→活动列表页；兼职→兼职列表页；外卖→点餐页；帖子→帖子详情（`pages/search/search.js:43,51,58,65,73,81,90`）。
- 分页：单类 tab 支持 `onReachBottom` 加载更多；**"全部" tab 不翻页**（`pages/search/search.js:165` 的 `hasMore: type === 'all' ? false : ...`）。
- 空态：`没有找到相关内容，试试其他关键词吧`（`pages/search/search.wxml:30`）。
- 错误态：显示错误文案 + "重新加载"（`pages/search/search.wxml:54`）。
- 关键词上限 64 字，前后端各校验一次（`pages/search/search.js:131`、`backend/src/main/java/com/campuslife/service/SearchService.java:24`）。

### 2.3 离线兜底

后端不可用（网络错误，非 server 错误）时，前端用本地 mock 数据按同样的分类语义出一份结果，并标记 `offline: true`（`utils/api.js:100-104,106-136`）。页面在数据源切换时会重置列表，避免真实数据与演示数据混在一页（`pages/search/search.js:154-155`）。

## 三、运营看到的样子（Web 端）

**Web 端没有搜索页，也没有任何搜索相关的运营视图。**

核实方式：

```bash
ls web/src/views/ | grep -i search        # 无输出
grep -n -i "search" web/src/router/index.js   # 无业务路由命中
```

- `web/src/views/` 下 33 个顶层 `.vue`，无 `Search.vue` / `SearchManage.vue` 之类。
- `web/src/router/index.js` 的 41 条路由里没有搜索页面。
- 管理端有帖子/商品/兼职等各业务域自己的筛选列表，但**没有一个跨域关键词检索入口**。运营要查"某条违规内容在哪个域"，只能逐个域翻。

因此本功能的 Web 端状态是 ⚫（无对应页），不是"半实现"。

## 四、接口清单

小程序端（`backend/src/main/java/com/campuslife/controller/ForumController.java`，类级 `@RequestMapping("/api")`）：

| 方法 | 路径 | 权限 | 作用 | 证据 |
|---|---|---|---|---|
| GET | `/api/search/all` | 匿名可 | 全站搜索：`keyword` + `type` + `page` + `size`，返回 `counts`（各类命中数）、`list`、`total`、`hasMore` | `ForumController.java:74-83` |
| GET | `/api/search` | 匿名可 | 只搜帖子（**旧接口，保留给既有调用方**） | `ForumController.java:59-70` |

`/api/search/all` 的入参约束（`ForumController.java:78-82`）：

- `keyword` 必填、`trim` 后非空、≤64 字；
- `type` 默认 `all`，服务端再校验是否在 `TYPES` 里（`backend/src/main/java/com/campuslife/service/SearchService.java:57`），非法值抛 `不支持的搜索类型：X`；
- `page` 最小 1；`size` 被夹在 1..50（`ForumController.java:82`）；
- `userId` 默认 1，经 `CurrentUser.resolve` 取登录态优先（`ForumController.java:81`）。

**鉴权边界**：两个都是 GET 读接口，`/api/search` 不在 `AuthInterceptor.PRIVATE_READ_PREFIXES` 里（`backend/src/main/java/com/campuslife/config/AuthInterceptor.java:76-86` 只列了 conversations/notifications/timetable/pet/points/circle-messages），所以**匿名可调，且无限流**。

管理端：**无搜索接口**。

小程序 API 封装：`utils/api.js:94-137`（`searchAll` + `localSearchAll` 离线兜底）。

## 五、数据表与字段

**本功能没有自己的数据表。**

逐项核对：

| 期望的表 | 是否存在 | 证据 |
|---|---|---|
| 搜索日志表（记录关键词，供热搜/无结果分析） | ❌ 不存在 | `grep -rn -i "search" backend/src/main/resources/db/*.sql` **零命中** |
| 热词表 | ❌ 不存在 | 同上；`pages/search/` 里也无热词 UI（`grep -i "hot\|热门\|history\|历史"` 零命中） |
| 搜索历史（本地） | ❌ 不存在 | 同上，`pages/search/search.js` 无 `wx.setStorage` 调用 |

搜索是纯查询：`backend/src/main/java/com/campuslife/mapper/SearchMapper.java` 全文件只有 `@Select`，**没有一条 INSERT/UPDATE**。

### 5.1 被查询的 7 张表与字段

| 域 | 表 | 参与 LIKE 的字段 | 过滤条件 | 证据 |
|---|---|---|---|---|
| 帖子 | `post` | `title`、`content` | `status=1` | `SearchMapper.java:16,33` |
| 圈子 | `circle` | `name`、`description`、`category` | `status=1` | `SearchMapper.java:17,46` |
| 闲置 | `goods` | `title`、`description`、`category` | `status=1` | `SearchMapper.java:18,58` |
| 活动 | `campus_activity` | `title`、`location` | `status=1` | `SearchMapper.java:19,69` |
| 兼职 | `job` | `title`、`location`、**`status`** | **无** | `SearchMapper.java:20,79` |
| 外卖店铺 | `shop` | `name`、`category`、`notice` | **无** | `SearchMapper.java:21,90` |
| 外卖菜品 | `shop_goods` | `name`、`category` | `status=1` | `SearchMapper.java:22,102` |

> 两处"无过滤"是本功能最实际的问题来源，见第七节与 `03-优缺点与问题.md` 的 18-01、18-02。

### 5.2 与 `db/module-hotness.sql` 的关系

本轮任务把 `db/module-hotness.sql` 列为 18 的锚点。**读完后确认：该文件与搜索无关。**

该文件的全部内容是给二手商品与外卖店铺加行为计数（`view_count`/`favorite_count`/`contact_count`/`order_count`）、建 `goods_favorite` 表、加热度排序索引、回填初始热度（`backend/src/main/resources/db/module-hotness.sql:1-63`），服务对象是首页「今日推荐」的排序（`:2` 文件头注释），**不含任何搜索相关表、列或索引**。

因此正确的表述是：搜索**不需要新增表**，它没有任何持久化。真正与搜索性能相关的是索引，而当前**全库无一个 FULLTEXT 索引**（`grep -rn -i "fulltext" backend/src/main/resources/db/*.sql` 零命中）。

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 会拒绝的情况

| 条件 | 行为 | 证据 |
|---|---|---|
| `keyword` 为 null / 空串 / 全空格 | 抛 `请输入搜索关键词` | `backend/src/main/java/com/campuslife/service/SearchService.java:22` |
| `keyword` 超过 64 字 | 抛 `关键词不能超过64字` | `SearchService.java:24` |
| `type` 不在 7 个枚举内 | 抛 `不支持的搜索类型：{type}` | `SearchService.java:57` |

### 7.2 各 tab 的"排序"实际是什么

| tab | 排序 | 是否相关性排序 | 证据 |
|---|---|---|---|
| 帖子 | `created_at DESC, id DESC` | ❌ 纯时间倒序 | `SearchMapper.java:34` |
| 圈子 | `hot DESC, member_count DESC, sort` | ❌ 圈子自身热度 | `SearchMapper.java:47` |
| 闲置 | `created_at DESC, id DESC` | ❌ 纯时间倒序 | `SearchMapper.java:59` |
| 活动 | `id`（升序） | ❌ 就是插入顺序 | `SearchMapper.java:70` |
| 兼职 | `id`（升序） | ❌ 就是插入顺序 | `SearchMapper.java:80` |
| 外卖店铺 | `monthly_sales DESC, id` | ❌ 销量倒序 | `SearchMapper.java:91` |
| 外卖菜品 | `monthly_sales DESC, id` | ❌ 销量倒序 | `SearchMapper.java:103` |

结论：**没有一处按"标题命中优于正文命中""开头命中优于中间命中"排序**。搜"台灯"，标题叫《台灯》的帖子可能排在正文提了一句台灯的新帖子后面。

### 7.3 混排（`type=all`）的取数规则

- 每类取 `per = Math.max(2, size / 3)` 条（`backend/src/main/java/com/campuslife/service/SearchService.java:84`）。`size` 默认 10 → `per = 3`，即每类 3 条，7 类最多 21 条。
- 类间顺序固定：`post → circle → goods → activity → job → food`（`SearchService.java:85`），不按命中数多的类优先。
- `total` 是各类计数之和（`SearchService.java:95`），**不是列表长度**。
- `hasMore` 硬编码 `false`（`SearchService.java:96`）。

于是出现了这个用户可见的矛盾：**页面写"共 137 条结果"，但列表只有 21 条，且滑到底什么都不发生。**

### 7.4 关键词到 LIKE 模式：转义规则是"部分保留通配符"

`likePattern()`（`backend/src/main/java/com/campuslife/service/SearchService.java:31-46`）：

- `%` → 原样保留为 `%`（`:37-38`）
- `_` → 原样保留为 `_`（`:39-40`）
- `\` + 下一字符 → 转义下一字符（`:35-36`）
- 其他字符（含单引号）→ 按字面处理（`:42`、`:48-51`）

注释说明这是刻意为之，目的是"与前端 keywordMatcher 语义保持一致"（`SearchService.java:28-30`）。代价：用户输入 `%` 会变成 `LIKE '%%%'`，在 7 张表上全命中全表扫。

### 7.5 SQL 注入

**无风险，依据明确**：全部 7 个查询都用 `#{like}` 参数绑定（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:8` 注释 + `:16-107` 逐条确认无 `${}` 拼接）。关键词里的单引号由 MyBatis `PreparedStatement` 处理，不进入 SQL 文本。`SearchService.java:30` 也明确写了这一点。

### 7.6 补偿边界

**没有补偿。** 无搜索日志、无失败重试队列、无缓存。搜索失败就是失败，前端仅展示错误态 + "重新加载"（`pages/search/search.wxml:54`）。

### 7.7 跨校边界

7 个查询**全部没有 `school_id` 条件**（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java:16-22,26-107` 逐条确认）。也就是说：

- 内蒙古大学的学生搜"台灯"，会看到其他学校学生发布的二手商品（含卖家昵称，`:56`）；
- 搜"兼职"，会看到所有学校的岗位；
- 搜"外卖"，会看到所有学校的店铺并可直接进入点餐页（`pages/search/search.js:73`）。

这在单校部署下不是问题，在多校 SaaS 下是跨租户内容混出。产品定位需确认，见 `03-优缺点与问题.md` 的 18-03。
