## 二、资金与对账

**结论：不涉及。** 依据：

- 搜索无任何写操作（`backend/src/main/java/com/campuslife/mapper/SearchMapper.java` 全文件只有 `@Select`）。

### 4.2 与任务锚点 `module-hotness.sql` 的关系（必须澄清）

本轮任务把 `db/module-hotness.sql` 列为 18 的锚点。**该文件与搜索无关**，它是给首页「今日推荐」加行为热度的（`backend/src/main/resources/db/module-hotness.sql:1-2` 文件头注释）：

| 内容 | 行 | 服务对象 |
|---|---|---|
| `goods` 加 `view_count`/`favorite_count`/`contact_count` | `:5-19` | 首页推荐排序 |
| `shop` 加 `order_count`/`view_count` | `:22-31` | 首页推荐排序 |
| 建 `goods_favorite` 表 | `:34-42` | 商品收藏（跨用户累计） |
| 加 `idx_goods_hot(status, view_count, favorite_count, contact_count)` | `:44-47` | 首页推荐排序 |
| 回填初始热度 | `:51-58` | 冷启动 |

**没有一行与搜索的查询条件、排序、索引相关。** 所以正确表述是：搜索零持久化，不需要迁移；但若要做第 3 节之外的性能改进（全文索引），需要**新增**迁移脚本（当前不存在）。

### 4.3 若要做全文索引（建议项，非上线前置）

```sql
-- MySQL 8.0+，中文需 ngram parser（默认 ngram_token_size=2）
ALTER TABLE post     ADD FULLTEXT INDEX ft_post_title_content (title, content) WITH PARSER ngram;
ALTER TABLE goods    ADD FULLTEXT INDEX ft_goods_title_desc (title, description) WITH PARSER ngram;
ALTER TABLE circle   ADD FULLTEXT INDEX ft_circle_name_desc (name, description) WITH PARSER ngram;
ALTER TABLE job      ADD FULLTEXT INDEX ft_job_title_location (title, location) WITH PARSER ngram;
ALTER TABLE shop     ADD FULLTEXT INDEX ft_shop_name_notice (name, notice) WITH PARSER ngram;
ALTER TABLE shop_goods ADD FULLTEXT INDEX ft_shop_goods_name (name) WITH PARSER ngram;
```

- 这是一次大表 DDL，需在低峰执行，且要确认 `innodb_ft_min_token_size` / `ngram_token_size` 配置。
- 回滚：`ALTER TABLE post DROP INDEX ft_post_title_content;` 等逐个删除。
- **未实跑**，标注为建议方案。

## 五、性能与容量

**结论：不通过。** 原因：单次搜索 ≥13 次全表扫、无索引可用、无缓存、无限流、匿名可调。

| 检查项 | 结论 | 证据 |
|---|---|---|
| 是否可走索引 | ❌ `LIKE '%kw%'` 前置通配，B-Tree 完全失效；全库零 FULLTEXT | `backend/src/main/java/com/campuslife/mapper/SearchMapper.java:16-107`；`grep -i fulltext` 零命中 |
| 单次请求 SQL 数 | ❌ 混排 = 1 次 counts（含 7 个全表 COUNT）+ 6 次分页 = **≥13 次全表扫描** | `SearchService.java:62,88`；`SearchMapper.java:14-24` |
| 深翻页 | 🟠 `LIMIT/OFFSET`，页码越大越慢 | `SearchService.java:59`；`SearchMapper.java:35` |
| 缓存 | ❌ 无 | `SearchService.java:1-15`（依赖只有 `SearchMapper`） |
| 限流 | ❌ 无。同文件发帖接口有 `limiter.acquire`，搜索没有 | `ForumController.java:74-83` vs `:88` |
| 匿名放大 | ❌ 未登录即可调，无成本 | `AuthInterceptor.java:76-86` |
| 压测 | ❌ 未执行 | `docs/v3.2/04-证据与复核台账.md` 第四节第 8 项 |

**粗算最坏情况**：一个脚本以 20 QPS 打 `/api/search/all?type=all`，等价于 260 次全表扫/秒。假设 6 张表各 5 万行，就是每秒扫过 780 万行——单机 MySQL 会在几十秒内 CPU 打满，**连带拖垮整个小程序**。

这是本功能唯一可能造成"全站不可用"的缺陷，因此即使没有 P0，也必须在上线前处理。

**容量上限判断**：内容量在万级以下时，全表扫的绝对耗时还能忍（单次几十到几百毫秒）；超过十万行必须换全文索引或独立搜索服务。

## 九、结论

**有条件上线。**

条件（必须在首次对外放量前完成）：

1. **18-04 加限流** —— 复用 `RateLimiter` 给 `/api/search/all` 加档（0.5 人日）。不做则存在"匿名脚本打满 DB → 全站不可用"的路径。
2. **18-01 修兼职过滤** —— 去掉 `status LIKE`，按 `workflow_status` 过滤（0.5 人日）。
3. **18-02 修店铺过滤** —— 加 `s.status = 1`，`counts()` 内同步（0.2 人日）。
4. **跨校边界需产品签字** —— 明确"搜索是全局的"是特性还是缺陷（0 人日，一次决策）。

不阻断上线但应在下个迭代处理的：18-06（"共 N 条"与可见数不符）、18-05（`%` 通配符）、18-08（匿名按用户 1 算）。

**为什么不是"可上线"**：第 1 条不做，搜索就是全站唯一的无成本 DoS 入口；第 2、3 条不做，用户会搜到已下架岗位与已关闭店铺，直接构成功能错误。

**为什么不是"不可上线"**：没有 P0。搜索无写入、无资金、无私有数据、注入已排除，最坏情况是"搜到不该有的内容"或"搜索变慢"，不会造成数据泄露或资金损失。
