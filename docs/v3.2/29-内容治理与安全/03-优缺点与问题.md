## 一、设计优点（为什么这么设计，好在哪）

1. **敏感词引擎换了，但换的理由被写在代码里。** 从 houbb 换到 ToolGood.Words 的注释逐条列了差异（`SensitiveWordEngine.java:18-27`），pom 里还留着"旧依赖已移除、属死依赖、拖着三个传递依赖"的说明（`backend/pom.xml:86-93`）。这种"为什么换、换完去掉了什么"的记录，是六个月后没人敢动这套代码的主要原因之一。

2. **白名单按"出现位置"判断，不是按整词相等。** ToolGood 自带的 `wordAllow` 只能整词剔除，管不了"违规词是白名单词子串"——词表有「押金」，白名单有「押金退还」，后者照样被判违规。`isCoveredByAllowWord` 补了一层：命中词在文本里的**每一处**都被某个白名单词包住才放行（`AuditService.java:118-162`）。所以「押金退还」放行、「先交押金」仍拦。这个细节比市面上大量"整词白名单"实现精确一档。

3. **拒绝也要留痕，且用独立事务。** 被拦下的内容还没入库、没有 `target_id`，按常规做法这条记录会跟着业务异常一起回滚，结果"拦了但没证据"。`rejectWithLog` 用 `REQUIRES_NEW` 单开事务（`AuditService.java:237-251`），注释还解释了"同类自调用不走 Spring 代理、注解不生效"这个坑——说明是被线上问题教育过的代码。

4. **安全闸门的默认值方向是对的。** 普通开关 `isEnabled` 查不到按"开启"（保可用性），资质类闸门 `enabledStrict` 查不到按"关闭"（保合规）（`FeatureFlags.java:37-56`）。注释把两种取向的取舍讲清楚了："多关一次只是少卖一次，多开一次可能违规"。这是全仓库最清醒的一段设计说明。

5. **限流 fail-closed，且明确拒绝"退回进程内计数"。** 共享限流存储挂了就抛 503，注释写明"否则一次 Redis 抖动就等于所有限流形同虚设"（`RateLimiter.java:17-22,49-58`）。多实例部署下这是唯一正确的选择。

6. **举报不自动下架，理由写在类注释里。** "自动下架容易被恶意举报利用"（`ContentReportService.java:14-22`）。配合唯一键"同一人同一条内容只能举报一次"（`db/module-content-report.sql:25`），把"刷举报把内容顶下去"这条路堵了。

7. **审核台是单一条 UNION 查询，不 N+1。** 六类内容一次查出来，带学校范围过滤、类型/状态/关键词/日期筛选、分页（`AuditMapper.java:12-55`）。运营点一下就能看到全平台待审，不需要在六个菜单之间跳。

8. **图片审核只从 `/uploads/` 读，拒绝任意 URL。** `uploadName()` 校验路径前缀、拒绝子目录、拒绝外部主机（`AuditService.java:341-348`）。避免"提交一个外部图片 URL 让服务端去抓"的 SSRF 面。

9. **敏感词改完立即重建引擎，不用重启。** `addWord/updateWord/deleteWord/importWords` 全部在写库成功后调 `reloadWords()`（`AuditService.java:484,491,496,507`）；引擎用 `volatile` 整体替换实例（`SensitiveWordEngine.java:33-34`）。运营改词不需要开发介入。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **审核的默认姿态是"放行"，且不可观测。**
   五条路径（缺参、非真实 openid、微信异常、图片未配置、图片异常）+ 一条队列满，全部指向"内容照常上线"（`AuditService.java:180-186,204-207,263-267,297-302,317-321`）。
   - **代价不是"漏审"，而是"无法知道漏没漏"**：日志会给跳过的那次写一条 `source=wechat/result=pass`（`AuditService.java:213-215`）。事后查 `audit_log` 看到的是"审过了、通过了"，实际一次微信调用都没发生。
   - 这条比任何单点漏洞都危险：它让所有依赖审核日志的判断（合规举证、事故复盘、运营决策）全部失真。

2. **审核状态分散在六张业务表里，没有统一的审核实体。**
   六张表各有一份 `audit_status/audit_reason/audit_at`（`db/module-audit.sql:6-46`），审核台靠 6 段 `UNION ALL` 拼（`AuditMapper.java:12-40`）。
   - 代价：**新增一类内容必须同时改四处的四处**（建列、UNION、`decide` 分支、`getTarget` 分支、前端类型下拉）。群聊 `circle_message` 漏了（`db/module-circle-chat.sql:5-17`），活动 `campus_activity` 也漏了（`BizService.java:338-368` 无审核调用）。这不是疏忽，是结构决定的必然遗漏。

3. **敏感词是平台级单表，校管却能改。**
   `sensitive_word` 无 `school_id`（`db/module-audit.sql:63-70`），而增删改接口只要求"是管理员"（`AdminAuditController.java:69-92` 无 `requireSuper`）。同一个仓库里 `AppConfigController` 对平台级配置做了 `requireSuper` 并写明理由（`AppConfigController.java:19-23,45-46`），审核模块没有做。
   - 代价：A 校管理员删掉「刷单」，B 校的诈骗内容就不再被拦。**跨租户影响 + 无留痕（敏感词表无 updated_by）。**

4. **举报与处置是两条断开的线。**
   举报只是"记一笔 + 标记状态"（`ContentReportService.java:78-86`），下架必须去审核台另一条路径（`AuditService.java:428-439`）。
   - 代价：运营在举报页点"已处理"，内容仍在线上。页面顶部只能写一句"处理完请到对应模块下架或忽略"（`Reports.vue:6-8`）来提醒。`handled` 这个状态名本身就在骗人——它既不表示内容被处理，也不表示举报人被回复。

5. **词表覆盖与业务场景错配。**
   默认 22 个词全在"兼职诈骗 + 代写代考"（`db/module-audit.sql:73-76`）。而校园 UGC 最常见的四类风险是：辱骂、色情、涉政、诈骗。默认配置下**前三类在本地零拦截**，全靠微信——而微信在缺参时是放行的。运营看到"启用敏感词 22"这个数字，会以为词表在工作。

6. **审核台的"统计"口径与运营的理解不一致。**
   - "今日审核"= `audit_at >= CURDATE()`，通过和拒绝都算（`AuditMapper.java:83-88`）。
   - "累计拦截"= `audit_log WHERE result='reject'`，**包含人工拒绝**（`AuditMapper.java:101-102`），注释却写"发布入口被敏感词直接拦下"。
   - 结果：运营以为在看"敏感词拦了多少"，实际在看"所有拒绝加起来多少"。

7. **`pending` 态没有出口。** 审核台三个 tab 只有 reviewing/rejected（`Audit.vue:110`），而 `pass()` 接受 pending（`AuditService.java:418`）。带图帖（`ForumService.java:152-157`）、二手（`BizService.java:246`）、当年首次迁移的存量行（`db/module-audit.sql:8`）都可能是 pending。**这些内容运营看不到、点不到。**

8. **举报没有频控，也没有落库前的有效性校验。**
   `POST /api/reports` 无 `limiter`（`ContentReportController.java:27-39`），且不校验 `targetId` 对应的内容是否存在（`ContentReportService.java:35-62` 只校验 id > 0）。脚本可以对 1..100000 逐个举报，全部入队。举报处理台每页 20 条，积压起来就废了。

9. **敏感词检测测试接口对所有管理员开放。**
   `POST /api/admin/sensitive-words/check` 会把命中的具体词返回（`AdminAuditController.java:100-105`）。任何人都能拿它做**词库探测**——逐个试探哪些词被拦，从而构造绕过写法。它本该是开发联调工具，却是生产接口。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 原设计 | 替代方案 | 为什么当时没选（据代码与注释推断） | 代价留给了谁 |
|---|---|---|---|
| 微信审核失败即放行 | 失败即拒绝 | 论坛是主链路，拒绝会让发帖整体不可用（注释 "accepting after local moderation"，`AuditService.java:205`） | 合规：失败窗口内违规内容直接上线 |
| 群聊审核失败即拒绝 | 与论坛一致的放行 | 群聊扩散快，宁可不可用（`CircleChatService.java:140-146`） | 用户：微信抖动时不能发言 |
| 只用手工词表，不加载第三方大词典 | 加载完整违规词典 | 内置词典含大量单字（如「靠」），会误伤「靠窗」「依靠」（`AuditService.java:100-103`） | 运营：涉政/辱骂/色情类只能靠微信 |
| 举报不自动下架 | 举报达 N 次自动隐藏 | 自动下架容易被恶意举报利用（`ContentReportService.java:17-18`） | 运营：每条举报都要人判断 |
| 举报与下载解耦 | 举报页直接给"下架"按钮 | 下架动作要写 `post.status` + `audit_status` 两个字段，耦合在举报服务里会破坏分层 | 运营：两个页面来回跳，容易漏 |
| 普通开关查不到按开启 | 统一 fail-closed | 一次查询失败不该关掉全站功能（`FeatureFlags.java:17-19`） | 内容安全：开关表丢了，群聊/发帖全部打开 |
| 资质闸门用 `enabledStrict` | 与普通开关统一 | 资质类必须"查不到就关"（`FeatureFlags.java:46-51`） | 无（这个取舍是对的） |
| 敏感词表全局单表 | 加 `school_id` 支持各校自定义 | 一张表最简单，跨校共享同一套词更"统一" | 多校 SaaS：校管改词影响全平台 |

## 五、如果重做会怎么改

1. **建立统一的 `content_audit` 实体，业务表只留一个外键。**
   现在六张表各挂三列、审核台靠 6 段 UNION（`AuditMapper.java:12-40`）。改成：

   ```text
   content_audit(id, content_type, content_id, author_id, school_id,
                 status, reason, source, matched_words, created_at, decided_at, decided_by)
   ```
   业务表只留 `audit_id`。审核台一条 `SELECT` 搞定，新增内容类型不用改列表 SQL，`audit_log` 与审核记录合一（顺带解决 29-14）。

2. **把"审核是否生效"变成可观测状态，而不是布尔。**
   四种结果分开：`passed_by_wechat` / `passed_by_local_only` / `skipped_no_credentials` / `review`。管理端首页展示"今日跳过数"，跳过数 > 0 就告警。现在的实现把"没审"写成"审过了"（`AuditService.java:213-215`），这是所有排查失真的源头。

3. **举报与处置合并成一个动作。**
   `POST /api/admin/reports/{id}/handle` 的 body 改成 `{action: "offline" | "ignore", reason}`，`offline` 时内部调 `AuditService.reject`。运营一步完成"判定 + 下架 + 记录"，而不是两个页面来回跳（现在只能靠 `Reports.vue:6-8` 的一句提示）。

4. **敏感词库分校 + 全局双层。**
   `sensitive_word(school_id NULL=全局)` + 匹配时合并；接口按 `school_id` 判权限，全局词只有超管能动。这样解决 29-10 与 29-13。

5. **词表按"风险类别"配默认值，而不是按"当前想到的案例"。**
   默认词表现在是 22 个诈骗词（`db/module-audit.sql:73-76`）。应该按微信小程序审核的四类红线（涉政/色情/暴恐/辱骂）+ 校园特有四类（诈骗/学术不端/隐私/违禁品）各配基线词，并把"每类词数 > N"做成启动自检。

6. **把审核接进"内容通道"抽象，而不是接在 service 里手写四步。**
   现在每个 service 各自 `checkText → rejectWithLog → initialStatus → logTextResult`（`ForumService.java:136-159`、`BizService.java:229-256`、`CampusService.java:30`、`CircleService.java:142-143`），漏一步就是一条缺口——活动（`BizService.java:338-368`）和群聊（`CircleChatService.java:22`）已经漏了。

7. **限流规则要能被"内容通道"复用，而不是各自记得调。**
   `RateLimiter` 只有 4 条规则（`RateLimiter.java:33-40`），举报、点赞、浏览都没接。做成注解或拦截器级能力，新增写接口默认带上。
