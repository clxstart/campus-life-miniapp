## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：三个 SQL 必须先跑；词表需要人工补基线；回滚需手写 SQL）。**

### 4.1 必须按序执行

```sql
-- 1) 审核列（六张业务表）+ 索引 + sensitive_word + audit_log
SOURCE backend/src/main/resources/db/module-audit.sql;
-- 2) 举报表（唯一键是防刷的唯一保障）
SOURCE backend/src/main/resources/db/module-content-report.sql;
-- 3) 功能开关 + 6 个安全闸门（默认关闭）
SOURCE backend/src/main/resources/db/module-feature-flag.sql;
SOURCE backend/src/main/resources/db/module-safety-gates.sql;
```

- 四份均幂等：审核列用 `information_schema` 判存在（`module-audit.sql:6-9`），举报表 `IF NOT EXISTS`（`module-content-report.sql:13`），开关用 `INSERT ... ON DUPLICATE KEY UPDATE flag_key=flag_key` 不覆盖运营已改值（`module-feature-flag.sql:24`），闸门用 `INSERT IGNORE`（`module-safety-gates.sql:6`）。
- **顺序约束**：`module-audit.sql` 必须早于任何内容发布，否则新内容落在 `audit_status` 默认值上（若列不存在则直接 SQL 报错）。
- **`module-audit.sql` 的副作用**：首次执行会把 `post/comment/goods/job/chat_message/circle` 里所有 `audit_status='pending'` 的行**批量提为 passed**（`module-audit.sql:10,17,24,31,38,45`）。这是为了迁移存量数据，但如果脚本在已有大量真实待审数据的库上重跑（列已存在则跳过 UPDATE），不会重复提——幂等正确。
- **`module-safety-gates.sql` 必须在功能上线前执行**，否则六个资质闸门查不到 key，`enabledStrict` 返回 false——方向是安全的（关），但会让兼职/钱包功能"莫名不可用"（`FeatureFlags.java:53-56`）。

### 4.2 词表基线（SQL 无法自动完成的部分）

```sql
-- 检查当前词数（未补基线时约 22）
SELECT category, COUNT(*) FROM sensitive_word WHERE enabled=1 GROUP BY category;
-- 期望（按 01-功能说明.md 7.6 的风险分类）：fraud ≥ 22、abuse ≥ 20、politics ≥ 10、custom 按运营
```

**当前默认只有 22 条 fraud + 12 条学术不端**（`module-audit.sql:72-76`），`abuse`/`politics`/`色情` 三类为 0。这是数据就绪度问题，不是代码问题，但会直接决定审核效果。

### 4.3 回滚

```sql
-- 回滚一次误拒（把被误杀的内容放回）
UPDATE post SET audit_status='passed', status=1, audit_reason=NULL
WHERE id=? AND audit_status='rejected';
-- comment/goods/job/circle 同理（注意各表的"可见位"字段不同：
--   post/goods/circle 用 status(0/1)；job 用 status 字符串 '招聘中'/'已下架'；comment/chat 无可见位）

-- 回滚一次被删的敏感词（无法自动恢复，必须从备份取）
-- 建议：删词前先 SELECT 备份
SELECT * FROM sensitive_word WHERE id=?;

-- 回滚一条被误处理的举报
UPDATE content_report SET status='pending', handled_by='', handled_at=NULL WHERE id=?;

-- 结构回滚（整版回退；会丢审核状态与举报记录）
ALTER TABLE post DROP INDEX idx_post_audit_status, DROP COLUMN audit_status,
  DROP COLUMN audit_reason, DROP COLUMN audit_at;
-- 其余五表同理
DROP TABLE IF EXISTS content_report;
DROP TABLE IF EXISTS sensitive_word;
DROP TABLE IF EXISTS audit_log;
```

**现实约束**：`sensitive_word` 删除是物理删除且无软删（`AuditMapper.java:129`），删错只能从数据库备份恢复。**这就是 29-10 必须加 `updated_by` 与"先停用再删除"的原因。**

## 五、性能与容量

**结论：有条件通过（条件：举报与审核列表的索引；关键词 LIKE 全表扫；量起来前压测）。**

| 核查点 | 结论 | 证据 |

| 核查点 | 结论 | 证据 |

| 审核日志来源是否可信 | ❌ 可写成 `wechat/pass` 而实际未调用 | `AuditService.java:213-215` |
| 审核队列积压是否告警 | ❌ 只有计数，无阈值告警 | `AuditMapper.java:89-94` |
| 举报积压是否告警 | ❌ `countPending` 吞异常返回 0，连"读不到"都看不见 | `ContentReportService.java:88-90` |

## 七、失败与降级（依赖挂了会怎样）

**结论：不通过（原因：五条依赖失败路径全部指向"放行"，且不通知任何人）。**

| 依赖 | 挂了会怎样 | 证据 | 可接受吗 |
|---|---|---|---|
| 微信 `appid/secret` 未配 | 全站内容只过本地词库，日志写 `wechat/pass` | `AuditService.java:180-182,213-215` | ❌ |
| 微信文本审核超时/5xx | 捕获后放行 | `AuditService.java:204-207` | ❌ |
| 微信 token 获取失败 | 同上 | `AuditService.java:350-358` | ❌ |
| 微信图片审核挂了 | 图片直接通过并转正 | `AuditService.java:317-321` | ❌ |
| 审核线程池队列满 | 图片直接通过 | `AuditService.java:260-267` | ❌ |
| 敏感词表读不到 | 退化到 23 个兜底词，不阻断 | `AuditService.java:89-105` | ⚠️ 有兜底，可接受 |
| 敏感词引擎抛异常 | 视为未命中 → 放行 | `SensitiveWordEngine.java:88-93` | ❌ |
| 限流存储不可用 | 503 fail-closed | `RateLimiter.java:52-57` | ✅ 方向正确 |
| 开关表不可用 | 普通开关按"开启"（群聊/发帖全部打开）；安全闸门按"关闭" | `FeatureFlags.java:41-44,53-56` | ⚠️ 方向分裂但可解释 |
| 数据库不可用 | 所有审核动作报错；发帖因查用户 openid 失败也可能报错 | `AuditService.java:176-179` | ⚠️ 常规 |

**方向性结论**：同一个仓库里，限流选择 fail-closed 并写了理由（`RateLimiter.java:17-22`），群聊审核选择 fail-closed（`CircleChatService.java:142`），论坛/图片审核选择 fail-open（`AuditService.java:204-207`）。**三种策略并存且没有统一文档**——这是最该在上线前收敛的一处设计债。

建议的统一策略矩阵：

| 场景 | 建议策略 | 理由 |
|---|---|---|
| 内容审核（任何通道） | fail-closed 到"待审"，不是"拒绝"也不是"放行" | 用户能发、不进公域、可人工兜底 |
| 限流 | fail-closed（503） | 现值正确，保持 |
| 资质闸门 | fail-closed（关闭） | 现值正确，保持 |
| 普通功能开关 | fail-open（开启） | 现值正确，保持 |
| 图片审核 | fail-closed 到"待审" | 与文本一致 |

**止血演练缺口（最重要的一条）**：假设线上出现一条涉政内容被大量转发。当前可行动作：
1. 关 `post.publish.enabled`（止新增，30 秒生效）；
2. 到 `/audit` 找到那条内容 → 拒绝（若它已经是 `passed` 状态，`pass/reject` 都会报"该内容当前不能拒绝"，必须先去 `/posts` 下架）；
3. 通知作者。

**第 2 步存在断点**：`reject` 只接受 `reviewing`/`pending`（`AuditService.java:432-434`），已经 `passed` 的内容在审核台上**无法直接拒绝**，必须切到"内容管理"页下架。运营如果不知道这个规则，会在审核台反复点击并看到"该内容当前不能拒绝"。这是上线后第一次事故就会踩到的坑。
