# 写作规范（所有功能文档必须遵守）

> 用途：30 个功能文件夹、120 份文档共用一套格式与判级标准。
> 动笔前先读完本文；写完按第九节自检。

---

## 一、读者与目标

| 读者 | 他要用文档做什么 |
|---|---|
| 项目负责人（你） | 决定"这一版能不能上线、先修哪几个" |
| 开发者 | 拿到问题就能定位、能估工作量、能动手 |
| 外部评审 / 投资人 / 学校客户 | 判断工程成熟度与合规风险 |

所以每句话都要能验收：**看到位置、看到影响、看到修法、看到代价。**

---

## 二、每份文档开头的 front-matter（6 行，逐字保留格式）

```
> 编号：07 · 支付与退款
> 核实时间：2026-11-10
> 代码快照：merge-all @ 083f7b4（工作区 238 项未提交）
> 实现状态：🟠 半实现（后端 ✅ / 小程序 🟡 / Web 🟡）
> 最高风险：P0 模拟支付开关误开（示例）
> 证据范围：读码；未跑真实支付
```

- `实现状态` 用第五节状态字典里的标记；三端分开写。
- `最高风险` 没有 P0/P1 就写"无 P0/P1（依据见问题清单）"。
- `证据范围` 必须诚实：只读码就写"读码"；跑过命令就写命令名。

## 三、`01-功能说明.md` 骨架（标题逐字保留）

```markdown
# 07 · 支付与退款 —— 功能说明

> front-matter 6 行

## 一、这个功能解决什么问题
## 二、用户看到的样子（小程序端）
## 三、运营看到的样子（Web 端）
## 四、接口清单
## 五、数据表与字段
## 六、与旧文档的对应关系
## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）
```

要求：
- 第二节写**用户操作路径**（点哪个入口 → 哪个页面 → 哪个按钮 → 什么反馈），不要写"支持支付"这种空话。
- 第四节列**接口表格**：方法 + 路径 + 权限（用户/管理端/商家/骑手）+ 作用。以代码里的 `@*Mapping` 为准。
- 第五节列**表名 + 关键字段 + 用途**，说明这张表归谁写。
- 第六节写清与 `docs/v3.1/`、`docs/v3.1-交付/`、`docs/接口文档-全量211端点.md` 的对应或冲突。

## 四、`02-实现现状.md` 骨架

```markdown
# 07 · 支付与退款 —— 实现现状

> front-matter

## 一、总览（三端完成度表）
## 二、后端：逐条核对
## 三、小程序端：逐条核对
## 四、Web 端：逐条核对
```

- **每条核对项**格式：`- [状态] 能力描述 —— 证据：\`path:line\``
- 状态只用：✅ / 🟡 / 🟠 / 🔴 / ⚫（见 README 第五节）。
- 第六节必须给**可直接复制执行的命令**（`mvn -Dtest=XxxTest test`、`curl ...`、`node tools/xxx.js`），并写清"本次是否执行、结果如何"。没执行就写"未执行，原因 X"。
- 第七节专门打旧文档的口径：数字、字段名、状态机、是否完成。

## 五、`03-优缺点与问题.md` 骨架

```markdown
# 07 · 支付与退款 —— 优缺点与问题

> front-matter

## 一、设计优点（为什么这么设计，好在哪）
## 二、设计缺点与代价（架构/体验/合规/维护）
## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）
## 四、问题清单
## 五、如果重做会怎么改
```

### 4.1 问题清单表（固定列，不许增删）

| 编号 | 现象 | 证据（`path:line`） | 触发条件 | 影响面 | 等级 | 复现/验证方式 | 建议修法 | 工作量(人日) | 阻断上线 |
|---|---|---|---|---|---|---|---|---|---|

- 编号格式：`<功能编号>-<序号>`，如 `07-01`。
- 等级只用 P0 / P1 / P2。
- `阻断上线` 列只填"是 / 否"。
- 至少 3 条问题；确实少于 3 条的，在表后写"为什么只有 N 条"并给依据（例如代码量仅 80 行、无写操作）。

### 4.2 判级细则

| 情形 | 等级 |
|---|---|
| 资金可伪造 / 可重复扣款 / 可越权退款 / 金额可被客户端篡改 | P0 |
| 数据可跨校 / 跨用户读取（手机号、学号、私有材料、订单） | P0 |
| 鉴权可绕过（接口缺拦截、前端隐藏当权限） | P0 |
| 合规缺失导致审核不通过（隐私政策、用户协议、资质、实名、未成年人保护） | P0 |
| 发布版配置未替换导致全站不可用（如占位域名） | P0 |
| 主链路崩溃 / 页面打不开 / 接口必 500 | P0 |
| 审核漏审、通知不到、状态不同步、错误提示误导、无告警、无回滚 | P1 |
| 性能明显劣化（N+1、缺索引、全表扫）到影响可用 | P1 |
| 批量操作缺失、移动端适配、埋点不全、文案粗糙 | P2 |

## 六、`04-商业上线核查.md` 骨架（8 维，一维都不能空）

```markdown
# 07 · 支付与退款 —— 商业上线核查

> front-matter

## 一、合规与隐私
## 二、资金与对账（不涉及资金写"不涉及"并给依据）
## 三、权限与越权
## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）
## 五、性能与容量
## 六、可观测与告警（日志、指标、错误上报、告警渠道）
## 七、失败与降级（依赖挂了会怎样）
## 八、开关与回滚（怎么关、怎么退、数据怎么退）

## 九、结论
## 十、上线前置清单（按执行顺序）
```

- 每一维给**结论词**：`通过 / 有条件通过（条件：X）/ 不通过（原因：Y）`，并带证据。
- 第九节结论只能三选一：**可上线 / 有条件上线（列出条件）/ 不可上线（列出阻断项编号）**。
- 第十节按"必须先做什么 → 再做什么"排序，能写成命令的写成命令。

---

## 七、证据规范

1. 代码位置写 `相对仓库根的路径:行号`，例如 `backend/src/main/java/com/campuslife/service/PayService.java:273`。
2. 行号以**当前工作区文件**为准；改过代码的行号会漂，写证据时顺手核对一次。
3. 命令必须可直接复制执行，并写清预期输出。
4. **没跑过的，写"未验证"**，不要写"应该没问题""理论上可以"。
5. 推测必须显式标注：`（推测，未验证）`。

---

## 八、语言与禁止表述

- 中文；术语沿用仓库现有叫法（如"圈子""外卖""私有上传""兜底"）。
- **禁止**："暂无""后续优化""架构上还有提升空间""基本可用""应该没问题""建议关注"。
- 要写就写："缺 X 能力，约 N 人日，条件 Y 下必须补"。
