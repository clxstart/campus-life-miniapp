## 一、合规与隐私

**结论：不通过（原因：匿名输入不过内容审核；用户对话原文无边界可读；无 AI 生成标识）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 用户输入是否过内容安全 | **不通过**：`chat()` 全程无 `AuditService` 调用 | `AiChatService.java:38-92` |
| 输出话术是否过内容安全 | **不通过**：运营配置的 `reply` 直出 | `AiChatService.java:62-74` |
| 是否匿名可用 | 是（设计如此），因此输入没有任何身份门槛 | `AuthInterceptor.java:61-71`、`AiChatController.java:18-20` |
| 是否收集个人信息 | **不通过（超范围）**：对话原文入库，无脱敏、无保留期 | `module-ai-config.sql:15`、`AiChatService.java:84` |
| 日志访问是否有边界 | **不通过**：接口无超管判定、查询无校域 | `AiAdminController.java:55-58`、`AiChatService.java:164-172` |
| AI 生成标识 | **不通过**：无任何标识或免责 | `pages/ai-chat/*` |
| 未成年人保护 | 不通过（同上：匿名输入无审核） | 同第一行 |
| 隐私政策是否覆盖对话数据 | 本目录无法核实（需 `01-登录与鉴权` 域对齐） | — |

监管口径提醒：生成式 AI 服务要求「输入输出内容安全 + 显著标识 + 投诉入口」。当前三项全缺。若对外宣传"AI 助手"，风险等级会从"内部工具"上升到"受监管的生成式服务"。**最省事的路线是：改名「校园小助手」，去掉 AI 承诺，同时补上输入审核。**

## 二、资金与对账

**结论：不涉及（依据：本功能无任何金额字段与支付调用；`ai_chat_rule`/`ai_chat_log`/`ai_chat_config` 三张表无金额列）**

一条成本侧提醒（**推测，未验证**）：当前是纯规则匹配，无外部模型调用，**边际成本为零**；这也是它最大的商业优点——不像真 AI 那样会随使用量烧钱。若将来换成大模型，必须同时上"每人每日调用上限"，否则一次营销活动就能把预算烧穿。

## 三、权限与越权

**结论：不通过（原因：前端 `superOnly` 当权限，后端无判定；日志跨校可读）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| `/api/ai/chat` 是否需登录 | 否（设计允许游客） | `AuthInterceptor.java:61-71` |
| 客户端传 `userId` 能否冒充他人 | 是（匿名时）：`CurrentUser.resolve(request, body.userId, 1L)` 会采用 body 里的值 | `AiChatController.java:35`、`CurrentUser.java:26-31` |
| 冒充的后果 | 把日志记到别人名下、占用别人的限流配额 | `AiChatService.java:82-88` |
| 管理端接口是否需 token | 是 | `WebConfig.java:43`、`AiAdminController.java:17` |
| 管理端接口是否区超管/校管 | **否** | `AiAdminController.java:17-71` 无角色判断 |
| 前端 `superOnly` 是否等于后端限制 | **否**（判级细则：前端隐藏当权限 → P0） | `web/src/router/index.js:31` |
| 日志查询是否按校 | **否** | `AiChatService.java:164-172` |

实际攻击面：任何持有校管 token 的账号（校管账号通常由学校老师担任，人员流动大）可直接 `GET /api/admin/ai-stats` 拉走全站用户与 AI 的对话原文，包括别校学生。不需要任何前端操作。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：`module-ai-config.sql` 必须先于 `module-perf-index.sql` 执行）**

```bash
# 1) 规则表 + 24 条种子
mysql -u root -p campus_life < backend/src/main/resources/db/module-ai-chat.sql
# 2) 日志表 + 配置表（必须先于 3 执行！）
mysql -u root -p campus_life < backend/src/main/resources/db/module-ai-config.sql
# 3) 索引（含 ai_chat_log 的 school 索引，依赖步骤 2 的表）
mysql -u root -p campus_life < backend/src/main/resources/db/module-perf-index.sql
# 4) 核对
mysql -u root -p campus_life -e "
SELECT COUNT(*) rules FROM ai_chat_rule;
SELECT COUNT(*) logs, MIN(created_at) earliest FROM ai_chat_log;
SELECT config_key FROM ai_chat_config;"
```

- 本次**未执行**，原因：无 MySQL 会话。
- **顺序坑**：`module-perf-index.sql:57-61` 对 `ai_chat_log` 加索引，若表还没建，`ALTER TABLE` 会直接报错中断整个脚本（脚本用 information_schema 判断的是"索引不存在"，不是"表不存在"）。

回滚 SQL：

```sql
DROP TABLE ai_chat_log;
DROP TABLE ai_chat_config;
DROP TABLE ai_chat_rule;
```

⚠️ 会丢全部规则与运营改过的欢迎语。规则表有 24 条种子可重新导入，**日志不可恢复**（所以回滚前应先 dump）。

**结论：通过（依据：无外部模型调用，单次对话为 1 次规则全表读 + 1 次日志插入，成本极低；未压测）**

## 九、结论

**不可上线（阻断项：15-01、15-02）**

- 15-01 阻断理由：一个**匿名可用、不审核、原文入库**的输入框，等于给平台开了一个不受控的 UGC 通道。判级细则「合规缺失导致审核不通过 → P0」。而修它只需要 0.2 人日——没有理由不做。
- 15-02 阻断理由：判级细则「鉴权可绕过（前端隐藏当权限）→ P0」与「数据可跨校读取 → P0」。校管能直接拉全站对话原文，是安全评审必挂项。
- 15-03（匿名限流撞车）不阻断但会被用户直接感知：一个游客就能让全天所有游客用不了。
- 另有一条**表述性风险**：对外不要说"AI 大模型/智能对话"。它是 24 条关键词规则。

## 十、上线前置清单（按执行顺序）

1. **（P0，0.2 人日）输入审核**
   - `AiChatService.chat()` 第一行加 `auditService.checkText(message, "ai_chat", userId)`，命中即抛 `IllegalArgumentException`（不落原文）。
   - 验收：输入敏感词被拒，且 `ai_chat_log` 无该条记录。

2. **（P0，0.5 人日）日志访问边界**
   - `AiAdminController.ai-stats` 加超管判定（与其它 admin 接口的超管语义保持一致）。
   - `stats(schoolId)` 加校域过滤，SQL 补 `AND school_id=#{schoolId}`。
   - 前端展示脱敏（手机号/学号打码）。
   - 验收：校管调该接口返回 403 或仅本校数据。

3. **（P1，0.2 人日）限流分桶**：匿名用 IP、登录用 userId。

4. **（P1，0.2 人日）规则话术过审**：保存 `reply` 前跑 `checkText`。

5. **（P1，0.1 人日）加标识**：对话页顶部「由话术自动回复，仅供参考」。

6. **（P1，0.5 人日）日志治理**：入库脱敏 + 90 天清理任务 + 注销时删除该用户日志。

7. **（P1，8 上下文）改文案与定位**：对外统一叫「校园小助手·快捷问答」，去掉 AI 大模型暗示。

8. **（P2）** 修「我先记住你的话了」这句假话；加响应耗时/429 指标。

9. **（数据）** 严格按第四节顺序执行三个 SQL 脚本。
