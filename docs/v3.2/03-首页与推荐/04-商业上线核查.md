## 二、资金与对账

**结论：不涉及（依据：本功能无任何支付、扣款、退款、结算代码路径；`RecommendController` 5 个端点全部是读取与计数自增）**

但有一条间接关联需登记：推荐位影响外卖店铺曝光，而店铺曝光与商家付费意愿相关。当前**没有任何"付费推广位"逻辑**，也没有曝光计费。若后续要做竞价排名，03-03（计数可刷）会直接变成计费漏洞。现在不做，但不要在这个基础上加收费能力。

## 三、权限与越权

**结论：不通过（原因：推荐跨校；热度计数可单账号操纵）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 写接口是否强制鉴权 | 通过：浏览/咨询/收藏/店铺浏览都是 POST，未登录 401 | `AuthInterceptor.java:136-137`；`CurrentUser.java:8-11` 注释说明写操作必带 token |
| 客户端传的 `userId` 能否冒充他人 | 通过：登录态优先，`claimed` 只在匿名只读时用 | `CurrentUser.java:26-31` |
| 读接口是否跨校 | **不通过**：推荐榜无 `school_id` 条件 | `RecommendMapper.java:23-24`、`:51-52` |
| 计数接口是否可刷 | **不通过**：无去重、无限频 | `RecommendMapper.java:63`、`:79`、`:82` |
| 管理端 banner 接口是否需 token | 通过：挂在 `/api/admin/**` | `WebConfig.java:43` |

越权风险的实际形态：不是"看到别人的手机号"，而是"看到别校的店铺和商品，并可以把它刷到本校首页第一屏"。对多校 SaaS 客户，这等于隔离承诺失效。

## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：两个迁移脚本必须先执行并核对行数；`module-hotness.sql` 的初始浏览量脚本要单独确认是否要刷）**

执行顺序（必须先 01 登录与鉴权域的 `module-multischool-admin.sql`，因为 `goods/shop.school_id` 是它加的）：

```bash
# 1) 热度列 + 收藏表 + 热度索引（幂等，可重复执行）
mysql -u root -p campus_life < backend/src/main/resources/db/module-hotness.sql

# 2) 学校维度索引（幂等）
mysql -u root -p campus_life < backend/src/main/resources/db/module-perf-index.sql

# 3) 核对
mysql -u root -p campus_life -e "
SELECT COUNT(*) AS zero_view_goods FROM goods WHERE status=1 AND view_count=0;
SELECT COUNT(*) AS shops FROM shop WHERE order_count>0;
SHOW INDEX FROM goods WHERE Key_name IN ('idx_goods_hot','idx_goods_school');"
```

- 本次**未执行**，原因：本轮无 MySQL 会话，只读码。
- `module-hotness.sql:54` 的 `UPDATE goods SET view_count=12` **只影响 `view_count=0` 的存量行**，重跑不会覆盖已有计数（幂等）。若不想造初始热度，删掉该行再执行。

回滚 SQL（只在必须回退时执行，会丢计数）：

```sql
ALTER TABLE goods DROP INDEX idx_goods_hot;
ALTER TABLE goods DROP COLUMN view_count, DROP COLUMN favorite_count, DROP COLUMN contact_count;
ALTER TABLE shop  DROP COLUMN order_count, DROP COLUMN view_count;
DROP TABLE goods_favorite;
```

⚠️ 回滚会同时丢掉 `goods_favorite` 的全部收藏关系，**不可恢复**。上线后不建议回滚数据，只回滚代码（代码回滚后这些列变成无用列，不影响运行）。

## 五、性能与容量

**结论：有条件通过（条件：单实例部署，或先补 Redis 共享缓存）**

| 检查项 | 结论 | 证据 |
|---|---|---|
| 首屏是否 N+1 | 通过：一次请求 5 条 SQL（2 COUNT + 2 排序 + 1 IN），无逐行查询 | `RecommendService.java:86-95` |
| 排序能否走索引 | 不通过：`ORDER BY heat` 是计算式，`idx_goods_hot` 用不上 | `RecommendService.java:19-21` 注释、`module-hotness.sql:47` |
| 缓存是否覆盖最贵部分 | 有条件通过：60s 进程内，命中时只剩 1 条 IN | `RecommendService.java:26-55` |
| 多实例是否一致 | 不通过：各实例独立 Map | `RecommendService.java:32` |
| 是否有压测数据 | **无**，本轮未压测 | `04-证据与复核台账.md` 3.2 |
| 首页请求数 | 4–5 个（推荐/学校/会话/通知/登录态） | `pages/index/index.js:49`、`components/bottom-nav/index.js:55-60` |

容量判断（**推测，未验证**）：`goods` 十万行时，`ORDER BY heat DESC LIMIT 2 OFFSET n` 仍需全表扫+filesort。按每分钟一次计，单次耗时若为 200–400ms，则在 60 秒窗口内会持续占用一个连接。这个数量级在校园场景（单校商品通常 <3000）不会触发，**多校汇总或数据迁移导入后会触发**。

## 九、结论

**不可上线（阻断项：03-02）**

- 阻断理由：多校 SaaS 的核心承诺是"每所学校只看到自己的数据"。首页第一屏是最高频入口，它跨校展示别校店铺与商品，属判级细则中的"数据可跨校读取（P0）"，且用户在首屏就能感知。
- 03-01（可见性口径不一致）虽判 P1，但它是内容合规问题，建议与 03-02 同批修——两条都要动 `RecommendMapper` 的 `WHERE`，一次改完。
- 03-03/03-04 判 P1：不阻断上线，但必须在"允许商家竞价/允许运营主推"之前修完，否则排序可被购买。
