## 一、设计优点（为什么这么设计，好在哪）

1. **一人一票用数据库兜底，而不是只靠内存判断。** 业务层先查重（`backend/src/main/java/com/campuslife/service/IdolService.java:26`），表上再压 `UNIQUE KEY uk_idol_vote(contestant_id,user_id)`（`backend/src/main/resources/db/schema.sql:14`）。这是本功能最扎实的一处：即使将来有人绕过 service 直接写库，唯一键仍然拦住重复票。

2. **票数自增用 SQL 表达式而不是"读-改-写"。** `setSql("vote_count = vote_count + 1")`（`backend/src/main/java/com/campuslife/service/IdolService.java:28`）把并发问题交给数据库行级锁，比 `set(voteCount, c.getVoteCount()+1)` 安全一个量级。全仓库同类计数（点赞、评论数）也是这个写法，口径统一。

3. **投票人身份从 token 取，不从 body 取。** `r.setUserId(CurrentUser.resolve(request, r.getUserId()))`（`backend/src/main/java/com/campuslife/controller/IdolController.java:33`）配合 `AuthInterceptor` 对 POST 强制 token（`backend/src/main/java/com/campuslife/config/AuthInterceptor.java:137-145`），堵住了"改 userId 替别人投票"这条老越权路。类注释也明确写了这条设计意图（`IdolController.java:30`）。

4. **小程序端投票是乐观更新 + 失败回滚，且回滚统一还原三处状态。** 选手的 `voted`、选手的 `voteCount`、全局 `stats.votes` 一起还原（`pages/activity-idol/activity-idol.js:88-103`）。弱网下用户不会看到"票数涨了又没涨"的错乱。

5. **管理端写操作全部落操作日志，且日志带业务可读文案。** `新增选手 / 编辑选手 / 设置选手状态 / 删除选手`（`backend/src/main/java/com/campuslife/controller/AdminModuleController.java:65,74,84,92`），事后可追责到人。

6. **前端对"已投过"做了本地预判，省掉一次必然失败的请求。** `if (target.voted)` 直接 toast（`pages/activity-idol/activity-idol.js:83-86`），减少无意义的 500 与网络往返。

## 二、设计缺点与代价（架构/体验/合规/维护）

### 2.1 活动参数写死在 Java 常量里，等于"活动不可运营"

标题、阶段、截止时间三样东西在 `IdolService.java:8,12` 写死。代价：

- 办第二届评选要**改代码、重新发版**；
- 截止时间到了系统不会停，因为 `vote()` 根本不读这个常量（`:23-29`）；
- 该常量当前值 `2026-10-31 23:59:59` 相对核实时间已过期 10 天，也就是说**这套代码今天跑起来就是一个"过期了还在收票"的活动**。

### 2.2 报名链路断在"照片没上传"这一环

`pages/idol-join/idol-join.js:33` 把 `wx.chooseMedia` 的 `tempFilePath` 直接存进 `photo`，`:50` 原样提交。后端 `IdolService.java:31` 也只把这个字符串写进 `photo` 列。

代价按严重度排列：

- 报名者自己的照片，在别人手机上**打不开**（`wxfile://` 只在本机临时目录有效，重进小程序即失效）；
- 运营在 Web 端 `NoImageUpload` 组件里看到的是一个不可解析的路径（`web/src/views/Idol.vue:27` 的 `<img :src="row.photo">`）；
- 图片从未经过 `UploadController`，也就从未经过图片内容安全审核。

同仓库有正确写法可抄：`pages/activity-enroll/activity-enroll.js:81`（`const uploaded = await api.uploadImage(path)`，失败抛 `材料上传失败，请重试`）。**评选报名漏抄了这一步。**

### 2.3 报名 = 立即公开展示，审核完全缺位

`schema.sql:13` 的字段注释写着 `status 0=待审核 1=展示`，`AdminModuleMapper.java:540` 也支持设 0，但 `join()` 直接 `setStatus(1)`（`IdolService.java:31`），全仓没有任何代码路径把新报名写成 0。

后果：昵称、宣言、照片三样用户输入全部未经审核就上墙，且这是**真人照片公开展示**场景。对比发帖链路，发帖会走 `auditService.checkText(...)` + `rejectWithLog(...)` + 图片异步审核（`backend/src/main/java/com/campuslife/service/ForumService.java:136-137,161`），评选报名一样都没走。

### 2.4 "一人一票"挡住了重复票，挡不住"多账号"

唯一键解决的是同一 `user_id` 的重复；刷票的真实路径是**批量注册账号**，每人投一票。当前没有任何手段覆盖这条：

- 投票无频控（`IdolController.java:17-18` 未注入 `RateLimiter`）；
- 无设备指纹、无手机号/学号绑定、无图形验证；
- 报名无人数上限：同一用户可以无限次报名（`IdolService.java:30-31` 无查重、表无 `user_id` 唯一键），一人造多张选手卡，再用多账号给自己投。

### 2.5 票数冗余但无重算机制，一次偏差永久存在

`idol_contestant.vote_count` 是冗余计数，真相在 `idol_vote` 的行数。当前两者已经天然对不上（种子票数手写，`schema.sql:15-22`），而全仓没有任何"按投票记录重算票数"的代码或脚本。代价：一旦出现偏差（删选手不删票、种子数据、并发异常回滚），**没有任何自愈路径**，只能人工改库。

### 2.6 多校 SaaS 下"全平台评选"是产品选择，但没有配套的身份约束

`AdminModuleMapper.java:508` 明确注释"评选是全平台活动，不按校隔离"。作为产品取舍可以成立，但配套缺失：`college` 字段由用户自填（`pages/idol-join/idol-join.js:39`），无任何校验或与 `school_id` 的关联。代价：任选一所名校的"学院"名义参赛，平台无从核实，事后争议无据可查。

## 三、权衡过的替代方案（如果不这么做还能怎么做，为什么没选）

| 现方案 | 替代方案 | 为什么没选（从代码能看出的原因） | 本方案的真实代价 |
|---|---|---|---|
| 活动参数写 Java 常量 | 建 `idol_activity` 配置表 / 复用 `app_config` | 代码注释自承"演示期固定……接入管理后台后改为读配置"（`IdolService.java:7`），说明是**临时方案被留下了** | 改活动必须发版；截止时间形同虚设 |
| 照片存 tempFilePath | 走 `api.uploadImage()` 落图床 | 无技术障碍，同仓库 `activity-enroll` 已这么做（`pages/activity-enroll/activity-enroll.js:81`） | 照片所有人看不到，审核无从进行 |
| 报名直接上墙 | 报名写 `status=0`，管理端审核后置 1 | `status` 字段和 `setIdolStatus` 接口都已就绪（`AdminModuleMapper.java:540`），只差 `join()` 里改成 0 和管理端一个审核 tab | 违规内容零延迟公开 |
| 只靠 `selectOne` + 唯一键 | 加 `SELECT ... FOR UPDATE` 或用唯一键异常映射成业务提示 | 没做异常映射 | 并发时用户看到 500 而非"你已投过" |
| 全平台评选不隔离学校 | 加 `school_id` 列按校评选 | 作者明确选了全平台（`AdminModuleMapper.java:508`） | 学院名无法核实；多校客户会问"为什么我校学生和别校混排" |
| 无频控 | 投票按 `userId` 限流（`RateLimiter` 已有 `PUBLISH` 等档位可复用） | 没做 | 多账号刷票无成本 |

## 五、如果重做会怎么改

按"漏了什么能力"排序，不谈抽象原则：

1. **先把活动抽成数据。** 建 `idol_activity(title, phase, vote_start_at, vote_end_at, status)` 一行一活动，`idol_contestant` 加 `activity_id`。收益：办第二届不用发版；`vote()` 有时间边界可判断；`activity()` 不再写死标题。约 1.5 人日。

2. **报名链路三步补齐**：上传图床 → 内容审核 → 落 `status=0`。三步都是同仓库已有能力，只是没接（`api.uploadImage`、`AuditService.checkText`、`setIdolStatus`）。约 2 人日。

3. **加"报名唯一性 + 投票频控"两道闸**：`idol_contestant` 加 `uk(activity_id,user_id)`；投票走 `RateLimiter` 新档位并按 `userId + IP` 双维度计数。约 1.5 人日。

4. **票数做成可重算的派生值**：写一个 `recountVotes(activityId)` 维护接口 + 定时任务，从 `idol_vote` 全量重算 `vote_count`；管理端加"重算票数"按钮。这一步做完，2.5 节的"偏差永久存在"才真正解决。约 1 人日。

5. **审核队列进管理端**：`Idol.vue` 加"待审核"tab（`status=0`），卡片加"通过/驳回"；不通过时给报名者一条 `notification`（复用 `CampusMapper.notifyUser`）。约 1.5 人日。

6. **合规三件套**：报名页授权勾选并留痕、未成年人拦截、隐私政策里写明"参赛照片将公开展示"。约 1 人日。

合计约 9 人日。其中第 1、2 项不做完，这个功能不应对外宣称"可以上线"。
