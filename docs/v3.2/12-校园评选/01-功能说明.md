## 一、这个功能解决什么问题

校园里每年都有"校草校花评选"，原本靠线下扫码、公众号投票或表格收集，运营方需要三件事：

1. **选手收口**：让用户自己报名（上传照片、填昵称、学院、参赛宣言），后台能改、能停用、能删。
2. **投票计数**：同一个人对同一位选手只能投一票，票数实时累加。
3. **榜单呈现**：按票数倒序分"校草组 / 校花组"两栏展示，带倒计时，鼓励分享拉票。

代码里的产品形态就是这么三件事，没有第四件。标题写死在 `活动标题=校园人气王评选`（`backend/src/main/java/com/campuslife/service/IdolService.java:12`），阶段写死为 `voting`，说明它被设计成**一次性活动页**而不是可复用的"评选系统"。

## 二、用户看到的样子（小程序端）

入口链路（读码确认）：

1. 发现页顶部 banner（种子数据里的第 1 条，`backend/src/main/resources/db/schema.sql:53`）——文案 `CAMPUS IDOL / 校草校花评选 / 投票进行中 · 上传照片赢校园人气王`，`link_type=page`、`link_value=/pages/activity-idol/activity-idol`。
2. 点 banner 进 `pages/activity-idol/activity-idol`（已在 `app.json:15` 注册）。
3. 页面上半部是统计与倒计时：选手数、总票数来自 `GET /api/idol/activity`（`pages/activity-idol/activity-idol.js:47-58`）；倒计时由 `countdownText()` 每 60 秒重算一次（`pages/activity-idol/activity-idol.js:31-33`）。
4. 两组切换：`switchGender()` 改 `gender` 后重新拉列表（`pages/activity-idol/activity-idol.js:72-77`）。默认 `gender=2`（校花组）。
5. 选手卡按票数倒序，`rank` 由前端数组下标生成（`pages/activity-idol/activity-idol.js:63-68`）。
6. 点"投票"→ `onVote()`：**先本地加一票并置灰，再上报，失败回滚**（`pages/activity-idol/activity-idol.js:87-103`）。已投过的按钮直接提示"已经给 TA 投过票啦"。
7. 点"我也要报名"→ `goJoin()` 跳 `pages/idol-join/idol-join`（已在 `app.json:16` 注册），带当前 `gender`。
8. 报名页：`choosePhoto()` 选图（`pages/idol-join/idol-join.js:27-36`）、填昵称/学院/宣言、`submit()` 提交，成功提示"**报名成功，已进入展示队列**"并 `navigateBack`（`pages/idol-join/idol-join.js:50-52`）。
9. 分享：`onShareAppMessage` 标题"校草校花评选进行中，快来为 TA 打 call！"（`pages/activity-idol/activity-idol.js:40-45`）。

> ⚠️ 第 8 步的文案是"已进入展示队列"，但后端 `join()` 直接把 `status` 写成 `1`（立即展示），见第七节。

## 三、运营看到的样子（Web 端）

## 五、数据表与字段

两张表，**都在 `backend/src/main/resources/db/schema.sql`，不在 `module-market-jobs-activities.sql`**：

### `idol_contestant`（选手）

| 字段 | 类型 | 用途 |
|---|---|---|
| `id` | BIGINT PK AI | 选手 id |
| `user_id` | BIGINT NOT NULL | 报名者 user id |
| `name` | VARCHAR(32) NOT NULL | 展示昵称 |
| `gender` | TINYINT NOT NULL DEFAULT 1 | 1=校草组 2=校花组 |
| `college` | VARCHAR(64) | 学院（用户自填） |
| `photo` | VARCHAR(255) NOT NULL | 照片地址 |
| `slogan` | VARCHAR(128) | 参赛宣言 |
| `vote_count` | INT NOT NULL DEFAULT 0 | 票数（冗余计数） |
| `status` | TINYINT NOT NULL DEFAULT 1 | 注释写 `0=待审核 1=展示` |
| `created_at` | DATETIME | 报名时间 |

索引：`KEY idx_idol_gender(gender,status)`（`schema.sql:13`）。**无 `user_id` 唯一约束，无 `school_id` 列。**

### `idol_vote`（投票记录）

| 字段 | 类型 | 用途 |
|---|---|---|
| `id` | BIGINT PK AI | 记录 id |
| `contestant_id` | BIGINT NOT NULL | 被投选手 |
| `user_id` | BIGINT NOT NULL | 投票人 |
| `created_at` | DATETIME | 投票时间 |

唯一键：`UNIQUE KEY uk_idol_vote(contestant_id,user_id)`（`schema.sql:14`）——**这是"一人一票"的唯一实质防线**。

### 种子数据

`schema.sql:15-22` 插了 7 位假选手：4 位校花组（苏晚 862 票、林小满 645、陈知意 531、白若曦 418）、3 位校草组（陆知远 774、沈亦辰 590、顾言 456）。**票数是手写进种子的**，不对应任何 `idol_vote` 记录，所以首次跑起来时"总票数（4,276）"与"投票记录数（0）"天然矛盾。

### 谁写这些表

| 表 | 写入方 |
|---|---|
| `idol_contestant` | 小程序 `IdolService.join()`；管理端 `AdminModuleMapper.insertIdolContestant/updateIdolContestant/setIdolStatus` |
| `idol_vote` | 仅 `IdolService.vote()`；`AdminModuleMapper.deleteIdolContestant` **不删**投票行 |
| `banner` | 种子 `schema.sql:53`，入口靠它 |

## 七、业务规则与边界（什么情况会拒绝、什么情况会补偿）

### 7.1 投票会拒绝的情况

| 条件 | 行为 | 证据 |
|---|---|---|
| 选手不存在 或 `status != 1` | 抛 `选手不存在或已下架` | `IdolService.java:25` |
| 同一 `(contestant_id,user_id)` 已有记录 | 抛 `每人为同一位选手只能投一票` | `IdolService.java:26` |
| 未登录 | 401，前端提示 `请先登录` | `AuthInterceptor.java:137-145` |

### 7.2 **不会**拒绝的情况（边界洞）

| 条件 | 实际行为 | 证据 |
|---|---|---|
| **投票截止时间已过** | `vote()` 完全不读 `VOTE_END_AT`，照常计票 | `IdolService.java:23-29` 全函数无时间判断；常量仅在 `activity()` 里回显（`IdolService.java:8,12`） |
| 时间常量本身 | 写死 `2026-10-31 23:59:59`，**相对当前时间（2026-11-10）已过期 10 天** | `IdolService.java:8` |
| 同一用户重复报名 | `join()` 不查已有记录、表上无 `user_id` 唯一键 → 可无限报名 | `IdolService.java:30-31`、`schema.sql:13` |
| 报名内容违规 | `join()` 不调 `AuditService`、不查敏感词、不做微信内容安全 | `IdolService.java:30-31`（对比发帖 `ForumService.java:136-137`） |
| 报名照片不是图床地址 | `photo` 只校验 `@NotBlank @Size(max=255)`，`wxfile://` 临时路径合法通过 | `IdolJoinRequest.java`（`photo` 字段声明）、`pages/idol-join/idol-join.js:50` |
| 投票频率 | 无任何限流，`IdolController` 未注入 `RateLimiter` | `IdolController.java:17-18` 只有 `service` 一个字段 |

### 7.3 并发边界

`vote()` 是"先查后插"：`selectOne` 查有无（`IdolService.java:26`）→ `insert` 投票行（`:27`）→ `update vote_count+1`（`:28`），整体 `@Transactional`（`:23`）。

- 唯一键 `uk_idol_vote` 是最终防线：两个并发请求都过了 `selectOne` 时，第二个 `insert` 会被唯一键拒绝。
- 但拒绝方式是抛 `DuplicateKeyException`，不经过业务分支，前端拿到的是 500 类错误而非"你已投过"（详见 `03-优缺点与问题.md` 的 12-06）。
- `update vote_count` 用 `setSql("vote_count = vote_count + 1")` 原子自增，**不丢计**；但返回给前端的是 `c.getVoteCount()+1`（`:29`）——用的是**更新前读到的旧值**，并发下返回给用户的票数会偏小。

### 7.4 补偿边界

**没有补偿。** 没有"票数重算"任务、没有"从 `idol_vote` 重建 `vote_count`"脚本、删选手不级联删票。一旦 `vote_count` 与 `idol_vote` 行数不一致（种子数据天生不一致，见第五节），没有任何代码路径能自愈。
