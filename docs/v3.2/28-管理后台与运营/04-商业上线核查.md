## 四、数据与迁移（前置 SQL、执行顺序、回滚 SQL）

**结论：有条件通过（条件：`scheduler_lock` 表在集群模式必须存在，否则启动失败）。**

执行顺序：

```sql
-- 1) 学校 + admin_user + admin_log + 业务表 school_id（后台一切的前提）
--    db/module-multischool-admin.sql
-- 2) 功能开关（后台「止血」能力的存储）
--    db/module-feature-flag.sql
-- 3) 运营配置（三份，顺序：基础 → 分组 → 认证项）
--    db/module-app-config.sql；db/module-app-config-group.sql；db/module-app-config-verification.sql
-- 4) 前端错误上报
--    db/module-client-error.sql
-- 5) 集群模式必需（含 token_version 与 scheduler_lock）
--    db/module-commerce-consistency.sql
```

回滚：

```sql
-- 可回滚
DROP TABLE IF EXISTS client_error;
DROP TABLE IF EXISTS feature_flag;      -- 注意：丢掉后所有 isEnabled 变默认「开」，enabledStrict 变默认「关」
DROP TABLE IF EXISTS app_config;        -- 丢掉后小程序二维码/文案回落到代码默认
-- 不要回滚
-- admin_log：审计数据，删了等于销毁证据
-- scheduler_lock：集群模式删了启动会失败（fail-fast），属预期
```

**数据风险点**

1. `feature_flag` 表丢失的效果是**不对称**的：`isEnabled` 默认开（功能全开），`enabledStrict` 默认关（合规功能全关）。删除或重置这张表会同时造成「该关的没关」和「该开的没开」。
2. `admin_log` 没有 `school_id`，也没有 before/after 快照（28 第三节第 7 条）。**迁移阶段无法回填**，只能从迁移日之后开始正确记录。
3. `app_config` 三份脚本有顺序依赖（基础表 → 分组项 → 认证项），跑错顺序会有列缺失。

## 六、可观测与告警

**结论：不通过（原因：这是「可观测」功能本身，但它自己没有告警，且高危操作不留痕）。**

| 检查项 | 现状 | 证据 |

| 健康状态**主动告警** | 🔴 无：只在有人打开页面时才计算 | 全仓无推送/告警渠道 |

## 七、失败与降级（依赖挂了会怎样）

| 依赖 | 挂了的表现 | 是否可接受 | 证据 |
|---|---|---|---|
| MySQL | 管理端全部不可用（令牌校验 503）；看板/审核 500 | 可接受（管理端不承担用户流量） | `AdminTokenGuard.java:38-43` |
| `feature_flag` 表查询失败 | `isEnabled` 按「全开」、`enabledStrict` 按「全关」 | **有条件可接受**：安全类功能自动关（对），普通功能自动开（可能放出未准备好的功能） | `FeatureFlags.java:120-124` |
| `app_config` 读取失败 | 返回空，小程序显示「咨询入口尚未配置」而不是白屏 | 可接受（代码有明确兜底） | `AppConfigService.java:59` |
| 上传目录不可写 | 系统状态 problems 标记「上传目录不可写」；上传接口 500 | 可接受（无主动通知，见第六节） | `SystemStatusService.java:74-77` |

**降级缺口**：管理端没有「只读模式」。数据库主从切换/只读期间，管理端所有写操作会 500，而不是给出「系统维护中，暂不可修改」的明确提示。

## 八、开关与回滚（怎么关、怎么退、数据怎么退）

| 开关 | 默认 | 谁能改 | 效果 | 证据 |
|---|---|---|---|---|
| `feature_flag` 各 key（6 个已知） | 见 `System.vue` 的 `FLAG_LABELS`：AI 陪聊、上传、支付、材料报名、圈子群聊、发帖评论 | 仅 super | 关闭后对应入口显示维护文案，数据不变，随时可开 | `System.vue:216-224`、`FeatureFlags.java:37-41` |
| `campus.ha.mode` | prod 无默认值 | 部署时 | `single`↔`cluster`，需重建 `scheduler_lock` 前提 | `application-prod.yml` |
| `campus.production-guards.enabled` | true | 部署时（不建议关） | 关掉 = 不再拦截泄露口令账号 | `ProductionDemoAccountGuard.java:23` |
| 运营配置项 | 代码默认 | 仅 super | 改文案/二维码/入口开关 | `AppConfigService.java:90-105` |

**回滚方案**

1. **出问题先关开关，不要回滚代码。** 6 个开关覆盖 AI 陪聊、上传、支付、材料报名、圈子群聊、发帖评论——这是设计好的止血路径。**但注意**：改开关不留审计（28-03），所以事后无法证明「是谁在几点关的」。
2. **代码回滚**：管理端无破坏性 schema（除 `admin_log` 建议新增 `school_id`），可直接回滚。
3. **数据回退**：
   - 审核驳回的内容可用 `restore` 接口恢复（`AdminAuditController.java:55-59`）；
   - 下架的帖子/商品用 status 改回 1；
   - **删除操作不可回退**：`DELETE /api/admin/posts/{id}`、`/shops/{id}`、`/school-locations/{id}`、`banners/{id}` 都是物理删除（无回收站、无软删标记）。
4. **管理员失联**：只能改库 `must_change_password=0, status=1, locked_until=NULL`；没有「找回密码」通道。

## 九、结论

**有条件上线（本章自身无 P0；平台整体被 `02-多校隔离与权限/` 的 7 条 P0 阻断，见该文档第九节）。**

本章条件（四条 P1 必须先修，因为它们是「出事之后唯一的追查手段」）：

1. **28-01**：审计覆盖率从 2/48 提升到覆盖所有高危写接口（退款、订单状态、导出、审核、配置、开关）。
2. **28-02**：导出加二次确认 + 审计 + 订单导出行数上限。
3. **28-05 / 28-06 / 28-07**：租户账号不得看到全平台系统状态、不得读/删全平台错误日志。

其余 P1（28-03 开关审计、28-04 配置审计）与这四条同源，建议一并修（合计约 5 人日）。
