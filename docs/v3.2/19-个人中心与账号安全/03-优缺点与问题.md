## 一、设计优点（为什么这么设计，好在哪）

1. **「我的数据」用同一个函数守门。** 16 个用户接口里凡涉及私人数据，第一行都是 `requireSelf(id, request)`（`controller/UserController.java:24-29`）。一个函数、一处逻辑，没有「某个接口忘了判」的空间——比每个方法自己比对 `userId` 可靠得多。
2. **地址的改/删用 `id + userId` 双条件，查不到就当不存在。** `service/UserService.java:84-92, 95-99`。不是「先查再判断 owner」，而是一次带条件的 UPDATE/DELETE——并发下也不会误删。这是本仓里写得最好的越权防护之一。
3. **拉黑做成双向不可见。** `mapper/UserBlockMapper.java:20-29` 用 `UNION` 把「我拉黑的」和「拉黑我的」合成一个集合，`UserBlockService.java:60-64` 再对双方都判断。注释写清了为什么不单向（「单向屏蔽会让被拉黑方继续单向骚扰」）。比很多社交产品的单向拉黑更保护被骚扰者。
4. **拉黑有缓存但操作后主动失效。** 30 秒 TTL 挡掉帖子流的重复查询（`UserBlockService.java:29, 42-43`），拉黑/解除时 `cache.remove` 双方（`:80-82`），做到「操作立即生效」。
5. **上传做了魔数校验，不只信扩展名。** `service/UploadService.java:74-79, 118-138`：读前 12 字节比对 PNG/JPEG/GIF/WEBP 签名，把 `.php` 改名成 `.jpg` 挡在门外。文件名由 `UUID` 生成且 `safeName` 拒绝 `..` 与路径分隔符（`ha/LocalObjectStorage.java:63-69`）。
6. **注销后旧 token 立即失效。** `UserController.java:145-148` 主动 `invalidate` 缓存，`AuthInterceptor.java:113-119` 每请求校验，做到「点了注销，下一秒旧 token 就 401」。这是注销功能最容易漏的一环。
7. **空态与失败态分得清。** 个人中心计数失败时显示 `—` 而不是 `0`（`pages/profile/profile.js:60-79`），用户不会把「网络失败」误读成「我确实没有收藏」。同类系统这里普遍显示 0。

## 二、设计缺点与代价（架构/体验/合规/维护）

1. **「私有」只是命名，不是隔离。** 私有文件写进 `<upload root>/private/`（`LocalObjectStorage.java:27, 37`），而静态映射把整个 `root` 挂到 `/uploads/**`（`WebConfig.java:54`）。私有目录是公开目录的子目录——注释里那句「不走 `/uploads/**` 静态映射，因此无法被直接访问」（`UploadController.java:49-50`）是错的。
2. **注销做成了「半匿名化」。** 只改 `user` 一行，帖子、评论、收藏、地址（含手机号）、浏览记录、反馈全部留着。「注销」对用户意味着一个承诺，对系统只是一次 UPDATE。
3. **注销的文案在说谎。** 弹窗写「你的资料、帖子、收藏等将被删除且无法恢复」（`pages/profile/profile.js:145`），实际只删了昵称和 openid。这是合规问题，不是文案问题。
4. **`user.school` 与 `user.school_id` 两套字段并存，注销时只清一个。** `UserService.java:132` 清了字符串，`school_id` 留着（`User.java:15-17`）。凡是「按校统计」的地方都会把已注销用户算进去。
5. **注销前置校验只看外卖订单。** `CampusMapper.java:147-155` 单表 COUNT。用户有进行中的兼职合约、未审的活动报名材料、未结算的骑手任务时，照样能注销，之后这些流程的操作人变成一个「已注销用户」。
6. **拉黑在数据库抖动时会失效。** `UserBlockService.java:45-50` 的 catch 里 `ids = List.of()`，只打 warn。被拉黑的人在这段时间能重新看到你——一个保护性功能在故障时默认「不保护」。
7. **资料只能改昵称，头像是管理端特权。** `UserService.java:37-41` 只写 nickname；小程序无头像上传入口。用户想换头像必须找运营。
8. **`post_view` 只增不删。** 每次浏览插一行，读时去重（`UserService.java:47-50`），全仓 3 个定时任务都不清理它。一个日活 1 万的学校，一年就是千万级行。
9. **现有测试把「私有不可读」测成了「类库层不可读」，掩盖了 Web 层的洞。** `LocalObjectStorageTest.java:32-41` 的 `privateFileIsNotExposedThroughPublicDir` 只断言 `readPublic()` 不穿越，没测 HTTP 路径，所以它绿着、漏洞还在。测试边界画错，比没有测试更危险——它会让人相信这里已经安全了。
10. **注销是「一次 UPDATE 就完事」的不可逆动作，却没有任何回执与审计。** 用户点完只见 Toast「账号已注销」（`pages/profile/profile.js:156`），系统不记谁在什么时候注销、删了什么、保留了什么。出争议时双方都拿不出证据。

## 三、权衡过的替代方案

| 当前做法 | 替代方案 | 为什么当前更合适 | 代价 |
|---|---|---|---|
| 私有文件放 `root/private/`，靠「不对外说路径」保护 | 私有文件放**另一个根目录**（`uploads-public/` 与 `uploads-private/` 分离），或走鉴权下载接口（`GET /api/files/private/{name}` 校验归属） | 现状零改动、上传响应不用改 | 「不可猜的 UUID」不是访问控制；路径会通过日志/DB/Referer 泄露 |
| 注销 = 软删除 + 匿名化 user 行 | 真删（物理 DELETE + 关联表级联） / 完全匿名化（保留 id 但清空所有 PII，并删 UGC） | 订单与审计按法规必须保留，物理删除会变孤儿 | 对客户的承诺说不到位，合规审查会问「我的帖子和手机号呢」 |
| 拉黑 30 秒缓存 + 失败放行 | 无缓存（每请求查）/ 失败关闭（拉黑期间拒绝所有非本人读取） | 帖子流性能优先 | 故障期保护失效 |
| 头像只能管理端改 | 用户自助上传（走私有→公开迁移链路） | 省一套审核流程 | 体验缺口，运营负担 |
| 隐私政策正文内嵌 JS | 正文放 CMS，可热更 | 离线可读，后端挂了也能看 | 政策变更要发版（更新日期 2026-10-27 已写死在 `agreement.js:8`） |

## 五、如果重做会怎么改

1. **公开与私有存储物理分离。** 两个根目录、两个 ResourceHandler（只挂公开那个），私有文件一律走 `GET /api/files/private/{name}` 鉴权下载。现在的「UUID 不可猜」不是访问控制，只是运气。
2. **注销做成两阶段可审计的流程。** ① 冷却期（7 天，期间可撤销）；② 到期执行「删 UGC + 匿名化主表 + 保留订单号聚合」；③ 产出注销记录（谁、何时、删了什么计数）。当前一步到位且只改一行，既不安全也不可审计。
3. **把「个人信息清单」做成代码可查的表。** 一张 `user_pii_fields` 配置（表名/字段/是否需删除），注销时按清单执行。这样新加一个功能表时，注销流程不会静默漏掉它——现在漏了 6 张表。
4. **拉黑改 fail-closed，并把「拉黑集合」放进内存缓存 + 变更事件。** 读库失败时按「全屏蔽」降级，宁可多屏蔽不可少屏蔽。
5. **头像/学校自助编辑 + 内容安全联动。** 用户自助改是基本预期，不能长期靠运营。
6. **所有「删除/注销」类操作产出可读回执**（删了多少条、保留了什么、依据哪条法规），既给用户交代，也给合规审查留证据。
