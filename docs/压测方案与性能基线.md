# 压测方案与性能基线

> 把「腾讯云 4 核 4G 单机、1000 同时在线」翻译成可执行、可判定、可复现的压测流程。配置数字均取自仓库实际文件并标注出处；仓库里没有的东西直接说「没有」。

## 〇、依据说明
| 文件 | 用途 |
| --- | --- |
| **backend/src/main/resources/application.yml**、**application-prod.yml** | Tomcat 线程数、HikariCP 连接池、生产 profile 开关 |
| **backend/src/main/resources/db/module-perf-index.sql** 及其余 24 个 **db/*.sql** | 已补的 10 个 school_id 索引；表结构与已有索引，用于判断哪些查询会全表扫 |
| **backend/src/main/java/...**（Mapper / Service / Config） | 第六节瓶颈预判的证据来源 |

**容量估算的出处**：README_BACKEND.md:21 原先指向一份已不存在的旧部署文档；现由 **docs/部署与上线指南.md** 补齐了鉴权规则、环境变量与 Nginx 配置。但那份文档同样没给出可测的容量口径，故本文直接从 **application.yml:18-19** 的注释接手：

> 「连接池：默认 10 个撑不住 1000 同时在线，按 4C4G 机器调到 25。计算依据：单请求占用时长约 20ms，25 连接 ≈ 1250 QPS 上限」

算法（Little 定律：并发 = QPS × 单请求耗时）正确，但 20ms 是**假设值**，本文任务之一就是用实测替换它。

## 一、压测目标
### 1.1 「1000 同时在线」不是「1000 并发」
在线只说明有 1000 个会话活着，不说明每秒打多少请求。换算必须写明假设：

| 假设项 | 取值 | 依据 |
| --- | --- | --- |
| 同时在线人数 | 1000 | 需求给定 |
| 人均请求频次 | 2 次/分钟 | 校园应用：刷帖子流 + 看消息，无强交互 |
| 均值 QPS | 1000 × 2 ÷ 60 ≈ **33 QPS** | 直接换算 |
| 峰值系数 / 峰值 QPS | 3～5 倍 / **100～170 QPS** | 午间 11:30-13:00、晚间 21:00-23:00 集中刷；33 × 3～5 |
| 突发系数 / 突发 QPS | 10 倍，持续 30 秒 / **≈ 330 QPS** | 开学季推送、活动开抢、全房间刷新；33 × 10 |

结论：要扛的不是 33 QPS，而是**峰值 170 QPS、突发 330 QPS 且 P95 不塌**。按峰值设计，按突发验韧性。

### 1.2 验收指标与判定规则
| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| QPS（L1 纯读 / L2 混合 9:1） | ≥ 150 / ≥ 60 | 写接口有事务与行锁，天然低于纯读 |
| P95 / P99 延迟（读 / 写） | P95 ≤ 300 ms / ≤ 800 ms；P99 ≤ 1500 ms | 读为「不卡」上限；写含事务提交与审核调用；P99 看有无单点长事务 |
| 错误率 / 5xx | < 0.1% / 0 个 | 5xx 出现即该层不通过 |
| 长连接（L3） | 单机 500 条稳定 10 分钟 | 心跳不掉线、内存不持续增长 |

**判定规则**：连续 10 分钟 P95 达标且错误率 < 0.1% 为通过；并发每加一档（50→100→200→400），P95 涨幅超 50% 或错误率越过 0.1% 的那一档即容量拐点；出现 5xx、P95 > 1 s、或 GC 后堆内存不回落即不通过。

### 1.3 从现有配置反推的理论天花板
| 资源 | 当前配置 | 出处 | 理论上限 |
| --- | --- | --- | --- |
| Tomcat 线程 / 排队 / 连接数 | 200（min-spare 10）/ accept-count 200 / max-connections 8192 | **application.yml:4-9** | 200 个请求同时处理；排队 200 个，超出直接拒；连接数不是瓶颈 |
| HikariCP 最大连接 | 25（min-idle 5） | **application.yml:20-26** | 25 ÷ 实测单请求耗时 = DB 侧 QPS 上限 |
| 获取连接超时 | 10000 ms | **application.yml:23** | 超 10 秒拿不到连接 → 500 |
| 上传单文件 / 单请求 | 5 MB / 10 MB | **application.yml:31-32** | 不参与本轮压测 |

**结构性矛盾**：Tomcat 200 线程，却只有 25 个数据库连接。一次慢查询就把 200 个线程全堵在 getConnection() 上，10 秒后成片 500。所以必须重点看「活跃连接是否长期打满 25」，而不只是 QPS。

## 二、环境准备
### 2.1 机器分工
| 角色 | 规格 | 要求 |
| --- | --- | --- |
| 被压机 | 4C4G，与生产同规格 | 跑 Spring Boot + MySQL 同机（当前部署目标就是单机） |
| 压测机 | ≥ 4C8G，同 VPC 内网 | **必须与被压机分离**，否则 wrk 抢 CPU 把数据搞脏；走公网则带宽先成瓶颈 |

单机部署意味着 MySQL 与 JVM 抢同一块 4G 内存，是最大先天风险。压测前先确认 innodb_buffer_pool_size 实际值——4G 机器默认往往只有 128 MB，装不下任何有代表性的数据量。

### 2.2 数据量准备
太少则索引全命中缓存、结果虚高；太多则 4G 机器撑不住。建议按「一所万人高校跑满一学期」规模：

| 表 | 建议行数 | 为什么需要这么多 |
| --- | --- | --- |
| user | 5,000 | 用户列表分页、school_id 索引选择性 |
| post | 50,000 | 帖子流深翻页，idx_post_school(school_id,status,created_at) 才有意义 |
| comment | 300,000 | 每帖 6 条；**该表无 post_id 索引**，必须真实量才暴露 |
| post_like | 200,000 | 点赞关系，决定「我赞过吗」的代价 |
| goods / shop / shop_goods | 20,000 / 200 / 3,000 | 二手列表与首页推荐排序（全表 filesort）；外卖店铺与菜品（每店 15 个） |
| user_order | 100,000 | 管理端看板/对账统计、AdminPaymentService.stats 的 N+1 |
| chat_message / circle | 200,000 / 100 | 未读数统计 idx_chat_receiver(receiver_id, created_at)；群聊房间数 |

总量约 1 GB 数据 + 索引，4G 机器可承载，又足够让全表扫描真正变慢。

### 2.3 怎么造数据
MySQL 8 递归 CTE 一条语句灌一张表，比逐行循环快得多。可直接在压测库执行（列名取自 schema.sql 与 module-multischool-admin.sql）：

```sql
SET SESSION cte_max_recursion_depth = 100000;   -- 默认 1000，不够 5 万行
SET autocommit = 0; SET unique_checks = 0;
INSERT INTO user(nickname, avatar, school, school_id, created_at)      -- 5 所学校轮流分配
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 5000)
SELECT CONCAT('压测用户',n), NULL, CONCAT('压测大学',(n%5)+1), (n%5)+1, NOW()-INTERVAL (n%180) DAY FROM seq;
INSERT INTO post(user_id,title,content,tag,location,like_count,comment_count,
                 view_count,status,school_id,created_at)               -- 5% 跨校帖，95% status=1
WITH RECURSIVE seq(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM seq WHERE n < 50000)
SELECT (n%5000)+1, CONCAT('压测帖子',n), REPEAT('用于验证分页与索引的压测内容。',3),
       ELT((n%5)+1,'校园','二手','兼职','活动','学习'), '内蒙古大学',
       n%50, n%10, n%300, IF(n%20=0,0,1), IF(n%20=0,NULL,(n%5)+1), NOW()-INTERVAL (n%365) DAY
FROM seq;
INSERT INTO comment(post_id,user_id,content,created_at)                -- 每帖 6 条，专压无索引表
SELECT p.id,(p.id%5000)+1,CONCAT('压测评论',p.id,'-',n.n),NOW()-INTERVAL (p.id%90) DAY
FROM post p CROSS JOIN (SELECT 1 n UNION SELECT 2 UNION SELECT 3
                        UNION SELECT 4 UNION SELECT 5 UNION SELECT 6) n;
COMMIT;
```

订单/消息表用 INSERT ... SELECT 自我复制最快，但先确认唯一键（post_like.uk_post_user、follow.uk_follower_followee）不会撞。造完必须补：

```sql
ANALYZE TABLE post, comment, goods, shop, user_order, chat_message;    -- 统计信息要反映真实分布
SELECT table_name,index_name,GROUP_CONCAT(column_name ORDER BY seq_in_index) cols
FROM information_schema.statistics WHERE table_schema=DATABASE()
  AND table_name IN ('post','goods','shop','comment') GROUP BY table_name,index_name;
SET GLOBAL slow_query_log='ON'; SET GLOBAL long_query_time=0.2; SET GLOBAL log_queries_not_using_indexes='ON';
```

## 三、工具选型
| 工具 | 模型 | 脚本能力 | 长连接 | 报告 | Windows | 适合 |
| --- | --- | --- | --- | --- | --- | --- |
| wrk | 多线程 + epoll | Lua，能参数化 | 不支持 | 终端直出 P50/P90/P99 | 需 WSL | **打单一读接口的极限 QPS**，自身开销最低 |
| ab | 单线程 | 无 | 不支持 | 文本表 | 有 | 30 秒冒烟摸底；并发过千会自己成瓶颈 |
| JMeter | 全协议 | GUI + 组件化 | 支持 | HTML 报告完整 | 有 | 复杂业务编排、给非技术同事看报告 |
| k6 | HTTP/WS，JS | JavaScript，**内置阈值断言** | 支持 | 终端 + JSON/HTML | 单文件 exe | **混合读写 + 自动判定通过/失败** |

**推荐**：L1 用 wrk（要的是把 QPS 顶到极限，wrk 自身开销最小）；L2 用 k6（需按比例混合读写、每 VU 持不同 token、以及「P95 > 300ms 即失败」的硬断言，这三点 wrk 别扭、ab 做不到）；L3 用自写脚本（项目里没有现成 WebSocket 压测脚本，Node.js 的 ws 库最直接）。不推荐 ab 作主力：单线程，本机 CPU 先满，数字没有参考价值。

## 四、分层压测方案
三层由浅入深，**必须按顺序做**：L1 不过就别做 L2，否则写请求和慢读一起占死连接池，分不清是谁的问题。

### 4.0 公共准备：取 token
```bash
curl -s -X POST http://127.0.0.1:8080/api/admin/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<你的密码>"}'      # 管理端 token，8 小时有效（application.yml:54）
curl -s -X POST http://127.0.0.1:8080/api/auth/dev-login -H 'Content-Type: application/json' -d '{"userId":1}'  # 小程序用户 token
```
/api/auth/dev-login 在 prod profile 下不生效（AuthService 检查 active profile），所以 L2 建议用独立 perf profile。

### 4.1 L1：只读热点
| 接口 | 代码位置 | 说明 |
| --- | --- | --- |
| GET /api/posts?page=1&size=10 | **ForumController.java:44** → ForumService.page | 帖子流，全站最高频 |
| GET /api/recommend/home?batch=0&perType=2 | **RecommendController.java:19** → RecommendService.home | 首页聚合，**内含全表 filesort**（见第六节） |
| GET /api/goods?page=1&size=10 | **BizController.java:85** | 二手列表 |
| GET /api/circles?page=1&size=10 | **CircleController.java:18** | 圈子列表 |
| GET /api/schools | **CampusController.java:19** | 学校列表，量小但首页每次都调 |

```bash
wrk -t4 -c100 -d60s --latency "http://<被压机IP>:8080/api/posts?page=1&size=10"
wrk -t4 -c200 -d120s --latency -H "Authorization: Bearer $TOKEN" "http://<被压机IP>:8080/api/posts?page=1&size=10"
wrk -t4 -c100 -d60s --latency "http://<被压机IP>:8080/api/recommend/home?batch=0&perType=2"
ab -n 2000 -c 50 "http://127.0.0.1:8080/api/posts?page=1&size=10"   # Windows 冒烟，只为确认接口通，不出数
```

**并发阶梯**：50 → 100 → 200 → 400，每档 60 秒，档间停 30 秒让连接池回落，逐档记录 QPS / P95 / P99 / 错误数。**预期**：150 QPS 时 P95 ≤ 300 ms；帖子流单独压应能到 400+ QPS。
**失败判据**（任一命中即不通过）：错误率 > 0.1% 或出现任意 5xx；P95 > 300 ms；日志出现 HikariPool-1 - Connection is not available, request timed out after 10000ms；压测结束后 Hikari 活跃连接不回落（连接泄漏）。

### 4.2 L2：混合读写
| 接口 | 代码位置 | 写什么 |
| --- | --- | --- |
| POST /api/posts/{id}/like、/api/posts/{id}/view | **ForumController.java:96**、**:113** | post_like 增删 + post 计数 + 通知；post_view 插入 + 浏览数 |
| POST /api/orders | **BizController.java:45** → BizService.order | 4～5 次查询 + 订单插入 + 店铺计数，单事务 |
| POST /api/goods/{id}/favorite | **RecommendController.java:29** | 收藏 + 计数重算 |

load-l2.js，用 k6 run -e TOKEN=$TOKEN -e BASE=http://<被压机IP>:8080 load-l2.js 执行：

```javascript
import http from 'k6/http'; import { check, sleep } from 'k6';
const BASE = __ENV.BASE || 'http://127.0.0.1:8080';
const HEAD = { headers: { Authorization: 'Bearer ' + __ENV.TOKEN } };
export const options = {
  scenarios: { mixed: { executor: 'ramping-vus', startVUs: 0, stages: [
    { duration: '1m', target: 50 }, { duration: '2m', target: 150 }, { duration: '2m', target: 300 }, { duration: '1m', target: 0 } ] } },
  thresholds: { http_req_duration: ['p(95)<800'], http_req_failed: ['rate<0.001'] },
};
export default function () {
  const r = Math.random(), id = Math.floor(Math.random() * 50000) + 1;   // 读写比 9:1
  const req = r < 0.45 ? ['GET', BASE + '/api/posts?page=1&size=10']
            : r < 0.70 ? ['GET', BASE + '/api/recommend/home?batch=0&perType=2']
            : r < 0.90 ? ['POST', BASE + '/api/posts/' + id + '/like']
            :            ['POST', BASE + '/api/posts/' + id + '/view'];
  check(req[0] === 'GET' ? http.get(req[1], HEAD) : http.post(req[1], null, HEAD), { ok: x => x.status === 200 });
  sleep(Math.random() * 2 + 0.5);
}
```

下单接口（POST /api/orders）单独压、不要混进来：它会真写订单、改店铺计数，量大污染数据，还会因自增主键与索引页分裂产生额外开销。要压先准备专用店铺 + 一批专用用户。
**预期**：150 VU 时 P95 ≤ 800 ms，QPS ≥ 60，错误率 < 0.1%。**失败判据**：点赞出现 Duplicate entry（post_like 有 uk_post_user，说明先查后插存在竞态）；下单出现 Deadlock found when trying to get lock；Threads_running 长期 > 10 且 Innodb_row_lock_waits 快速增长；CPU 打满且 P95 持续上升。

### 4.3 L3：长连接（圈子群聊 WebSocket）
| 项 | 值 | 出处 |
| --- | --- | --- |
| 连接地址 / 鉴权 | ws://<host>:8080/ws/circle?circleId=<id>&token=<jwt>，token 必须属于该圈子成员 | **CircleWebSocketConfig.java:17**、**CircleWebSocketHandler.java:31-33** |
| 心跳 / 踢出 | 服务端每 30 秒发 {"type":"ping"}，客户端须回 pong；90 秒无 pong 即关闭 | **CircleWebSocketManager.java:34**、**:92**、**:96** |
| 单用户单房间 | 同一用户重复连接会顶掉旧连接 | **CircleWebSocketManager.java:45** |

项目里**没有** WebSocket 压测脚本，需自己写（npm i ws）：

```javascript
// node ws-load.js ws://host:8080 1 <token> 500
const WebSocket = require('ws');
const [base, circleId, token, total] = process.argv.slice(2);
let opened = 0, failed = 0, pongs = 0; const socks = [];
for (let i = 0; i < Number(total); i++) {
  const ws = new WebSocket(base + '/ws/circle?circleId=' + circleId + '&token=' + token); socks.push(ws);
  ws.on('open', () => opened++);
  ws.on('message', (b) => { if (JSON.parse(b).type === 'ping') { ws.send('{"type":"pong"}'); pongs++; } });
  ws.on('error', () => failed++);
}
setInterval(() => console.log('opened=' + opened + ' failed=' + failed + ' pongs=' + pongs
  + ' alive=' + socks.filter(s => s.readyState === 1).length), 5000);
```

**关键提醒**：同一个 token 只算一个用户，join 会顶掉前一条连接（**CircleWebSocketManager.java:45** 的 put 返回旧会话并被关闭）。压「一个房间 500 人」必须准备 **500 个不同用户的 token**，否则你以为连了 500 条，实际只有 1 条。
**预期**：单机 500 条连接稳定 10 分钟，内存增长 < 100 MB，心跳无掉线。**失败判据**：建连阶段 CPU 飙到 100%（join 时向全房间广播 join 和 online，见 **CircleWebSocketHandler.java:39-40**，500 人依次加入 ≈ 12.5 万次推送，O(n²)）；发一条消息后 HTTP 接口 P95 明显上升（broadcast 在请求线程里串行发）；90 秒内被踢；堆内存持续上涨不回落。

## 五、必须盯的指标
**前提**：pom.xml 里**没有** spring-boot-starter-actuator，所以没有 /actuator/metrics。压测期间要么临时加依赖（属改代码，本轮不做），要么用下面的 JDK 命令 + 日志。这是当前可观测性的真实短板。

### 5.1 应用侧
| 指标 | 怎么看 | 命令 |
| --- | --- | --- |
| QPS / P95 / P99 | 压测工具侧 | wrk --latency 直出；k6 输出 http_req_duration |
| 错误率 | 工具侧 + 服务端日志 | grep -c "ERROR" backend.log |
| 连接池活跃数 | Hikari DEBUG 日志 | 临时设 logging.level.com.zaxxer.hikari=DEBUG，看 active=/idle=/waiting= |
| 堆内存 / GC / 线程栈 | JDK 自带 | jcmd <pid> GC.heap_info；jstat -gcutil <pid> 1000 60；jcmd <pid> Thread.print > t.txt（数 http-nio-8080-exec，接近 200 即打满） |
| 审核线程池 / 实测单请求耗时 | 日志 + 反算 | 搜 Image audit queue is full（**AuditService.java:256**）；用 P50 反算 25 × (1000 ÷ P50ms) = DB 侧 QPS 上限 |

Windows 取 PID：Get-Process java | Select-Object Id, WorkingSet64。压测前先跑一次空载基线（0 并发静置 2 分钟），记录 CPU、内存、连接数作为底噪，否则分不清「涨的这 10% 是打出来的还是本来就有」。

### 5.2 数据库侧
```sql
-- 连接数 / 慢查询
SHOW GLOBAL STATUS LIKE 'Threads_connected'; SHOW GLOBAL STATUS LIKE 'Threads_running'; SHOW GLOBAL STATUS LIKE 'Max_used_connections'; SHOW VARIABLES LIKE 'max_connections';
SHOW GLOBAL STATUS LIKE 'Slow_queries'; SHOW GLOBAL STATUS LIKE 'Questions'; SHOW FULL PROCESSLIST;
-- 缓冲池命中率 = 1 - reads/read_requests，<99% 说明 4G 内存装不下工作集
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests'; SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads'; SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
-- 锁等待与 filesort 信号
SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_waits'; SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg'; SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables'; SHOW GLOBAL STATUS LIKE 'Sort_merge_passes';
SHOW ENGINE INNODB STATUS\G
```

压测时每 5 秒跑一次的组合查询：

```sql
SELECT
 (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Threads_connected')     AS conn,
 (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Threads_running')       AS running,
 (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Slow_queries')          AS slow,
 (SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME='Innodb_row_lock_waits') AS lock_waits;
```

### 5.3 系统侧

### 6.1 先澄清几个「看着像瓶颈其实不是」的地方
避免把优化力气花错地方：
- **帖子流不是 N+1**。ForumService.pageResult 用 selectBatchIds 批量取作者、批量取点赞与关注关系（**ForumService.java:105**、**:110**、**:114**），一页 10 条固定 4～5 次查询，不随行数增长。
- **post 表有 school_id 索引**。**module-multischool-admin.sql:118** 建了 idx_post_school(school_id, status, created_at)；但帖子流条件是 status=1 AND (school_id=? OR school_id IS NULL)（**ForumService.java:17**），那个 OR ... IS NULL 会让索引只能部分命中——压测时用 EXPLAIN 确认，别直接假设。
- **连接池 25 不是拍脑袋**：**application.yml:18-19** 写了推算过程，方向正确，只是 20ms 需实测替换。**上传/静态文件**走 campus.upload.dir（**application.yml:67**），不经数据库，压图片下载不影响本轮结论。
