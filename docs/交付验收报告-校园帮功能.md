## 三、核心设计说明

### 3.1 六个 fail-closed 闸门

全部走 `enabledStrict()`，**键不存在或读库失败都按关闭处理**：

| 开关 | 默认 | 关闭时的行为 |
|---|---|---|
| `wallet.enabled` | 0 | `/api/wallet/summary` 固定返回 `enabled:false`，且**不返回任何金额字段**；不存在充值/支付/提现接口 |
| `job.offsite.enabled` | 0 | 校外岗位发布与报名服务端 403；前端同时隐藏入口（双保险） |
| `job.paid.enabled` | 0 | 有偿岗位发布与接取 403，即使人已核验 |
| `job.category.takeover_class.enabled` | 0 | 替课类目发布/接取 403 |
| `rider.grab.enabled` | 0 | 抢单接口 403，改走楼栋自动派单 |
| `verification.student.enabled` | 0 | 自助申请入口不出现在接口返回里（`selfApplyOpen=false`） |

### 3.2 并发与幂等（全部落在数据库，不靠"先查后写"）

| 场景 | 机制 |
|---|---|
| 校内先到先接 | `UPDATE job SET taken_by=?, workflow_status='taken' WHERE id=? AND taken_by IS NULL AND workflow_status='open' AND scope='campus'`，**影响行数=1 才算成功** |
| 校外录用名额 | `UPDATE job SET accepted_count=accepted_count+1 WHERE id=? AND audit_status='passed' AND accepted_count<headcount AND workflow_status IN ('open','recruiting')` |
| 报名重复 | `INSERT IGNORE` + `UNIQUE(job_id, applicant_id)` |
| 报名重复处理 | `UPDATE job_application SET status=? WHERE id=? AND status='pending'` |
| 圈子同日活跃 | `INSERT IGNORE circle_activity_day` + `UNIQUE(circle_id, active_date)` |
| 派单不重复 | `UPDATE ... WHERE rider_id IS NULL AND status='accepted'` |
| 配送报酬只记一次 | `delivery_pay_recorded` 条件更新（0→1）+ `earnings_ledger.biz_no='delivery:{id}:income'` 唯一键 |
| 兼职结算幂等 | `earnings_ledger.biz_no='job:{cid}:payable|fee|income'` 唯一键 |
| 聊天/emoji 重试 | 既有 `UNIQUE(sender_id, client_id)` |
| 支付回调重复 | 既有 `UNIQUE(transaction_id)` + 回调先查重（未改动） |

### 3.3 改派后旧骑手立即失去权限

`user_order.rider_id` 是**单一责任列**：改派即改写它。骑手侧 `pick/deliver` 的 SQL 都带 `rider_id=#{riderId}` 条件，旧骑手调用会命中 0 行 → 409。没有"多个骑手都能推进"的中间态。

### 3.4 时间与金额

- 圈子"哪一天"：统一 `LocalDate.now(ZoneId.of("Asia/Shanghai"))`，不用设备时间、不用 MySQL `NOW()`（避免部署时区差异）
- 金额：一律人民币**分**的 int；配送费在下单/派单时快照成 `delivery_pay_cents`，兼职报酬在**承接/录用那一刻**快照进 `job_contract.*_snapshot`，之后改价不影响旧单

## 七、复现方式

```bash
# 1. 迁移（按顺序，每个脚本都幂等）
for f in module-safety-gates module-verification module-circle-streak \
         module-rider-dispatch module-earnings-ledger module-jobs-marketplace; do
  mysql -u root -p < backend/src/main/resources/db/$f.sql
done

# 2. 编译启动（验收环境需要允许登录非演示账号，生产不要开）
cd backend && mvn -q -DskipTests clean compile dependency:build-classpath -Dmdep.outputFile=cp.txt
CAMPUS_DEV_LOGIN_ANY_USER=true java -cp "target/classes;$(cat cp.txt)" com.campuslife.CampusLifeApplication

# 3. 后端验收（4 个套件，脚本间自动等待限流窗口，约 5 分钟）
bash tools/acceptance/run-all.sh

# 4. 静态检查（含资金红线）
node tools/check-all.js

# 5. 管理端构建
cd web && npx vite build
```

> **为什么必须串行**：登录接口限流是「同 IP 每分钟 10 次」，发布接口是「同用户每分钟 10 次」。
> 连着跑会撞 429，脚本拿到的 token 变成空串，测出来的失败全是假的。
> `run-all.sh` 已在每个套件之间等一个干净窗口。
>
> **改动 `feature_flag` 必须走管理端接口** `PUT /api/admin/feature-flags/{key}`（会立即清缓存）；
> 直接改数据库会被 30 秒缓存挡住，测出来的结论不可信。
