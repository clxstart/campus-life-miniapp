## 二、第 1 件：点赞"不同步"（已修复）

### 我查到的真相

先把数据链路走了一遍（小程序点赞 → 读管理端接口）：

```
目标帖子 id=95  初始 likeCount=0
小程序点赞 → 返回 {"liked":true}
管理端读   → likeCount=1        ← 已经同步了
小程序再读 → likeCount=1        ← 一致
```

数据库也核对了：帖子 93 的 `like_count=1`，`post_like` 表里也确实有 1 条记录。**后端从来没有丢数据。**

### 那你为什么会觉得没同步？

因为**管理端页面不会自己刷新**。你打开内容管理页时它拉了一次数据，之后小程序点赞、你切回浏览器，看到的还是打开那一刻的快照 —— 必须手动点右上角「刷新」才会变。

这不是 bug，是"页面太安静"，但确实会让人误判成数据没同步。

### 修复内容

**① 加了「切回页面自动刷新」**

新建 `web/src/utils/auto-refresh.js`，接到 6 个会被小程序改动的列表页：

| 页面 | 自动刷新时机 |
|---|---|
| 内容管理 `#/posts` | 切回标签页 / 窗口重新获得焦点 |
| 圈子管理 `#/circles` | 同上 |
| 用户管理 `#/users` | 同上 |
| 业务管理 `#/business` | 同上 |
| 外卖管理 `#/shops` | 同上 |
| 订单管理 `#/orders` | 同上 |

带 1.2 秒节流，切窗口不会连打好几个请求；刷新失败也不会打断页面。

**② 你问的那个"中间的圆圈"**

那是**评论数图标**，源码里用的是 `◌`（一个空心圆圈）：

```html
<!-- 改之前 -->
<text class="icon">◌</text> {{item.commentCount||0}}

<!-- 改之后 -->
<text class="icon">💬</text> {{item.commentCount||0}}
```

它确实不像"评论"，你看着困惑很正常。已换成 💬，和左边「↗ 转发」、右边「♥ 赞」形成一组明确的图标。

### 怎么验证这个修复

1. 管理端打开 `#/posts`，记下某条帖子的 ♥ 数字
2. 小程序（开发者工具）进社区，给那条帖子点赞
3. **不点任何刷新按钮**，直接把鼠标点回浏览器窗口
4. 预期：♥ 数字自己 +1

> 如果没自动刷新，可能是浏览器标签页在后台被节流了 —— 手动点「刷新」仍然可用，这是兜底。

## 三、第 2 件：支付能不能真实走通

### 现在是什么状态

**不能真实支付，走的是模拟。**

代码里的逻辑（`PayService`）：

```java
if (!properties.isEnabled()) {
    requireSimulationAllowed(orderId);   // 要求 campus.pay.simulate=true
    markPaid(order, "SIM-" + order.getOutTradeNo(), ...);  // 直接把订单标记为已支付
}
```

当前配置：

| 项 | 值 |
|---|---|
| `wxpay.enabled` | `false` |
| `campus.pay.simulate` | `true`（dev） |
| 小程序 AppID | `touristappid`（测试号） |

所以你现在下单 → 支付 → 订单立刻变「已支付」，**一分钱都没真的收**。

### 真实支付需要的 5 个前置条件

| # | 条件 | 你现在有吗 |
|---|---|---|
| 1 | **真实小程序 AppID**（不能是 touristappid） | ❌ 没有 |
| 2 | **微信支付商户号**（mch-id）+ 已绑定该 AppID | ❌ 没有 |
| 3 | **APIv3 密钥**（32 位）+ **商户证书序列号** + **私钥文件** `apiclient_key.pem` | ❌ 没有 |
| 4 | **公网 HTTPS 回调地址**（`/api/pay/notify`、`/api/pay/refund/notify`） | ❌ 本地 127.0.0.1 不行 |
| 5 | 小程序后台配置「request 合法域名」为你的 HTTPS 域名 | ❌ 未配 |

**缺任何一个都走不通**，这不是代码问题，是资质问题。

### 如果条件齐了，怎么配（供参考）

```bash
export WXPAY_ENABLED=true
export WXPAY_APP_ID=wx真实appid
export WXPAY_MCH_ID=商户号
export WXPAY_CERT_SERIAL_NO=证书序列号
export WXPAY_API_V3_KEY=32位密钥
export WXPAY_PRIVATE_KEY_PATH=/opt/campus/certs/apiclient_key.pem
export WXPAY_NOTIFY_URL=https://api.你的域名.com/api/pay/notify
export WXPAY_REFUND_NOTIFY_URL=https://api.你的域名.com/api/pay/refund/notify
# 同时小程序 utils/config.js 的 ENV 改成 'prod' 并填真实域名
```

### 没有商户号时，怎么做"像真的一样"的测试

这是现实做法，**不花钱也能验完整个链路**：

| 步骤 | 操作 | 验证点 |
|---|---|---|
| 1 | 小程序外卖下单 | 订单进入「待支付」 |
| 2 | 点支付 | 走模拟，订单变「已支付」 |
| 3 | 管理端订单管理 | 能看到这笔订单、金额正确 |
| 4 | 管理端触发退款 | 退款走模拟，订单变「已退款」 |
| 5 | 查 `payment_record` 表 | 有 `verified` 标记、金额与订单一致 |

**模拟模式的三条安全限制**（我之前加的）：
- 必须显式 `campus.pay.simulate=true` 才允许
- **prod profile 下强制拒绝**（配了 true 也没用）
- 每次模拟支付会打 WARN 日志，方便事后审计

### 我的建议

**毕设/答辩阶段不要接真实支付。** 理由：
- 需要企业资质（个体户也行但要走流程），学生身份申请麻烦
- 需要备案域名 + HTTPS，部署成本上升
- 答辩时演示"模拟支付 + 完整的订单状态机 + 退款链路"已经足够说明问题，反而更安全（不会真扣钱）

如果确实要接，告诉我，我按上面 5 个条件逐项帮你配。

## 四、第 3 件：报名要不要上传材料

### 现在是什么状态

**一键报名，没有任何表单和上传。**

代码就这一句（`BizService.enrollActivity`）：

```java
moduleMapper.insertEnrollment(activityId, userId);   // 只写 (活动ID, 用户ID)
```

表结构也只有三个字段：

```sql
activity_enroll: id, activity_id, user_id, created_at
```

所以你截图里点「报名」→ 直接变「已报名」，中间没有任何页面。

### 为什么"应该有上传"是个合理需求

像「校园歌手大赛」这种活动，现实里报名需要：**伴奏文件、演唱视频、身份证/学生证照片**。一键报名拿不到这些，主办方没法筛选。

### 三个方案，你选一个

#### 方案 A：报名表单（无文件上传）

主办方在管理端给活动配几个自定义字段，学生报名时填。

| 项 | 内容 |
|---|---|
| 学生体验 | 点报名 → 弹出表单（姓名/学号/手机/自我介绍）→ 提交 |
| 管理端 | 活动编辑页加「报名表单配置」，可增删字段 |
| 数据结构 | 新增 `activity_enroll_field`（字段定义）+ `activity_enroll_value`（填写值） |
| 工作量 | 约 1 天 |
| 风险 | 低（不涉及文件存储） |
| 适合 | 只需要收集文字信息的活动 |

#### 方案 B：报名 + 文件上传（单文件）

在方案 A 基础上，允许传 1 个文件（伴奏/视频/截图）。

| 项 | 内容 |
|---|---|
| 学生体验 | 表单 + 「上传材料」按钮，选 1 个文件 |
| 管理端 | 报名列表里能看/下载材料 |
| 数据结构 | `activity_enroll` 加 `material_url` 字段 |
| 工作量 | 约 1.5 天 |
| 风险 | 中（要限制类型和大小、防刷） |
| 适合 | 歌手大赛、设计比赛这类"交一个作品"的场景 |

**复用现成能力**：项目里已经有上传接口（`/api/upload`，限 5MB、校验真实图片头、按 IP 限流），直接复用即可，不用重写。

#### 方案 C：报名 + 多材料 + 审核流程

| 项 | 内容 |
|---|---|
| 学生体验 | 表单 + 最多 N 个文件 + 提交后等审核，状态显示「待审核/已通过/被驳回」 |
| 管理端 | 新增「报名审核」页，逐条通过/驳回并填原因 |
| 数据结构 | 新增 `activity_enroll_material`（多文件）+ `activity_enroll.status/audit_reason` |
| 工作量 | 约 3 天 |
| 风险 | 中高（状态机 + 通知 + 审核页） |
| 适合 | 正式比赛、需要筛选的场景 |

### 方案对比

| 维度 | A 表单 | B 表单+单文件 | C 多文件+审核 |
|---|---|---|---|
| 工作量 | 1 天 | 1.5 天 | 3 天 |
| 学生操作步数 | 2 步 | 3 步 | 4 步 |
| 能否筛人 | 只能看文字 | 能看作品 | 能看作品并分级 |
| 管理端新增页面 | 无（改活动编辑） | 无 | 有（审核页） |
| 答辩演示效果 | 一般 | 好 | 最好但风险也最高 |

### 我的建议

**选方案 B。** 理由：
- 「校园歌手大赛」这类活动，主办方真正需要的是"听到/看到作品"，纯文字表单不够
- 单文件已经能覆盖绝大多数场景，工作量可控（1.5 天）
- 复用已有上传接口，不引入新的存储风险
- 比 C 少一个审核状态机，答辩演示时不容易翻车

如果你要"能筛选、能驳回"，那就上 C，但建议放到核心功能稳定之后再做。
