# AI 校园助手（关键词匹配）实现说明

> 实现时间：2026-10-17
> 定位：**不接大模型**，用规则匹配 + 真实校园数据，做出「够用且有温度」的陪聊。

---

## 一、为什么是关键词匹配

用户明确说「关键词匹配就行」。这个判断在工程上是合理的：

| 维度 | 大模型方案 | 关键词方案（当前） |
|---|---|---|
| 成本 | 每次对话都花钱 | 零成本 |
| 延迟 | 1-3 秒 | <50ms |
| 内容安全 | 需要额外审核，可能生成违规内容 | 回复完全可控，不会跑偏 |
| 微信审核 | 需说明 AI 生成内容合规 | 容易过审 |
| 可维护性 | 需要 prompt 工程 | 改数据库即可 |

**代价**：理解能力有限，只能覆盖预设场景。但对「校园助手」这个定位来说，覆盖高频场景（学习、吃饭、作息、情绪、校园信息）已经够用。

---

## 二、关键设计：接真实校园数据

这是和「纯话术机器人」的本质区别。

```
用户：中午吃什么好
助手：这个点该吃饭了。你学校这边有「茶言观色奶茶」「二食堂快餐」「果然鲜果切」，要不要去试试？
```

**回复里的店铺名是查数据库得到的**，不是写死的。同理：

| 用户问 | 数据来源 |
|---|---|
| 吃什么 | `shop` 表（本校启用中，按 order_count 排序取前 3） |
| 有兼职吗 | `job` 表（本校，取前 3 条标题） |
| 有什么活动 | `campus_activity` 表（本校启用中，取前 3 条） |

**数据为空时的兜底**：不能崩，也不能说「有」，而是换成通用话术。

```
数据为空 → "这个点该吃饭了。食堂和小程序里的外卖都可以看看，别拖到太晚。"
```

## 三、数据表

```sql
CREATE TABLE ai_chat_rule (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  category      VARCHAR(32)  NOT NULL,   -- greeting/study/food/sleep/mood/campus/help/fallback
  keywords      VARCHAR(255) NOT NULL,   -- 逗号分隔，命中任意一个即匹配
  reply         VARCHAR(500) NOT NULL,
  quick_replies VARCHAR(255) NULL,       -- 逗号分隔，前端渲染成快捷按钮
  priority      INT          NOT NULL DEFAULT 0,
  status        TINYINT      NOT NULL DEFAULT 1,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**22 条种子规则**，覆盖 8 个分类：

| 分类 | 条数 | 覆盖场景 |
|---|---|---|
| greeting | 2 | 问候、问身份 |
| study | 6 | 学习、考研、考公、论文、就业、学不进去 |
| food | 2 | 吃什么、减脂 |
| sleep | 2 | 睡觉、早起 |
| mood | 4 | 难过、开心、求鼓励、孤独 |
| campus | 5 | 课表、活动、兼职、图书馆、二手 |
| help | 2 | 功能说明、致谢 |
| fallback | 1 | 兜底 |

迁移脚本：`backend/src/main/resources/db/module-ai-chat.sql`（可重复执行）

## 四、匹配算法

```
1. 遍历所有启用规则，检查用户消息是否包含任一关键词
2. 命中的规则里按「关键词长度降序 + priority 降序」取第一个
3. 都没命中 → 用 fallback 规则
```

**为什么关键词长度优先**：长关键词更精确。比如用户说「我不想学习」，
「不想学」比「学习」更能表达真实意图，长关键词优先能选对规则。

**为什么兜底规则不参与匹配**：它没有真实关键词（用的是 `__fallback__` 占位），
只在无命中时被代码显式调用。

## 五、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/chat` | 发消息，返回回复 |
| GET | `/api/ai/rules` | 规则列表（供管理端后续维护） |

**请求**：
```json
{"userId": 1, "schoolId": 1, "message": "中午吃什么"}
```

**响应**：
```json
{
  "code": 0,
  "data": {
    "reply": "这个点该吃饭了。你学校这边有「茶言观色奶茶」…",
    "quickReplies": ["看看有什么好吃的", "我在减肥", "不想出门"],
    "matched": true,
    "category": "food"
  }
}
```

**为什么不要求登录**：游客也能试试，降低体验门槛；登录后能拿到本校数据，回复更具体。

## 六、小程序页面

路径：`pages/ai-chat/ai-chat`

| 能力 | 实现 |
|---|---|
| 对话气泡 | 用户右侧蓝底，助手左侧白底 + ✦ 头像 |
| 快捷追问 | 回复带的 `quickReplies` 渲染成可点芯片 |
| 打字动画 | 三个点闪烁，避免「发出去没反应」的焦虑 |
| 历史记录 | 存 `storage`，最多 60 条，进页面自动恢复 |
| 清空对话 | 导航栏右上角，二次确认 |
| 离线兜底 | 后端挂了显示「网络好像不太好，我先记住你的话了」+ 离线横幅 |
| 空输入拦截 | 不发空消息；超 200 字提示 |

**入口**：首页导航栏右侧 ✦ 按钮。

| 项 | 说明 |
|---|---|
| 管理端规则维护页 | 后端已有 `GET /api/ai/rules`，加个 CRUD 页面即可 |

| 宠物形象绑定 | 当前是纯文字，接宠物后可带头像和表情 |
| 多轮上下文 | 现在是单轮匹配，多轮需要会话状态 |

### 关于定时提醒的硬约束

微信小程序的订阅消息：
- 用户必须**每次主动授权**，一次授权只能推**一条**
- 长期订阅消息只有特定类目能申请，校园生活类基本批不下来

所以「宠物每天定时提醒」**做不到系统推送**。现实方案：
- A. 用户打开小程序时，助手弹出待办（被动）
- B. 攒订阅次数，用户点一次授权推一条

这个约束在设计宠物提醒功能时必须先确认。

## 九、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | 单轮对话，无上下文 | 说「那它呢」接不上 |
| 2 | 理解能力有限 | 只能覆盖预设关键词 |
| 3 | 规则需人工维护 | 新场景要加规则 |
| 4 | 无内容审核 | 回复是预设的，不会生成违规内容，但也无法识别用户输入的敏感内容 |
